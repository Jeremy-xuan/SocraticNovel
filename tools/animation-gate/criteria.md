# ANIM-GATE 判据与阈值来源

> 这份文件回答一个问题：**每一条判据是怎么定义的、阈值是怎么来的、在哪会失效。**
> 所有阈值都来自对 `poc_动画可写性/` 那 24 个样例（12 个对照轮 + 12 个第一轮）的实测分布，
> 不是拍脑袋；凡是我"没有数据只能凭物理直觉取"的，下面逐条标了 **[直觉]**。

---

## 0. 为什么是这四类

上一轮实测（`取证_动画可写性PoC_对照轮_2026-09-24.md`）的结论是：**12 个样例渲染全部成功，
但只有 7 个教学可用，5 个有瑕疵且瑕疵全在画面层**。所以闸门要挡的是"渲染成功但学生不能看"。
画面层的瑕疵可归为四类可计算的东西：

| 类 | 一句话 | 判据 |
|---|---|---|
| 文字重叠 | 两块文字压在一起 | D1 |
| 元素整段消失 | 脚本说了要画，画面里没有 | D2 |
| 箭头/连线缺失 | 脚本画了 Arrow，画面里没有 | D3 |
| 元素被压住 | 一个盖住另一个，读不出来 | D4 |

语义层（概念标签用错、术语与教材不一致、数值算错）**明确不覆盖**，见 §5。

## 1. 共同底座：怎么从一帧里认出"文字"

### 1.1 墨迹
- 背景色 = 该帧颜色直方图的众数（16 级量化后取均值）。
- 墨迹 = 与背景色的 **L∞ 距离 > `BG_TAU` = 48**。
  **来源**：实测文字核心像素与黑底的距离 ≥ 120，抗锯齿边缘落在 20–80 之间；48 取在
  "真笔画"与"压缩噪声/暗边"之间。**[直觉 + 抽样验证]**

### 1.2 色相族（12 族 + 灰阶）
- 每个墨迹像素按 HSV 归族：饱和度 < `SAT_TAU` = 0.15 → 灰阶；否则按色相 30° 分族，
  分界**相对纯色相平移 `HUE_SHIFT` = 15°**。
  **来源**：不平移的话 Manim 的 `RED`（h≈4.7°）会被 0/360 的环绕切成两族，实测直接
  造成"同一个红字被判成两个对象"的误报。
- 明度 < `VAL_FLOOR` = 0.45 的灰阶像素直接丢弃（黑底上的抗锯齿暗边）。
- 再用 **5×5 邻域多数投票**（`majority_family`，至少 8 票）消掉逐像素判色的抖动。
  **来源**：不做这一步时，一个字的边缘像素会被判成另一种色相，同一个字被拆成两个
  "对象"，D1/D4 变成一片误报（实测第一版 C_P1 一次报出 986 处）。

### 1.3 连通域分类（决定哪些墨迹算"文字"）
逐连通域按 bbox 与填充率分四类：

| 类 | 条件 | 用途 |
|---|---|---|
| 单字 | bbox ≤ 48×48，面积 ≥ 6，填充率 ∈ [0.06, 0.80] | 文字 |
| 实心块 | 宽 ≥ 24，高 ≥ 12，填充率 ≥ 0.50 | 进度条/色块（不算文字） |
| 文字条 | 宽 ≥ 60，高 ≤ 40，面积 ≥ 80，填充率 ∈ [0.06, 0.60]，**且每列墨迹纵向跨度中位数 > 8** | 文字与框线/下划线粘成一域 |
| 线状结构 | 宽或高 ≥ 60，**每列墨迹纵向跨度中位数 ≤ 8** | 箭头/连线/长横线 |
| 其余 | —— | **仍算文字墨迹**（"框线 + 里面的字"就落在这一档） |

**为什么要有"每列墨迹纵向跨度中位数"这一条**：箭头与文字条在 bbox 与填充率上分不开
（实测 A_P2 的红箭头：bbox 209×28、填充率 0.191，与一行文字的统计量几乎一样），但
**箭头每列只有笔画那么厚（中位数 4 px），文字行每列有半个字高（≥ 8 px）**。
这一条把箭头挡在"文字"之外，是 D1/D4 不误报的关键。

**为什么"其余"要保留**：实测 `r1_A_P1` 的「已完成 / 接着跑」两个标签与框线下边粘成了
一个 260×158 的大连通域；如果只认"单字 + 文字条"，这两个标签会**整块消失**（这正是
我第二版的漏报原因）。保留未分类墨迹后它们才被看见。

### 1.4 文字行
- 按色相族各自做行投影（**不跨族合并行带**——跨族合并是第二版最大的误报源），
  行内像素 ≥ 5 才算"有内容"，连续行成一条带。
- 行带再按 x 方向空隙 **> `X_SPLIT_PX` = 30 px** 切成若干条，避免同一 y 上左右两处
  不相干的碎屑被并成一行。
- 逐条过滤：宽 ≥ 24、面积 ≥ 80、高度 ∈ [8, 90]、填充率 ≥ 0.05。
- 每行记录**真实色相中心**（饱和像素的圆均值）与**平均饱和度**；饱和像素占比
  < `COLOR_FRAC_MIN` = 0.30 的行按灰阶行处理。
  **来源**：不设这条时，白字压在彩色条边上会从几个彩色像素里算出假色相（实测 C_P3
  的「完成时刻」行被判成 hue 86），D2 会把它的颜色认错。

## 2. D1 文字重叠

### 2.1 行对判据（主判据）
对同一帧里任意两条**不同色相族**的文字行 a、b：

1. 色相差 ≥ `HUE_DIFF` = **45°**；
   灰阶行参与的配对，要求灰阶那一侧的平均饱和度 ≤ `ACHROM_SAT_MAX` = **0.10**
   （否则"浅绿标签里的细笔画字母"会被当成"灰字压在绿字上"——实测 C_P3 的
   「换成 B → C → A 的顺序」整句被拆成"黄绿行 + 灰阶行"两行，误报）；
2. x 支撑相交 / 较短者 ≥ `OVERLAP_X` = **0.30**；
3. y 区间相交 / 较矮者 ≥ `OVERLAP_Y` = **0.25**；
4. 相交区里**双方都必须有墨迹**（`a_in > 0 且 b_in > 0`）。
   这一条挡掉"只是 bbox 相交、画面上并没有压在一起"（实测 r1_C_P1 的绿色高亮格与其
   中的「指令 3」：格子边框的 bbox 与文字 bbox 相交，但相交区里没有任何绿色墨迹）。

**阈值来源**（24 例 × 全帧的行对分布）：
- 色相差：**单字内的压缩色噪产生的假双峰，gap 全部 ≤ 50°**；真重叠实测为
  52.2°（r1_A_P1）、140°（C_P1）、180°（r1_C_P3）。45° 取在两者之间，并靠
  §2.2 的空间分离判据与 §1.3 的"真灰阶"约束兜住 45–52° 这一段。
- x / y 相交比：真重叠实测 x 相交 0.317–0.993、y 相交 0.833–1.0；0.30 / 0.25 是
  在"足够大以挡住擦边"与"足够小以不漏掉半字重叠"之间取的 **[直觉]**，实测 24 例
  无误报。

### 2.2 同域双峰（辅判据）
两个文字对象压得太狠、笔画连成一个连通域时，§2.1 看不见（它们已经不是两条行了）。
这时改看**一个连通域内部**：色相直方图出现两个峰，且

- 峰间距 ≥ 45°；
- 两个峰各自 ±15° 覆盖的像素占比 ≥ `BIMODAL_MIN_MASS` = **0.30**；
- **两簇的 x 质心相距 ≥ `BIMODAL_MIN_SEP` = 25 px**。

**来源**：前两条不够——单字内部因压缩会产生 gap 40–50°、两簇质量都 ≥ 0.3 的假双峰
（实测 8 例，全部是单个字、宽 ≤ 42 px、质心相距 < 25 px）。加上第三条后，8 例假阳性
全部消失，而 C_P1 的真重叠（质心分离明显、gap 140°）保留。

### 2.3 持久性
同一处命中必须出现在 **≥ 2 个抽样帧**（`PERSIST_FRAMES` = 2）才算"持久"→ 判阻断；
只出现在 1 帧的降级为 `warn`。
**来源**：Manim 的 `Transform` / `FadeIn(shift=...)` 会在中途帧造成短暂的"压在一起"
（实测 r2_A_P1 的卡片飞入、r2_C_P1 的途中帧），上一轮报告也正是靠"9.6s 与 10.3s
两帧像素一致"来区分持久重叠与淡入瞬时态——这里把那个做法固化成了判据。

### 2.4 在哪会失效（写死）
- **同色文字重叠抓不到**：两块同色/同族文字压在一起，色相差为 0，§2.1 不触发。
  实测 `r1_B_P2` 末帧标题被结论句压住（两句都是白色）**闸门只给出 warn 级信号**
  （灰阶文字块数 3→2），没有判阻断。这是本轮唯一一处已知漏报。
- 我试过用"行高异常"补这一类（同族相邻两行若中间还有全空行会被切开，切不开且行高
  近两倍 → 疑似同色重叠），但**合法堆叠标签与同色重叠在数据上分不开**：实测 A_P2 的
  「时钟中断！」/「硬件打断」两个标签正常堆叠，行高 52–59 px、本帧行高中位数 18–19 px，
  与 r1_B_P2 的真重叠（39 px / 中位数 18 px）落在同一区间。**该判据已删除，不留在代码里
  当摆设。**
- 色相相差 < 45° 的两个对象（例如 Manim 的 `RED` 与 `ORANGE`）压在一起也抓不到。

## 3. D2 元素整段消失

### 3.1 脚本预期（静态分析）
从 manim 脚本里静态抽出"末帧应当还在画面上"的文字对象：

- 收集 `Text` / `MarkupText` / `MathTex` / `Tex` 及其**返回 Text 的本地辅助函数**的赋值，
  记录颜色（支持调色板常量名与 `#RRGGBB` 字面量）。
  **链式写法必须剥到最内层构造器**：`Text("x").move_to(...)` 的赋值右侧是 `move_to` 调用，
  不剥的话几乎全部漏收（实测修复前 C_P3 只认出 1 个文字对象，修复后 11 个）。
- 收集 `VGroup(...)` 成员；`FadeOut/Remove/Uncreate` 里的名字（含 VGroup 展开）视为移除；
  `play/add` 里出现过的视为加入。
- **被 `Transform` / `ReplacementTransform` 改写过的对象不计入预期**，并记入"未核对"。
  **来源**：实测 r1_B_P2 的 `tb_lab`（YELLOW）被 `Transform` 成 `tb_new_lab`（RED），
  末帧本来就不该有黄色；不排除的话闸门会误报"黄色文字整段消失"。

### 3.2 画面实测
末帧里，把每条文字行**就近归属**到脚本声明的色系（色相最近且差 ≤ `HUE_MATCH_TOL` = **40°**；
灰阶行归灰阶组），再按 y 合并成"文字块"（相邻 ≤ `LINE_MERGE_PX` = 10 px 视为同一块的多行），
数块数。

- `HUE_MATCH_TOL` = 40°：**h264 实测色相漂移可达 25°**（A_P2 脚本写 `ORANGE` h≈25°，
  画面实测 h≈50°）。
- 必须"就近归属"而不是"按容差圈各自计数"：实测一个 84° 的浅绿块会同时落进 60° 与 90°
  两个容差圈，把两边都算错。

### 3.3 判定
- 实测 **0 块**且该色系在全片别的帧出现过 → **阻断**（该色系的文字在末帧整段消失）；
- 实测 < 预期但未归零 → **warn**（可能被图形盖住、多行合并、或本判据的分解粒度不够）；
- 该色系在全片任何抽样帧都没出现 → **warn**（多半是色相/编码对不上，不当作缺失）。

### 3.4 在哪会失效（写死）
- **被图形盖住的文字**（例如被一个实心块完全遮住、或被删除线贯穿）会从"文字行"里消失，
  于是被算成"块数减少"→ 只给 warn，不给阻断。
- **分解粒度是"色系 × 文字块"**，不是"对象"：同一色系的两个对象若在同一行，只算 1 块，
  预期 2 就会误报为 warn（不会误报为阻断）。实测 24 例里这类 warn 共 8 处，全部出现在
  "多行 Text / 标签堆叠"的样本上。
- 脚本里颜色写成运行期表达式的对象无法核对，全部记入"未核对"清单，不猜。

## 4. D3 箭头/连线缺失

两条独立的判据：

- **D3a（纯静态）**：脚本里创建了 `Arrow/Line/CurvedArrow/DoubleArrow/DashedLine/Vector/Arc`
  对象，但该名字**在整份脚本里只出现在它自己那次赋值上**（没被任何 play/add/helper 引用过）
  → 必然没画出来 → 阻断。
  **宁漏不误报**：静态分析认不全的用法（VGroup、`.animate`、helper 函数）一律按"用过"处理。
- **D3b（画面）**：脚本声明并 play 了某色系的箭头/连线，而**全片所有抽样帧里该色系的
  "非字形墨迹"总量 ≈ 0**（阈值 150 px）→ 阻断。
  这一条只在"该色系在画面里连框线都没有"时才响。

### 4.1 为什么 D3b 只能做到这一步（写死）
**箭头与同色框线在像素上分不开**。上一轮报告点名 `r1_B_P2` "缺箭头"，逐像素复核的结果是
**箭头在**（红色箭头像素 3119 px、紫色 3193 px，见验收表）。也就是说 24 个真样本里
**没有一个真的缺箭头**——D3 的阳性对照只能用人为突变造（见 `selftest_positive_controls.py`）。
若要真正区分"箭头"与"同色框线"，需要按脚本里箭头两端的坐标做几何预测，那已经超出
"画面层排版断言"的范围，本轮不做。

## 5. D4 元素被压住

与 D1 共用行对遍历，区别在"谁被吃掉了"：

- `a_frac_in` = a 落在相交区内的墨迹占 a 自身墨迹的比例（b 同理）；
- 若一方 `frac < OCCLUDE_FRAC` = **0.10** 而另一方 `frac ≥ OCCLUDE_PEER` = **0.20**
  → 判 **D4**，前者是被压住的一方；
- 否则判 **D1**（并置相压）。

**来源**：真重叠实测 frac 组合为 (0.948, 0.004)（r1_A_P1）与 (0.993, 0.412)（r1_C_P3）；
0.10 / 0.20 取在"确实有墨迹被吃掉"与"双方都还在"之间 **[直觉]**，实测 24 例无误报。

**分工说明**：D1 与 D4 是同一物理现象的两个面（两元素 bbox 相交），差别只在"被压方还剩
多少可见墨迹"。两者都是阻断级，都进同一张 contact sheet。

### 5.1 在哪会失效
- 被压住的是**实心块/框线**（不是文字）时，`victim` 侧的"文字行"可能不存在 → 不判。
- 被压住的一方在相交区里**一点墨迹都不剩**时，本判据会跳过（那是"整段消失"，归 D2）。

## 6. 被删掉的判据（留档，防止有人再加回来）

**D1b「行带填充率异常」已删除。** 想法是"两块文字压在一起 → 墨迹填充率升高"。
实测数据不支持：24 例里宽度 ≥ 60 px 的文字行，填充率 **p95 = 0.367、p99 = 0.447、
最大 0.501**；而 C_P1 那处真缺陷行的填充率是 **0.42**——落在正常分布里。
**没有区分度，删掉，不留假判据。**

## 7. 人看的那一半

机器判定 ≠ 最终放行。每次运行都产出：

- `contact_sheet.png`：全部抽帧拼一张图（每格标帧名与时间），**有命中的帧画红框**；
- `zoom/`：每处命中的 3–6× 放大图；
- `verdict.md` 末尾的「待你目视确认」三条（看联系表 → 看放大图 → 语义层必须人工读教材）。

语义层（概念标签用错、术语与教材不一致、数值算错）**闸门不做任何判定**，
这是设计边界，不是遗漏。
