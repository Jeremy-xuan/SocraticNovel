# portrait2live —— 静态立绘 → 会动（PoC）

> 任务代号 **P2L-1**。本目录是「**一张静态立绘（PNG）→ 真的动起来**」这条技术方案的**跑通证据**。
> 配套报告（不在本仓库内）：`实现报告_P2L1_静态立绘转动起来_2026-09-24.md`

---

## 〇 · 一句话结论

**跑通了。** 不需要任何大模型权重、不需要 CUDA、不需要装任何新依赖：
用一张静态立绘 → 自动分层 → 程序化驱动（呼吸/眨眼/口型/头发摆动）→ **MP4 + GIF**，
在 Apple M3 上 **1024² 分辨率 42–74 fps**，整条管线端到端 **3 分 39 秒**，产出共 **4.4 MB**。

## 一 · 一条命令复现

```bash
bash tools/portrait2live/run_all.sh
```

它会依次跑完 ① 生成立绘 → ② 自动分层+无损校验 → ③ 渲染三模式各 90 帧 → ④ 编码 MP4/GIF → ⑤ 程序化质检。
**不装任何东西**：默认用 PATH 上的 `python3`（需含 numpy/scipy/Pillow），缺依赖时脚本会**响亮失败**并退出。
换解释器：`PY=/path/to/python3 bash tools/portrait2live/run_all.sh`。
🔴 **第三方与输入素材未分发**：本仓库只含自研脚本、README 与分层配置契约（`src_assets/palette.json`）。
示例立绘（`portrait_flat.png` / `portrait_nearest.png`）与全部 `out/` 产物**不随仓库走**；
缺失即视为"未提供输入素材"，由 `00_gen_source_portrait.py` 重新代码绘制或用户自备。

交付物自检（文件在不在、能不能播、哈希对不对）：

```bash
bash scripts/50_check_deliverables.sh
```

## 三 · 管线四步（每一步都是可单独跑的脚本）

```
scripts/00_gen_source_portrait.py   静态立绘（代码绘制）
        ↓  src_assets/portrait_flat.png（成品）＋ portrait_nearest.png（分类/校验真源）
scripts/10_segment_layers.py        自动分层 + 无损校验
        ↓  out/layers/*.png（9 层）＋ manifest.json
scripts/20_animate.py               程序化驱动渲染
        ↓  out/frames_{idle,speak,write}/f_*.png
scripts/40_encode.sh                ffmpeg 编码
        ↓  out/anim_*.mp4 ＋ out/anim_*.gif
scripts/30_verify.py                程序化质检（不靠目视）
```

### 3.1 分层怎么做的（`10_segment_layers.py`）

**输入只有一张 PNG，脚本不看画图代码，只从像素出发**：

1. **调色板精确分类** —— 每个像素归到调色板里**完全相同**的颜色（不是"最近色"，理由见 §五坑①）。
2. **连通域标记**（`scipy.ndimage.label`）找锚点：
   - 眼睛 ← **虹膜色**连通域（2 个）
   - 嘴 ← **口腔色**连通域（唯一色）
   - 脸 ← **皮肤色**连通域里"跨在头顶与下巴之间"的那些（额头与脸被刘海切成两块，两块都要）
   - 刘海 ← 头发高光连通域 ∪ 头顶带
   - 侧发 ← 在脸的纵向范围内，**逐行从脸的外缘向两侧扫头发游程**
   - 后发 ← 头发里剩下的
   - 躯干 ← 上衣/领口 + 脖子 + 肩以下后发 + **兜底**（见坑⑤）

3. **🔴 无损校验（自带断言）**：把 9 层按序合成，必须与输入位图**逐像素完全相同**；
   漏一个像素、重复覆盖、或背景被图层碰到，都会直接报错退出。

产出 9 层：`torso / hair_back / face / eye_l / eye_r / mouth / side_l / side_r / bangs`。

### 3.2 驱动量（`20_animate.py`）

全部**程序化**，没有任何模型权重：

| 驱动量 | 做法 |
|---|---|
| 呼吸 | 正弦；躯干纵向伸缩 ±1.0% + 位移 ±2.4 px |
| 眨眼 | 事件驱动（间隔随机 2.4–5.2 s）；**眼皮＝皮肤，从上往下"擦"过眼睛**（lid wipe） |
| 口型 | 说话时按文字节奏开合（两个频率叠加，段间夹停顿＝标点闭嘴）；**写字时恒 0** |
| 摆动 | 侧发/刘海/后发做**延迟跟随**（相位滞后 14–34°，幅度 2.2–3.0 px） |

## 四 · 实测数字（Apple M3 / 24 GB / 无 CUDA）

| 项目 | 数值 |
|---|---|
| 分辨率 / 帧率 | 1024 × 1024 @ 30 fps |
| **渲染速度** | **18–74 fps**（随机器负载波动；多数干净测量落在 **32–74 fps**） |
| 每帧耗时 | 13.6–53.9 ms |
| 端到端（含编码） | **3 分 39 秒**（218.8 s） |
| 内存峰值（渲染） | **257 MB** RSS |
| 内存峰值（分层） | 276 MB RSS |
| 内存峰值（ffmpeg 编码） | 385 MB RSS |
| **模型/依赖体积** | **无模型权重（0 GB）**；依赖＝已存在的 venv 里 numpy+scipy+Pillow（146 MB） |
| 本 PoC 产出总量 | **4.4 MB**（含 270 帧 PNG + 4 个 MP4 + 3 个 GIF） |
| 是否需 GPU | **不需要**。CPU 纯算，无 CUDA / 无 MPS |
| 首次产出耗时 | ≈ 4.5 s（生成立绘 3.1 s + 分层 1.4 s） |

🔴 **关于 fps 的诚实说明**：以上数字是**在极高系统负载下**测的 ——
实测当时 `load average = 51.36 / 69.81 / 63.96`（8 核机器，约 **6–9 倍超订**，其它工作线在并发跑）。
所以 18 fps 那一档是**保守下界，不是这台机器的上限**；同一命令在较轻负载下测到 66–74 fps。
多轮实测台账见 `out/perf_ledger.json`。

**结论**：目标 30 fps 在多数测量下达得到，但**这个 Python/PIL 渲染器是"离线产出"形态**。
产品里要在浏览器实时驱动，应移植成 canvas/WebGL 合成（同一套图层、同一套驱动公式，见报告 §五）——
那才是能真正跑满 60 fps 的形态。

对比：报告里调研的路线（THA4 学生模型需逐角色训练 ~30 h / LivePortrait 权重 2.14 GB / See-through 权重 14.7 GB）
在本机要么跑不了、要么要下 GB 级权重 —— **本方案是零权重方案**。

## 五 · 踩过的坑（都写进代码注释了，别改回去）

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| ① | **用"最近色"分类** | 背景灰 `(232,232,235)` 与眼白 `(255,255,255)` 距离仅 ~40 → **整个背景被判成眼白**，"眼白连通域"变成 13 万像素一整块，眼睛根本找不到 | 必须**精确相等**匹配；非调色板颜色直接报错，不静默错分 |
| ② | **两张降采样图混用** | 用 LANCZOS 版（抗锯齿）取色、用 NEAREST 版（纯净）分类 → 边界像素上两张**必然不同**，无损校验假失败 13144 px | **分类与取色/校验共用同一张**（NEAREST）；LANCZOS 版只作成品 |
| ③ | **图层外接框太紧** | 眼框 = 虹膜 bbox + 固定 pad：pad 小则描边漏像素（528 px），pad 大则**把眉毛吃进眼层**（眨眼时眉毛消失） | 眼框改用**眼球像素有界膨胀 + 上沿钉在虹膜上缘**；眉毛与眼睛描边同色，只能靠几何关系分开 |
| ④ | **图层内部有透明洞** | 图层是**互补**的（face 在嘴处是洞、bangs 在额头处是洞）→ `alpha_composite` 遇到 alpha=0 不填色 → **背景色从人物内部冒出来**（最差帧 3315 px） | 合成前把每层的洞按**最近不透明像素色**填满（一次距离变换，线性时间） |
| ⑤ | **逐条规则认领必然漏** | 衣领描边（line 色）既不在脸层也不在嘴/眼框里 → 漏 436 px | 把"**人物像素必须被覆盖**"写成**结构性不变量**：躯干作底层**兜底** |
| ⑥ | **头部件各自大位移 → 开白缝** | 侧发与脸是同一块头发切成的**前后两片**，各自位移就错开露底 | 头部件**刚性同动**（共用同一个位移），摆动幅度压到 2.2–3.0 px，远小于图层重叠量 |
| ⑦ | **眨眼"压扁 + 交叉淡入"会混出脏色** | 半闭帧是半透明虹膜压在皮肤上 → 实测出现 `(151,166,184)`、`(134,116,105)` 这类不在调色板里的灰蓝/灰褐 | 改用 **lid wipe**：眼皮就是皮肤，让 face 层皮肤色从眼睛上沿**往下推进**，任何中间态都是两个纯色相接 |
| ⑧ | **三角波眨眼采样不到峰值** | 0.14 s 眨眼 ≈ 4.2 帧，峰值落在两帧之间 → 采样峰值只有 **0.70**，画面上永远"闭不严" | 不要"造波形再采样"，**对每帧直接算平滑凸包**；并**自带断言**峰值 ≥0.90 |
| ⑨ | **填洞后外接框失效** | 填洞把 alpha 全置 255 → `getbbox()` 返回整张画布 → 每帧按 1024² 合成，**渲染从 87 fps 掉到 8.5 fps** | 外接框必须在**填洞之前**用原始 alpha 算 |
| ⑩ | **开缝判据用"实心内部出现背景色"** | 静止立绘在轮廓内部本来就有**合法背景凹口**（两发之间、肩颈之间，首帧就有 2511 px）→ 直接假阳性 | 必须用**差分**判据：**某帧是背景、而静止立绘在该处不是背景** |

## 六 · 已知边界（换素材/换场景要重核）

1. **分层依赖"平色块 + 唯一色"画风**。本 PoC 的立绘是**代码绘制**的（每个语义区域颜色唯一），
   所以"精确色分类"成立。**换成真实手绘立绘（渐变、厚涂、无唯一色）这套分层会失效** ——
   那需要 See-through 那类基于模型的自动分层（需 CUDA，或走官方 HF Space）。
2. **正面、左右大致对称的胸像构图**。侧脸/全身/多角色未验证。
3. **闭眼与闭嘴两张小图是"新画的"**，不是从原立绘拆出来的（原立绘里没有这两张画）：
   `out/layers/_gen_closed_eye.png`、`out/layers/_gen_closed_mouth.png`。
4. **不是 `.moc3`**。本方案输出**位图帧**，不是 Live2D 模型 —— 与只吃 `.moc3` 的渲染宿主的
   整合方式完全不同（见报告 §四接线说明）。
5. **帧渲染是 Python/PIL**，用于**离线产出**。产品里要在浏览器实时驱动，
   应移植成 canvas/WebGL 合成（同一套图层与同一套驱动公式，见报告 §五）。
