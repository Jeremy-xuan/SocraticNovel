## 3 · 改动三（核心）：替换 turn 首步判定

**位置**：`index.mjs` 第 70–89 行（整块替换）

### 🔴 原行（第 70–89 行，逐字，一字不改地摘录）

```js
  // ---- 3) 每回合 chat 注入（turn 首步，实测③的模式） ----
  ctx.on('agent/pre-step', async (payload, next) => {
    const isFirstStepOfTurn = payload.step === 1 && payload.messages.length > 0
    if (!isFirstStepOfTurn) return next()

    phase.noteTurnStart()
    const due = planTurnInjections(manifest.blocks, phase, { classroom: manifest.classroom.id })
    if (due.length === 0) return next()

    const decision = await next()
    if (decision?.kind !== 'enter') return decision
    const injected = due.map((d) =>
      createUserMessage({
        content: [{ type: 'text', text: d.text }],
        source: { kind: 'socratic-engine', form: 'classroom-block', block: d.id },
      }),
    )
    log(`turn ${phase.turnCount} 注入 ${injected.length} 块：${due.map((d) => d.id).join(',')}`)
    return { kind: 'enter', messages: [...decision.messages, ...injected] }
  })
```

### 新行（同样 20 行，保持原有风格与缩进）

```js
  // ---- 3) 每回合 chat 注入（幂等门：键 = sessionId + turn） ----
  // 取证：agent/pre-step 按 **step** 触发，payload = { agent, messages, turn, step, signal }
  //   tmp/dsh-installed/dsh-agent-loop/lib/index.js:894,937
  //   tmp/dsh-installed/dsh-agent/lib/index.js:209（waterfall 注入 agent）
  // 旧判定 `payload.step === 1 && payload.messages.length > 0` 把「是否注入」与
  // 「本次 claim 是否非空」耦合在一起：step===1 但空批 → 漏注入且计数不推进。
  // 改为只看 (sessionId, turn)：同 turn 一律拦、新 turn 一律放，与 messages 空否无关。
  ctx.on('agent/pre-step', async (payload, next) => {
    const decision = await next()
    // 先拿到下游汇合结果：只有真要进这个 step 时才消耗本 turn 的注入额度，
    // 否则 reject 路径会把额度吃掉却不注入（见本文件 §5 的不变量 I3）。
    if (decision?.kind !== 'enter') return decision

    const gate = dedup.shouldInject({
      sessionId: sessionIdOf(payload),
      turn: payload.turn,
      step: payload.step,
    })
    if (!gate.inject) return decision
    if (gate.mode !== 'turn') log(`去重门退化（${gate.reason}）`)

    phase.noteTurnStart()
    const due = planTurnInjections(manifest.blocks, phase, { classroom: manifest.classroom.id })
    if (due.length === 0) return decision

    const injected = due.map((d) =>
      createUserMessage({
        content: [{ type: 'text', text: d.text }],
        source: { kind: 'socratic-engine', form: 'classroom-block', block: d.id },
      }),
    )
    log(`turn ${payload.turn} 注入 ${injected.length} 块：${due.map((d) => d.id).join(',')}`)
    return { kind: 'enter', messages: [...decision.messages, ...injected] }
  })
```

### 三处语义变化的说明（逐条对应）

| # | 旧 | 新 | 为什么 |
|---|---|---|---|
| a | `payload.step === 1 && payload.messages.length > 0` 判「首步」 | `dedup.shouldInject({sessionId, turn, step})` 判「本 turn 是否已注入」 | 旧式把**注入资格**与**claim 是否非空**绑死；二者语义无关。空批时会**漏注入且不推进 turnCount**，让 `frequency: n_turns`（`turnCount % n`）相位漂移。 |
| b | 先算 `due` 再 `await next()` | **先 `await next()`**，再判门、再算 `due` | 保证「消耗额度」与「真的注入」是同一件事，reject 路径不吃额度（不变量 I3）。 |
| c | `log(... turn ${phase.turnCount} ...)` | `log(... turn ${payload.turn} ...)` | `phase.turnCount` 现在只统计**真正注入过的** turn；日志里报**宿主给的 turn 号**才不会在漏注入/重试时对不上。 |

> 🔴 **注意 `payload.messages.length > 0` 这个条件被整条去掉**，不是搬到别处。
> 理由：注入纪律是「每回合贴尾一次」，**哪怕本 step 没有新输入（空批）也该注入**——
> 空批恰恰说明模型要在这一个 step 里继续干活，更该带上教学纪律。

## 5 · 必须成立的三条不变量（供集成代理验收）

- **I1 · 每 (turn, 块) 恰好一次**：任何 turn 内多个 step 只放行 1 次；每个 turn 各放行 1 次。
  → 由 `test/dedup.test.mjs` 用例 ①②⑥ 覆盖；集成层由 `test/integration/multiturn.mjs` 的
  「🔴 无 (turn, block) 重复注入」断言覆盖。
- **I2 · 退级可见**：拿不到 `turn` 时 `shouldInject` 返回 `mode === 'sequential'` 且 `stats.degraded` 增长，
  **绝不静默退回旧语义**。→ 单测 ⑤；接线里 `if (gate.mode !== 'turn') log(...)` 把它打到日志。
- **I3 · 不空耗额度**：`decision.kind !== 'enter'`（reject）时**不得**消耗本 turn 的注入额度。
  → 这正是改动三「先 `await next()` 再判门」的原因。

## 6 · 接线前 vs 接线后的**预期差值**（务必按这个口径读集成结果）

### 6.1 先纠正一个容易写错的预期

🔴 **在「正常的、单个 turn 内多个 step」场景下，接线前后每 turn 的注入条数是一样的**
（都是「每 turn 每块 1 条」）。原因：旧判定用 `payload.step === 1`，**step 号在一个 turn 内单调递增**
（取证 §2.4-C：`phase.step = 0` 只在新 turn 开始时重置），所以 3 个 step 的 turn 里旧判定**也只放行 step 1 一次**。

**不要把"接线后条数变少"写成验收标准**——那样测出来"没变化"会被误判成没接线成功。
真正的差别在**鲁棒性**，不在正常路径的条数。

### 6.2 真正会变的地方（这才是要验的）

| 场景 | 接线前 | 接线后 | 可观测差别 |
|---|---|---|---|
| 正常 turn（1 step） | 每块 1 条 | 每块 1 条 | 无差别 |
| 正常 turn（3 step） | 每块 1 条 | 每块 1 条 | 无差别（但接线前的"对"是靠 step 号巧合） |
| `step===1` 但 claim 空批 | 🔴 **0 条**（漏注入），且 `turnCount` 不 +1 → `n_turns` 相位漂移 | ✅ 每块 1 条，`turnCount` +1 | 注入条数 +1 组 |
| 同一 turn 内 `step===1` 出现两次 | 🔴 **每块 2 条**（双注入） | ✅ 每块 1 条 | 注入条数 −1 组 |
| `decision.kind === 'reject'` | 先算 `due` 并已 `noteTurnStart()`（额度/计数被吃，但没注入） | 不吃额度、不计数 | `classroom_status` 回报的 turn 数不同 |
| 插件热重载后首个 turn | 按 `injectedOnce` 决定（`every:turn` 块会再注一次） | 同左（门是内存态，见 `lib/dedup.mjs` R2） | 无差别（已声明） |

### 6.3 已实测的基线数字（可直接用作对比锚点）

**本 fixture（`test/fixtures/minimal-classroom`）有 2 个 `every: turn` 且相位门放行的块**（`anchor`、`state-brief`）
→ **每个 turn 应注入 2 条**。S3 接线前实测（2 turn）：

```
turn/start = [1, 2]
每 turn 的 step 数 = {"1":1, "2":1}
socratic-engine 注入 4 条 → turn1:[anchor, state-brief]  turn2:[anchor, state-brief]
perTurn = {"1":2, "2":2}
```

→ **接线后重跑应仍是 `perTurn = {"1":2,"2":2}`**。若变成 `{"1":1,...}` 或出现 `(turn,block)` 重复，即为回归。

🔴 **重要**：「每回合注入一次」的正确口径是**每 (turn, block) 一次**，不是「每 turn 总共一条消息」。
把这两个混起来会把正常的 2 条误判成双注入（S3 已踩过这个理解坑，特此写死）。

### 7.1 🔴 请务必补跑 `PROMPT_STYLE=tools`（S3 因额度未跑）

S3 实测发现：**纯对话 prompt 每个 turn 只有 1 个 step**（落盘 `每 turn 的 step 数={"1":1,"2":1}`）
→ 那种运行下 `agent/pre-step` 每 turn 只被调 1 次，**去重门与旧判定的差别测不出来**，
「多 step 只放行一次」这条路径**只有单测覆盖，集成层未覆盖**。

`PROMPT_STYLE=tools` 会让每轮先用 `bash` 跑 `echo`，使 turn 内出现工具调用 → ≥2 个 step；
脚本在该模式下**强制断言**「确实出现了多 step 的 turn」，没有就**判失败**（防止再把弱证据当强证据）。

### 7.2 集成脚本的计数口径（写死，供复核）

- **数什么**：落盘 `session.v3.jsonl.zstd`（`zstd -dc` 解压）里
  `type === 'user/message' && data.source.kind === 'socratic-engine'` 的事件条数。
- **归属哪个 turn**：取该事件之前**最近的** `turn/start` 的 `data.turn`。
- **定位哪个日志**：优先用 driver 报告里的 `sessionId` 比对日志**首行 header 的 `id`** 精确定位
  （同一 `$DSH_HOME` 上可能有并行会话在写盘，不能只靠"最新 mtime"）。
- **为什么这个口径可靠**：`user/message` 只在 step 的**首次 attempt** 落盘
  （`tmp/dsh-installed/dsh-agent-loop/lib/index.js:1015,1028`），
  → **LLM 重试不会重复计数**，该指标对重试免疫。
