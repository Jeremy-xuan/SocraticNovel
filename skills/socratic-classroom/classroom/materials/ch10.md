## 本讲要回答的核心疑问

> **上一讲我们看到：把"读—改—写"围起来、让同一时刻只允许一个线程进去，就能避开竞态。可是——"检查有没有人占用"和"标记为已占用"，这两件事本身不也是两步吗？它们之间不也能被插队吗？**

**先把题目讲清楚**：这是本讲真正的技术核心，也是最容易被跳过去的一步。上一讲的结论是"我们需要一个互斥机制"，但**光说"我们需要一个锁"是没用的**——因为用普通指令写出来的锁，会掉进同一个坑里。本讲要让学生看到：**锁不可能只靠软件堆出来，它的地基必须是硬件提供的原子操作。**

不要把隐喻的物件当成机制本身：先讲清"锁是一个对象，有两个动作——获取和释放"，再进入技术问题。

## 教学地图（选择动作，不按顺序过关）

### 值得学生推导的关键关口

**一、用普通变量写一把锁，会怎么坏？** 🔴 让学生自己写、自己拆。

起点由教师给：锁可以用一个变量 `flag` 表示，0 表示空闲、1 表示已占用。然后问："你会怎么写'获取锁'？"

学生大概率写出类似"先读 flag，如果是 0 就把它设成 1"的结构。接着问：

"**'读 flag'和'设 flag'之间，能不能被切走？**"

到这里学生就回到了上一讲的同一个窗口。**关键结论**：只要"检查"和"设置"是两个分开的可打断步骤，两个线程就可能**同时**看到 flag 为 0，**同时**认为自己抢到了锁。这把锁等于不存在。

这时可以顺势让他自己得出结论：**需要的不是"更小心地写这两步"，而是一个"检查并设置"不可分割的操作。**

**二、硬件提供的是什么？** 教师在这里给事实（不要让学生猜指令）：

硬件可以提供一个**原子的读—改—写**操作。其中最常被用来讲锁的语义是 **test-and-set**：它读取一个内存位置的值，**同时**把一个新的值写进去，并把**读到的旧值**返回给调用者——整个过程不可分割。

关键就在于那个"返回旧值"：拿到 0 的人知道"刚才它是空闲的，而且现在已经是我的了"；拿到 1 的人知道"有人先占了"。**判断和占用发生在同一个不可分割的操作里**，所以中间没有缝。

⚠️ **术语与事实边界**：不同体系结构提供语义相近但名字不同的原子指令（例如有的用交换、有的用比较并交换）。**具体指令名与语义细节随体系结构而异，本教材不逐个断言（标「待核」）**。教学要讲清的是"**存在这样的硬件原子操作**"以及"**锁为什么必须建立在它之上**"。

**三、"抢不到"的时候该干什么？** 这是第二个关口。

最直接的做法是**一直重试**——这就是**自旋锁（spin lock）**：循环调用 test-and-set，直到拿到为止。让学生自己说代价：

- 单核上：🔴 拿不到锁的线程在自旋，而**持锁的线程可能正等着被调度**。也就是说，自旋者正在**白占着 CPU**，而它等的那个线程恰恰**需要 CPU 才能放手**。这不是"浪费一点时间"，而是**几乎必然的白等**。
- 多核上：自旋可能是有意义的——持锁的那个线程**真的正在另一个核上跑**，锁很快会释放，自旋比重调度更划算。所以"自旋是不是浪费"取决于**有没有别的地方能推进**。

走到这里，"自旋锁好不好"这个问题就变成了一个更有意思的问题：**好的答案取决于场景**。可以顺势介绍常见的折中做法：**先自旋一小会儿，还没拿到就让出 CPU**（两阶段做法）。这是工程上的常见选择，不是理论上的最优。

### 关键点之后的讲解主线

- **片段一 · 锁的接口与语义**：锁提供获取（acquire/lock）与释放（release/unlock）两个操作。语义上要保证的是：**同一时刻最多一个线程处于临界区**。要让学生分清两件事——锁**不保证执行顺序**，也不保证"公平"（谁先请求谁先进）；它保证的是**互斥**。很多并发 bug 来自把这两件事搞混。
- **片段二 · 为什么"忘了释放"是最常见的错误**：锁的获取与释放必须成对。如果在临界区里提前返回、或者抛了异常，而释放语句被跳过，那么这把锁就**永远被占着**——所有后来的线程都会卡住。学生能自己想出这条后果，就说明他理解了锁是"状态"，不是"动作"。
- **片段三 · 保护数据结构比加一把锁难**：这是 KP-10.3。给学生一个具体结构（比如一条链表）的插入操作。关键问题是：**如果只在函数入口加一把大锁，好处和代价各是什么？** ——好处是简单、不容易漏；代价是**所有操作串行化**，哪怕它们互不冲突（比如两个线程同时读）。而如果想让读并行，就要考虑更细的方案（比如读写锁、或让更新本身成为原子操作）。这一段的目的不是让他实现，而是让他看到：**"加锁"这个动作本身是有成本的设计决策，不是一个安全开关。**
- **片段四 · 粒度（granularity）**：同一份数据，可以只锁其中的一部分（细粒度），也可以整体锁住（粗粒度）。细粒度换来并发度，代价是**复杂度、死锁风险与开销**（要维护多个锁、要考虑加锁顺序）。粗粒度换来简单与正确性容易保证，代价是并发度低。可以补一句：**粒度不是一个定值，它取决于访问模式**——这也是第 12 讲死锁问题的直接来源（多把锁就会出现加锁顺序问题）。

### 真正值得再停下来的地方

- 学生说"用普通变量也能做锁，只要检查得快一点"：直接给出反例——两个线程都可能读到 0。**"快"不是"不可分割"**，这两件事必须分清。
- 学生把"锁"理解成"把代码变成不可中断的"：澄清锁**只约束竞争同一把锁的线程**；不碰这把锁的代码照跑不误。锁不是关掉中断（那是内核内部另一种手段，不是这里讲的应用层机制）。
- 学生问"自旋锁是不是错的"：不要给"对错"，给**条件**——有没有别的地方能推进。单核上等一个正在等 CPU 的线程，是白等；多核上等一个正在运行的线程，可能是划算的。
- 学生认为"锁能保证公平"：用提问检验——"如果十个线程都在等，锁释放时一定给最早请求的那个吗？"答案是**不保证**，这就是上面说的"互斥 ≠ 公平"。真实系统里饥饿（starvation）是可能的，需要额外的机制处理。
- 学生把"锁的粒度"当成"锁的大小"这种物理概念：说明它指的是**保护范围**——"这一行"还是"整叠"。范围小则并发高、难写对；范围大则好写、并发低。
- 学生问"为什么不用一把大锁把整个程序锁住"：这个方向值得认真回答——**它是正确的但会退化成串行**。可以问他："那多线程还有什么意义？"

### 检验理解的一个新情境

给一个简单的共享计数器结构，并说明有两个操作：`inc()` 和 `read()`。问：

1. 如果只加一把大锁，`inc` 和 `read` 会互相阻塞吗？（会）
2. 如果想让两个 `read` 能同时进行，你需要改什么？（不能只靠一把互斥锁；需要更细的方案）
3. 如果给这个结构里**两个字段各加一把锁**，会带来什么新风险？（加锁顺序问题 → 死锁，第 12 讲）

学生能说出第 3 问的方向（多把锁会引入顺序问题），就说明他理解了"粒度变细付出复杂度"这句话的实质。不必要求他写出完整实现。

## 本讲核心事实（知识锚 · 不许说错）

- **锁（lock）** 提供两个操作：**获取（acquire/lock）** 与 **释放（release/unlock）**；语义目标是最多一个线程处于临界区，即**互斥（mutual exclusion）**。
- **用普通变量实现锁会失败**：因为"检查"与"设置"是两个可被中断的步骤，两个线程可能同时认为自己拿到了锁。这不是写得不够小心，而是**缺了原子性**。
- **test-and-set**：硬件提供的一种**原子读—改—写**操作，读取内存中的值并写入新值（通常写 1），**返回读到的旧值**；调用者据旧值判断自己是否抢到。原子性由硬件保证，这是锁能够成立的地基。
- ⚠️ **待核**：不同体系结构提供的原子指令名称与细节不同（交换／比较并交换等）。本教材**不逐一断言具体指令名与语义**；教学要点是"存在这样的原子操作"以及"锁必须建立在它之上"。
- **自旋锁（spin lock）**：抢不到锁时循环重试。其代价取决于场景——**单核上自旋几乎必然是浪费**（持锁者也需要 CPU 才能释放）；多核上若持锁者确实在另一核上运行，自旋可能比重调度更划算。
- **常见的折中**：先自旋一段时间，仍未获得则让出 CPU（两阶段做法）。这是工程取舍，不是理论最优。
- **互斥 ≠ 公平**：锁不保证请求顺序，也不保证不会饥饿。
- **忘记释放**会导致锁永久被占用，后续所有请求者卡住；因此获取与释放必须成对，包括异常与提前返回的路径。
- **锁的粒度（granularity）**：指保护范围而非物理大小。细粒度 → 并发度高、实现复杂、且引入**多把锁与加锁顺序**的新风险；粗粒度 → 简单但并发度低。
- **用锁保护数据结构的难点**：不是"加一把锁"这个动作，而是决定**哪些操作需要互斥、哪些可以并行**，以及粒度如何与访问模式匹配。

## 类比的边界（可能误导时讲清）

**海洋隐喻在哪不成立？**
- "扣一枚贝壳标记表示占用中"看起来是一**个**动作；而机器上的"检查并设置"**本来是两个动作**，是硬件把它做成了一件——这正是本讲的中心。隐喻顺手掩盖了技术难点，用它之前必须说清这一点。
- 人挂标记时会**看到**别人已经挂了；机器**不会自动看到**。所谓"规则是所有人认的"，在机器上必须由**一条原子指令**来实现，不能靠默契。
- 人会累、会不好意思一直站着等，**自己就走了**；自旋的线程**没有这种自觉**，它会一直转下去。不要用"人不好意思"来解释自旋的代价。
- 现实里"忘了摘标记"过一会儿总会有人提醒；程序里**没有提醒**，这把锁就永久僵住了。不要把它类比成一次小的疏忽。
