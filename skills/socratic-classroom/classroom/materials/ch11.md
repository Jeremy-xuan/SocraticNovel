## 本讲要回答的核心疑问

> **一个线程要等一件事发生——比如"队列里终于有东西了"——才继续。它怎么等？如果它一直检查条件，就在烧 CPU；如果它睡着了，那谁来叫醒它？醒来的时候，那件事还在吗？**

**先把题目讲清楚**：锁解决的是"不许同时进来"，本讲解决的是"**要等一件事**"。这是两类完全不同的问题。用锁去解决等待，只会得到两种坏结果之一：要么忙等（浪费 CPU），要么睡下去再也没人叫（卡死）。条件变量和信号量就是为"等待"这件事造的机制。

不要让学生猜"通行证"指什么：先讲清"它是一个计数器，表示还有几个名额"，再进入技术问题。

## 教学地图（选择动作，不按顺序过关）

### 值得学生推导的关键关口

**一、忙等为什么不行？** 学生通常能说出"浪费 CPU"。可以往下推一层，让它变成一个更准的答案：

"如果只有一个核，而等的人正占着这个核——那件它等的事，还有机会发生吗？"

学生大概率会意识到：**可能永远不会**。这就是忙等比"浪费"更严重的地方——它可能把本该推进的那一方也一起饿死。第 10 讲的自旋锁已经出现过同一件事（单核上等一个需要 CPU 才能放手的线程），这里是它的另一半：**等待要有效，必须先把执行机会让出去。**

**二、那"睡下去等人叫"要配齐哪几件东西？** 这个关口值得让学生自己列。他列出的应该包含：

1. 一个**排队的地方**（等待队列，wait queue）——不然叫谁？
2. 一个**让出锁并睡下**的动作——注意，必须把锁交出去，否则叫醒你的人根本进不来；
3. 一个**叫醒**的动作；
4. 一个**保护"条件本身"的锁**——条件（比如队列是否为空）是共享状态，读写它需要互斥。

第 2 点是最容易漏的：学生常以为"睡觉"只是把线程挂起。**实际上它必须原子地完成"释放锁 + 入睡"**，否则在两者之间，另一个线程可能已经改了条件、发了通知——而通知是发给"队列里的人"的，此时你还没进队，就会**永远错过**。这个问题叫**丢失唤醒（lost wakeup）**，是本讲最该讲清的机制细节之一。

**三、醒来之后，条件还是原来的条件吗？** 🔴 这是本讲最重要的一个关口（KP-11.2）。

让场景具体：一个线程在等"队列非空"。它被叫醒了，然后……

"在它被叫醒到它真正开始执行之间，有没有可能别人已经把队列里的东西取走了？"

答案是**有可能**。所以：

> **等待返回不等于条件成立。醒来的那一刻必须重新检查条件。**

这就是为什么代码里用 `while (!condition) wait(...)` 而**不是** `if (!condition) wait(...)`。用 `if` 的话，只检查一次就往下走——它可能在条件已经又不成立的情况下继续执行，接着去操作一个空队列或空缓冲区。

⚠️ 教学上要守住一条：**不要把"用 while"讲成"一种防意外的好习惯"**。它不是防御性编程，而是**语义上的必然要求**——因为"条件成立"与"此刻执行"之间本来就存在着不可消除的间隔。

### 关键点之后的讲解主线

- **片段一 · 条件变量的三件套**（KP-11.1）：条件变量本身只提供三样东西——一个**等待（wait）**、一个**通知（signal）**、一个**广播（broadcast）**；它**不自带锁**，必须配一把锁使用。三者的分工是：锁负责保护条件这个共享状态；wait 负责"释放锁并入睡"；signal 负责"叫醒其中一个"。可以强调：**条件变量自己不记住任何事**——如果没有人正在等，signal 就什么也没发生（后面会说这为什么重要）。
- **片段二 · 通知的两种模式**：**signal** 叫醒等待队列里的**一个**；**broadcast** 叫醒**全部**。选择取决于"条件变化后有多少人可能可以继续"：如果条件一变、只有一个人能继续（比如队列多了一个元素），signal 够用；如果一次变化让**多个**等待者都有机会（比如状态变成"可以开始了"），就必须 broadcast，否则可能有人白白错过。广播的代价是**惊群（thundering herd）**：一堆线程被叫醒、抢锁、然后发现自己还不能继续、又睡回去。这不算错，只是浪费。
- **片段三 · 信号量：一个带计数的抽象**（KP-11.3）：信号量的核心是**一个计数器加两个原子操作**——通常写作 `sem_wait`（也被叫做 P 操作／down）与 `sem_post`（V 操作／up）。它的语义可以这样记：**`wait` 把计数减一；如果减完会变成负数，就等待（也就是把"欠的"记在等待队列上）；`post` 把计数加一，并在有人等的时候唤醒一个。** 计数初值决定了它的用途：
  - **初值为 1 → 当互斥锁用**（每个线程先 wait 后 post，把临界区夹在中间）；
  - **初值为 0 → 当顺序／信号用**（一方 post，另一方 wait，用于表达"这件事做完了，你可以开始了"）。
  同一个机制、两种用法。让学生各举一例，是检验他真懂了的最快方法。⚠️ **待核**：P／V 这两个字母来自荷兰语（Dijkstra 的命名），本教材只说明它们与 `sem_wait`／`sem_post` 的对应关系，不展开命名史细节。
- **片段四 · 生产者-消费者**（KP-11.4）：这是本讲的综合练习，也是并发课程里的经典例子。设置：一个**有界的缓冲区**（bounded buffer），生产者往里放，消费者从里取。需要四件事同时成立：**缓冲区本身要互斥访问**（同一刻只能一个人动它）；**满的时候生产者要等**；**空的时候消费者要等**；**每种等待都要有人来叫**。可以让学生推演几种写法的失败路径：
  - 完全不加锁 → 竞态条件（第 9 讲）；
  - 加锁但用 `if` 而不用 `while` → 醒来的线程在条件已变的情况下继续，动到不该动的数据；
  - 用一把锁同时保护"缓冲区"和"等待"→ 死锁或丢失唤醒（wait 需要释放锁，而锁被同一把锁的语义缠住）；
  - **只用一个条件变量同时管"空"和"满"**：生产者被叫醒却发现是自己这一侧满了、消费者被叫醒却发现是空的 → 可能互相叫醒、互相睡回去。**两个方向各自需要一个条件变量**，这不是风格问题，是正确性问题。
- **片段五 · 极端情况**：缓冲区大小为 1 时会发生什么？（生产者放一个就得等，消费者取走才有人叫）这能帮学生把"容量"这个参数与"需要几个等待位置"联系起来。

### 真正值得再停下来的地方

- 学生把条件变量当成"能记住状态的变量"：🔴 直接纠正——**它不记任何状态**。条件本身存在**别的共享变量**里（比如队列长度）；条件变量只是"叫号的地方"。如果 signal 时没人在等，这个信号就丢了。所以"先检查再等待"的顺序与"发送方也要持锁"这两件事才这么重要。
- 学生问"为什么 wait 必须原子地释放锁并入睡"：用丢失唤醒的具体时序讲——A 检查条件不成立 → （此刻 B 改条件并 signal，但 A 还不在队列里，信号丢了）→ A 入睡，再也没人叫它。**这个时序必须让学生自己走一遍**，比背结论有效得多。
- 学生认为"signal 一次就该叫醒所有需要的人"：说明 signal 与 broadcast 的差别，并说明"该用哪个"取决于一次条件变化能让几个等待者继续。用错不会立刻崩，但会变成偶发的卡住——这类问题最难查。
- 学生说"那干脆全用 broadcast，反正不会错"：可以承认**这样确实更不容易错**，但让他自己说代价（惊群：一堆线程被叫醒又睡回去，还要抢锁）。这是"正确性优先于效率"的一个真实取舍。
- 学生把信号量的两种用法混成一种：用一个检验题分开——"初值 1 的信号量，和一个初值 0 的信号量，各自想让线程等待什么？"答案不同，说明是两种用途，不是同一个东西的两个名字。
- 学生把 `sem_wait`／`sem_post` 与条件变量的 `wait`／`signal` 混为一谈：明确两者的区别——条件变量必须**配锁**使用，且**不记状态**；信号量**自带计数**，因此它**记得住**（先 post 后 wait 也能通过）。这个区别是学生最容易搞混的一处。

### 检验理解的一个新情境

给一个大小为 1 的缓冲区，两个生产者、一个消费者。问：

1. 生产者 P1 放入一个元素后，它要通知谁？（等待"非空"的消费者）
2. 如果生产者只在**缓冲区从空变非空**时通知，而 P2 放入时缓冲区已满、它必须先等——这时 P2 在等什么？（等"非满"，即消费者取走）
3. 如果这里只有一个条件变量，最坏情况会怎样？让学生把时序写出来。

学生能指出"两种等待方向需要分开"，并且能说清"通知发出去时没人在等就等于没发"，就说明他掌握了本讲的核心。不必要求他背诵预设句子。

## 本讲核心事实（知识锚 · 不许说错）

- **条件变量（condition variable）** 提供 **wait / signal / broadcast** 三个操作；它**本身不保存任何状态**，必须与一把**锁**配合使用。
- **`wait` 的语义**：原子地完成"释放锁并进入等待队列"；被唤醒时**重新获取锁**再返回。
- **为什么会**丢失唤醒（lost wakeup）**：若"释放锁"与"入睡"不是原子的，另一线程可能在你进队之前就发出通知，该通知无人接收而丢失，你将永远等待。
- **为什么用 `while` 而不是 `if`**（KP-11.2）：**等待返回时条件可能已经再次改变**（别人抢先取走了数据、或条件被改回不成立）。因此必须循环重新检查条件。这不是防御性编程，是语义要求。
- **`signal` vs `broadcast`**：前者唤醒等待队列中的**一个**，后者唤醒**全部**。选择依据是"一次条件变化能让几个等待者继续"。broadcast 更不容易出错，代价是**惊群（thundering herd）**。
- **信号量（semaphore）**：一个**计数器**加两个**原子操作**——`sem_wait`（P／down，计数减一；若结果会是负数则等待）与 `sem_post`（V／up，计数加一，必要时唤醒一个等待者）。⚠️ **待核**：P／V 源自荷兰语命名，本教材只说明其与 `sem_wait`／`sem_post` 的对应，不展开命名史。
- **信号量的两种典型用法**（KP-11.3）：**初值 1 → 互斥**（把临界区夹在 wait／post 之间）；**初值 0 → 顺序**（一方 post、另一方 wait，表达"我做完了，你可以开始"）。
- **信号量与条件变量的关键区别**：信号量**自带计数、记得住**（先 post 后 wait 也能通过）；条件变量**不记事**（没人等时 signal 相当于没发）。
- **生产者-消费者（有界缓冲区）** 需要同时满足：缓冲区访问互斥；满时生产者等待；空时消费者等待；两个方向各自有对应的通知。**只用一个条件变量同时管"空"和"满"会导致互相叫醒又睡回去**，属于正确性问题。
- **本讲的边界**：本讲不讨论"等待时谁先被唤醒"这类公平性问题，也暂不展开更复杂的同步模式（读写锁、屏障等）。

## 类比的边界（可能误导时讲清）

**海洋隐喻在哪不成立？**
- 人会自己看情况：没名额就先去干别的、等会儿再来。**线程不会**——它只有"等"或"跑"两种模式；所谓"等会儿再来"必须由等待队列和唤醒动作实现。
- 学生把"通行证"当成一个**物体**，于是以为"还回来"就自然会有人拿走。真实机制里，**唤醒是一个明确的动作**：`post` 的时候要有人正在等着，否则这个名额就只是被记在计数里。通行证的比喻漏掉了"计数的存在"这件事，正好是信号量最要紧的部分。
- 人拿了通行证会知道是谁在后面等；**信号量不保证顺序**，被唤醒的不一定是等最久的那个。
- 人在旁边一直问"好了吗"会累、会被劝走；**忙等的线程不会累**。不要把"人不好意思一直问"当成忙等会被自动纠正的理由。
- **"两张通行证"是一个具体数字，容易让人以为关键在数量**。真正关键的是"**等待要成对**"：拿了就必须还，不还就再也没有名额了。可以顺着 ch08 里那句"那要看有几个人"往下问一句：**这里真正决定的是谁在等、在等什么。**
