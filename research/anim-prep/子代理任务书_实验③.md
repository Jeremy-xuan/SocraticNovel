# 实验③ · 老师自己写 vs 派子代理写 —— 任务书（逐字留档）

> 本文件是**实验③用过的子代理任务书原文**（连同两次的产物路径），供复核。
> 子代理＝**带执行权限**的 DSH 子代理：它能自己跑 `manim`、看到报错、自己改，再交脚本。
> 这正是要验证的那条（ANIM-ORCH 的 A_P4 例）：**"生成方自己跑过一遍就能自己修好"**。

## 任务书（逐字）

```
你是一名能自己动手的动画脚本工程师，任务是给一段操作系统课的教学动画写 ManimCE 脚本，
并且**自己跑一遍确认它能渲出来**——不是把脚本交出来就算完。

教学场景（第 3 讲 · 处理器调度）：
三个任务都在 0 时刻到达：A 需要 100 个时间单位，B、C 各需要 10 个。
要讲的是「为什么 FIFO 会让一个很长的任务把后面短的任务全堵住」。
请画两条时间轴做对比：先到先服务（A→B→C）与最短作业优先（B→C→A），并标出每个任务的完成时刻。

硬约束（违反就会渲不出来）：
- 本机**没装 LaTeX**：不许用 Tex / MathTex / NumberLine(include_numbers=True) / DecimalNumber；
  公式与刻度一律用 Text 写成普通文本。
- 中文一律 font="PingFang SC"。
- 脚本里**恰好一个** Scene 子类，总长 ≤ 200 行。
- 渲染命令（自己跑）：
  <MANIM> -ql --disable_caching --media_dir <WORK>/media -o out.mp4 <SCRIPT> <SceneClass>
  其中 <MANIM> = <MANIM_ENV>/bin/manim

要求：
1. 先把脚本写到 <WORK>/scene.py；
2. **自己运行上面的渲染命令**，直到真的产出 mp4（最多试 4 次）；
3. 每次失败都要读报错、改脚本、重跑（不要跳过这一步直接把失败的脚本交出来）；
4. 一开始用 `date +%s > <WORK>/start.txt`、结束时用 `date +%s > <WORK>/end.txt` 自己计时；
5. 最后写 <WORK>/report.json，字段：
   { "attempts": 试了几次, "success": true/false, "sceneClass": "…",
     "failures": ["每次失败的原因"], "startEpoch": …, "endEpoch": …,
     "scriptPath": "…", "mp4Path": "…" }
6. 回复我一段话：试了几次、每次失败原因、最终是否成功、你自己计时的墙钟秒数。
```

## 两组的可比性

| | 老师自己写（A 组，实验①） | 派子代理写（C 组，本实验） |
|---|---|---|
| 谁写脚本 | 教学会话里的同一个模型 | 一个**带执行权限**的子代理 |
| 能不能自己跑一遍 | **不能**（工具只落盘＋后台渲染，模型看不到报错） | **能**（自己跑 manim、看报错、改） |
| 量什么 | turn/start → 写脚本那次工具调用 | 子代理从开始到交付成功片子的墙钟 |
| 端到端 | ＋渲染 ＋闸门（引擎在后台做） | 子代理自己渲染（含在它的墙钟里） |
| 失败代价 | 老师拿到 `failed` 通报后**下一回合**才知道，学生已经听完了那一步 | 子代理**在交付前**就修好了 |

🔴 这张表本身就是本实验要回答的问题：子代理多的那一段（自己跑一遍）**是纯成本还是保险**。
