## 一 · 舞台有哪几屏，每屏要什么

屏的划分照 STAGE-3 已定的四类（**这四类是从真实截图量的，不是拍的**）：

| 屏 | 是什么 | 要的数据 |
|---|---|---|
| **开场** | 对话推进 | 背景、立绘、**对话文本**、**说话人**、**在场者**、讲次、相位 |
| **板书／投影** | 讲解 | 上述 ＋ **板书图**（`classroom_draw` 的产物） |
| **选择肢** | 元层面选项（继续说／画给我看／我自己写一步…） | **选项清单**、当前选中 |

- **顶部书脊条**（14 讲，当前讲一枚既读点）← 讲次 ＋ 课程表
- **表情**（立绘的脸）← 表情状态

### 2.1 🔴 数据源分工（实测得出，**两个都要用**）

`conversation.view` 条目实测拿得到 **19 项 props**（`shell.overlay` 只有 7 项、无对话流）。
其中两个读口**用途不同，不是二选一**：

| 读口 | 形状（实测） | 用来干什么 |
|---|---|---|
| **`useProjection("turnOutline")`** | 数组 **11 条**，每条 `{turn, seq, prompt, response}`——**天然按回合成对** | 🎯 **对话正文的主数据源**。一讲＝一回合，"谁说了什么"成对给出，比细粒度节点更贴舞台要的形态 |
| **`useChat`** | `s.order` 长度 **167**；节点形状 `{key,kind,id,target,anchorSeq,location,visibility,data}`，`data` 键 `{kind,seq,time,content,source}`；kind 分布实测 `user 3｜turn-process 3｜assistant-step 69｜tool-call 88｜turn-tail 3｜steering 1` | 🎯 **取工具过程**——**板书图（`classroom_draw` 的结果）在 `tool-call` 那 88 条里**，`turnOutline` 拿不到 |

**其余可用性（逐项实测）**：`sessionId` 是**值**（44 字符非空）｜`useInput` 返回 `{draft,attachmentIds,draftRev,phase,occurrences,queue}`｜
`inputActions` 7 个方法｜`useTrajectory` 返回 `{eventNodes,eventLocations,requests,callSchemas,partial,runningCalls}`｜
`useSessionStatus` 返回 Map｜`useProjection("todos")` **本次为 null**。
🔴 **`t` / `actions` / `useStore` / `renderSlot` 在本条目上没有**（没声明 locale/store/children）→ **不要用它们**。
🔴 **`usePanelInfo` 必须传选择器**（如 `usePanelInfo((info) => info.activePanelId === null)`），不传会抛错并被 `data-slot-error` 顶掉整块视图。

## 三 · 四个缺口，逐条对策

### 缺口 1 · 谁在说（说话人身份）

**事实**（`取证_P3` §2.5，置信度高）：

- `conversation.chat.node` 的 `keyDomain` 是**固定 key 表**，已占 18 个
  （`assistant-step` / `command` / `context` / `steering` / `tool-call` / `user` / …）；
  `registerOptions` **只有 `key`** → 🔴 **新增 kind 必须改上游 `ChatNodeKind`，做不到**。
- 全库检索 `agentId` / `agentName` / `speaker` / `roleName` / `persona` / `character`
  在 `ui-chat` / `ui-conversation` **均 0 命中** → **宿主确实没有这个字段**。
- 🔴 **但有一条零改动的通道**：`contextProvenance` 的 `default` 分支逐字是
  `role: "inject"` ＋ `label: kind` → **任何新的 `source.kind` 都被归为"注入"，并以该 kind 名作标签**。

**对策（采用，零上游改动）**：
第二个及以后的角色**不走 assistant 通道**，走 **`user/message` 的注入通道**，并给**独有的 `source.kind`**
（例如 `classroom-role-teammate-a`）。客户端**自动**把它渲染成一条带标签的注入行。
→ 一个回合里既有 `assistant` 气泡（老师），又有标注了名字的注入行（同学）。

**代价（必须写进验收）**：注入行是"上下文注入"的**视觉形态**（斜体/引用式），**不是气泡**。
如果这不够像"同学在说话"，那就得走 **路 C（改上游）**——**当前不做**，但要在验收里明确记录这个观感差距。

### 缺口 2 · 在场者名单

**现状**：教室现在只有 **1 张角色卡**（`characters/komari.md`），`classroom.yaml` 里也没有"角色表"字段。
→ **R15（多角色同台）未开工**，这是它的前置。

**对策**：`classroom.yaml` 增一个 **`cast:`（角色表）** 段，形状照既有的 `characters/` 声明方式：

```yaml
cast:
  - id: komari            # 对应 characters/komari.md
    role: teacher         # teacher | teammate | guest
    present_by_default: true
  - id: <同学 id>          # 第二张角色卡（尚未存在）
    role: teammate
    present_by_default: true
```

**为什么放 `classroom.yaml` 而不是新文件**：项目已定「**教室 `runtime/` 文件＝真源**」，
而**角色表是"教室的静态构成"，不是运行时状态**——它跟 `characters/` 声明同类，
应当跟课程表、知识点一样放在**教室包本体**里，不随每课变化。

🔴 **`present_by_default` 与 R15 的「常驻 ≠ 常发言」对应**：常驻的是**存在感**（立绘／名牌／确定性反应），
发言是**稀疏事件**。所以"在场"和"发言"**必须是两个字段**，不能合并。

### 缺口 3 · 选择肢选项

**现状**：STAGE-3 定的六条是**元层面**的（继续说／画给我看／我自己写一步…），
但**机制未定**——`实现报告_STAGE3` §5.2 自己列了这条：「要不要把自由输入做成第七条、选完怎么回到对话，没定」。

**对策（分两步，本批只做第一步）**：

1. **六条固定项写死在舞台侧**（它们本来就是元层面的，**不随课程变化**，
   不需要引擎供给）→ **这一项从"缺口"降级为"UI 常量"**。
2. **可变项**（例如「复习第 N 讲的错题」这类由 `runtime/review_queue.md` 决定的）→ 走【文件】，
   与其它 runtime 数据同一条路。

🔴 **不做的事**：不让引擎**生成**选项。理由与 R1 结论③一致——
「**教学的事实正确性不能靠生成式注入，必须靠文件逐字回查**」。
选项若是生成出来的，学生点到的那条可能与教室实际状态不符。

### 缺口 4 · 多角色立绘

**现状**（`实现报告_STAGE3` §5.2 已记）：
立绘只有 **3 张同角色差分**，**做不了"三个不同的人同台"**；背景只有 2 张（夜／傍晚）。
且 `live2d-host` 的 `vendor/`（Cubism 官方框架）与 `samples/` **未随仓库分发**。

**对策**：**这不是软件问题，是素材问题** → 归到「**等你给透明底立绘素材**」那条待办
（用户 2026-09-25 已知悉）。软件侧本批**只做"未部署时显式状态"**，不白屏、不冒充。

## 五 · 实现约束（**实测得出，写舞台时必须遵守**）

> 来源：`研究_UI-B1_舞台落点与成熟案例_2026-09-28.md` §2.5／§2.5-bis／§2.5-quater。
> **这些不是设计偏好，是宿主实测行为**——违反哪一条都会出真实故障。

| # | 约束 | 违反的后果 |
|---|---|---|
| **C-1** | 🔴 **全屏根节点必须显式 `pointerEvents: 'none'`**，要接收点击的子控件**各自显式 `'auto'`** | 宿主 CSS `.overlayLayer > * { pointer-events: auto }` 已把条目默认 opt-in（`pointer-events` 是**继承属性**）→ **不写＝整帧接管鼠标＝把整个应用变成不可点** |
| **C-2** | 🔴 **全屏落点用 `position: fixed; inset: 0`**，不用 `width/height: 100%` | 层的父容器是 `overflow:hidden` 但**可程序化滚动**的；流内写法会跟着 `scrollLeft` 偏（实测 −11px），还可能被裁边 |
| **C-3** | 🔴 **`order` 用负值**（例如 `-1`） | 官方 8 个 `shell.overlay` 条目**一个都不传 `order`**（默认 0）；我们传正值＝排最后＝最上层 → **盖住官方弹层**（会话重命名框、提示条、配额提示全出不来） |
| **C-4** | **不要试图"在 layer 上写样式"** | 条目外面还有一层 `display: contents` 的 wrapper（`renderSlot` 包的），**能命中你的 CSS 规则在 wrapper 上**；只能在自己的根节点上声明 |
| **C-5** | **固定画布上的纵向尺寸一律用 px** | 用 `vh`/`%` 在"容器高度 auto"处**静默失效**（症状是"看起来只是有点小"，不是报错）——这是 STAGE-3 踩过的坑 |
| **C-6** | **`captureFrame()` 要自己实现并暴露** | 验收要截图证据；抄 airi 的做法（每个渲染后端统一暴露 `canvasElement` / `captureFrame` / `setExpression`） |
| **C-7** | **`shell.overlay` 拿不到对话流**（无 `useChat`/`useConversation`/`sessionId`） | 任何"要显示对话内容"的部分**不能放在 overlay 层**——它必须走 `conversation.view` 或由下层传入 |
| **C-8** | 🔴 **本轮所有结论只对 `dsh 0.1.7-rc.2` 成立**（`dsh-client-ui-layout` sha256 前 16 位 `0aa7c7437cc30a09`） | `display:contents` wrapper 是**宿主实现细节，官方座目录未承诺**；升级后必须重验 |
| **C-9** | 🔴 **舞台必须自带「回到对话」控件** | 「选中的视图」是**按会话持久化**的（官方 `activateView` / `restoreView` / `readConversationViewPreference(sessionId)`）→ **刷新页面会回到舞台**，学生不会被自动送回对话。**这不是技术细节，是产品设计**：要么舞台里放显式退出控件，要么依赖官方切换器那个 tab（实测：必须**先点「Chat」**才回得去） |
| **C-10** | 🔴 **舞台必须自带能落盘的报错通道**；**禁止任何「hook 数随渲染变化」的代码路径** | 条目崩溃会被宿主**按条目隔离**（DOM 里出现 `<div data-slot-error="conversation.view">`），**不会带倒整个 app**——但症状是**视图静默变空白**，线上就是一块白板而没人知道为什么。实测崩因是条件式 hook（`usePanelInfo()` 漏传选择器 → 两次渲染 hook 数不同 → React `#310`）。另：条目会被宿主**重复渲染**（实测 `renderCount 2`），被 store 订阅驱动的子组件会再渲染一次 |
| **C-11** | **`usePanelInfo` 等 hook 一律传选择器**（如 `usePanelInfo((info) => info.activePanelId === null)`） | 不传选择器会抛 `l is not a function` → 整块视图被 `data-slot-error` 顶掉（C-10 的实证崩因） |

**验收清单（每条都要有证据，不许"看起来没问题"）**：
① 舞台在场时**官方输入框仍能聚焦**（`document.activeElement` 是它）；
② 舞台在场时**官方弹层能出现在舞台之上**（**主动触发一次**，例如开会话重命名框）；
③ 撤场后**节点零残留**（给出前后节点计数）；
④ 全程 **`console.error` 与 `pageerror` 为 0**；
⑤ 舞台自己的控件**点得到**（在 root `none` 的前提下，子控件 `auto`）；
⑥ 🔴 **DOM 里不出现 `[data-slot-error]`**（宿主给崩掉的条目留的错误占位——出现它就等于视图静默变空白）；
⑦ 🔴 **「回到对话」控件真的能切回官方 chat**（见 C-9）。

**可用的官方 DOM 钩子**（实测存在，验收直接拿来判，不靠文字匹配）：
`[data-conversation-tabs]`（`role="tablist"` 容器）｜`button[role="tab"]`（各视图标签，`aria-selected` 表选中）｜
`[data-chat-flow]` / `[data-chat-flow-kind]` / `[data-chat-turn]`（官方消息区，**切到舞台时全部归零＝整体卸载**，实测 5415→900 节点）｜
`[data-slot-error="conversation.view"]`（崩掉的条目占位）。

## 五-bis 🔴 **已实测确认**：空会话下舞台挂不上

**问题**：新会话（空会话）下舞台能不能挂上？

**答案（2026-09-28 实机实测，对照实验）**：🔴 **挂不上。**

| | 有内容的会话（对照组） | **新建的空会话（实验组）** |
|---|---|---|
| 官方视图切换器 `[data-conversation-tabs]` | ✅ 有 | 🔴 **没有** |
| tab 列表 | `["Chat","Trajectory","课堂舞台"]` | 🔴 **空** |
| 我们的舞台 | 可切进去 | 🔴 **不可达** |

**机制**（与读源码的推断一致）：官方 `DefaultConversationViews` 在 `session.blank` 时返回 `null`，
`ConversationSessionHeader` 在 `tabs.length <= 1` 时不渲染切换器 → **连切换器都没有，舞台自然挂不上**。

🔴 **产品含义**：「上课模式」恰恰从"学生还没说第一句"那一刻开始，**而那一刻舞台挂不上**。

**可行应对（未实施，仅列选项，需拍板）**：
① **接受它**——第一轮对话在官方界面发生，之后学生再切到舞台（**最省，零代码**）；
② 另找一处只服务"课前"的落点（例如 `shell.overlay`，**已实测可当全屏层**，四条判据全过）；
③ 让引擎在会话创建时就注入一条开场消息，会话立刻非 blank——
**但这要改引擎，且会改变"谁先说第一句"的教学设计**（教学上是老师先开口还是学生先开口，是有讲究的）。

**证据**：`/tmp/overlay-probe-lead/stage-accept/blank-session.json` ＋ `20-with-history.png` / `21-blank-session.png`。
