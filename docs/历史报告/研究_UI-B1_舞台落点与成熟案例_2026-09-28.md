### 2.3 `shell.overlay` 的官方原文（逐字，本裁决的根据）

> "Frame-wide floating layer, above every column and outside their scroll containers.
> Deliberately generic and unowned by any feature: a badge, a toast stack or a status pill all belong here,
> and entries order among themselves. **The layer itself is click-through — entries opt back into pointer
> events — so an occupant never blocks the app underneath.**
>
> **This is the additive seat for a frame-wide surface of your own: a fresh `id` is added beside the
> shipped entries instead of replacing them.**"

三个要点，逐条对上我们的需求：

1. **`above every column`** → 能盖住整个 frame，包括侧栏与主区 → **够全屏**。
2. **`click-through`，条目自己 opt back into pointer events** → **官方 UI 不会被我们挡住**，
   上课模式可以随时退出、下面照常能用 → 这是影子 `main` 给不了的。
3. **`a fresh id is added beside the shipped entries instead of replacing them`** → **纯增**，
   与 `replaceRisk: "none"` 一致 → 不担上游升级风险。

**官方已有 8 个占位者**（`chat.quota-notice` / `schedule.delete-toast` / `desktop-onboarding` /
`account.platform-page` / `shortcuts` / `workspace.session-rename` / `workspace.session-archive` /
`workspace.row-toast`）——全是 badge／toast／dialog 类。
它们**自己之间排序**（`order` 字段），所以我们的舞台是"一个很大的占位者"，**语义上不冲突**。

### 2.4 架构建议：两层落点

```
┌─ shell.overlay（root，纯增，click-through）────────────────┐
│  选择肢菜单 / 过场 / 需要盖住侧栏的全屏演出                 │
│  拿不到对话流 → 数据由下层传入或读教室文件                  │
└────────────────────────────────────────────────────────────┘
        ↑ 盖在下面这层之上
┌─ conversation.view（session，有全套会话接口）──────────────┐
│  主舞台：背景 / 立绘 / 对话文本 / 姓名牌 / 在场者栏 / 板书  │
│  sessionId · useChat · useConversation · useProjection      │
└────────────────────────────────────────────────────────────┘
        ↑ 官方视图切换器在 chat ↔ 课堂舞台 之间切
```

**「切过去官方消息区不渲染」不是缺陷，是特性**：
「上课模式」本来就是把消息区换成舞台；学生想聊天就切回官方 `chat` 视图。
这比"舞台浮在聊天上"更干净——**一个时刻只有一个主视图，不会两套滚动条打架**。

**官方已有的两个占位者**（`client-ui-chat ChatView id 'chat'` 与
`client-ui-trajectory TrajectoryView id 'trajectory'`）证明这是**官方设计的正常用法**，
不是我们硬塞。

### 2.5 实机验证结果（**两路独立实测**）

**两路都跑了**：主代理自测（`/tmp/overlay-probe-lead/`）＋ 子代理独立复测
（`/tmp/overlay-probe/`，**自己的隔离 home、自己的端口、自己的探针源码**）。
两路结论一致；**子代理那一路更细，并纠正了主代理一处措辞**。

| 判据 | 结果 | 关键读数 |
|---|---|---|
| **C1 铺满 frame 且在所有列之上** | ✅ **过** | rect `{0,0,1680,1050}` 与视口**完全相等**；8 个取样点**全部**命中探针；层 `z-index:20`，官方列 `z-index:auto` |
| **C2 会话数据可达** | ✅ **过** | `useSessions` 返回 `{ids,byId,phase,projectionsBySession}`；**1744 条会话**；**当前会话 id 非空**；`cwd` 正是会话工作区 |
| **C3 官方 UI 不被破坏** | ⚠️ **过，但有前提**（见下） | 显式 `none` 时官方取样点被挡 **0 个**；真点输入框 → `activeElement` 是官方输入框 |
| **C4 零残留** | ✅ **过** | `disposer()` 后我们的节点 **7 → 0**；`body` 元素数 579 → 572；零报错 |

🔴 **C3 的真相：官方文档说"opt-in"，实测是"opt-out"。**

从 `document.styleSheets` 扫出的**逐字 CSS**（不是读文档）：

```
.pI_x6G_overlayLayer      { z-index: 20; pointer-events: none; position: absolute; inset: 0px; }
.pI_x6G_overlayLayer > *  { pointer-events: auto; }   ← 🔴 宿主已经替条目 opt-in 了
```

`pointer-events` 是**继承属性** → 一个**不写 `pointerEvents`** 的全屏条目 **＝ 整帧接管鼠标**：
官方 7 个取样点里 **6 个**被挡住，真点输入框后 `document.activeElement` 是 **`body`**（拿不到焦点）。
→ 🔴 **舞台必须写成「root 显式 `pointerEvents:'none'` ＋ 自己的控件各自显式 `auto`」。不写就等于把整个 app 变成不可点。**

**主代理此处的措辞错误（已更正）**：我先前把它写成"**不接管指针时**官方 UI 点得到"，
听起来像"默认穿透、想接管才接管"。**实际相反**——默认就是接管，**必须显式声明穿透**。

### 2.5-bis 🔴 另外两条会改变写法的实测事实

**① 全屏落点必须用 `position: fixed; inset: 0`，不要用 `width/height: 100%`。**

层的父节点 `frame` 是 `overflow: hidden` 但**可被程序化滚动**的容器
（实测 `scrollWidth 2436 > clientWidth 1680`，抓到 `scrollLeft = 11`）。
层自己是 `position: absolute; inset: 0` → **层会跟着这个滚动一起偏**。
`fixed` 的 root 免疫（恒 0）；流内 `100%` 的 root **跟着偏 −11px**，还可能被 `overflow:hidden` 裁掉一条边。

**② 条目外面还有一层 `display: contents` 的 wrapper**（`renderSlot` 给每个条目包的）：

```
div[data-overlay-probe="root"]   position:fixed 1680×1050 pointer-events:auto（继承来的）
  └ div（无类名）                 display:contents  0×0  pointer-events:auto ← 宿主 CSS 命中的是它
      └ div.pI_x6G_overlayLayer   position:absolute inset:0 z-index:20 pointer-events:none
```

→ **「在 layer 上写样式」的直觉在这里不成立**：能命中你的规则在 wrapper 上；
你只能在自己的根节点上显式声明指针策略。

### 2.5-quater 官方弹层与舞台谁压谁（**静态取证，非实机压测**）

**先说不成立的那半**：全页 z-index 普查（程序化扫全部元素）结果——
**`z-index ≥ 20` 的元素全页只有 2 个**：官方层 `pI_x6G_overlayLayer`（**20**）与我们的探针根节点（2147483000）。
→ **官方没有任何东西在 z-index 上高于我们这一层。**（官方列 `z-index: auto`；把手 11、leadingSeat 15，都在层之下。）

**再说没测成的那半**：官方 8 个 overlay 条目都是**条件渲染**的，本轮试了 `?`／`Shift+/`／`Ctrl+K`／`Cmd+K`／`Esc`
**一个都没触发出来**（层里始终只有我们 1 个子节点）→ **"弹层真出现时谁压谁"没有实机压测。**

**于是改走静态取证（读官方包自己的注册代码）**：

| 包 | 条目 id | `order` |
|---|---|---|
| `dsh-client-ui-shortcuts` | `shortcuts` | **不传** → 默认 0 |
| `dsh-client-ui-workspace` | `workspace.session-rename` / `workspace.session-archive` / `workspace.row-toast` | **不传** → 默认 0 |
| `dsh-client-ui-settings-account` | `desktop-onboarding` / `account.platform-page` | **不传** → 默认 0 |
| `dsh-client-ui-chat` | `chat.quota-notice` | **不传** → 默认 0 |
| `dsh-client-ui-schedule` | `schedule.delete-toast` | **不传** → 默认 0 |

座目录对 `order` 的逐字定义是 *"Position among the entries, **ascending** (default 0)"*。
→ 我们的探针传的是 **`order: 100`** → **排在全部官方条目之后 = 最上层**。

🔴 **推论（按此取证成立，但仍标"未实机压测"）**：
**一个用 `order: 100` 的全屏舞台会盖住官方弹层**——会话重命名框、各类提示条、配额提示都出不来。

→ **正式舞台的处方：用负 `order`**（例如 `-1`），让官方条目排在我们之后。
**这条要写进舞台的实现验收**：真机验收时必须**主动触发一次官方弹层**（例如开一次会话重命名框），
确认它**出现在舞台之上**，而不是被舞台吃掉。

### 2.6 🔴 自我更正（同日，本件内部）

**本件初稿写的是「舞台落点 = `shell.overlay`，唯一同时满足三条件」——这条被推翻了，如实记录。**

**推翻它的证据**：把四个座的 `standardProps` 并排打出来对比，发现**接口是分层给的**：

| 座 | 6 个通用项（`useResource` / `useWorkspaces` / `usePanelInfo` / `useSessions` / `useSessionStatus` / `useSessionRetainInfo`） | 8 个**会话专属**项 |
|---|---|---|
| `shell.overlay`（root） | ✅ | 🔴 **一个都没有** |
| `conversation.view`（session） | ✅ | ✅ 全有 |
| `conversation.chat.node`（session） | ✅ | ✅ 全有 |
| `conversation.input.dock`（session） | ✅ | ✅ 全有 |

**推论**：`scope: "root"` 的座**拿不到当前会话的消息读口**。
`useSessions` 是"会话列表/状态"，**不是**"当前会话的消息流"——这两件事**名字像，能力不同**。
→ 我先前把 `useSessions` 当成了会话数据可达的证据，**这是误读**。

**教训（写给下次的自己）**：座目录里 `standardProps` 是**逐座不同**的，
**不能只读一个座就下结论**；判断"某个座能不能拿到某类数据"，必须**把候选座的 props 并排比**。
`kind` / `scope` / `replaceRisk` 决定"能不能安全占"，**`standardProps` 才决定"占到了能干什么"**。

### 2.7 `conversation.view` 的视图切换机制（**静态取证，读官方 `ui-conversation` 客户端源码**）

官方 `dsh-client-ui-conversation/lib/client.js` 里有一个 `viewTabs()`，逐字逻辑：

```js
for (const entry of slots.entries("conversation.view")) {
  if (entry.options.id === void 0) continue;                       // ① id 必填，没有就跳过
  if (!developerTools.enabled && entry.options.id === "trajectory") continue;  // ② trajectory 只在开发者工具开启时显示
  tabs.push({ id: entry.options.id,
              label: resolveSlotLabel(entry.options.label) ?? entry.options.id });  // ③ label 会被读
}
```

**三条对我们直接有用的事实**：

1. 🔴 **`label` 在 `conversation.view` 上真的会被读**（`resolveSlotLabel(entry.options.label)`），
   拿不到才退回 `id`。→ **这与 `shell.overlay` 相反**（那里 `order`/`label` 实测无可观测效果）。
   → **舞台的中文名就写 `label`**（例如"课堂舞台"），会直接出现在切换器上。
2. **`id` 必填**（`undefined` 直接跳过）——探针/舞台都必须给 `id`。
3. **`trajectory` 默认不显示**（除非开发者工具开启）→ 默认视图集合只有官方 `chat` ＋ 我们新增的那个，
   **UI 上不会挤**。

**切换与持久化**：`activateView(sessionId, preferred)` → `uiConversation.binding(sessionId).activate(id)`；
另有 `readConversationViewPreference(sessionId)` ＋ `restoreView(sessionId)` →
🔴 **视图选择按会话持久化**（学生切到舞台后，这个会话就停在舞台；换会话各自记各自的）。
还有官方 `openView(view, focus)` 动作可直接跳转。

> ⚠️ **以上是读源码得出的，不是实机跑出来的**。"注册后真的出现在切换器里、真的能切入切出"
> 仍以实机验收为准（见 §2.5 的 V1）。

| 它的包 | 干什么 | 对我们 |
|---|---|---|
| `stage-shared` | **契约层**（跨端共享的类型与工具） | 🎯 **正对应我们要立的「回合数据契约」** |
| `stage-ui` | 界面（组件／stores／features／services） | 🎯 对应我们的 `classroom-ui` / `classroom-stage` |
| `stage-ui-live2d` · `-mmd` · `-spine` · `-tachie` · `-three` | **可插拔渲染后端**（Live2D／MMD／Spine／立绘／three.js） | 🎯 对应我们的 `live2d-host`——**它应该是"其中一个后端"，不是唯一** |
| `stage-layouts` | ⚠️ **更正**：实测是**路由级外壳**（Header ＋ RouterView ＋ safe-area），**不是**"版式变体" | ❌ **不借**（我先前读错过，如实改口） |
| `ui-transitions` / `ui-loading-screens` | 转场／加载屏独立成包 | 🟡 可借其"演出与加载也是正式模块"的态度 |
| `font-xiaolai`（霞鹜文楷）· `font-cjkfonts-allseto` · `font-chillroundm` | **CJK 字体当一等包** | 🎯 **直接回应我们的悬空问题**「中文正文用哪个黑体没定」 |
| `model-driver-lipsync` | 口型驱动（wLipsync 方案） | 🟡 我们已有自己的嘴型通道，**只作对照** |

**`stage-ui/src/components/scenes/Stage.vue` 里可直接照搬的四条**：

1. **渲染器路由**：一个 `Stage` 组件按 `stageModelRenderer` 切到 `Live2DScene` / `ThreeScene` /
   `SpineScene` / `TachieScene` / `MMDScene`——**所有 Scene 共享同一套 props 契约**
   （`model-src` / `model-id` / `background-url` / `paused` / `v-model:state`），各自只加私有 props
   （Live2D 与 MMD 多 `mouth-open-size` / `now-speaking`；Spine 多 `premultiplied-alpha`）。
   → **这就是"可插拔后端"的具体形状**，我们的 `live2d-host` 应长成 `Live2DScene` 这样。

2. **统一 `defineExpose`**：每个 Scene 都暴露 `canvasElement()` / `captureFrame()` / `setExpression()`。
   → 🎯 **`captureFrame()` 对我们的验收直接有用**——舞台能自己截图，不用外部截屏工具。

3. **口型/说话状态是"外部算好传进去"的**，不在渲染器内部算：
   `mouth-open-size` 与 `now-speaking` 来自 store，源头是音频分析出的口型值。
   → **与我们的设计一致**（`live2d-host` 已有说话／写字两条通道），**互为独立印证**。

4. **加载状态机 ＋ 可恢复错误**：`componentState = 'pending' | 'loading' | 'mounted'` 由 Scene 回写；
   渲染出错走 `StageRenderError` ＋ `retryStageRenderer()`（`showStage=false → nextTick → true` 强制重挂载）。
   → 🎯 **这条我们完全没有**，值得抄。

**`Stage.vue` 里最该抄的一条——「特殊 token → 信号」通道**：

它监听 LLM 流的特殊 token，分派成三类信号：

| 信号 | 含义 | 落到哪 |
|---|---|---|
| `act` | 含 `motion` 与 `emotion`（经 `normalizeActPayload` 归一化） | `motion` → 直接设动作；`emotion` → 归一化到 9 个情绪名（happy/sad/angry/think/surprised/awkward/question/curious/neutral）后**入队** |
| `delay` | 演出停顿秒数 | `await sleep()` |
| plugin CALL | 工具调用 | 转给插件通道 |

🔴 **这正是我们「回合数据契约」的现成形状**：**模型输出里夹带结构化 token → 前端解析成信号 → 分派给舞台**。
而且它把情绪**入队**（`createQueue`）而不是直接打断——避免并发情绪互相踩。
我们的引擎已经有动画／表情／白板三个通道，**契约要做的就是把它们的"信号形状"统一到这一套**。

**不借的**：它的 Vue/Pinia/Router 技术栈、它的 TTS/语音链路（我们定的是最后做）、
它的 Godot/VRM/MMD 后端（我们只需要 Live2D ＋ 静态立绘）。

### 3.2 VNDev Wiki（**设计空间的真源**）

来源：<https://vndev.wiki/Textbox>（VN 开发者社区 wiki，`User Experience` 类目）

**它给了 STAGE-3 从单一样本量不出来的东西——整个设计空间**：

| 格式 | 定义 | 我们的位置 |
|---|---|---|
| **ADV** | 立绘基本不被遮挡，文本框占**下三分之一**。「**by far the most common**」 | STAGE-3 方向 **C·書庫**（对话压到底部一条带） |
| **NVL** | 文本框**盖住立绘或大部分屏幕**，用于叙事密集／独白 | STAGE-3 方向 **A·夜读**（无框直排满列） |
| **Floating** | 文本框在屏上移动，仿漫画分格 | ❌ 不适用 |

> ⚠️ **注意一处张力**：魔夜实测是「**没有框**、文字直接排在全屏画面上」——
> 这在 VNDev 的分类里**既不是标准 ADV 也不是标准 NVL**（NVL 仍假设有一个"框"盖住屏幕）。
> → **结论：魔夜是 ADV 的一个变体（无框化），不是 NVL。** 这更正了 STAGE-3 未明说的一点。

**它列出的标准功能清单（我们该逐条决定"做/不做"）**：

| 功能 | 说明 | 我们的状态 |
|---|---|---|
| 逐字/逐行出现 | **关键细节**：逐字显示时也**先做好折行再隐藏**，否则字会"出现后再跳行" | ❓ 未做（STAGE-3 只做了推进指示器闪烁） |
| **Name tag** | 说话人名字；**不同角色可用不同字体/颜色**；颜色通常上在名牌文字，也有上在台词、背景或装饰件的 | ✅ 已定（方向 B 的「短册」） |
| **Side image** | 贴在文本框上的头像/半身像；三种用法：主角侧像／镜像对话侧像／**隐藏角色侧像** | 🎯 **「隐藏角色侧像」正好解我们一个难题**——不在场角色的表情怎么表达 |
| **Click-to-continue 指示器** | 表示"没更多字了，点击继续"；在文字旁或框角 | ✅ 已定（33×30 青色梯形，跟在末行末尾） |
| **Quick menu** | 文本框上的小菜单，通常**下中／下右**，**不论屏上什么文字都在** | ❓ **未做，且值得做** |
| — 其中的按钮 | 跳过／自动播放／历史回溯／**隐藏文本框**／快速存读／设置 | 🎯 **「隐藏文本框」对教室是刚需**（想看板书） |
| — 还可放滑块 | 例如**文本框不透明度** | 🟡 可选 |

🔴 **「Quick menu 不论屏上什么文字都在」这一条**，与我们「常驻 ≠ 常发言」的思路同源——
**常驻的是可预期的控制面，不是内容**。

### 3.3 Ren'Py / Monogatari（**实现参考**）

- **Ren'Py**：最广泛使用的 VN 引擎（Python）。有 `say` screen（ADV 模式）与
  **`00nvl_mode.rpy`**（NVL 模式的独立实现）→ **"两种文本呈现方式各自独立成模块"**，
  与 airi 的"渲染后端可插拔"是同一种架构直觉。
  来源：[Special Screen Names](https://renpy.org/doc/html/screen_special.html) ／
  [`00nvl_mode.rpy`](https://github.com/renpy/renpy/blob/master/renpy/common/00nvl_mode.rpy)
- **Monogatari**：**Web 上的 VN 引擎**（MIT，v2.8.0），"你的游戏就是一个真网站"，
  可跑在浏览器／桌面／移动，可 PWA 离线装。
  它的定位原话是「**Think of your game as a website: anything you've seen on the web is within your reach.**」
  → 🎯 **这条与我们"用插件做、不 fork 宿主"的路线同构**：把能力建在 web 平台本身之上。
  来源：<https://monogatari.io/> ／ [GitHub](https://github.com/Monogatari/Monogatari)

**不借的**：两者的完整引擎（我们不是做 VN 引擎，是做**一个教室的舞台**）；
Monogatari 的"自建一整套"路线（我们已经定了**插件组**，不 fork 宿主）。
