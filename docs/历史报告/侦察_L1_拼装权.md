## §2 每轮请求的消息数组组装

### 2.1 消息来源：`Session.surface` → `deriveMessages()`

**DSH 的消息数组不是内存里累积的列表，而是从会话日志（surface 节点）派生的投影。**

`packages/core/session/src/index.ts:842` `deriveMessages(): Message[]`
- 遍历 `surface.nodes`（由 `surfaceOp` 标记维护的有序 seq 列表）
- 每个节点经 `deriveEventMessage()` 投影为 Message（五类 message-producing 事件）
- **compaction 的 `replace` 会从派生中删掉被遮蔽的节点**（注释 L831-834 原文）
- 返回**新的数组快照**，但 Message 对象是**共享且 deep-frozen** 的

`deriveMessages()` 的生产调用点只有两处：
- `packages/core/agent-loop/src/agent.ts:631`（`buildRequest` 里取 boundary messages）
- `packages/core/agent-loop/src/invariant.ts:40`（不变量校验）

### 2.2 一轮 step 的完整组装链（`packages/core/agent-loop/src/agent.ts`）

```
turn()                                   L295  开一个 turn
 └─ preStep(target, {turn, step})        L266
     ├─ L270  claimed = inbox.claim(target, turn)        ← 用户消息出队
     ├─ L271  assembly = systemPrompt.assemble(...)      ← §1，每个 step 重拼
     ├─ L273  sections = renderContextSections(assembly)
     ├─ L274  context = runtimeContext.project(...)      ← runtime-context user 消息
     ├─ L275  waterfall('agent/pre-step', {messages: claimed, turn, step, signal}, 默认 → enter)
     │        默认实现 L277-280: messages = [...claimed, context]
     └─ 返回 {kind:'enter', messages, assembly}
 └─ step(decision)                        L380
     ├─ L387  renderedPrompt = renderPrompt(assembly)
     ├─ L390  prepareRequest(turn, step, signal)   ← L529，路由/config 解析
     ├─ L392  systemPrompt.project(renderedPrompt, {...})  ← 生成 system/message 提交
     ├─ L398  session.append('system/message', ...)        ← system prompt 入 surface
     ├─ L401-405  首次 attempt: session.append('user/message', message, {surfaceOp:'append'})
     │            ← 即 decision.messages（claimed + context + 各插件注入的）逐条落盘
     ├─ L407  request = buildRequest(config, preparedCall, assembly.tools, ...)
     ├─ L418  stream = preparedCall?.stream(request) ?? loopCtx.llm.stream(request)
     └─ L514-519  有 tool-call → executeToolCalls → 结果 splice 进 inbox 'next-step'
```

**关键点**：
- **user 消息先 `claim` 出队，再经 `agent/pre-step` waterfall 加工，最后才 append 回 session**（L401-405）。所以 `agent/pre-step` 里对 `decision.messages` 的增删改，会**真实改变进入请求的消息数组**。
- `preStep` 的 `messages` 参数（L276）是 **claimed**（尚未落盘），而 `decision.messages` 才是最终入历史的。**区分这两者**是写注入插件的关键。
- 只有 `firstAttempt === true` 时才 append user 消息（L401）——重试不重复落盘。

## §3 注入点裁决

### 3.0 先纠正一个前提（🔴 重要）

任务书里把 SillyTavern 的 `populationInjectionPrompts(prompts, messages)` 类比为"按 injection_depth splice 进消息数组"——这个类比在 DSH 里**只对一半**：

- **对的一半**：DSH 确实有等价的 splice 原语（`agent/pre-step` 得到 `decision.messages`，可用 `toSpliced` 任意位置插入）。
- **不对的一半**：DSH 的消息数组**不是可变数组**，而是**会话日志 surface 的派生投影**（§2.1）。`decision.messages` 最终经 `session.append('user/message', ...)`（agent.ts L401-405）**落盘成为 durable 事件**，然后由 `deriveMessages()` 重新派生。

**这意味着**：注入不是"在请求前改一个数组"，而是"**往会话日志里追加一条 user 消息**"。后果：
1. 注入内容**会持久化在整个会话历史中**（换轮次也不消失，除非 compaction 抹掉）；
2. 想要"每 N 轮注入"，需要**避免重复落盘**（否则历史里会堆积 N 份副本）；
3. 想实现"固定 depth"，需要理解 depth 是**相对 surface 节点**而非相对某个可变的 in-memory 数组。

### 3.1 三个可选的实现层

| 层 | 接口 | 能否 splice messages | 能否改 system prompt | 是否 fork |
|---|---|---|---|---|
| **L1** `agent/pre-step` waterfall | `ctx.on('agent/pre-step', ...)` | ✅ 任意位置 | ❌ | **不需要**（原生 Cordis 插件即可） |
| **L2** `system-prompt/assemble` waterfall | `ctx.on('system-prompt/assemble', ...)` | ❌ | ✅ 改 sections/contexts/tools/variables | **不需要** |
| **L3** 核心改代码 | 改 `agent.ts` / `session` | ✅ | ✅ | **需要 fork** |

**（推断，需验证）** L1 与 L2 都是**作用域过滤**的（`runtime-types.ts:320`、`system-prompt/src/index.ts:31` 均注明 "Scope-filtered dispatch"），所以一个原生 Cordis 插件可以挂在 agent preset 上只对特定 agent 生效。

### 3.2 场景 (a) 固定 depth 注入（内容块永远贴着最新消息前 N 条）

**推荐落点：L1，`agent/pre-step` waterfall。**

**难度：低。可逆 count 的实现要点**——`agent/pre-step` 的 `payload.messages` 是**本次 step 新 claim 的批次**，`decision.messages` 是"claimed + 所有插件注入"的完整待入消息。所以：

- "贴着最新消息前 N 条"中的"最新消息"应当是**落盘后的 batch 尾部**——即 `decision.messages` 的末尾（因为这一批马上就会 append 成 surface 尾部）。
- 插入位置 = `decision.messages.length - N`（若 < 0 则取 0），即 **从 batch 尾部往前数 N 条**。
- 现成的 `toSpliced` 用法参照：`context/agent-instructions/src/index.ts:338-339`。

**⚠️ 与 agent-instructions 的冲突（必须处理）**：agent-instructions 把 AGENTS.md 插在 `lastClaimedIndex + 1`（L338-339），而 runtime-context 由 driver 追加在**更后**（agent.ts L279 的默认 enter 决策）。所以"claimed batch 之后"这一段是**多个宿主插件共用的 zone**。我们的 depth 注入如果直接用 `messages.length - N`，会与它们**抢位置**。稳妥做法是**明确锚定真实 surface 位置**（用 `agent.session.surface.nodes.length` 或 `session.deriveMessages().length` 计算），而不是锚定 batch 内位置。

**⚠️ compaction 侵蚀（§2.6）**：固定 depth 若超出 `retainTokens` 预算（默认 `retainRatio = 0.16`，`config.ts:23`），注入内容会落入被压缩区并被 `replace` 抹掉。→ **固定 depth 实现必须每轮重新注入**（不能"写一次留在历史里"）。

### 3.3 场景 (b) 每轮贴尾自检清单（历史之后，权重最高）

**推荐落点：L1，`agent/pre-step` waterfall，append 到 `decision.messages` 末尾。**

**难度：最低。这几乎是把 skill catalog 的做法照搬**：
- 参照 `packages/skill/tool-skill/src/index.ts:252`：`messages: [...decision.messages, catalog]`
- 参照 `packages/hooks/hooks-claude-code/src/index.ts:239-241`：`messages: [...downstream.messages, ours]`

**🔴 但"每轮"与"落盘"的矛盾**：`decision.messages` 会落盘（agent.ts L401-405）。如果每个 step 都 append 一份相同清单，历史会长满重复副本。
- **规避方案 A（推荐）**：用 `agent.inbox` 机制复用同一条消息——参照 agent-instructions 的 `syncInbox`（L227-252）：如果 payload 相同且在 surface/inbox 里已存在，就**不重复注入**。
- **规避方案 B**：把清单放进 **L2（`system-prompt/assemble` 的 contexts 或 sections）**——`contexts` 的定位是 "materialized as a durable user-role snapshot"（system-prompt L78），且 `RuntimeContextProjection`（runtime-context.ts L114+）**自带 replace 语义**（`this.replace(node.seq, '')` L115，会清掉旧快照），所以**天然不堆积**。代价是它**不在历史尾部**，而是在 claimed batch 之后、system prompt 附近。

**权衡**：如果"历史之后、权重最高"是硬需求（SillyTavern 的 in-chat depth 语义），必须走 L1 并自己做去重；如果可接受"每轮一个最新快照"，L2 的 `contexts` 更贴合 DSH 设计。

### 3.4 场景 (c) 每 N 轮注入

**推荐落点：L1 `agent/pre-step`，用自己的计数器 + `agent.inbox` 去重。**

**可用的事实源**（都已在 `agent/pre-step` 的 payload 里或可经 `agent.session` 取到）：
- `payload.turn`（`runtime-types.ts:320` 签名含 `turn`）——**turn 号是现成的轮次计数**
- `payload.step` —— step 号（一个 turn 内可能有多个 step，因为 tool call 会续 step）
- `agent.session` —— 可读 `session.surface` / `requestHeader()` 等

**"每 N 轮"的判据建议用 `turn % N === 0`**（因为 turn 是用户语义上的"轮"，step 是模型循环次数）。
**⚠️ 注意**：`turn` 在 `agent/pre-step` 的 payload 里是**即将开启的 turn 号**，不是刚结束的。需实测确认（标 **待确认 T2**）。

**落盘去重**：同 3.3，建议用 `source` 字段打标记（照 `MessageSourceMap` 的模式，见 `packages/llm/llm/src/message.ts` 与各插件的 `declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap { ... } }`），然后在下一轮用 `agent.inbox.nextStep.filter(isOwn)` + `remove` 清掉旧副本。

### 3.5 关于 role：系统性缺陷（🔴 对 SocraticNovel 尤其重要）

**DSH 没有"任意 role 注入"的能力。** 逐个核实：

| role | 能否注入 | 证据 |
|---|---|---|
| `user` | ✅ 完全自由 | `createUserMessage`，四个宿主插件都用 |
| `system` | ⚠️ 只能经 surface | `session.append('system/message', ...)`（agent.ts L399），但**只有 `SystemPromptProjection` 一个 owner**（`session/src/known-event-types.ts:24` 邻近的 surface 类型）|
| `developer` | ❌ **已声明但序列化器拒绝** | `packages/llm/llm-deepseek/src/serialize.ts` 原文：`if (message.role === 'developer') return unsupported('developer message')`，注释 "Developer history is persisted for V4; provider serialization is intentionally deferred" |
| `assistant` | ❌ 语义上不可注入 | surface 事件 `assistant/message` 由模型流产生 |
| `tool/result` | ❌ 需工具调用配对 | `executeToolCalls` 路径（agent.ts L516-519） |

**结论**：想要 SillyTavern 那种"system 角色 + depth 注入"，在 DSH 里**只能映射成 user 角色的 `<system-reminder>` 包装**。而宿主自己就是这么做的——skill catalog 用 `<system-reminder>` 包裹（`tool-skill/src/index.ts:259,264`），system-prompt 的伪 XML 转义在 frame 层（`renderCatalogEntries` 注释 L310-313）。

→ **对 SocraticNovel 的建议**：用 user 角色 + `<system-reminder>`（或自定义 XML 标签）包装来近似 system 语义；如果**必须**要真正的多 role，那就要 **fork `packages/llm/llm-deepseek/src/serialize.ts`**（把 developer 序列化打开），或 fork surface 层加新的消息类型。

## §4 模型无关性

### 4.1 路由在哪一层

**三段式，职责清晰分离：**

1. **默认选择**：`packages/core/agent-default-model/src/index.ts` —— `provider`/`model`/`reasoningEffort` 是 `Volatile<string>`（L26-29），经 `settings`（L58）持久化。`current()` L68 返回选择，`save()` L74+ 写回。
2. **Agent 级选择**：`packages/core/agent/src/model-selection.ts` —— `installModelSelection()`（L78）注册**三个** scoped listener：
   - `system-prompt/assemble`（L79-92）：把 `provider`/`model` **作为 prompt variables 注入**，并快照 `selection.assembled`
   - `agent/request`（L93-110）：把选中的 provider/model/effort **覆盖到请求 config**
   - `agent/pre-step`（L111-125，`{prepend: true}`）：路由变化时注入一条 `[model changed: ...]` 的 user 通知
3. **适配器**：`packages/llm/llm/src/index.ts` `LlmRuntime.stream()` / `prepareCall()`，按 `provider` 查注册的 `LlmAdapter`。

**`ctx.on(..., { prepend: true })` 是真实 API**：`vendor/cordis/src/events.ts:114` `prepend?: boolean`，L143 `const method = options.prepend ? 'unshift' : 'push'`。→ **注入插件可以插到 waterfall 队列最前**（model-selection 就是这么干的，L125）。

### 4.2 拼装层与模型是否耦合

**结论：拼装层本身模型无关，但有三个"由模型能力决定"的开关。**

| 开关 | 位置 | 作用 |
|---|---|---|
| `systemPromptUpdate: 'in-history'` | `packages/llm/llm-deepseek/src/models.ts:12`、`config.ts:89`（`z.const('in-history')`）| 决定 system prompt 是**原地替换 head** 还是 **append 新节点**（`SystemPromptProjection.project()`，runtime-context.ts L88-110）|
| `contextWindow` | `requestContext`（agent.ts L612-626）| 驱动 token meter 与 compaction 阈值 |
| `inputModalities` | `PreparedLlmCall`（llm/index.ts L176 附近）| 图像等能力 |

**核实**：`packages/llm/llm-deepseek/src/models.ts:12` 与 `config.ts:89` 都把 DeepSeek 的模型标为 `systemPromptUpdate: 'in-history'`；`config.ts:177-179` 校验"catalog model 的 systemPromptUpdate 必须是 'in-history' 当存在时"。

**🔴 对定制的关键含义**：
- **DeepSeek 路由下，system prompt 走"in-history"模式** —— 即 system prompt 是 messages 数组里的一条 **system 角色消息**，且**变更时 append 新节点**（runtime-context.ts L108-110 `if (latest.text === rendered) return []` / 否则 append）。
- **system prompt 段落顺序改变 → 会 append 一个新的 system 节点** → 历史里会累积多个 system 消息。**每个 step 重新拼装时如果段落顺序不稳，会不断堆积**（这是 `sameContextPayload` 去重逻辑存在的原因）。
- `runtime-context.ts` 的 JSDoc（L59-63）原文："A capable continuing series appends changed nonempty text after the cached history. An incapable route, broken series, or cleared prompt instead normalizes the first system node and empties later active nodes."

### 4.3 不同模型是否有不同 instruction 模板

**未找到"按模型分派不同 section 模板"的机制。** 已试检索词：
- `grep -rn "systemPrompt" --include=*.ts packages/llm/llm-deepseek/src/` → 只命中 models/config/serialize 的能力开关，无模板分派
- `grep -rn "sectionDefinitions\|byModel\|perModel" packages/core/system-prompt/src/` → 无
- `grep -rn "assembleContextFor" packages/` → 只有一个定义处（agent.ts 内），不含模型分支

**已存在的模型相关分支**只有两处，都与"模板"无关：
1. `systemPromptUpdate` 能力（影响 system 消息落法，不是内容）
2. `model-selection.ts` 的 `[model changed: ...]` 通知（运行时插入的 user 消息）

**但**：`systemPrompt.variable('provider'|'model', ...)`（`agent-loop/src/index.ts:370-371`）+ section 的 `{{provider}}`/`{{model}}` 插值（`renderPrompt` L279 + `interpolate()` L325-362）**允许在模板里按模型分支**——这是"内容层面"的模型相关性，由文案作者决定，不是框架强制的。

### 4.4 多供应商路由

供应商清单由 `settings` 驱动（`agent-default-model` L58 `ownerContext.inject(['settings'], ...)`）。
`prepareRequest()`（agent.ts L529-578）在配置解析后调 `llm.prepareCall(proposedConfig, signal)`（L569）；若抛 `LlmError` 且 `code === 'NO_ADAPTER'` 则**降级用未注册的 proposedConfig 继续**（L571-575）——注释原文："Middleware may serve an unregistered route; terminal dispatch still requires an adapter."

**→ 这意味着 `agent/request` waterfall 的 listener 可以"劫持"到任意 provider/model 字符串，由中间件层服务。** 这是做"按用途路由到不同模型"的官方入口。
