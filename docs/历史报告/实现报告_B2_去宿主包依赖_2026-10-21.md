## 二 · `defineTool` 的实质结论（先查清，再决定能不能 duck-type）

### 2.1 它到底做了什么

读的是 `@deepseek-ai/dsh-tools@0.2.1-rc.2` 的 `lib/index.js`（`defineTool` 在 838–884 行）。
它**只有**三件事，**不碰 ctx、不注册、不改 execute 的语义**：

| 做的事 | 代码依据 | 是"运行期必须"吗 |
|---|---|---|
| 校验 `timeoutMs` 是正的有限数 | 847 行 | 宿主 `register()` 也会再查一遍（2985 行） |
| 把**作者面** schema 编译成受支持的 raw JSON Schema 子集：`parameters` 走 `propertySchemaSpecToJsonSchema`（隐式对象根），`output.schema` 走 `valueSchemaSpecToJsonSchema` | 848–849、796–810 行 | **必须**。`register()` 会对 `output.schema` 跑 `assertSupportedJsonSchema(output.schema)`（2977 行），作者面里的 `required: true` 在 raw schema 里是非法位置 —— 不编译就注册不上 |
| 给 `execute` 套一层参数校验（非法 → `ToolArgsError('invalid arguments: …')`），给 `presentCall/presentResult/isConcurrencySafe` 套软校验 | 858–877 行 | 只有它自己做。**宿主其它地方都不校验参数**（`createSuccessResult` 只校验返回值，3639 行） |

它**没有**做的事（这些是 registry 干的，`defineTool` 不参与）：
登记进注册表（`ToolRuntime.register`，2974 行）、包装 `execute` 之外的派发、注入额外字段。
⇒ **duck-type 可行**：只要交出去的对象满足 `register()` 的四个硬要求
（`name`、`output.render` 是函数、`output.schema` 在子集内、`timeoutMs` 合法），宿主照收。

### 2.2 复刻了哪几条（`plugins/socratic-engine/lib/toolshape.mjs`）

- 作者面 schema 的全部编译规则：`required:true` 上提、`additionalProperties` 必须显式、
  `type:'json'` → 无 type 的注解节点、`oneOf`（≥2 支、不可与 type 同写）、`enum`/`const`、
  四个注解键、循环 schema 拒绝；
- `execute` 的参数校验，覆盖本仓库用到的全部关键字（type/properties/required/additionalProperties/
  items/enum/const/oneOf），**消息文案与路径写法逐字对齐**（`arguments.lesson`、`list[1]`、
  `missing required property "nested.a"`、`"x" is not a declared property (additionalProperties: false)`）；
- `presentCall/presentResult/isConcurrencySafe` 的软校验（现在没人用，但不做等于给以后埋一个静默降级点）。

### 2.3 没复刻的（写清楚，免得以后有人以为等价）

1. **`HarnessError` 的类身份**：本地的 `ToolArgsError` 只带 `name`/`code`，不是宿主 `HarnessError` 的子类。
   后果只有一个：工具失败结果里的 `error: {name, code}` 结构化元数据缺（宿主 `errorInfo()` 用
   `instanceof` 判），正文消息不受影响。活体验证里能看到实际形状（§2.5 的 `execute-invalid`）。
2. **`assertSupportedJsonSchema`**：编译产物是否属于子集，继续由宿主 `register()` 把关，不在本地重复实现
   （两处判据容易漂移）。

### 2.4 证据：与真宿主逐字段比对

**方法**：把 `@deepseek-ai/dsh-tools@0.2.1-rc.2` 从 npm 装到 `/tmp/hostref`，与本地实现同时编译同一批声明。

- 5 组真实工具形状（照抄 `index.mjs` / `discovery.mjs` 的 `classroom_status` / `classroom_set_phase` /
  `classroom_draw` / `classroom_animate_template` / oneOf）：
  `parameters`、`output.schema`、definition 的键集合**全部 `deepStrictEqual`**。
  另有「注解四件套 + const/enum」一组：**`JSON.stringify` 逐字节相同**（键序也对齐了，见下）。
- 13 组参数值 + 8 组作者面错误：违规文案数组与宿主**逐字相同**（含 `-0`、`Infinity`、稀疏数组、
  类实例当对象、`oneOf` 命中 0/1 支这些边界）。比对过程中**真抓到两处分叉并修掉**：
  ① 我漏了"普通数组原型"判据（`[1,2]` 被判成非法）；② 稀疏数组的洞应交给"dense"判据而不是元素校验。

  已按宿主顺序产出（语义等价，但让"逐字节相同"这条更强的性质成立）。

- 原子写：同一段操作（`writeFileAtomic` 0600 → `withFileLock` 里再写一次）跑宿主与本地实现，

### 4.2 但「白板走的这条路」不是「另一条路」也能走的路

原任务的选项 (b)（把 `dsh-typert-protocol` 的用法换成不 import 的等价写法）**必须**做，
不是为白板，而是为**叙事服务**：`classroomNarrative` 的消费者在 `lib/client.js:5228+`（「日记」tab），
它同样 `extends TypertRemoteService`。所以：

- **白板**：下线（删实现，删测试，删清单）；
- **叙事**：保留，基类换成 `lib/remote-service.mjs`（本地、不 import）。

### 4.3 本地基类凭什么成立（宿主网关逐字契约）

| 网关要求 | 本地实现 | 依据（`0.2.1-rc.2`） |
|---|---|---|
| `ctx.reflect.props[key].type === 'service'` | `lib/index.js` 的 `ctx.provide(key, instance)` | `@deepseek-ai/cordis/lib/index.js` 的 `Reflect.provide()`：`this.props[name] = { type: "service" }` |
| `binding.service === originalOf(receiver)` | `typertRemote.service = this`（构造函数里） | `dsh-api-gateway/lib/index.js` 的 `readBinding()`；`originalOf()` 读 `Symbol.for('cordis.original')`，取不到就用接收者本身 |
| `binding.serviceKey === serviceKey` / `typeof namespace === 'string'` | 同上，`{service, serviceKey, namespace}` 冻结 | 同上 |
| 原型上的 `"@deepseek-ai/dsh-typert-protocol/remote-methods"` 描述符（`{version:1, methods:[…]}`） | `markRemote()` 写同一个字符串键 | `dsh-typert-protocol/lib/index.js` 的 `remoteMethods()` |
| 方法形参名（`Function.prototype.toString` 解析） | 普通 class 方法，参数名照旧 | `dsh-api-gateway` 的 `methodParameterNames()` |

**与 `TypertRemoteService` 的实质差异（三条，都无害，但必须写）**：
1. 不自己注册（宿主那个类在构造函数里 `super(ctx,key)` 就 provide 了）；这里由 `lib/index.js` 的
   `ctx.provide` 注册 —— 是**同一条** cordis 路径，只是把"谁注册"挪到调用点（保留既有的幂等门）。
2. 实例上不打 `Symbol.for('cordis.tracker')`：`getTraceable()` 见不到 tracker 就返回裸实例
   （宿主那边是 proxy）。两个后果：`this` 就是实例本身；方法里读不到派发时 extend 出来的
   `ctx.invocation` —— 两个方法都不读它。
3. 不装 root 上的 `ctx.invocation` 访问器（宿主的 `provideInvocationAccessor`）：那是宿主自己的
   官方服务早装过的 root 级约定，面板不该去动宿主的 root 状态。

换过去是**语义变更**，不是等价替换。所以只保留一条实现路径，不做双路径 fallback。

### 原子写本地实现的正确性论证

复刻对象是宿主的 220 行，逐条保留它证明过的性质，并用单测钉住（`test/atomic-write.test.mjs`，12 项）：

| 性质 | 为什么成立 | 单测 |
|---|---|---|
| **原子**：读者只会看到旧全文或新全文 | 内容先写同目录随机后缀临时文件，再 `rename` 覆盖（同一文件系统内 `rename` 是原子的） | 「临时文件在 rename 前失败 → 目标保持旧内容」 |
| **权限 0600 是严格结果，不是尽力** | `writeFile(temp, content, {mode, flag:'wx'})` 让**新 inode** 一开始就是该 mode，`rename` 把 inode 带过去 —— 不存在"先宽后 chmod"的窗口 | 「替换已有 0644 文件后被收紧到 0600」 |
| **不跟随符号链接** | `wx` 独占创建拒绝复用已存在的临时路径；`rename` 替换的是链接本身 | 「目标是符号链接时替换链接、不写穿」 |
| **失败不留垃圾** | `try/catch` 里 `rm(temp, {force:true})` 后原样抛 | 「rename 失败后目录里没有 `.tmp`」 |
| **跨进程串行** | `<file>.lock` 用 `wx` 创建（内容 `<pid>\n`），争用指数退避，到点**抛错**（不猜锁死没死） | 「两个写者不交错」「活着持锁者不被抢，到点抛错」 |
| **死持锁者不永久卡死** | 信号探针 `ESRCH` 证明持锁进程已死 → 凭 `<lock>.takeover-<记录哈希>` 认领文件删锁，删前重读记录并复核 PID | 「持锁进程已消失 → 接管」「活着的持锁者不会被抢」 |
| **临界区抛错也释放锁** | `finally { rm(lockPath) }` | 「抛错后下一次能立刻拿到锁」 |
| **可取消** | 每次尝试前 `signal.throwIfAborted()` | 「signal 已 abort → 立刻抛错、不建锁」 |

Windows 的 `EACCES/EBUSY/EPERM` 重命名重试（有界 8 次、20→200ms）也照搬了 —— 那不是兜底策略，
是那个平台的原子替换必需条件；本机不覆盖这条路径（macOS），**未实测**。
