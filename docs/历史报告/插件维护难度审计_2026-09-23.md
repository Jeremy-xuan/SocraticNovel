# SocraticNovel × DSH · 插件维护难度审计（2026-09-23 终版）

> **触发**：用户 2026-09-23——*"一整套自己的插件好维护吗？这样我们还是需要时不时就全盘对新版本 dsh 做适配。而且我觉得我们的插件很可能要到快 20 个这个量级，是不是需要仔细审计一下我们的计划，评估维护难度？"*
> **依据**：五路源码侦察（L1 拼装权／L2 loop与维护成本／L3 工具与记忆／L4 客户端UI／L5 机制全普查）＋M1 manifest 草案，全部关键结论经主代理抽查核实；churn 数字全部主代理亲测（2026-09-23）。

## §0 三句话结论

1. **包数量收敛为 4 个代码包＋1 个数据格式**（不是 20 个）——适配成本随"依赖面断点数"而不是包数走，按依赖面分包后，每次升级要盯的接口总共约 **8 个**。
2. **实测"时不时全盘适配"不成立**：我们依赖的接口面 18 天里签名**零变化**（服务端）或中速演进（客户端）；全仓 250 提交/天的狂奔主要烧在**我们不依赖的内部实现**上。
3. **零 fork 成立**：所有需求在官方 extension-cookbook 里有行（"No row modifies the loop"）；"整棵 fork"在功能上被插件全覆盖，在维护上被 git 数据否决——🔴 **用户 2026-09-23 已拍板：做插件组**（见 §5）。

## §1 包粒度收敛（≤6 的实际答案：4＋1）

| 包 | 内容 | 依赖面（=适配断点） |
|---|---|---|
| **P1 `socratic-engine`**（服务端·教学引擎） | manifest 加载＋注入引擎（A1–A5：逐个注入/每回合自查/知识锚/状态模板/教材按相位）；教学相位机（B1，用 `ctx.sessionProjections`）；课后自动更新（B2，`agent/turn-stopping`）；教学工具（B3/B4：对答案逐字回查、知识点读取、画图→生成业务节点）；教室 preset 注册 | `agent/pre-step`｜`agent/turn-stopping`｜`system-prompt` `section()`｜`ctx.sessionProjections`｜tools 注册｜`storage-domain` |
| **P2 `socratic-chat-render`**（客户端·消息流渲染） | mermaid／Live2D／白板引用的 **业务节点渲染器**（`conversation.chat.node` keyed by ChatNodeKind） | ChatNodeKind 契约｜`register-node-renderers` 先例（ui-chat:25-75） |
| **P3 `socratic-panels`**（客户端·面板） | 教室 main panel / rightbar tab：微信界面（R11 模板）、角色卡、课程状态、Live2D 常驻 | `ui-slots` SlotMap｜`ui-sidebar-right` tab registry |
| **数据格式** | `classroom.yaml` manifest（M1 v0 已出）＋教室内容包；skill 模式 = frontmatter＋AGENTS.md 投影视图（同源） | 无代码依赖（教室包零代码，贡献者不碰接口） |

- **记忆不单列**：课程状态采用**双层**——**教室 `runtime/` 文件＝真源**（可见/可编辑/可分享，服务终局 F3"它记得你"的展示面，守"文件式记忆"定案）；P1 把状态同步索引到 `storage-domain`（运行时恢复层），**不让宿主存储变唯一真源**。跨会话用户记忆可选装现成 **dsh-memento**（见 §4 先例）。（🔴 2026-09-23 终局对照修正：初版"状态全走 storage-domain"违背文件式定案，已改。）
- **20 个量级的错误在哪**：那是"功能粒度"。一个 Cordis 插件包内可以装任意多个 section/tool/listener——拆 20 个包只会把 8 个断点重复盯 20 遍。

## §3 升级策略（把"适配"变成主动窗口，而不是被动挨打）

1. **Pin 版本**：插件对接**已装宿主**（当前 web/desktop profile），不跟 master。上游一天 250 提交与你无关。
2. **升级=主动窗口**（按需/季度）：每次升级四步——① fetch 后对 §2 的表重测 churn；② `dsh --dump-config` 校验插件树；③ 跑各包自带回归测试（vitest）；④ 修断点。**每个断点都有预案**（见下）。
3. **断点预案**：`pre-step` payload 变 → P1 只改注入适配层（一处）；ChatNodeKind 变 → P2/P3 各改注册行；`section()` 变 → P1 注册调用行。**每个依赖面在包内只有一个消费点**（收敛分包的直接收益）。
4. **内容永不锁死**：教室包在 skill 模式下永远可用（零插件也能上课，靠模型自律）——插件断了 ≠ 项目死了，**降级路径就是 MVP 本身**。
5. ✅ **桌面壳自动更新（⑥ 已核）**：**没有全局关闭开关，也没有版本 pin**（electron-updater 启动 15–30 秒后检查、每 6 小时补查；跳过只对单一版本有效）→ 升级纪律（§3）从"可选"变"必须"：升级前备份 profile＋升级后 `dump-config`＋插件回归。web profile 用 CLI 启动天然不受桌面更新影响。

## §4 实证先例：memento 就是我们要写的那个插件（已验证）

**`dsh-memento` v0.5.0 是一个真实在跑的独立 Cordis 插件**（主代理实测：`~/Library/Application Support/dsh-desktop/harness/profiles/web/node_modules/dsh-memento`，自带 `cordis.patch.yml`，经 profile 装载；**monorepo 与桌面 bundle 里都没有它**）——它的复杂度等级（自述：capability seam＋SQLite provider＋memory 工具＋冻结快照注入）**正好是 P1 教学引擎的量级**。它证明：外部插件走 profile 装载在这套宿主上**当前真实可用**，不是纸面架构。
