## 2. 🔴 K6 专项：「模型写得好不好」的公开证据（本项目最关心的一条）

**结论先行（这一段是本调研最硬的发现）**：**Manim 是唯一一个有"专门训练的模型 + 专门基准 + 逐模型渲染成功率"公开数据的方案**，而且这些数字**不利于"模型天然写得对"这个假设**：官方论文明确说 Manim API 在通用预训练语料里"under-represented"，并给出**未微调模型渲染成功率最低只有 7%**。

### 2.1 一手证据 A：arXiv:2604.18364（Manim 专用训练/推理论文）

- 标题：*Training and Agentic Inference Strategies for LLM-based Manim Animation Generation*
- 作者：Ravidu Suien Rammuni Silva, Ahmad Lotfi, Isibor Kennedy Ihianle, Golnaz Shahtahmassebi, Jordan J. Bird（Nottingham Trent University）
- arXiv: [2604.18364](https://arxiv.org/abs/2604.18364)（v1 2026-04-20，v2 2026-08-31）；HTML 全文：<https://arxiv.org/html/2604.18364v2>
- 论文 license：**CC BY-NC-ND 4.0**（一手：arXiv 页面 "License: CC BY-NC-ND 4.0"）
- 对应代码仓库：<https://github.com/SuienS/manim-trainer>（star 21，2026-09-24 抓取）——其 `LICENSE` 原文实为 **CC BY-NC-SA 4.0**（"Attribution-NonCommercial-ShareAlike 4.0 International"，用 `curl raw.githubusercontent.com/SuienS/manim-trainer/HEAD/LICENSE` 读到首段原文）。**非商业限制**，不可随商业安装包分发。

**逐字引句（Abstract，来源 <https://arxiv.org/abs/2604.18364>）**：

> "Generating programmatic animation using libraries such as Manim presents unique challenges for Large Language Models (LLMs), requiring spatial reasoning, temporal sequencing, and familiarity with domain-specific APIs that are **underrepresented in general pre-training data**."

> "The Qwen 3 Coder 30B model with GRPO and RITL-DOC achieved the highest overall performance, with a **94% Render Success Rate (RSR)** and **85.7% Visual Similarity (VS)** to reference videos, surpassing the baseline GPT-4.1 model by +3 percentage points in VS."

**逐字引句（§1 Introduction，来源 <https://arxiv.org/html/2604.18364v2>）**：

> "generating correct Manim code **remains difficult**, as it requires not only syntactic fluency in Python but also reasoning about three-dimensional coordinate systems, sequencing of animations over time, and knowledge of the Manim API, which is **under-represented in general code-based pre-training datasets**"

**关键数字（§4.1 Table 1「vanilla inferencing」，即不做任何 loop、直接让模型写一次就跑）**：RSR = 生成样本成功渲染的百分比。

| 模型（未微调 base） | Visual Similarity | Render Success Rate |
|---|---|---|
| Qwen 2.5 0.5B | 6.3 | **7.0** |
| LLaMA 3.2 1B | 6.4 | 7.0 |
| LLaMA 3.2 3B | 12.8 | 14.0 |
| Qwen 2.5 Coder 1.5B | 23.8 | 27.0 |
| Qwen 2.5 Coder 7B | 42.0 | 46.0 |
| SeedCoder 8B | 60.3 | 67.0 |
| Qwen 3 Coder 30B (A3B) | 59.2 | 66.0 |
| Qwen 3 Coder Next 80B | 63.7 | 72.0 |
| **OpenAI GPT-4.1** | **68.6** | **77.0** |

同一论文在加入"渲染器进回路 + 文档检索"（RITL-DOC）后的结果（Table 3）：

| 设置 | Visual Similarity | Render Success Rate |
|---|---|---|
| GPT-4.1（RITL-DOC，单次） | 81.9 | 92.0 |
| GPT-4.1（RITL-DOC@3，三次修正） | 82.8 | **94.0** |
| Qwen 3 Coder 30B + GRPO（RITL-DOC@3） | **85.7** | 94.0 |

> 注意「VS」是**与参考视频的相似度**，不是"讲对了知识点"的分数。论文自己在 Construct Validity 里承认：参考代码/视频由专家撰写、取自 Manim 官方文档，"may penalise generated videos that are visually relevant to the provided textual description and high-quality, but differ from the reference code and video"。→ **拿 VS 高当作"教学正确"是不成立的**。

**可直接用于本项目的三条工程含义（含【推断】标注）**：

1. 【事实·论文 §4.1】"the models learned to **fix failing code rather than write new code**"——微调主要提升的是**修错能力**，不是**一次写对**的能力。
2. 【事实·论文 §3.4.1】论文用的渲染器是 **Manim Community Edition 0.19.0**；【事实·Limitations】"the findings are specific to Manim Community Edition 0.19.0 and may not apply to other types of programmatic animation" → **该论文的结论只对 ManimCE 成立，不能外推到 motion-canvas / Remotion 等**。
3. 【推断】原文最高的 94% RSR 是**三次修正循环之后**的结果。单轮 naive 生成的最强模型（GPT-4.1）RSR 只有 77% → **本项目若要让 agent 自动出片，必须内建"渲染→读报错→改→再渲染"的循环**，且要预留 3 轮左右的重试预算与 token 成本。

**论文给出的失败模式（§2.3 / §4.4，间接证据）**：
- 论文引用 Code2Video [34] 指出："highlighting **the gap between the code execution success and the quality of the visual outputs**"——**能渲染 ≠ 画对了**。
- 论文引用 [5]（ManimBench）指出：CodeBLEU / CodeBERT 这类代码指标"**may penalise Manim snippets that produce similar visual outputs via different coding pathways**"；§4.4 实测"code and visual metrics exhibit a **relatively weak overall correlation**" → **不能只看代码"看起来像不像 Manim"，要看画面**。

### 3.1 Manim Community Edition（ManimCE）

- **官方仓库**：<https://github.com/ManimCommunity/manim>｜**官网/文档**：<https://www.manim.community> / <https://docs.manim.community/>
- **star**：**41000**（GitHub API，2026-09-24 抓取）
- **license**：**MIT**。一手核实两处：① GitHub API `license.spdx_id = "MIT"`；② `pyproject.toml` 原文 `license = "MIT"`、`license-files = ["LICENSE", "LICENSE.community"]`（来源 <https://raw.githubusercontent.com/ManimCommunity/manim/main/pyproject.toml>）。⭐ 注意是**两个**许可文件（`LICENSE` + `LICENSE.community`），本次未逐字读 `LICENSE.community` 内容 → 见 §6 待确认。
- **当前版本**：**0.21.0**（`pyproject.toml` 的 `version` 字段原文）
- **运行时前置（一手，同 pyproject）**：
  - `requires-python = ">=3.11"`，classifiers 覆盖 3.11–3.14
  - 依赖里有**大量编译型/图形栈**：`pycairo`、`manimpango`、`moderngl` / `moderngl-window`（**需要 OpenGL**）、`skia-pathops`、`isosurfaces`、`mapbox-earcut`、`scipy`、`numpy`、`av>=15.0`、`pillow`、watchdog 等（完整列表见原文件）
  - 官方 README 对 3b1b 版的系统要求写的是 "System requirements are [FFmpeg], [OpenGL] and [LaTeX] (optional…)"；ManimCE 的 README 指向安装文档 <https://docs.manim.community/en/stable/installation.html> 要求按 OS 分别安装前置。**体积量级：未实测**（本次未下载安装，不编造数字）；但从依赖清单可判断为"**重**：Python 3.11+ 运行时 + 原生图形栈 + ffmpeg"，若再叠 LaTeX（`texlive`）会显著更重。【推断】
- **产出格式**：社区版支持 mp4 / webm / gif（官方 CLI 的 `--format`／`-f` 选项）；本次未逐字抓到该选项的文档原文 → 见 §6 待确认。论文里提到 3b1b 系 GIF 常用 5 FPS（一手：arXiv:2604.18364 §3.2.2 "based on many Manim-based GIF images that work at 5 FPS"）。
- **LLM 驱动方式（K2）**：模型写 **Python 脚本**，用 `Scene` 子类 + `self.play(...)` 这类 API；然后 CLI 渲染。**完全无 GUI 依赖**（写代码 → 渲染文件），天然可自动化。✅
- **模型可写性证据（K6）**：**本调研里最强的一项，但结论是"需要专门训练/agent 循环才可靠"**——见上文 §2.1 全文。要点：官方论文明确 Manim API 在预训练语料中 under-represented；未微调模型 RSR 低至 7%；最好的组合（Qwen3-Coder-30B + GRPO + RITL-DOC@3）达 94% RSR，但这是**训练 + 三次渲染修正循环**之后。
- **教学适配度（K1）**：**高**。官方定位逐字："Manim is an animation engine for explanatory math videos. It's used to create precise animations programmatically"（来源 <https://raw.githubusercontent.com/ManimCommunity/manim/main/README.md>）。它天生就是**为"讲清楚数学/机制"**设计的（Transform、坐标轴、LaTeX 公式、轨迹动画）。对"两个程序同时跑为什么互相捣乱"这类**时序/状态交叠**也能做（用 `AnimationGroup` / `Succession` + 状态条，但**这属于把机制建模成图元，需要人/模型自己设计画面**）。⚠️ **Manim 不是"时序图 DSL"**——它不会自动替你摆出正确的时序图。
- **确定性/可复现（K7）**：**高（同一环境内）**。Manim 是确定性渲染：写定帧率与时间，逐帧渲染 → 同脚本同输出。⚠️ 但**跨版本不保证**：论文 Limitations 明确 "the findings are specific to Manim Community Edition 0.19.0"，而当前版本已是 **0.21.0**（`pyproject.toml`）；两个 minor 版本之间 API 有无破坏性变更，**本次未核**（→ §6 待确认）。**这正是用户担心的"模型按旧 API 写"风险的现实来源**：社区里大量教程/训练语料停留在 0.17–0.19。
- **主要风险**：
  1. **单轮写不对**（RSR 未微调最强模型仅 77%），必须配"渲染器进回路"的重试机制 → **每张图可能 2–4 次渲染**，成本与延迟要算进产品设计。【事实+推断】
  2. **安装摩擦大**：cairo/pango/OpenGL/ffmpeg 原生依赖，打进桌面安装包要做多平台打包（macOS arm64 / Windows / Linux 各一套）。【推断，未实测】
  3. **版本漂移**：语料版本 vs 本地版本不一致 → 渲染报错。
  4. **许可**：MIT 本身干净；但**训练/参考用生态（如 SuienS/manim-trainer）是 CC BY-NC-SA（非商业）**，不能把它的权重/数据随商业包分发。⚠️ 这是**风险报告**，取舍请用户自行研究。

  - K7：❌ **不可复现**：同一 prompt 两次生成不同结果，**教学材料最需要的"可复跑"直接不成立**。
- **结论**：**结构性不满足 K1/K7**，排除。可作为"配图素材生成"的补充，**不能承担"把机制讲清楚"这个核心用途**。

## 6. 🔴 反证与风险（**不利证据，不只写优点**）

### 6.1 最硬的两条反证

**反证一：Manim 的"模型天然写得对"是不成立的，且这是有公开量化证据的。**

- 官方论文逐字：Manim API "**underrepresented in general pre-training data**"、"**under-represented in general code-based pre-training datasets**"（<https://arxiv.org/abs/2604.18364>）。
- **未做任何训练的模型，渲染成功率低到不可用**：Qwen 2.5 0.5B **7%**、LLaMA 3.2 1B **7%**、LLaMA 3.2 3B **14%**；即使 GPT-4.1 也只有 **77%**（§4.1 Table 1，vanilla inferencing）。
- 微调提升的主要是"**修错能力**"而不是"一次写对"：原文 "the models learned to **fix failing code rather than write new code**"。
- 论文还指明**版本锁定风险**：结论只对 **ManimCE 0.19.0** 成立；而**当前最新版是 0.21.0**（`pyproject.toml`），且 **0.21.0 有 Breaking Changes**（一手，`docs/source/changelog/0.21.0-changelog.md` 原文：`.Code` 不再接受 `paragraph_config={"color": ...}`；`Camera.convert_pixel_array()` 的 `convert_from_floats` 参数**已被移除**）→ **模型按旧版本文档写的代码，在新版本上会真实报错**。这正是用户担心的那条。
- 社区里已有同型抱怨（**二手线索，仅作线索，未取一手证据**）：Reddit r/manim 帖 "**AI-generated Manim code using parameters I can't find in docs**"（<https://www.reddit.com/r/manim/comments/1qlpzma/aigenerated_manim_code_using_parameters_i_cant/>）与 "Manim broken after VS Code restart"（<https://www.reddit.com/r/manim/comments/1v0prt0/manim_broken_after_vs_code_restart/>）。本次 `reddit_fetch.py` 搜索**超时（60s，被 SIGTERM）**，故**未取到帖文正文**，不引用其内容。

**反证二：Manim 的运行时前置是真的重，且"打进安装包"这件事它天然不友好。**

- 一手依赖清单（ManimCE `pyproject.toml`）：`pycairo`、`manimpango`（**Pango 绑定**）、`moderngl` / `moderngl-window`（**OpenGL**）、`skia-pathops`、`scipy`、`numpy`、`av`、`pillow`、`isosurfaces`、`mapbox-earcut` 等。
- ManimGL README 原文："System requirements are **FFmpeg**, **OpenGL** and **LaTeX** (optional…) For Linux, **Pango** along with its development headers are required."
- 而**先例项目实测需要的额外系统件**（一手，makefinks/manim-generator README）：macOS `brew install ffmpeg` + `brew install --cask mactex`；Linux `texlive texlive-latex-extra texlive-fonts-extra texlive-science` → **一旦要 LaTeX（数学推导几乎必然要），安装包体积与打包难度会再上一个台阶**。
- 🔴 **对比**：**Revideo 的运行时依赖只有 2 个 npm 包（`culori` + `mp4-wasm`）**（`@revideo/core` package.json 原文）——**这是全部候选里"打进安装包"最轻的一条路**，代价是教学适配度与模型可写性证据都弱。
- 【未实测声明】**本次调研没有实际安装任何一个方案、没有测过任何体积数字**。上表的"重/轻"是基于**依赖清单与官方 README 原文**的判断，不是实测。

### 6.2 不利于"排除 Manim"的证据（即：换成别的也不见得更安全）

- **其它方案在 K6 上是"零证据"而不是"更好"**：Manim 至少有 3 篇独立学术工作 + 2 个公开基准（ManimBench、Manim-Bench）+ 一个公开排行榜；**motion-canvas / Remotion / Lottie / Rive / D3 / p5 / Three / Pixi / Asymptote / TikZ / Blender / Matplotlib / Processing 全部"未找到公开的 LLM 生成成功率证据"**。→ 换成它们**不是"不确定性变小"，而是"不确定性变得无法评估"**。
- **浏览器类方案（GSAP/SVG/D3/p5）的"确定性"有公开实测反证**（一手，本机 `huashu-design` skill 的 `references/animation-pitfalls.md`，MIT）：
  > §5："用 `setTimeout` + `fireOnce(key, fn)` 链式触发动画状态。正常播放没问题，但**做逐帧录制/seek 到任意时间点时，之前的 setTimeout 已经执行过就无法「回到过去」**。"
  > §7："**Playwright `recordVideo` 默认 25fps**…页面加载、字体加载的前 2 秒都被录进去。交付时视频前面 2 秒空白/闪白。"
  > §14：60fps 默认用帧复制，因为 minterpolate 有 "known compat bug"（曾多次踩到 macOS QuickTime 打不开）。
  → 即：**"HTML 动画 → 视频"这条路要自己补齐一整套录屏工程**（该 skill 为此专门写了 `render-video-seek.js`），而**模型天生爱用 setTimeout 写演出脚本**，正好撞在 K7 上。
- **Remotion 的许可不是标准开源**（一手，`LICENSE.md`）：个人/≤3 员工的营利组织免费，**"不允许复制或修改 Remotion 代码用以出售、出租、再许可你自己的衍生品"** → 与"把依赖打进安装包分发"这一形态相关（**风险报告，取舍请用户自行研究**）。
- **GSAP 的许可有两条与产品化相关的限制**（一手，<https://gsap.com/licensing/>）：终端用户被收费则需 Business 会员；**禁止用于"允许用户无代码构建视觉动画的工具"**（这可能覆盖"AI 自动生成动画的工具"，也可能不覆盖——**本次不做判定**）。
- **Lottie / Rive 是结构性不满足 K2**（不是"略差"，是"模型无法写"）：Lottie 的源头是 AE 拖时间轴（README 原文直指 Bodymovin 插件）；Rive 的产物是二进制 `.riv`。

### 6.3 还有哪些"未知"会推翻结论

见 §8 待确认清单。最可能改变结论的三项：
1. **motion-canvas / Remotion 的"确定性导出"到底官方支持到什么程度**（本次没取到原文）；
2. **DSH 打包形态能否接受"随包带一个 Chromium + ffmpeg"**（数百 MB 量级）【未实测】；

## 7. 结论

### 7.1 推荐：**保留 Manim Community Edition（ManimCE）为主轴**，理由是"证据密度"而不是"名气"

**逐条理由（每条都能追到上面的一手出处）**：

1. **K1 唯一正解**：官方定位逐字 "an animation engine for **explanatory math videos**"——它是本次全部候选里**唯一一个"出生就是为了讲清东西"的**。其余全是"通用动画/可视化/3D/视频"工具，讲机制要靠自己搭图元。
2. **K6 唯一有证据**：只有它有**专门训练的模型 + 专门基准 + 逐模型渲染成功率 + 公开排行榜**。要回答用户那句"模型写白板能不能写好是不是需要验证"，**只有 Manim 这条线能拿出可以核对的公开数字**。
3. **K2/K3/K7 天然满足**：写 Python → CLI 渲染 → mp4/webm/gif；无 GUI 依赖；逐帧确定性渲染。
4. **先例最多（本报告 §4）**：**7 个公开的"AI 教学动画"项目全部基于 Manim**。选它＝有大量可抄的实现；选别的＝第一个吃螃蟹。
5. **用户已明确"多加点依赖也是可以的"** → 直接把 K4（依赖重）这个最大短板**降级为非否决项**。

**但必须带上三件"配套工程"，否则会翻车**（这是从公开证据里直接推出来的）：
- 🔴 **① 渲染器进回路（RITL）：渲染 → 读报错 → 改 → 再渲染，预算 3 轮左右**。依据：单轮最强模型 GPT-4.1 只有 **77%** RSR，加到 3 轮修正才 **94%**（arXiv:2604.18364 §4.3.2、Table 3）。先例项目默认跑 **4–5 轮评审**（Manim-Bench 页脚 "4 review cycles"；manim-generator `--review-cycles` 默认 **5**）。
- 🔴 **② 把 Manim API 文档喂进上下文（RITL-DOC）**。依据：论文里 **RITL-DOC 明确优于纯 RITL**，且这是对抗"模型按旧 API 写"的直接手段（0.21.0 有 Breaking Changes，见 §6.1）。
- 🔴 **③ 版本锚定**：**把 ManimCE 版本钉死写进系统提示与依赖**，并让 agent 只查该版本的文档。依据：论文的结论只对 0.19.0 成立，而当前是 0.21.0。

### 7.2 备选（第二推荐）：**Revideo**——只在"安装包体积必须小"成为硬约束时才考虑

- 唯一同时满足"代码驱动 + headless 渲染出视频 + 依赖极轻（Node + 2 个包）"的候选；官方还明确声明 "A scene is plain TypeScript, so **Claude or Codex can produce one from a prompt**"（README 原文）。
- 🔴 **但它有三个未被证实的缺口**：① 教学适配度弱（通用视频引擎，无公式排版、无教学图元）；② **K6 零独立证据**（只有厂商自述）；③ 版本 0.11、star 4k、fork 血缘，长期维护未定。
- **定位**：当"Manim 的 LaTeX/cairo 装不进安装包"这件事被实测证明为**否决性障碍**时，才切到它。

### 7.3 不推荐其余的理由（各一句）

| 方案 | 一句话理由 |
|---|---|
| ManimGL（3b1b 原版） | **与 ManimCE 同能力但生态/文档/语料都弱，且没有任何 LLM 生成它的公开证据** —— 没有理由选它而不选 CE |
| motion-canvas | **"能不能导出 mp4"这条本次没查到官方答案**，K3 都没落实之前不能作为主轴 |
| Remotion | **许可不是标准开源且禁止再分发衍生品**，与"打进安装包分发"形态有潜在冲突（风险报告），且依赖比 Manim 更重（Node+Chromium+ffmpeg） |
| Lottie / bodymovin | **它是播放器不是创作器**，动画源头是 AE 拖时间轴 —— 结构性不满足 K2 |
| Rive | 同上，且产物是二进制 `.riv`，模型无法"写" |
| GSAP + SVG / D3 / p5 / Three / Pixi | 通用前端/2D/3D 库，**教学图元零供给、导出要自建录屏工程、确定性有公开踩坑记录、模型可写性零证据**；D3 定位还错（数据可视化） |
| Asymptote | 主职是静态矢量图（已被需求排除），**GPL-3.0**，语料极小（687 star） |
| TikZ + animate | **动画靠 PDF 放映器播放**（K3 弱），**TeX 全量依赖**，编译报错晦涩 |
| Blender `bpy` | **GPL 且原文"不提供其他许可"**，依赖极重，API 面数千算子，**面向 3D 而需求是 2D 时序** |
| Matplotlib animation | **图表动画强、机制/时序图弱**，且没有"讲台图元"；可作 Manim 的补充（ManimCat 就是这么做的），不作主轴 |
| Processing | 被 p5.js 完全覆盖（同生态，p5 语料更多），而 p5 本身也已不推荐 |
| 视频生成模型（Veo/Sora/Wan） | **不可控、不可复现、无法 review 代码、不能离线** —— 结构性不满足 K1/K7 |

## 10. 一句话总结

**没有替代方案能同时替代 Manim 的三件事——「为讲解而生」「有真实可核的模型可写性数据」「有 7 个先例可抄」。**
所以答案是：**保留 ManimCE，但把它当作"需要配套工程才能用好的引擎"而不是"装上就能出片的工具"**：必须内建**渲染-报错-修正循环**、**版本锚定 + API 文档注入**，并**先自测本项目模型的真实渲染成功率**（公开数据里没有它）。
**唯一值得认真评估的替代品是 Revideo**（依赖最轻 + 官方宣称 LLM 可写），**但它没有任何第三方证据，且教学适配度明显更弱** —— 它只在"Manim 装不进安装包"被实测证伪时才是答案。
