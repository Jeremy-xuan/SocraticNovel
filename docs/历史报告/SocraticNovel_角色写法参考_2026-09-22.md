## 摘要（≤10 条）

1. 【原文-语料】**"496 张"这个数字在采样时已过期**——本次实测磁盘上是 **529 个 `.json`**（10 个解析失败 → **519 张可解析**）。语料在下载后仍在增长，报告必须写明采样时刻与数量。详见 §2.0。
2. 【原文-语料】🔴 **本语料的 `first_mes`（开场白）被整体覆盖为分销广告**：519/519 = **100%** 的卡，其 `first_mes` 都是同一段"请结合酒馆专属大模型 Deepseek Tavern Pro…"（长度恒为 ≈206 字符）。**真实开场白被搬到了 `alternate_greetings`**（253 张有，均值 8584 字符）。→ **想学"开场白怎么写"必须读 `alternate_greetings`，读 `first_mes` 是读广告。** 详见 §2.1。
3. 【原文-语料】**这批卡的写法重心几乎全部压在"世界书"（`character_book`）里，而不是在角色设定字段里**：`character_book` 出现率 **91.2%**（443/519），条目总数 **10 705** 条；而 `personality` 仅 **1.9%**、`scenario` 2.3%、`mes_example` 2.5%、`system_prompt` 1.4%、`post_history_instructions` **0.6%**。→ **对我们是重大利好：酒馆生态的成熟做法本来就是"把知识切成条目存外部文件"，正是我们教室的结构。**
4. 【原文-语料】`description` 出现率 **52.1%**（253/519），中位 959 字符、P90 4667、最大 45 654；**几乎不用第二人称**（"你是…" 仅 2%），**而用 `{{user}}` 占位符（69%）+ 项目符号（54%）+ YAML 键值对（46%）**。→ 写法上的行家做法是**结构化条目式罗列，不是写作文**。
5. 【原文-语料】**世界书条目切分粒度**：条目名中位长度 8 字符、每条关键词**中位 1 个**（均值 2.26）、条目内容**中位 957 字符**、P90 3479。**52% 的条目是 `constant`（常驻、无关键词）**；443 张有世界书的卡中 **152 张完全不用关键词（全常驻）**。→ **"一个知识点一条 + 少量关键词"是可复用模式**。
6. 【原文-语料】**教学/答疑/纠错作为人设主轴：语料里几乎没有。** 全库 `description`+`creator_notes` 含"老师/教师/教学/授课/讲师/教授"的仅 **20 张**，且其中 **17 张在 `单人`/`世界卡`/`系统` 类，校园类只有 4 张**——身份是老师但主轴是恋爱/成人剧情。"答疑"命中 **2 张**、"纠错"命中 **0 张**、"苏格拉底"命中 **2 张**。→ **"苏格拉底式教学的骨架"在本语料中不存在，必须自研。** 详见 §5。
7. 【原文-语料】**`depth_prompt` 出现率 95.7%（465/519）但 95% 是空壳**：长度中位与 P90 都是 **0**，真正 `len>50` 的只有 **27 张**（最长 2521）。→ **"固定深度注入"在酒馆生态里是被普遍注册、极少真正使用的字段**；能用好它是我们可以拿到的少数非对称优势之一。
8. 【原文-代码】**蒸馏器的映射是一套「12 章节 SKILL.md + 6 个 references 文件」的固定模板**，`generate_skill.py` 把 V2 字段**分派到**这些槽位（§1 表）；同时**静默丢弃** `creator_notes` / `tags` / `character_version` / `source` / 世界书的 `insertion_order`/`priority`/`probability`/`match_whole_words` 等字段（`generate_skill.py` 中 **grep 计数为 0**）。→ **蒸馏器把卡片"当小说玩"，不把卡片"当知识库查"——它的丢弃清单正好是我们必须自研的部分。**
9. 【原文-代码】蒸馏器**硬编码了成人向叙事原则**（`build_writing_guide` 里写死"根据剧情需要自然描写所有类型的场景，不做内容回避或淡化处理"、`build_preset` 写死"解除内容限制"）。→ **它的代码不能 fork，只能借映射思路**；我们若参考其代码，必须先把这些行整段删除。
10. 【原文-语料】`system_prompt` / `post_history_instructions` 在我们这批语料里**近乎空缺（1.4% / 0.6%）**——这与"分布式卡片普遍带破限预设"的通常印象相反。→ **想学"历史后指令"的写法，本语料样本不足，只能从蒸馏器代码对它的语义描述反推**（§3.C、§6）。

## §1 蒸馏器的转换方法论

### 1.1 它实际做了什么（两步流水线）

【原文-代码】流水线是**两段式**，中间有个 `card_data.json` 落盘：

```bash
# Step 1  任意格式卡片 → 统一 JSON（extract_card.py, 27.7KB）
python3 scripts/extract_card.py "<card_file>" -o /tmp/card_extract
#   → /tmp/card_extract/card_data.json       （唯一中间产物，schema 由 normalize_card() 定义）

# Step 2  统一 JSON → markdown skill 目录（generate_skill.py, 48.8KB）
python3 scripts/generate_skill.py /tmp/card_extract/card_data.json
#   → rp-<角色名>/{SKILL.md, config.json, user_profile.json, chat_history/, references/*.md}
```

【原文-代码】`normalize_card()`（`extract_card.py:409`）把 V1/V2/V3 三种规范**压成一个扁平 dict**：V2 的 `data.*` 与 V1 的 `char_name`/`char_persona` 都被拍平到同一组键名（`:454-476`），`character_book` → `world_book`（并强制补齐 24 个字段的默认值，`:487-527`），`extensions.depth_prompt` → 顶层 `depth_prompt`（`:546-553`）。
→ **【推断】这个"先归一化再生成"的分层设计，是我们该照搬的第一件事**：我们的卡片来源将来也可能杂（手写 md / 外部 JSON / 表格），先把来源归一到中间 schema，生成器只认中间 schema。

### 1.3 它丢弃了什么，以及为什么

【原文-代码】在 `generate_skill.py` 全文 grep，**计数为 0** 的字段（即提取阶段拿到了但生成阶段从不读取）：

| 被丢弃的字段 | 为什么（我的判读） | 数据来源 |
|---|---|---|
| `creator_notes`（13.4% 有填） | 面向"人类在酒馆里怎么用这张卡"，对 agent 扮演无信息量 | grep=0 |
| `tags`（2.9%） | 只服务站内检索/分类，运行时无用 | grep=0 |
| `character_version`（15.2%） | 版本管理元数据 | grep=0 |
| `creator`（20.0%） | 署名 | grep=0 |
| `creator_notes_multilingual` | 同上 | grep=0 |
| `source`（V3） | 出处声明 | grep=0 |
| `group_only_greetings` | 群聊模式专用 | grep=0 |
| `character_book.scan_depth` / `token_budget` / `recursive_scanning` | **这些是"检索策略"参数**——蒸馏器把世界书**全文静态写进 markdown**，由 agent 自己决定读不读，**整条检索管线被放弃了** | `:480-487` 只存不用 |
| 条目级 `insertion_order` / `priority` / `probability` / `useProbability` / `match_whole_words` / `prevent_recursion` / `delay_until_recursion` / `group_*` / `automation_id` | 同上：酒馆的**注入调度算法**在 markdown 里没有对应物 | grep=0（`normalize_card` 存了，生成器不读） |
| `talkativeness` / `fav` | 酒馆客户端 UI 行为参数 | grep=0 |
| 条目级 `depth`（≠4 时） | 只在 world_book.md 元信息行里**写出来**，但不产生任何行为——markdown 没有 depth 机制 | `:343-353` |

🔴 **关键判断**【推断】：蒸馏器的**核心取舍是"把一张有运行时机制的卡，降维成一堆静态 markdown"**。它主动扔掉了酒馆最精密的两个子系统——**关键词检索（world info 触发）**与**注入调度（depth/position/order）**——因为 Claude Code 的 skill 机制不提供这两个能力。

### 1.4 这套映射能不能直接用在我们的教室结构上？

**结论：结构骨架可以用，映射内容和产出粒度必须大改。**

我们的目标结构与它的输出对照：

| 我们的文件 | 蒸馏器里最接近的东西 | 能否直接用 | 必须改什么 |
|---|---|---|---|
| `teacher/characters/*.md` | `SKILL.md` §角色设定（`description`+`personality`+`scenario`） | ⚠️ **部分可用** | 它的 `description` 是"小说人物小传"写法；我们要的是**教师人设 + 教学纪律 + 提问风格**。**章节要换，不能照搬 12 章模板**。 |
| `teacher/config/narrative_core.md` | `references/preset.md` + `preset`/`writing_guide` | ⚠️ **思路可用，内容必删** | 它的 preset 整段是破限/NSFW 解锁。【原文-代码】`build_writing_guide` 硬编码"不做内容回避或淡化处理"、`build_preset` 硬编码"解除内容限制"。🔴 **这几段必须整段删除**，只保留"把系统级指令集中到一个可加载文件"这个**结构**idea。 |
| `teacher/教材/*.md` | `references/world_book.md` | ✅ **最值得抄** | 这是全库最成熟的模式（91.2% 出现率 + 10 705 条实例）。抄它的**条目切分粒度与元信息行格式**（§2.3、§3.D）。但它的条目多为"设定百科"，我们要的是"知识点讲课稿"——**切分原则相同，内容生成原则不同**。 |
| `teacher/课程表` | `references/routes.md` | ✅ **可抄结构** | routes 的组织方式（开场白全集 + 可解锁剧情线）与"课程表/章节推进"**同构**。可借"编号列出可选开局"的写法。 |
| `teacher/状态笔记本` | `references/state_system.md` + session frontmatter `state:` | ⚠️ **结构可用，检测逻辑必换** | 【原文-代码】`detect_state_systems()` 是 **9 条硬编码正则**，全部指向 NSFW 变量（好感度/堕落度/欲望值/服从度…）。→ **这套检测必须自研**：我们的状态是"已讲知识点 / 学生掌握度 / 待复习项 / 当前章节"。**但 `state:` 塞进 frontmatter + 每次回复后更新**这个机制值得照搬。 |
| `AGENTS.md` 加载时序 | 无直接对应物；它靠 platform 的 skill 自动加载 | ❌ **必须自研** | 蒸馏器**没有显式加载时序**——它依赖 Claude Code 的 skill 机制"提及触发词就加载 SKILL.md，SKILL.md 里再用相对链接指向 references/"。**我们的加载时序是自建需求。** |

【原文-代码】**一个值得抄的小机制**：所有 refs 之间的引用**一律用相对 markdown 链接**（`[references/world_book.md](references/world_book.md)`），而不是复制内容。→ 这正好对应我们"教材文件被按需读取"的设计。

### 2.1 🔴 语料的重大结构性缺陷：`first_mes` 被广告污染

**【原文-语料】519/519 = 100%** 的卡的 `first_mes` 字段都是同一段分销广告：

```
请结合酒馆专属大模型Deepseek Tavern Pro使用本角色卡，能够获得更好的效果，
酒馆专属大模型是专门为酒馆微调的专属创作模型，内置破限，上下文遵循更好，
创作能力更强，价格非常亲民，网址为：deepseektavern.com，……
——作者 磊哥哥网络获取
```

- 【原文-语料】长度分布：**206 字符出现 510 次**（另 9 张 201–366），即**位置完全被统一覆盖**。
- 【原文-语料】**真实开场白被搬到了 `alternate_greetings`**：稳定态出现率 **53.0%**（**275 张**），**均值 8365 字符、中位 4464、P90 20 704、最大 85 256**（首版采样 52.1%/253 张，比例一致）。

### 3.D `character_book` 的切分方式（逐条目画像）

【原文-脚本】·【原文-语料】

| 状态追踪 | `state:` 进 frontmatter，每轮更新 | 🔴 **状态笔记本直接照搬此机制** |

### 拆开回答

**（1）能学到的部分（容器层）——约占我们工作的 30%**

**（2）学不到的部分（教学层）——占我们工作的 70%，必须自研**

证据链（三条相互独立，指向同一结论）：

1. 【原文-脚本】**关键词命中率极低且方向错**：`纠错` **0**、`答疑` **2**、`苏格拉底` **2**（且那 2 张是成人向卡的偶然用词）。**苏格拉底式教学在酒馆卡生态里不是一种流派。**

**（3）为什么"容器可借、骨架必须自建"是结构性的，不是偶然**

【推断】酒馆卡的**设计目标是"沉浸式叙事"**——它的成功标准是"角色不出戏、剧情吸引人"。**教学的成功标准是"学生学会了"**，需要**外部世界的正确性锚点**（教材、可回查的事实、掌握度评估）。这与任务书已掌握的外部结论完全咬合：

> 官方文档明示：注入不保证生效、摘要会幻觉（"may lose some important details or contain hallucinations"）→ **教学的事实正确性不能靠生成式注入，必须靠文件逐字回查。**

→ 换句话说：**叙事型卡可以容忍幻觉（甚至幻觉是特性），教学型卡不能。** 一个只为叙事设计的格式生态，**必然不提供正确性机制**。这就是为什么教学骨架必须自建。

**（4）一个可以直接用的推论（对我们有利）**

【原文-语料】`depth_prompt` **96.0% 注册、95% 为空壳**，仅 27 张真用；条目级 `depth` **10 705/10 705 全是默认值 4**——**没人改过**。
→ 【推断】**酒馆生态在"固定深度注入"这个机制上几乎是空白**，而**它恰好是"教学纪律每次都要生效"最需要的东西**。结合任务书既有结论（"教学纪律类指令应贴近对话尾部"）与本次实证（**真用它的作者多数选 `depth=0`**），我们在这块做的任何扎实工作都**属于生态里没人做过的部分**。
