## §2 docs/ 其余文档机制清单（每份定义了哪些可用机制/契约）

### 2.1 architecture.md（权威扩展点地图）— `docs/architecture.md`
- **Profiles & bundles 组合模型**（architecture.md:18-49）：运行中的 `dsh` = 从有序层组合出的插件树。
  - **Profile** = Harness home 里命名的组合，列出堆叠的 bundles、out-of-tree 插件、`cordis.patch.yml`。模板：`web`/`headless`/`sdk`/`sdk-minimal`/`acp`。
  - **Bundle** = Cordis 配置行 + 挂载代码的发行格式，**插入的内容仍可被上层 patch**（→ 插件可叠加改 bundle 行为）。
  - 层叠加顺序（architecture.md:34）：profile 列出的各 bundle → profile 的 `cordis.patch.yml` → home 级 patch → `--patch` overlay。**patch 按 id 改整块 config 或 insert 新行**（与 L2 §11 一致）。
  - `dsh --profile web --dump-config` 可看本机启动的插件树，"它打印的任一行都能被你自己的 patch 替换"（architecture.md:47）。
- **"Where new behavior goes" 扩展点表**（architecture.md:137-160）—— 官方给的"加 X 挂哪个 ctx"速查，逐条对我们：加模型能力=`ctx.tools`（同 cookbook 行10）；拦截 request/tool/turn=`agent/*`/`tools/*`+`agent/turn-stopping`（同 cookbook 行1/14）；加 UI=`ctx.agents`+`session/event`（同 cookbook 行23）；管理目标=`ctx.goals`（行2）；fork session=`ctx.agents.create({sessionId,seed,...})`（行？）。
- **Desktop application 节**（architecture.md:51-58）：Electron 桌面壳 = 签名资源里带 dsh 生产运行时，独占 `$DSH_HOME/profiles/desktop`；公共 CLI **不能**管理 Desktop 的 profile → 这直接影响 E2「自建发行版」：要么走 web profile 自建壳，要么动 desktop profile（CLI 不可管，需手动/替换）。
- **Projection seam**（architecture.md:127）：`ctx.sessionProjections` 增量折叠已提交事件，host 用 `stateOf()` 读类型化状态——**L2 §2.4「插件+session projection 实现相位状态」的官方机制**，相位状态可持久化/回放/崩溃恢复。

## §4 🔴 插件实际装载机制（settings/profile/patch，vendor/include，本机实测补充）
**这是本次 L5 最关键的"没人查过"项。** 综合 `docs/architecture.md`(Profiles & bundles)、`packages/boot/app-boot/`、`packages/boot/plugin-manager/README.md`、`docs/user/develop/basic/publish.md`、`vendor/include/`。

### 4.1 三层概念（务必分清）
| 概念 | 是什么 | 声明位置 |
|---|---|---|
| **Plugin** | 一个 Cordis 插件（对象/Service），通过 `ctx.effect()`/`ctx.on()` 贡献 service/event/effect | 包的 `index.ts`（`export const name` + `apply(ctx)`）|
| **Bundle** | 一个 **npm 包**，ship 一层 Cordis 配置；manifest 声明 `dsh.bundle.patch` | 包的 `package.json` `dsh.bundle` + `cordis.patch.yml` |
| **Profile** | `$DSH_HOME/profiles/<name>` 下一个**目录**，描述一个可启动组合；manifest 声明 `dsh.profile.bundles` 顺序 | 目录内 `package.json`(依赖+`dsh.profile`) + `cordis.patch.yml`(用户层 patch) |

> **官方原文**："A bundle is what you author and distribute; a profile is what a user boots with `dsh --profile <name>`. Nothing is both."（publish.md）

### 4.2 层叠加顺序（决定我们 6 包的优先级）
启动时的插件树按序组合（architecture.md:34；L2 §11 已引）：
```
空 entry 列表
 → 各 bundle（按 profile 的 dsh.profile.bundles 顺序）
 → profile 的 cordis.patch.yml        ← 用户层
 → home 级 patch
 → --patch overlay
```
- 每一层 patch **按 id 改整块 config**（替换，非 merge）或 **insert 新行**。
- 后写的层对同一行"last write wins"（base bundle patch 注释明确："the last write winning per row"）。
- **关键**：`cordis.patch.yml` 的 `- insert:`（无 `id`）可往 entry 列表尾部追加**全新条目，name 任意** → **新增插件包完全支持**（L2 §11.1 已确认；这是官方插件路线的根基）。

### 4.3 一个插件包（Bundle）的磁盘形态（publish.md 权威）
```
hello-plugin/
├── package.json      # {"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}, "main": "index.js"}
├── cordis.patch.yml  # YAML 数组：- insert: [{id, name: 'dsh-hello-plugin'}]
└── index.js          # export const name + export function apply(ctx){...}
```
- patch 行引用**包名**（Node 解析找已装代码），非相对源码路径（区别于 `--patch` overlay 的本地开发形式）。
- `patch` 字段也接受有序**文件列表** `["./base.patch.yml","./web.patch.yml"]`，launcher 按序作为一层应用。

### 4.4 🔴 "我们装 6 个插件包"的可操作路径（两条）
**路径 A — 发布为 npm bundle，用 `dsh plugin` 装进 web profile（官方推荐，零改桌面壳）**
1. 每个教室/引擎插件做成一个 bundle 包（`dsh.bundle` + `cordis.patch.yml` + `index.js`/ts）。
2. `dsh plugin --profile <name> add ./our-plugin-1`（publish.md 示例）→ 首次自动初始化 profile（以 `@deepseek-ai/dsh-base` 为首 bundle），pnpm link 并把 bundle 追加进 `dsh.profile.bundles`。
3. 也可用 Web 侧边栏 **Plugins** 页（`ui-plugin-manager`）或 `plugin_manager` 工具（Creator 模式）启停/安装/卸载——改的是 `cordis.patch.yml` 的 `disabled` 或 `dsh.profile.bundles`。
4. 包解析走 profile 的 `node_modules`；第三方包通过 symlink 接入（L2 §11.2 本机实测：`@deepseek-ai/dsh-*` 全是 app bundle 的 symlink）。
5. **HMR**：base 启用配置级 `dsh-hmr`（architecture.md:43）→ YAML/config 改动即时生效；改 JS 模块需重启进程（plugin-manager 已知限制："Package replacements require restarting"）。

**路径 B — 本地开发期用 `--patch` overlay 直接挂源码（publish.md 前置教程）**
- `dsh --profile web --patch ./our-dev-overlay.yml` 把本地插件（相对路径引用源码）作为顶层 overlay 加载——**开发期零发布**，与 A 的 bundle 形态共享同一份 `cordis.patch.yml` 语法。
- 这正是 cordis-tutorial 07 + publish.md 的"从零写插件"路径。

### 4.5 🔴 装载耦合点（宿主版本 churn 风险，必须列入维护审计）
1. **Patch 无法改 `name`/`id`**（L2 §11.1 已核 `vendor/include/src/index.ts:57`）：不能把内置 `dsh-agent-loop` 换成自建包——只能 `insert` 新包或改 `config`/`disabled`。→ 我们**不碰 loop**，与初筛 F1/F2 一致。
2. **包解析层是 symlink**（L2 §11.2）：profile `node_modules` 里 `@deepseek-ai/dsh-*` 指向 app bundle。→ 若硬要替换单包，可改 symlink（未实测，标待确认）；但官方路线是 A 的 insert，不依赖此 hack。
3. **桌面壳独占 desktop profile**（architecture.md:51-58）：公共 CLI **不能**管理 Desktop profile（"The public CLI cannot manage Desktop's profile"）。→ 若 E2 走桌面发行版，装插件须用 Desktop 自己的包操作（plugin-manager 已知限制："Desktop package operations remain owned by the Desktop shell"），或用 web profile 自建壳。
4. **HMR 缺失时改配置需重启**：headless/sdk/acp 关 HMR（architecture.md:43）。web profile 默认开。
5. **`dsh --profile web --dump-config`**：可打印本机启动的插件树，"任一行都能被你自己的 patch 替换"（architecture.md:47）——**装完后用它校验 6 包是否真挂上**。

### 4.6 双半插件（浏览器侧）机制 —— `extensions/cordis-client-runner`
- 这是 §3 标③的 `extensions` 包，现已查明：**"动态双半插件包"的浏览器一半**（README 原文）。
- 机制：一个动态包可含 host 半（进程内，普通 Cordis 插件）+ browser 半（页面内纯 JS，`React`/`console`/`styles`/`host` 注入；无 JSX/TS/模块导入）。
- 页面在**批准后请求或用户手势**后才加载 browser 半，Host 撤回即移除；**页面刷新不恢复**（需重新授权）。
- **对 C1-C4 客户端插件的意义**：mermaid/Live2D/白板/侧栏若需 in-page 渲染，应走"双半插件"——host 半接 `conversation.chat.node`（cookbook 行24）+ browser 半做渲染。`ui-cordis` 负责渲染面板/卡片（README 引）。**这是 C 类 UI 插件的官方落地形态**，L4 在查落点。

### 4.7 settings 包定位
- `packages/settings/settings` = 抽象用户设置 seam（`ctx.settings`），非装载器本身。装载/补丁逻辑在 `boot/app-boot` + `boot/plugin-manager`。
- 我们的教室设置（如"当前教室/相位开关"）可复用 `ctx.settings` + `adding-a-settings-card.md` 加设置卡。

**§4 结论**：装载机制**完全官方化、无黑魔法**。6 包=6 个 bundle，用 `dsh plugin add` 装进 web profile（或 dev 期 `--patch` overlay）。红线只有两条：① 不能换内置 loop 包（用 insert 而非 patch 替换）；② 桌面壳 CLI 不可管，需走 web profile 或 Desktop 自有操作。HMR 让 config 级迭代免重启。

## §5 apps/web 能否脱离 dsh-desktop 壳独立跑
**结论：能。** `apps/web` 是纯前端 Vite 应用，由 `apps/cli` 的 `dsh web` 命令提供服务，不依赖 Electron 桌面壳。

- `apps/web/package.json:2-3`：`@deepseek-ai/dsh-web-frontend`，描述 "Web application entry: vite build over the @deepseek-ai/dsh-client-web shell library; dist/ served by apps/cli's `dsh web`"。
- 脚本（apps/web/package.json:24-28）：`build`=vite build、`dev`=vite —— **纯前端构建**，无桌面壳依赖。
- 桌面壳本质（`apps/desktop/README.md`）：Electron 只是"完整 dsh Web 应用的壳"——"An Electron RunAsNode child starts the shared profile runner, and Electron immediately loads the packaged Web entry at `dsh-app://app/`"。即 Web 应用本身先存在，桌面只是包了一层 Host IPC + 签名资源。
- **端口佐证**（desktop README）：Web 默认 `3080`，Desktop 默认 `19387`——两者是同一 Web 应用 + 不同 carrier。

**对 E2「自建发行版」的含义**：
- ✅ 最轻路径：**直接用 `dsh --profile web` 跑官方 web 前端**（无需桌面壳），把我们的 6 个 bundle 装进 web profile 即可。这是"不依赖 dsh-desktop 壳"的现成答案。
- ⚠️ 若要定制 UI（C 类侧栏/面板），改的是 `packages/client/*`（L4 在查），重建浏览器 bundle 即可（AGENTS.md：`dev:web` 启动 vite，`pnpm run dev:web | dev:desktop` 说明 web 独立可构建）。
- 🔴 桌面壳**独占** desktop profile 且公共 CLI 不能管其 profile（§4.5(3)）→ 若坚持走桌面发行，**要么**用官方 desktop 壳 + web profile 插件，**要么**fork `apps/desktop`（属于 C 级最重手段，初筛 F2 红线区）。

> 注：本节省略 deep-dive（L4 在查客户端细节）。本结论基于 package.json + desktop README 的 carrier 关系，已足够回答"能否独立跑"。

### 6.2 机制侧**新增**发现（初筛未覆盖，值得补进裁定）
1. **`ctx.sessionProjections`（Projection seam）**——相位状态/教室进度的官方持久化、可回放、崩溃可恢复机制（architecture.md:127，L2 §2.4 已提但未在初筛 A/B 行点名）。→ 建议 B1 相位状态存储**直接用 projection**，而非手写 runtime 文件解析。
2. **双半插件 `extensions/cordis-client-runner`**（§4.6）——C1-C4 的 in-page 渲染官方落地形态：host 半（进程内 Cordis 插件，接 `conversation.chat.node`）+ browser 半（页面纯 JS，批准后加载，刷新不恢复）。→ 初筛 C 类只说"slots"，本普查补上"双半"这一确定性落地路径。
3. **`preset` 包（agent-preset-registry）**——教室"组合 agent"（人格+工具+相位策略）**现成声明式预设机制**（§3.1）。初筛未提；建议把"教室 = 一个 agent preset"作为数据面骨架，比纯 hook 组合更清晰。
4. **`agent-instructions`（context 包）**——宿主自己的指令注入示范（pre-step + 文件读取），**我们的注入引擎应直接扩展它**而非从零写（§3.1 / config-catalog:58）。
5. **`interaction`（commands 包）**——插件拥有的**人类命令注册表**（§3.3③）。教室可能要走 `/teach`/`/grade` 这类 slash command，值得评估是否用 interaction 而非纯 hook。
6. **HMR 让 config 级迭代免重启**（§4.5）——6 包开发中改 `cordis.patch.yml`/config 即时生效，降低维护成本（初筛 §3 提到"维护成本"但未利用此点）。

### 6.3 重申结论（支撑"哪些做成插件"）
- 初筛的全部 A/B/C/D 裁定在官方对照表里**都有对应行** → **全可插件化，无需改 loop**（cookbook:100"no row modifies the loop"）。
- 唯一 fork 红线仍是"相位改变 loop 控制流"（对照表无行）——而教学相位是 pre-step 注入 + projection 状态，**不碰 loop** → **fork 红线实际为空**（F1/F2 维持不用/待 L4）。
- 自建面集中在：① 注入引擎（扩展 `agent-instructions` + 新 hook 插件读教室 manifest）；② 相位机 hook + projection；③ UI 双半插件。其余（记忆/存储/子代理/工作流/工具/计划/调度）**全复用现成 seam/包**。
