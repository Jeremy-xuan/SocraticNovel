## 〇 · 先说结论

**跑通了。** 用一张静态立绘（PNG），**不装任何新依赖、不下任何模型权重、不用 GPU**，
产出**可播放的 MP4 ＋ GIF**，并能看出眨眼、口型、呼吸、头发摆动：

| 交付物 | 路径 | 规格【实测】 |
|---|---|---|
| 待机 | `out/anim_idle.mp4` | 1024² · 30 fps · 90 帧 · 3.0 s |
| 说话 | `out/anim_speak.mp4` | 同上（口型开合 73/90 帧） |
| 写字（嘴不动） | `out/anim_write.mp4` | 同上（口型 0 帧） |
| 三合一 | `out/anim_all_modes.mp4` | 1024² · 30 fps · 270 帧 · 9.0 s |
| GIF 版 | `out/anim_*.gif` | 512² · 30 fps · 90 帧 |

关键数字：**端到端 3 分 39 秒**、**内存峰值 257 MB**、**产出 4.4 MB**、**模型权重 0 GB**、
渲染 **18–74 fps**（详见 §三，本机当时负载 6–9 倍超订）。

**选型结论**：主选 **路线 C（分层 + 程序化摆动）**，备选 **路线 C-2 的浏览器实现（Anime2.5DRig 一类）**。
**路线 A 与路线 B 都出位图/视频帧，不出可驱动模型** —— 与"宿主只吃 `.moc3`"根本不能直接接（详见 §二）。

## 一 · 先读现成实现（prior art）

按项目硬规矩，技术选型先检索并读了同类开源实现。共查**四条路线**，
两份取证底稿：`tmp_p2l1/prior_art_A_D.md`（30.5 KB）、`tmp_p2l1/prior_art_B_C.md`（34.9 KB）。

### 1.1 路线 A —— 单图驱动动漫角色动画（Talking Head Anime 系列）

**代表**：`pkhungurn/talking-head-anime-2/3/4-demo`（THA4 ＝ WACV 2025，[arXiv 2311.17409](https://arxiv.org/abs/2311.17409)）

- **它怎么做**：THA4 论文页 Abstract 逐字 —— *"It takes as input (1) an image of an anime character's upper body and (2) a $45$-dimensional pose vector and **outputs a new image** of the same character taking the specified pose."*
  → **输出是位图帧**（THA2 README：*"will always output a 256x256 image"*），**不产出任何可驱动模型**。
- **输入是单张平图、不需要分层**（约束只有 512×512／带 alpha／单人正视／头落在中间 128×128 框内）。
- **本机能不能跑**：❌ 官方唯一支持路径是 **NVIDIA CUDA**（THA4 README：*"All programs require a recent and powerful Nvidia GPU"*）。
  Apple Silicon 有直接实测证据：THA3 issue #8（M1）—— 源码硬编码 `torch.device('cuda')`，换 `mps` **直接崩**
  （`mps_scatter_along_axis` → `Abort trap: 6`），4 个变体只有 float 两个能跑。
  **未找到任何第三方 Apple Silicon 移植。**
- **代价**：THA3 ≈20 FPS 且**仅 Titan RTX 或更强**；THA4 学生模型 ≥30 FPS、**<2 MB**，
  但**必须逐角色训练**（README：~30 h on RTX A6000；用户实测 RTX 4070 身体模型 10 天只到 37 万/150 万步）。

### 1.2 路线 B —— 人像动画/说话头（LivePortrait 等七个项目）

**代表**：`KlingAIResearch/LivePortrait`（19.1k★）、SadTalker、Wav2Lip、EchoMimic、Hallo、MuseTalk、AniPortrait

- **它们怎么做**：全部**输出 `.mp4`**（或逐帧位图）。LivePortrait 额外产出的 `.pkl` 是**驱动动作模板**，不是角色模型。
  → **没有一条产出可驱动模型。**
- **本机能不能跑**：**七个里唯一官方支持 Apple Silicon 的是 LivePortrait**
  （有 `requirements_macOS.txt`：torch 2.3.0 CPU wheel ＋ `onnxruntime-silicon`，
  跑法 `PYTORCH_ENABLE_MPS_FALLBACK=1 python inference.py`，官方注明 *"maybe 20x slower than RTX 4090"*）。
  SadTalker 有 macOS 文档但主线在 MPS 崩在 `RuntimeError: Conv3D is not supported on MPS`（issue #526）；
  其余五个 README 只写 CUDA 版本要求，**未找到 MPS 说明**。
- **代价**：权重 **2.14 GB（LivePortrait）～ 34.36 GB（EchoMimic）**【第三方 HF API 实测】。
- **对动漫的硬限制**：SadTalker `docs/best_practice.md` 逐字 —— *"Our model **only works on REAL people** … The anime talking head genreation method will be released in future."*
  且它的眨眼是 `--ref_eyeblink` **从参考视频借**，不是从图生成。LivePortrait 官方无此限制，但社区反馈 *"it works, but not good as human or animals"*。

### 1.3 路线 C —— 分层 + 程序化摆动（**本任务选的路线**）

分两段，两段都有现成实现：

**C-1 自动分层（单图 → 分层 PSD）**
- `shitagaki-lab/see-through`（4.1k★，**SIGGRAPH 2026**，[arXiv 2602.03749](https://arxiv.org/abs/2602.03749)）：
  单图 → **最多 23 层**带遮挡补全的 RGBA 分层 PSD ＋ 推断绘制顺序。脸被拆成 7 件（face/eyebrow/eyelash/eyewhite/irides/mouth/nose）。
- **代价**：torch 2.8.0+cu128、**CUDA**、1280 分辨率需 12–16 GB VRAM；权重 **14.7 GB**【第三方 HF 实测】。
  → **本机跑不了本地推理**；官方给了旁路：HF ZeroGPU demo（每天 1–2 次、每次 2–3 分钟）。
- 🔴 **作者本人对"这是不是 Image-to-Live2D"的官方表态**（README 专节，逐字）：
  *"**We don't think so — at least, not yet.**"* 并明确 ——
  *"**Rigging.** After decomposition, a Live2D model needs a deformation mesh, physics parameters, and motion curves … and **it is not covered in this project**."*

**C-2 分层 → 绑骨 + 摆动（浏览器内 / 无 CUDA）**
- `852wa/Anime2.5DRig`：拖入已分层 PSD → **自动绑骨** → idle 动作＋眨眼＋口型＋头发物理；**纯客户端免安装**；可导出透明 WebM/MP4。
- `MangoLion/stretchystudio`：同类，导出 **Spine 4.0 JSON**（不是 Live2D）。
- `Wzhang3912/image2live2d`（37★）：分层 PSD/图层夹 → **真 `.moc3` + model3/physics3/motion3/cdi3**（`moc3_emit.py` docstring：*"Build a `.moc3` (v3.00) from geometry + parameters"*）。
- `tsunehimatoi/psd2live`（449★）：PSD → 真导出 `.moc3`/`.cmo3`；**仓库里有真产物**，
  文件头已核：`ds.moc3` = `4D 4F 43 33 05 00 00 00`（magic `MOC3` + v5，95,104 字节）。
- `umamoorg/umamo`：开源建模编辑器，**MOC3 读＋写**（兼容到 Cubism 5.4），有 `macos-arm64` 构建；但 FAQ 逐字 *"Does Umamo do animations yet? **Not yet.**"*
- **轻量"假 Live2D"**：`maximus-choi/fake-live2d` —— README 全文一句：*"A trick that fakes Live2D by **scrubbing AI video frames** instead of rigging a model."*

**🔴 "眨眼怎么从单图做出来"—— 已有三条可核做法（都不需要动漫专用眼睑重建模型）**
1. **合成眼睑弧 + 透明度交叉淡入**：`image2live2d` 的 `core/synth/eye.py`，docstring 逐字 ——
   *"paints a shallow lid arc across the eye, in the character's own lash colour … lets the rig **crossfade it in as the eye closes (opacity 0 -> 1)**"*。
2. **内置通用闭眼差分 + 按锚点缩放着色**：Anime2.5DRig 的 `lib/genericparts.js`（无闭眼差分时自动生成）。
3. **几何裁剪法**：`iAJue/CanvasGame` 的「眨眼（**从上往下合眼**）」＝ 从上往下裁剪源图、底边固定。
- **明确没找到**：**"从单张睁眼动漫立绘反推真实眼皮几何"的动漫专用开源模型**。
  （AniEyelid 是 **SIGGRAPH Asia 2024 真人**眼睑，要**多视角采集**，不适用。）
  → 也就是说，**这一环"没有先例"**，各家都是用程序化合成绕过去的 —— 本 PoC 也走同一路。

### 1.4 路线 D —— 真正的 Live2D 自动绑定（静态图 → `.moc3`）

**分三层回答（避免"有/没有"这种会误导的二分）：**

| 层次 | 有没有公开方案 | 证据 |
|---|---|---|
| **① 单张平图 → `.moc3`（端到端）** | ❌ **没有公开可用实现** | 中间缺"单图分层"那一环，而它要 CUDA；且 See-through 作者明确 rigging 不在其覆盖范围 |
| **② 分层素材（PSD/图层）→ `.moc3`** | ✅ **有，且不止一个** | `image2live2d`（有实质 moc3 生成代码）、`psd2live`（**仓库内有真产物，文件头已核**）、`umamo`（MOC3 读＋写）、`Ludentes/py-moc3`（纯 Python 读写） |
| **③ Live2D 官方** | ❌ **没有任何 image→model 功能** | 官方 Editor 手册完整目录通读：自动化只覆盖 Editor 内部局部步骤（自动网格/自动变形器/自动面部动作/自动摇摆/模板套用），**输入前提始终是已分层已导入的 PSD** |

⚠️ **必须强调的限定**：准确说法是"**在本轮实际检索到的公开实现里没有**"，不是"不存在"。
（`AnimeCeleb`/`AnimeRun` 本轮检索未返回可用结果 → 报告对其**零陈述**，没有编造。）

### 1.5 🔴 我们借什么、明确不借什么

| 路线 | **借** | **明确不借** |
|---|---|---|
| A（THA） | 什么都**不借**。只借一个认知：**它的输出是位图帧，不是模型** —— 这条决定了它接不上我们的宿主 | 不借它的模型、不借它的训练流程、不借它的 CUDA 依赖 |
| B（说话头） | **不借**（本任务）。若要"预渲染视频 + 帧轴拖动"那种假 Live2D，LivePortrait 是唯一官方支持 MPS 的选项，可作**将来的备选素材源** | 不借它的位图输出当"可驱动模型"；不借它处理动漫（真人训练为主） |
| **C（分层 + 摆动）** | ✅ **借它整条思路**：单图 → 分层 → 程序化驱动（呼吸/眨眼/口型/摆动）<br>✅ 借 `image2live2d` 的**眼睑弧合成 + 交叉淡入**思路（本 PoC 用了同思路，见 §三）<br>✅ 借 `iAJue/CanvasGame` 的"**从上往下合眼**"几何思路（本 PoC 演化成 lid wipe） | ❌ 不借 See-through 的**权重**（14.7 GB / 要 CUDA）<br>❌ 不借 Anime2.5DRig / Stretch Studio 的**运行时**（本任务只做 PoC，不引入前端依赖）<br>❌ 不借它们的分层**精度假设**（我们的素材是平色块，用不上模型分层） |
| D（自动绑定） | 只借**结论**：单图→moc3 无公开实现；分层→moc3 有（将来若要走 `.moc3` 宿主，起点是 `psd2live`/`image2live2d`） | 本轮**不借**任何 `.moc3` 生成器（会引入 Java/Python 新依赖与 GB 级下载，按任务纪律"先报告再等"） |

**🔴 本任务自研的部分（明确标注"没有先例"）：**
1. **"按调色板精确分类 + 连通域锚点 + 水平游程"的自动分层** —— 这是**为本素材形态专门做的**。
   别人的自动分层是**学习式**的（See-through，要 CUDA/14.7 GB）；我们这个不需要模型，
   但**代价是只对"平色块 + 唯一色"的画风成立**（见 §六 边界）。
2. **lid wipe（眼皮＝皮肤，从上往下推进）** —— 别人的做法是"交叉淡入"或"裁剪"；
   我们改成"皮肤往下推进"，因为实测交叉淡入会**混出调色板外的脏色**（见 §三坑⑦）。

## 二 · 选型结论

按任务给的三条评：**① 能不能真的让静态立绘动起来 ② 能不能嵌进我们的教室面板 ③ 能不能表达我们要的特征（说话时嘴动、写字时嘴不动）**。

| 路线 | ① 真能动 | ② 能嵌面板 | ③ 说话/写字语义 | **输出形态** | 本机可跑 |
|---|---|---|---|---|---|
| A THA | ✅ 能动 | ⚠️ 要换整条渲染管线（宿主只吃 moc3） | ✅ 可（pose 向量） | **位图帧** | ❌ 要 torch + 只能 CPU，MPS 崩 |
| B 说话头 | ✅ 能动 | ⚠️ 只能当预渲染视频 | ⚠️ 要音频驱动，口型与"写字闭嘴"不是一回事 | **视频/位图** | ⚠️ 只 LivePortrait 官方支持 MPS，2.14 GB |
| **C 分层+摆动** | ✅ **能动（已跑通）** | ✅ **能（就是画布/图层）** | ✅ **能（模式直接映射相位）** | **位图帧（合成）** | ✅ **完全可跑，零权重** |
| D 自动绑定 | ✅ 若能生成 moc3 | ✅ 直接复用宿主机制 | ✅ 参数化 | **`.moc3`** | ❌ 单图路径要 CUDA；分层路径要新依赖 |

### 🔴 主选：**路线 C —— 分层 + 程序化摆动**

**理由（逐条对任务的三条评）**
1. **它是本机唯一"今天就能真跑通"的路线**，而且是**唯一零权重**的（0 GB vs 2.14–14.7 GB）。
2. **输出形态与教室面板天然同构**：它出的就是**图层＋每帧变换**，面板的立绘舞台本来就是一个 canvas。
   而 A/B 出位图视频、D 出 moc3 —— 两者都要**换掉面板的整合方式**。
3. **能精确表达教学语义**：说话时口型开合、**写字时嘴不动** ——
   这正是面板 `PHASE_STATES` 里 `answer`/`check` 相位走 `write` 通道的教学要求，
   本 PoC 的 `write` 模式**直接就是那个语义**（口型帧数 = 0，已程序化断言）。

### 备选：**路线 C-2 的浏览器实现**（Anime2.5DRig 一类）

**理由**：本 PoC 的渲染器是 **Python/PIL 的"离线产出"形态**（18–74 fps，受负载影响大）。
**产品里要在浏览器实时驱动，必须移植成 canvas/WebGL** —— 而这条路上**已经有现成开源实现**
（Anime2.5DRig 纯客户端、免安装、自动绑骨、含眨眼/口型/头发物理）。
**备选价值**：它验证了"这套东西在浏览器里能实时跑"，是我们移植时的**参照实现**（而不是要引入的依赖）。

### 为什么**不选** A / B / D 作主选

- **A、B 的根本问题**：🔴 **它们输出的是"视频/位图序列"，不是"可驱动的模型"。**
  这不是性能问题，是**形态问题** —— 我们现有宿主只吃 `.moc3`，
  接 A/B 就等于**放弃现有宿主、换一套逐帧渲染管线**，代价远大于收益。
  且两者在本机都有硬障碍（A 要 CUDA／B 要 GB 级权重）。
- **D 的根本问题**：**单图 → `.moc3` 目前没有公开可用实现**（§1.4）。
  真要走 D，得先解决"单图分层"（要 CUDA），再引入 `.moc3` 生成器（新依赖 + GB 级下载）——
  **按任务纪律"先报告再等"，本轮不做**，列为 §五 的待决项。

## 三 · PoC 结果与数字

### 3.1 输入素材（**来源已声明**）

🔴 **本 PoC 的立绘是"用代码画出来的"**（`scripts/00_gen_source_portrait.py`）：
- **不是下载的、不是 AI 生成的、不是任何现成作品的截图。**
- 为什么自己画：① 手上没有"合法可用 + 分层已知"的动漫立绘；② 用代码画 → 每个语义区域颜色**唯一**，
  自动分层才有一个可核对的答案。
- ⚠️ 它**不代表产品要用的美术风格**，只代表"一张静态位图"这个输入形态。
- 原计划用图像生成模型产出一张，但**图像生成额度不可用**（`Codex image generation quota is unavailable`），
  故改为代码绘制 —— 这条已在素材声明里写明。

### 3.2 分层结果（**无损校验通过**）

9 个图层，**按序合成后与输入位图逐像素完全相同**【实测 `out/layers/manifest.json`】：

|---|---|---|
| torso | 132,694 | 呼吸/整体位移（兼**兜底层**） |
| bangs | 64,433 | 摆动 |
| face | 51,717 | 跟随头部 |
| side_l / side_r | 29,082 ×2 | 摆动 |
| hair_back | 8,666 | 摆动 |
| eye_l / eye_r | 2,902 ×2 | 眨眼 |

校验明细：人物像素 **1,048,576 全画布**中未覆盖 **0**、不一致 **0**、背景被碰 **0**、重复覆盖 **0**。

### 3.5 🔴 失败项与踩坑（**如实报**）

**本轮没有"跑不通"的失败项** —— 主路线 C 从头到尾跑通了。但过程中**踩了 10 个真坑**，
每一个都曾让产出"看起来对、其实错"，全部已修并写进代码注释与 README §五。按危害排序：

| # | 坑 | 现象（**实测数字**） | 正解 |
|---|---|---|---|
| ④ | **图层内部有透明洞** | 图层是**互补**的（face 在嘴处是洞 868 px、bangs 在额头处是洞 12,616 px）→ `alpha_composite` 遇 alpha=0 不填色 → **背景色从人物内部冒出来**（最差帧 **3315 px**，连嘴、衣领、头发上都有） | 合成前把每层的洞按**最近不透明像素色**填满（一次距离变换）→ 降到 **85 px** |
| ⑦ | **眨眼"压扁+交叉淡入"混出脏色** | 半闭帧是半透明虹膜压在皮肤上 → 实测出现 `(151,166,184)`、`(134,116,105)` 这类**不在调色板里**的灰蓝/灰褐 | 改 **lid wipe**：眼皮＝皮肤，face 层皮肤色从眼睛上沿**往下推进** → 脏色降到 1322 |
| ⑧ | **三角波眨眼采样不到峰值** | 0.14 s 眨眼 ≈ 4.2 帧，峰值落在两帧之间 → 采样峰值只有 **0.70**，画面上永远"闭不严" | 不"造波形再采样"，**对每帧直接算平滑凸包** → 峰值 **0.985** |
| ① | **用"最近色"分类** | 背景灰 `(232,232,235)` 与眼白 `(255,255,255)` 距离仅 ~40 → **整个背景被判成眼白**，"眼白连通域"变成 **13 万像素**一整块，眼睛根本找不到 | 必须**精确相等**匹配；非调色板颜色直接报错 |
| ② | **两张降采样图混用** | 用 LANCZOS 版取色、NEAREST 版分类 → 边界像素上两张**必然不同**，无损校验假失败 **13,144 px** | 分类与取色/校验**共用同一张** |
| ③ | **图层外接框太紧** | 眼框＝虹膜 bbox + 固定 pad：pad 小则描边漏 **528 px**；pad 大则**把眉毛吃进眼层**（眨眼时眉毛消失） | 改"眼球像素有界膨胀 + 上沿钉在虹膜上缘" |
| ⑤ | **逐条规则认领必然漏** | 衣领描边（line 色）既不在脸层也不在嘴/眼框里 → 漏 **436 px** | 把"人物像素必须被覆盖"写成**结构性不变量**：躯干作底层**兜底** |
| ⑥ | **头部件各自大位移 → 开白缝** | 侧发与脸是同一块头发切成的**前后两片**，各自位移就错开露底（amp=7 px 时出现整条白缝） | 头部件**刚性同动**，摆动幅度压到 2.2–3.0 px |
| ⑨ | **填洞后外接框失效** | 填洞把 alpha 全置 255 → `getbbox()` 返回整张画布 → **渲染从 87 fps 掉到 8.5 fps** | 外接框必须在**填洞之前**用原始 alpha 算 |
| ⑩ | **开缝判据用"实心内部出现背景色"** | 静止立绘在轮廓内部本来就有**合法背景凹口**（首帧就有 2,511 px）→ **假阳性**，把好产出判成坏的 | 必须用**差分**判据：某帧是背景、而静止立绘在该处不是背景 |

**另外两条与"失败"相关的如实记录**：
- **图像生成额度不可用**：原打算用图像模型产立绘，报 `Codex image generation quota is unavailable` → 改代码绘制（已声明）。

## 四 · 与现有体系的接线说明

> ⚠️ **本节只写接线说明，不动任何别人的树**。以下行号取自
> `code/clients/classroom-ui/lib/client.js`，**读取时 sha256 = `10efcc450ded17a003ad7988af04c059a2cfefb28375a526f78f6a86b8f5ff41`**。
> 🔴 **该文件正在被另一条工作线改皮肤**（本轮期间它已从 `f0a6356a…` 变到 `10efcc45…`），
> **行号会漂 → 改之前先按引用的代码原文重新定位，别按行号硬改。**

### 4.1 我们的输出是**位图帧**，不是 `.moc3` —— 这决定了整合方式

| 现有宿主（`.moc3` 路线） | 本 PoC（位图帧路线） |
|---|---|
| 装载 Core（`live2dcubismcore.min.js`）→ 装载 framework bundle → 装载 `.moc3`+贴图+shader | **不需要** Core、不需要 framework、不需要 `.moc3` |
| 能力发现（`parseCapability`）读 `lipSync` / `expressions` / `phaseExpression` | **不需要** —— 没有"参数"这个概念 |
| 嘴型走 `TextRhythmProvider` / `WriteChannelProvider` 写**参数值** | 口型是**模式**（idle/speak/write），不是连续参数 |
| `applyPhase()` 按下标换**表情** | 相位→**模式**映射（见 4.3） |
| 渲染在 WebGL 里逐帧变形 | 逐帧**位图合成**（本 PoC 在 Python 里做；产品里应移植到 canvas/WebGL） |

🔴 **所以：`.moc3` 那套"能力发现/嘴型"机制在本路线上不能复用** ——
它复用的是**别的东西**：`readBinary` 资源通道（§4.4）与相位语义（§4.3）。

### 4.2 面板要怎么显示它（与现在"立绘 canvas"的关系）

**现状**【源码 `lib/client.js`】：
- 立绘舞台是一个 **`<canvas>`**（`width/height = PORTRAIT_CANVAS_SIZE`，`data-classroom-ui-portrait="canvas"`），
  由 `mountPortrait()`（`:1154`）装载 `.moc3` 并起 WebGL 渲染循环。
- 立绘资源根 = `live2dRoot()`（`:855`），默认 `DEFAULT_LIVE2D_ROOT = "开源线/DSH定制/code/clients/live2d-host/out"`（`:99`）。
- 资源按 session 缓存（`assetsFor`，`:1120`），**立绘缺一块资源就整块失败、不静默降级**。

**三个可选接线方案（按推荐度排序）：**

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **① 换掉装载源（推荐）** | 保持那个 `<canvas>` 不动。新增一条"位图帧源"：把本 PoC 的**图层 PNG + 每帧变换参数**读进来，在 canvas 2D 里按同一套公式合成 | 舞台 DOM、皮肤、尺寸全不动；相位语义照用 | 要把 Python 渲染公式移植成 JS（见 §4.5） |
| ② 替换成 `<img>`/`<video>` | 直接把 `out/anim_*.mp4` 当视频源，`<video autoplay loop muted>` 叠在舞台上 | **最省事，今天就能看** | 只有循环播放，**不能按相位实时切换**；写字的"嘴不动"只能靠切视频 |
| ③ 新开一块 | 立绘舞台旁边另开一块显示位图动画 | 与现有立绘零冲突 | 面板出现两个"人"，产品上讲不通 |

**推荐 ①**，**② 作为过渡/演示**（本轮证据本身就是 ② 的形态：MP4/GIF）。

### 4.3 相位 → 模式的映射（**这是最顺的一处**）

面板现有 `PHASE_STATES`（`lib/client.js:1086`）已经把"相位→立绘状态"定好了，
本 PoC 的三个模式**正好对得上**：

| 面板相位 | 面板现有语义【源码】 | 本 PoC 模式 | 说明 |
|---|---|---|---|
| `open` / `probe` / `review` / `close` | `channel: "speak"` | **speak** | 说话：口型开合 |
| **`answer`** | `channel: "write"`，注释逐字："**学生作答：退让——嘴不动（通道 write）**" | **write** | ✅ **完全对应** |
| **`check`** | `channel: "write"`，注释逐字："**对答案：通道切 write（写字时嘴不动）**" | **write** | ✅ **完全对应** |
| 相位未提供 | `IDLE_STATE`："默认待机（呼吸 + 眨眼，不改表情）" | **idle** | ✅ 完全对应 |

🔴 **也就是说：面板"说话时嘴动、写字时嘴不动"这条教学要求，本 PoC 已经用"模式"表达出来了**
（`write` 模式口型帧数 = 0，已程序化断言）。**接线时不需要改面板的相位表**，
只需把 `channel: speak|write` 映射到本 PoC 的 `speak|write` 模式。

### 4.4 资源通道**可以复用**（`readBinary`）

面板读立绘资源走的是 `readBinary(remote, sessionId, path, signal)`（§6.5 那一节），
支持**工作区相对路径**、按 session 缓存、失败即整块失败。
→ **本 PoC 的图层 PNG 可以直接走这条通道**：
把 `portrait2live/out/layers/*.png`（9 张，共 160 KB）与 `manifest.json` 放进
`live2dRoot()` 同级的资源根，用同一套 `readBinary` 读进来建 objectURL 即可。
**不需要服务端配合**（与 P3 的 `ctx.remote.workspaceFiles.read` 是同一条现成通道）。

### 4.5 🔴 若输出是"真 `.moc3`"（将来走 D 路线时）

**那时 `.moc3` 那套现有机制可以直接复用**，而且是**完全复用**：
`loadCore`（`:1042`）→ `loadFramework`（`:1069`）→ `assetsFor`（`:1120`）→ `mountPortrait`（`:1154`）
→ `parseCapability` 能力发现 → `applyPhase`（`:1299`）相位换表情 → `setChannel`（`:1319`）嘴型通道。
**一行都不用改** —— 因为那套机制本来就是按"只吃 `.moc3`"设计的。
**唯一要改的是资源**：把 `DEFAULT_LIVE2D_ROOT`（`:99`）指向新的模型产物目录，
以及 `modelName()`（`:862`）指向新模型名。

## 五 · 到产品里还差什么（分条，能照着排活）

按"能照着排活的颗粒度"分条。**P0 ＝ 不解决就不算产品可用**。

### P0

1. **把渲染器从 Python 移植到浏览器 canvas/WebGL。**
   本 PoC 是 Python/PIL 的**离线产出**形态（18–74 fps，受机器负载影响大）。
   产品要的是**按相位实时驱动**。移植范围＝`20_animate.py` 的 `compose_frame` 那 9 层合成与 4 个驱动公式
   （呼吸正弦 / 眨眼凸包 / 口型节奏 / 摆动延迟跟随），**公式本身可原样搬**。
   ⚠️ 移植时**必须一起搬**：lid wipe（别退回交叉淡入，会出脏色）、头部件刚性同动（别各自位移，会开缝）、
   图层洞填充（别直接用互补 alpha，背景会透出来）。
2. **真实美术立绘的分层。**
   本 PoC 的分层**只对"平色块 + 唯一色"画风成立**（因为它是按调色板精确分类的）。
   真实手绘立绘（渐变、厚涂、无唯一色）**这套分层会失效**。
   差的是：**要么走 See-through 那类学习式分层**（要 CUDA / 14.7 GB 权重，或走官方 HF Space 每天 1–2 次），
   **要么人工分层**（画师按 Live2D 惯例切 PSD）。**这是一条独立的工作线，不是本 PoC 的延伸。**
3. **闭眼/闭嘴素材的生产方式。**
   本 PoC 的闭眼、闭嘴两张小图是**程序化新画的**（原立绘里没有这两张画）。
   真实产品里应由**画师出闭眼/闭嘴差分**，或走"按角色线稿色自动合成眼睑弧"（`image2live2d` 的做法）。
   ⚠️ 这是**美术产能问题**，不是算法问题。

### P1

4. **口型的驱动源接上真实文字节奏。**
   本 PoC 的口型是**程序化节奏**（两个频率叠加 + 停顿）。
   面板侧已有 `TextRhythmProvider`（`live2d-host/src/text-rhythm-provider.js`），
   它把"正在流式输出的文字"转成节奏 —— **该 provider 的节奏信号可直接喂给本 PoC 的口型公式**（要写一个 JS 适配）。
5. **表情/差分切换。**
   本 PoC 只有"睁眼/闭眼"一对差分，**没有多表情**。
   面板的相位→表情（6 个相位按下标取）在**位图路线**上需要"每个相位一组差分图"，否则相位→表情失效。
   → 要么画师出 6 组差分，要么在位图路线上**放弃相位→表情**（只保留相位→模式）。
6. **性能与内存预算落到面板里。**
   面板是 Web GUI，本 PoC 是离线脚本。要测的是**浏览器里 9 层 canvas 合成的实际 fps 与内存**
   （本机 Python 是 257 MB RSS，浏览器侧应显著更低，但**未测**）。

### P2

7. **多角色/多老师。** 本 PoC 是单角色。`classroom.yaml` 里换老师时，需要"一位老师一套图层"。
8. **素材流水线化。** 现在分层是"针对一张图调好的规则"；要多张图，需要把 `10_segment_layers.py` 的
   锚点规则做成**可配置**（调色板由素材提供），并**自带失败检测**（分类失败即报错，不静默错分 —— 这条已经做了）。
9. **若最终要走 `.moc3` 宿主**（即路线 D）：起点是 `psd2live` 或 `image2live2d`（分层 PSD → `.moc3`），
   **需要先报告再决定**（引入 Java/Python 新依赖 + 要验证产物能否在我们宿主里加载）。
   ⚠️ 三家 `.moc3` 生成器**均无第三方独立复现**，必须自测。

   要下 ~2 GB 依赖 + 2.14 GB 权重，且官方自述比 RTX 4090 慢约 20 倍。
   **按任务纪律"先报告再等"，本轮未做**；是否值得做，由主代理/用户决定。
6. **【待确认】是否要试 `psd2live` / `image2live2d` 生成 `.moc3`。**
   需要新依赖（Java 21 或 Python 包）+ 验证产物能否在我们宿主加载。
   若能成，则"现有 `.moc3` 机制可完全复用"（§4.5）这条价值很大。**需先报告再决定。**
7. **【待确认】本机空闲时的真实 fps。**
   本轮测量受 6–9 倍超订污染，无法给出干净上限。若需要准确数字，应在机器空闲时重测
   （命令：`bash run_all.sh`，看 `out/perf_ledger.json`）。
8. **【待确认】素材风格与产品风格的差距。**
   本 PoC 的立绘是"代码画的平色块动漫胸像"，**不代表产品要用的美术风格**。
   产品要什么画风（厚涂/赛璐璐/写实），会影响分层方案的选择。
