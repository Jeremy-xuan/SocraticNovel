## 一 · 一句话结论

**通了。** Avalon 皮肤的两半（宿主半边 ＋ 浏览器半边）在 `dsh 0.1.7-rc.2` 上**装载成功、宿主起得来、浏览器半边渲染成功、运行期零报错**；
它**自己声明要 `>=0.1.5-rc.1`**，我们这版在范围内。

但它**不含任何图像/音频素材**（见 §四）→ 装上去是一个**能跑的空壳**：立绘、背景、UI 贴图全部 404。
**它的价值是"骨架与机制"，不是"现成的皮肤"。**

## 二 · 装载链路（逐步可复算）

```bash
# ① 隔离 harness（只拷 profiles 层，不拷 sessions/storages）
ISO=/tmp/avalon-recon
rsync -a "$DSH_HOME/profiles" "$ISO/dsh-home/"
export DSH_HOME=$ISO/dsh-home

# ② 从出厂 web 模板新建 profile（会带上 dsh-base ＋ dsh-web-app，见下"关键"）
dsh --profile avalon --from-default-profile web

# ③ 基线预检（组合 profile 但不启动应用）
dsh --profile avalon --dump-config   # → exit 0，291 个条目

# ④ 装皮肤（file: 协议，本地包）
dsh plugin --profile avalon add file:$ISO/skin-src

# ⑤ 装后预检
dsh --profile avalon --dump-config   # → exit 0；末段出现 skin-mahoyo

# ⑥ 真启动（换端口，别撞在跑的桌面实例）
dsh --profile avalon --port 4399 --no-open
# → dsh web: http://127.0.0.1:4399/?token=<每次重启都变>
```

### 关键 ① · `--from-default-profile web` 建出的 profile **自带 `dsh-web-app`**

实测 `profiles/avalon/package.json` 的 bundles 是：

```json
"bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"]
```

> 📌 这**修正**了 2026-09-28 那条记录（"`dsh plugin add` 建出的 profile 只有 base、起不了 UI"）。
> **差别在建法**：`plugin add` **隐式**建 profile vs `--from-default-profile web` **显式**从 web 模板建。
> **要起 UI 就用后者**；用前者要手工补 `@deepseek-ai/dsh-web-app`（它从 **harness 级** node_modules 解析，名字进 bundles 就够）。

### 关键 ② · `plugin add` **这次没有把 `dsh-web-app` 踢出 bundles**

装后 bundles 实测为：

```json
["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-skin-mahoyo"]
```

> 📌 与 2026-09-24 那条"`plugin add` 会重算 bundles、把没声明 `dsh.bundle` 的插件踢出去"**不冲突**：
> 这次被装进去的皮肤**声明了** `dsh.bundle.patch`，所以它进得来；而**同批没声明的**（如 `socratic-test`）当时被移出。
> → 结论不变：**每次 add/remove 之后都要核一遍 bundles 名单**（本次已核，见上）。

### 关键 ③ · 皮肤自己的启动保险没白写（我们直接受益）

| 保险 | 它怎么做的 | 本次实测 |
|---|---|---|
| 包**解析不到** → 整个 profile 起不来、代码兜不住 | 文档 §11 明写 | 反过来证实：**装好后 `--dump-config` exit 0** 就说明组合是好的（这就是他们的"第一层预检"） |
| 宿主半边 `apply()` 抛错 | 逐层 try/catch ＋ 逐项降级 | 启动日志无皮肤相关报错 |
| 浏览器半边渲染崩 | 错误边界 ＋（我们未测的）紧急开关 | `pageerror` 0 条 |
| 全崩 | `SAFE_MODE` 文件存在＝皮肤等于没装 | 未测（本轮不需要） |

## 四 · 🔴 真正的阻塞点：**仓库里没有素材**

| 类别 | 应有 | 仓库内实际 | 结论 |
|---|---:|---:|---|
| 图像（`assets/bg` 13 ＋ `sprite` 136 ＋ `ui` 128 ＋ `ui/conf` 80） | **357** | **0** | ❌ 缺失 |
| 音频（`assets/bgm` 16 ＋ `assets/se` 7） | 23 | **0** | ❌ 缺失 |
| 仓库内总图片 | — | **5 张**（全是 `screenshots/` 的效果图） | 不可用 |

`.gitignore` 逐行写着 `skin/assets/*`（仅放行 `.gitkeep` 与 `README.md`）→ **这是有意为之**，不是打包失误。

它自己的 `ASSET-RECOVERY.md` 逐字给了两条路：

- **音频（23 个）**：✅ **可从原著重建且完全可靠** —— `.hw` ＝ "64 字节头 ＋ 完整 OGG"，切头即得合法 `.ogg`，**不需要解码器**。
- **图像（357 个）**：❌ **不能从原著直接重建** —— 原著图像存在 `.hfa` 归档里，是私有 `.mzp`/`.cbg`，**解码代码不在仓库内**（其 `hfa_png/convert.py` 依赖的 `mahoyo` 包在整个仓库／pip 环境／pip 缓存里都不存在）。
  - 路线 A：拿到**解包产物** `hfa_png/out/`（24284 张 / 13 GB）→ 可全部复现、已逐像素验证；
  - 路线 B：有原著 `.hfa` ＋ **自备 `.mzp`/`.cbg` 解码器**（社区有 MIT 实现 `nike4613/MahoyoHDRepack` 可参照）；
  - 最省事：找作者要一份装配好的 `assets/`。

> **对我们的直接含义**：**"复用地基" ≠ "复用它的皮肤成品"。**
> 拿不到素材时，Avalon 能给我们的是**骨架与机制**（§五），视觉必须由**我们自己的素材 ＋ 暖纸配色**生成 ——
> 而这恰好是原计划的方向（我们本来就要换配色）。

## 五 · 值得借的机制（照抄级，都有本次实测支撑）

| # | 机制 | 它怎么做的（我们核过的事实） | 我们怎么用 |
|---|---|---|---|
| 1 | **自建根容器，与插槽系统解耦** | 根挂 `document.body`，`#myh-skin-root`，`position:fixed; inset` 铺满，`z-index:900`；DSH 原生 UI 仍在下面 | 舞台**整屏接管**的落点：**不进任何插槽** → 天然绕开"`root` 是 single 槽会顶掉 AppFrame"与"`shell.overlay` 一次抛错永久崩"两条红线 |
| 2 | **根节点 `pointer-events:none`** | 实测 `none`；交互元素各自 opt-in | 直接照抄（这是官方 overlay 那条坑的解法） |
| 3 | **两个半边** | `lib/index.js`（宿主 Node：静态路由 `GET /moye-skin/assets/*` **loopback-only**、设置持久化、人格注入）＋ `lib/client.js`（浏览器整屏 UI） | 我们同理：宿主半边管**素材路由 ＋ 教室配置**，浏览器半边管**舞台** |
| 4 | **无构建的手写产物** | `__ModuleLoader__.load({id, factory})`，只 `require` 种子（react / react/jsx-runtime / react-dom/client） | 照抄（本项目已实证过这条路） |
| 5 | **逃生门（整屏接管必须带）** | `Ctrl+Shift+M` 就地关、`Ctrl+Shift+U` 恢复；关＝删属性＋样式标签＋崩溃占位＋写 localStorage；**关闭态每次加载都弹横幅** | 照抄，且**关闭出口不放 `shell.overlay`**（我们根本不用那个座） |
| 6 | **hooks 排布铁律** | 所有 hook 集中在函数上半段、排在任何 `return` 之前；它们为 React #310 配了三道离线检查（`check-hooks.mjs` / `check-hooks-per-component.mjs` / `render-selftest.mjs`，后者**模拟 `enabled` false↔true 过界**） | 照抄：我们的舞台也是"异步设置到达后可能整棵不渲染"，同一个坑 |
| 7 | **启动前后三层保险** | ① `--dump-config` 预检；② 备份 ＋ 生成一键撤回脚本；③ 浏览器逃生门；外加 `SAFE_MODE` | 我们把它当作**每次改动的固定流程** |

## 五之二 · 同一会话里接着做的：自建「教室舞台」客户端插件（实测通过）

同一条隔离 profile 里又装了我们自己的 `classroom-stage-warm`（`file:` 本地包，两个半边），
**要借的就是 §五 那套机制**。结果与新增的坑：

| 项 | 实测 |
|---|---|
| 装后 profile | `bundles = [dsh-base, dsh-web-app, dsh-skin-mahoyo, classroom-stage-warm]`（**四件全在**，没被顶掉） |
| 预检 | `--dump-config` **exit 0**，末段出现 `classroom-stage-warm` |
| 真启动 | 无 boot 失败；`pageerror` **0**；`slotErrors` **0** |
| 浏览器半边下发 | 宿主 `/stage-static/health` 的 `clientSeen=true`（报到三条：`sensor` / `mount` / `ready`，`warnings` 全空） |
| 传感器落点 | `conversation.input.right`（**list / session / `occupants: []`**）—— 见下面的坑① |
| 整屏渲染 | ✅ 截图 `code/clients/classroom-stage-warm/shots/01-….png` |
| 端到端发送 | ✅ 舞台输入条 → `inputActions.setDraft()` → 下一帧 `submit()` → **用户消息真的出现在会话里** |

### 🔴 本轮踩到的三个坑（每个都花了排查时间，全部写进该包 README 的铁律）

**① 注册进 `conversation.session` 会把 DSH 自己的会话模块打瘫。**
A/B 归因（只注册传感器／只挂根／两者都做）实测：
- **只注册传感器到 `conversation.session`** → `@deepseek-ai/dsh-client-ui-conversation: failed`，
  并级联 **7 个条目 pending**（`waiting for service: uiConversation`），界面直接变成错误横幅；
- 改到 `conversation.input.right` → **`did not activate` 归零**。
→ 规则：**别往"别人已经占着的座"里塞**；要放隐形组件，选 **list 且 `occupants` 为空**的座。

**② 整屏层的 `z-index` 取 900 会被"原生件"盖住 —— 而且 DOM 与样式表全都"对"。**
症状极隐蔽：皮肤根 `position:fixed; inset:0; z-index:900`、DOM 结构完整、`outerHTML` 全对、
`getComputedStyle()` 全对，但
- 截图里**一点都看不到**（像素采样：纸带区域全是 `(0,0,0)`）；
- `document.elementFromPoint()` 在舞台输入框正中心命中的是**原生 hero 输入卡 `uV2eYG_hero`** → **点不进去**。
排查用的三个通道（都留了脚本）：**逐层隐藏做遮挡归因**（藏掉 Avalon → 1.1 MB 全屏图出来了，
纸带 `rgb(243,233,218)` ＋ 立绘 ＋ 背景全部正常）｜`elementFromPoint` 命中测试｜PNG 逐像素采样。
→ 规则：整屏层取 **1080**（在所有应用内容之上、仍在 **DSH 浮层 1100 之下**）。

**③ `z-index` 必须写在"根节点那个 div"上，不是它的子节点上。**
第一版把类给的是 `StageRoot` 返回的那个 div，而 `#stage-warm-root` 只是**外层挂载容器**
（`position:static`、在 body 流末、高度 0）→ 整屏层没有定位上下文，
子件的 `absolute` 是相对**初始包含块**落位的，**看着位置对，其实全靠运气**。
实测读数：容器 `rect = [0, 1050, 1680, 0]`、`position: static`，而内层 div `position: fixed`。

> 📌 坑②③ 同族：**"DOM 对、样式对、就是看不见／点不到"** —— 与项目既有那条
> 「温和症状必须用程序化度量定位」是同一类错误。这次的判据是**像素**与**命中测试**，不是目视。
