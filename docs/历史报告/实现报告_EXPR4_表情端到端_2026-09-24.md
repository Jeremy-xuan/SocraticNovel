## §1 ① 渲染侧那个字段：补成了什么形状、为什么这么补

### 1.1 先看引擎**读什么**（这一步决定形状，不是拍脑袋）

引擎侧唯一的消费点是 `expressionCapabilityFor()`〔A08〕，它取「逐参数路」的可写键清单**只有两条分支**：

- **第一分支**：`Array.isArray(entry.parameters)` → 逐个按 `p => typeof p === 'string' ? p : p?.id` 取 id〔A09〕；
- **第二分支（兜底）**：`Array.isArray(entry.parameterUniverse)` → 当成纯字符串数组〔A10〕；
- 两条都没有 → `paramPath = false`〔A11〕 → 引擎给不出 `face` 参数，**逐参数路在服务端就断了**。

而现盘的能力产物里**只有 `parameterUniverseCount`（个数）与 `parameterUniverseSource`（来源）**〔A03〕——
**个数写不出任何一个值**，所以两条分支都拿不到东西。这正是 EXPR-3 只能"用引擎自己的渲染器造状态文件"的原因。

### 1.2 补的形状：`parameters: [{ id, name }]`（选它、不选 `parameterUniverse: [id]`）

**做法**：在 `parseCapability()` 里，把**函数内部早就算好的那份参数全集**顺手带出去，
形状是 `[{ id, name }]`——`id` 逐字取自 `cdi3.json` 的 `Parameters[].Id`〔A01〕，
`name` 取同一条的 `Name`（**缺名时回落成 `id`**，不让它变成 `undefined`）〔A02〕；
没有 cdi3 时整项为 `null`（**与既有的 `parameterUniverseCount: null` 同口径**——
"没有 cdi3"与"cdi3 里 0 个参数"是两件事，用 `parameterUniverseSource` 区分）。
新键插在 `parameterUniverseCount` **紧后面**，其余键的相对次序与文本一个字都没动〔A04〕。

**为什么选 `parameters`（带 name）而不是 `parameterUniverse`（纯 id 数组）**：

1. 它是引擎的**第一分支**——命中第一分支就不会走到兜底，语义上更"正"；
2. `name` 是白送的（cdi3 里本来就有）：工具描述、面板、状态文件都可以直接说"这个参数叫什么"，
   纯 id 数组则每个消费方都要自己再查一遍 cdi3；
3. **两条分支的取值语义等价**（都只是取 id 字符串），所以**不需要两个都写**——写了就是同一份清单存两份，
   将来必然出现"两份不一致"。**我判不加 `parameterUniverse`**（列入 §8 待确认）。

## §4 ④ 两条口径的核对

### 4.1 参数 id 形状：**两侧逐字全等，不需要任何变换**

**问题**：客户端**不做**参数名形状变换（引擎侧负责归一化）——那"引擎拿到的 id 形状"与"客户端原样匹配"对不对得上？

**做法**（真面板、真模型、不用模型；脚本 `tmp_expr4/shape-check.cjs`）：
① 面板侧按**客户端同一段代码**取运行时模型的参数全表（`model.getParameterId(i).getString()`，〔A41〕——
这正是客户端 `parameterIndexMap()` 的键集〔A24〕）；② 引擎侧读能力产物的 `parameters[].id`；
③ 逐字比较（另一侧要不要"归一后"才相等，用同一个归一键另算一遍〔A42〕）。

| 模型 | 引擎给的 id | 运行时模型的 id | **逐字命中** | 只在一侧出现 | 形状相同但字符串不同 |
|---|---|---|---|---|---|
| **Haru**（驼峰） | 42 | 42 | **42** | 0 | **0** |
| **miku**（全大写蛇形） | 30 | 30 | **30** | 0 | **0** |

**结论：对得上，且是"逐字全等"级别的对得上。** 原因在链路上是**结构性**的：

1. 引擎 `classroom_express` 的 `face` 键**精确校验**：`cap.parameters.includes(id)`，不合法就抛错并列出全部合法值〔A20〕；
2. `cap.parameters` 的 id 逐字来自 cdi3（§1.2），**就是模型自己的 id**；
3. 客户端写值走 `Map<id, index>` 的**精确 `get(id)`**，**不做变换**；形状归一函数只用于**报错提示**〔A25〕；
4. 引擎侧的归一化（去分隔符＋大写〔A13〕〔A14〕）**只用在"兜底"那条路**——它拿表情表里的**正则角色**去匹配模型参数〔A12〕，
   匹配出来写进 `face` 的 id **仍然是模型自己的 id**，所以到客户端依旧逐字命中。

→ **两侧形状天然一致，不需要改任何一侧。**（若将来有人把"兜底"的正则直接当参数名写出去，才会破——
现在没有这条路径。）

### 4.2 客户端画面上应用：覆盖 **2/3** 条手段

见 §3.6：逐参数（模型驱动）＋ 动作组（引擎渲染器驱动）两条在**真面板上真的画出来了**（956 px / 12163 px），
命名表情这一条本轮端到端没跑（回归时用 EXPR-3 的隔离用例复现过，画面确实变了）。
**判为"覆盖 ≥2 条"成立**，但**"模型驱动"只有 1 条**——这条限制必须跟着数字一起读。
