## 0. 一句话结论（先给）

> **1. 用户的判断方向对了一半，但"先开始渲染再讲解"只省得下 3 秒。**
> 实测三段拆开（n=3 真实会话 ＋ 12 个真实脚本）：
> **① 模型写脚本 60.5–73.8 秒（均值 67.3 s）** ： **② 渲染 2.85 秒** ： **③ 落盘+取回 3 毫秒** ≈ **24000 : 1000 : 1**。
> 端到端里**渲染只占约 3%**——"先起渲染"救不了那一分半。
>
> **2. 真正让学生干等的，是"老师先闷头备课、一句话不说"。**
> 实测**学生空窗**（回合开始 → 学生第一次读到可读正文）＝ **17.2–131.4 秒**（8 次真实会话），
> **其中位数 ~54 秒与动画无关**：把动画工具整个拿掉，空窗照样 47–131 秒。
> 空窗里 **97% 是模型在生成**（读教材 ＋ 写脚本），工具执行只占 3.4–4.5 秒。
>
> **3. 所以编排的重点是"顺序"，不是"并行"。** 落地的四件事：
> ① **先讲后画**（工具描述 ＋ 引擎纪律：先给学生讲，再调工具）；
> ② **工具不阻塞**（落盘 → 拉起 detached 渲染器 → 立刻返回）——
>    **学生被这个工具挂住的时长：10 060 ms（同步）→ 8 ms（非阻塞），差 1258 倍**；
> ③ **跨回合就绪通报**（引擎在下一回合开头注入"你上一轮的动画已就绪"）——
>    **真实会话里跑通了**（含 `ready` 与 `blocked` 两条）；
> ④ **失败/被闸门拦下时明说 + 给两条出路**，不许"对学生说正在生成然后不放"。
>
> **4. 引擎侧那半做完了并跑通；客户端播放那半只写了接线说明（没改 clients）。**
> 全量单测 **321 全绿**（基线 297 ＋ 新增 24）；教室不声明 `animation:` 时行为**逐字不变**。
>
> 🔴 **5. 一条必须写明的负面发现：引擎把工具挂上 ≠ 老师会用。**
> 仓库里的教室内容有 **5 处**硬纪律规定"白板内容一律用 `classroom_draw` 画"，**一处都没提动画**
> → 模型在 fifo／interrupt 两个点位上都只画板书图，`classroom_animate` **一次都没被调用**。
> 只在**教室副本**里补了一条动画渠道纪律之后，工具才被用起来（C 组起效）。
> **生产启用需要教室内容侧也补一条**（`code/classrooms/**` 不在本轮可改范围内）。

## 2. 第二步：编排设计（**先写进报告，再实现**——本节即当时的设计稿）

### 2.1 老师想放动画时，该怎么做

按测量结果，**正确做法是"顺序编排"，不是"后台渲染"**：

| 选项 | 采不采 | 理由（对着数字说） |
|---|---|---|
| **先在后台起渲染、告诉学生"正在做"、继续讲、好了再回来放** | ✅ **采**（但"起渲染"不是重点） | 渲染只有 2.85 s，起它只省 3 秒；真正有用的是**工具不阻塞**（否则学生被挂住 10.06 s）与**跨回合把结果送回来** |
| **让动画晚一点播（课间／课后／下一讲开场）** | ⚠️ 部分采 | 不强制，但**引擎支持**：动画在哪个回合就绪，就在**那个回合的开头**通报，老师据此挑时机放。跨回合是常态，不是例外 |
| **先给静态的一帧占位，动态的随后补** | ❌ **不采** | 需要抽帧＋客户端改两处，而它省的是 2.85 s 的渲染——**投入产出比最差**；板书图（`classroom_draw`）已经是现成的"静态替代"，且是**另一条渠道**，不必再做一个半成品占位 |
| 🔴 **把"写脚本的 67 秒"挪到学生已经在听讲之后** | ✅ **采（这是本设计的核心）** | 这一条才是真正的编排：**先讲后画**。写脚本那 67 秒无法消除（模型必须产出脚本），但可以让它发生在**学生已经拿到讲解之后** |

### 2.2 状态从哪来、谁负责（**不需要客户端配合也能跑通**）

**状态机**（只前推，不回退）：`queued → rendering → gating → ready ｜ blocked ｜ failed`

- `ready` 与 `blocked` **必须分开**：两者都"渲染完成了"，但一个可播、一个**不许播**
  （闸门判画面有缺陷）。合并成一个状态＝把闸门拦下来的片子发到学生面前，闸门就白做了。
- `failed` ＝ 没有可播的片子（渲染崩了／渲染器自己死了）。

**落盘**（引擎负责，位置在教室 `runtime/` 下）：

```
<教室目录>/runtime/animations/
├── index.md                  ← 人读索引（一行一个任务，只追加）
└── <taskId>/                 ← taskId = L<讲次>-T<回合>-<yyyyMMdd-HHmmss>
    ├── scene.py              ← 模型交来的脚本原文（逐字，不补不删）
    ├── task.json             ← **宿主写**：讲次/回合/标题/announcedAt（通报幂等门）
    ├── status.json           ← **渲染器写**：**状态真源**（state/renderMs/bytes/durationSec/reason/gate）
    ├── render.log            ← manim 自己的输出
    ├── runner.log            ← 渲染器进程自己的输出（崩溃原因在这里）
    ├── <taskId>.mp4          ← 产物
    └── gate/                 ← 过闸门时的产出（verdict.json / verdict.md / contact_sheet.png / frames/）
```

**为什么这么选（三条都是被实测逼出来的，不是偏好）**：

1. **落 `runtime/animations/` 而不是 `runtime/` 根**：与既有板书图的 `runtime/diagrams/` 同一口径——
   `runtime/` 根下那 8 个文件是**状态文件**（每个都被 `classroom.yaml` 声明为注入块），
   动画是**产物**，混进去会让人以为它们也要被注入。
2. **状态真源是 `status.json`（一个任务一个文件、一个写者）而不是一份总的 `tasks.json`**：
   写它的是**另一个进程**（detached 渲染器）。一份共享文件＝两个进程抢写，得引入跨进程锁；
   一任务一文件＝**天然单写者**，且"读一个任务"不必先读全表。列表用 `readdir` 现算。
3. 🔴 **状态必须落盘、不能只在内存**：宿主是回合制的，进程可能重启；渲染器是独立进程，可能被杀。
   "上一节课的动画好了没"**必须跨进程、跨会话可读**。
   → 这也是**不用 `ctx.jobs` / worker 线程**的理由：`ctx.jobs` 是**内存注册表**，宿主一重启就空。

**老师下一轮怎么知道它好了 —— 引擎推，不靠老师查**：

- 每个回合开头（`agent/pre-step`）引擎调 `pendingNotices()`：终态且 `announcedAt === null` 的任务
  → 拼一条注入块送进本回合的上下文，**同时**标记 `announcedAt`（幂等门，落盘）。
- 为什么必须是"推"：宿主是回合制的，**模型不会无缘无故去查一个状态工具**；
  而"该放动画了"是一个**事件**，事件必须由引擎推过去。
- 老师**也可以**主动查：`classroom_animation_status`（只读）是兜底——
  🔴 **实测真的用上了**：C 组里动画比回合边界晚 6.6 s 就绪，通报没赶上，**老师自己查到了并放了**
  （见 §4.3）。

**不需要客户端配合也能跑通**：状态、通报、就绪判定、失败原因全在引擎侧与盘上完成；
客户端缺席时，老师照样拿到"已就绪"并把它"放出来"（放这个动作在客户端才可见，见 §5 接线说明）。

### 2.3 为什么**不**用"并行线程"这种重方案（够用的论证）

| 备选 | 为什么不用 |
|---|---|
| worker 线程 | 渲染是**跨语言**的（Python/ManimCE），进程边界本来就跑不掉；worker 只能在**同一进程**里并行，而真正要跨的是**回合** |
| `ctx.jobs`（宿主后台作业注册表） | 内存态：宿主重启就空；而"上节课的动画好了没"必须跨进程可读 |
| 让工具**同步**等渲染 | 实测学生被挂住 **10.06 s**；而"先起后收"完全不需要他等 |

**"回合内先起、回合末收" ＋ "跨回合就绪"这两条就够**，因为：
- 渲染 2.85 s（＋闸门 4.5–7.7 s），而模型在工具调用之后**平均还会继续讲 4.0–5.2 秒**
  （实测三例：4.4 / 5.2 / 4.0 s）→ **大部分情况下渲染在同一个回合内就跑完了**，只是"收"的时机在回合边界；
- 跑不完的那部分，**下一回合的注入把结果捞回来**（实测两例：`ready` 与 `blocked`）；
- 两段机制加起来不到 300 行，**没有引入任何新依赖**（渲染器是 Python 标准库 ＋ 已装的 manim）。

### 2.4 失败怎么办

| 情形 | 引擎做什么 | 老师该说什么 | 学生看到什么 |
|---|---|---|---|
| **渲染失败**（`failed`） | 通报里明说"**没有可播的片子**"，带渲染器给的**原因原文**（如 `manim 退出码 1，且没有产出 mp4` ＋ `render.log` 尾部）；并给出两条出路 | 不许说"动画正在生成"然后不放。按原因改脚本重起一段（`classroom_animate`），或改用 `classroom_draw` 画一张板书图把这一步讲完 | 正常的讲解文字；**看不到任何"正在生成"的占位**（引擎不注入占位，客户端也不该显示） |
| **闸门判不通过**（`blocked`） | 通报里明说"**不许播**"＋阻断级缺陷分类（如 `D2`）＋"另有需人工目视确认的项" | 同上：换路讲完这一步，不要放这段片子 | 同上 |
| **闸门自己起不来** | 🔴 **不算通过**：状态落到 `failed`，原因写"质量闸门没能跑起来……片子渲染出来了，但没有过闸，不许播" | 同上 | 同上 |
| **渲染器进程被杀/静默死** | 回合边界结算：**pid 不在 且 心跳停 >60 s** → 前推 `failed`，原因里带上 `runner.log` 尾部 | 同上 | 同上 |
| **脚本被结构性预检拒掉** | 工具**报错**（不是静默失败）：一次列全问题（空/超长/围栏/没有 Scene 子类/用了 LaTeX），**什么都没落盘、渲染器没起** | 模型下一轮自己改 | 学生看不到任何变化 |

## 5. 客户端接线说明（要点；全文见 `code/tools/animation-orch/接线说明_客户端播放.md`）

🔴 **`code/clients/**` 本轮一个字都没改**，下面只是接线说明。

1. **读哪个字段**：消息流里 `source.kind === 'socratic-engine' && source.form === 'animation-notice'`
   的那条消息。**不要解析正文中文路径**——用 `source.taskId / state / artifact / absPath / title / durationSec`。
2. **读哪个文件**：`<教室目录>/runtime/animations/<taskId>/<taskId>.mp4`。
   本项目的正常部署里**学生会话的 cwd 就是教室目录**（教室自己的 `AGENTS.md` 靠这条被注入），
   所以 `source.artifact` 就是**工作区相对路径**，直接走现成通道
   `ctx.remote.workspaceFiles.read(sessionId, 'runtime/' + source.artifact)`（该 API 逐字见
   `packages/api/workspace-files/src/index.ts:227`，P3 已取证）。
   ⚠️ **若教室被配到工作区之外**，这条路走不通，需要另开读取通道 → 标【待确认】，**未取证**。
3. **怎么播**：`state === 'ready'` → 在该行位置内嵌 `<video>`；
   `state === 'blocked' | 'failed'` → **什么都不播**，只显示一行灰字说明。
   🔴 被闸门拦下的片子**文件是存在的**，**只有 `state` 能区分它能不能播**。
4. **播的时机**：引擎把通报注入在**下一回合开头**，客户端按消息流顺序渲染就自动是正确时机，
   **不需要**自己做定时或轮询。
5. **幂等**：引擎侧 `announcedAt` 门保证同一任务只通报一次；客户端可按 `source.taskId` 再去一次重。

| # | 问题 | 选项 | 我的倾向 |
|---|---|---|---|
| 1 | **要不要把 `animation: {enabled: true}` 写进真教室 `cs-os/classroom.yaml`** | ①写 ②不写 | **倾向写**——不写则整条链路在生产里一次都不会触发。但**教室内容不在我可改范围内**，需要用户或内容维护方决定 |
| 2 | **要不要在教室内容里补一条"动画渠道纪律"** | ①补（照 `_anchor.md` 现有 5 处的写法）②不补 | **倾向补**，否则模型一律走 `classroom_draw`（B 组两个点位实证）。补的措辞我写在 `verify/ab-session.mjs` 的 `CLASSROOM_NOTE` 里，可直接取用 |
| 3 | **`animation.spokenFirst`（先开口再备课）默认开还是关** | ①关（现状）②开 | **现状＝关**。理由：n=1 vs n=1 的对照**没有显示它有效，方向还相反**（开 53.5 s / 关 17.2 s 空窗）。**没有证据的行为变更不进默认路径**；开关留着，等更大样本再定 |
| 4 | **空窗这件事本身要不要当成一条独立的编排任务去做** | ①做（把"先开口"做成一条更强的机制，例如引擎先注入一句"先用一句话回应学生"）②不做 | **倾向做**——它是**用户原话里那个痛点的主因**（47–131 s），而且比动画那 3% 大一个数量级。但它**超出了本任务的授权范围**（会改到教学行为），故本轮只测出来、没动 |
| 5 | **闸门要不要默认打开** | ①默认开 ②默认关（现状：不写 `animation.gate` 就不过闸） | **倾向默认开**（闸门判 BLOCK 的片子确实不能播）。现状默认关的理由是：闸门是**另一条工作线正在改的东西**，把它设成默认会让引擎耦合到一个移动目标上；且闸门要 numpy/PIL/scipy 与 ffprobe，**部署要单独配** |
| 6 | **并发上限 2 是否合适** | ①2 ②更多 | 倾向 2：实测一段动画端到端 6.6–10 s，课堂上同时起 3 段以上没有教学意义，且会抢 CPU |
