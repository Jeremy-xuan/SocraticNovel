## 〇 · 一句话结论

**上一版缺的那一块补上了，而且补出来的结论有一条是推翻性的。**

拿到了 **12 类真实界面视图 / 2500+ 帧真实游玩画面**（Steam 社区截图 79 张 + Steam 商店官方截图 10 张 + B站服务端抽帧 2498 帧 + ffmpeg 直取高分辨率帧 22 帧 + YouTube 帧 14 张 + B站封面 27 张）。

🔴 **最关键的一条**（有图有测量）：

> **魔夜的主对话视图根本没有"对话框"。**
> 文字**直接排在全屏画面上**——白色字 + 深色描边，**旧行整体压暗、当前行保持亮白**；文字块上下各一条**发丝花饰**划出文本带；最后一行末尾跟一个**青色梯形推进指示器**——它**跟着文字走**（实测在 x=81.7%、y=53.6%，即画面中部偏右），**不是固定在某个角落**。
> 实测（U1 ＝ `store_09`，1920×1080，官方商店截图）：文字列左起 **x=331（17.2%）**、右至 **x=1539（80.2%）**；行距 **≈80–90px（7.4%–8.3% 屏高）**、换段处 **≈145–155px**；字面高（含描边）**≈44px（4.1% 屏高）**；**文字带内外的行亮度几乎相同（76.0 vs 78.2/71.7）⇒ 文字背后没有底板、没有压暗层**。

这一条**部分推翻了上一版**：上一版从资源里量出 `txtwindow00/01/02.mzp`（60%/51%/40% 黑的整屏层），据此断言"魔夜的对话框＝整屏压暗层"。**资源确实存在，但真实游玩画面里它并不生效**（配置项里有「窗口透过率」〔见 §六·六〕，且官方商店截图里场景是**全亮**的）。**"压暗层是对话框"这个推断，被真实截图否掉了。**

**另有三条要更正上一版的**：① **引擎不是 KiriKiri，是 HuneX**；② **`.hfa` 根本没加密**（"加密"是误诊）；③ **姓名条不存在**（姓名直接排在正文里，没有独立姓名牌）。

### 3.2 通道 A：B站 **服务端抽帧**（`videoshot` API）—— 主力

**这是本次最有效的一条**：B站自己提供视频的**帧雪碧图**，等于服务端替我们抽好了帧。

- 接口：`https://api.bilibili.com/x/player/videoshot?bvid=<BV>&index=1`
- 返回：`image[]`（雪碧图 URL，每张 10×10 格）+ `index[]`（每格的**时间戳秒数**）+ `img_x_size/img_y_size`（单帧 480×270）
- 本机实测：`BV1HW4y1P7KB` → **14 张雪碧图 / 1390 帧**，覆盖 **t=0…9493s**（≈7 秒一帧）；`BV1tceN62EAu` → 12 张 / 1110 帧
- **产出**：`video_frames/bili_frames/`，文件名格式 `<BV>_t<秒数6位>.jpg`，**每帧都能反查视频页与时间点**（`_meta.json` 里存了 `page` = `https://www.bilibili.com/video/<BV>?t=<秒>`）

|---|---|---|---|

| [BV1tceN62EAu](https://www.bilibili.com/video/BV1tceN62EAu) | 【NS】【完结】【魔法使之夜】通关流程 | 2289 min | 1110 |

### 3.3 通道 B：`playurl` + `ffmpeg` 直取 —— 提高分辨率

雪碧图只有 480×270，对"看清字"不够。改用 B站 `playurl` 拿直链，用 `ffmpeg -ss` **只拉需要的那一段**：

```
curl -A "Mozilla/5.0" -H "Referer: https://www.bilibili.com/video/<BV>" \
  "https://api.bilibili.com/x/player/playurl?bvid=<BV>&cid=<CID>&qn=64&fnval=4048&fourk=1"
# → data.dash.video[].baseUrl
ffmpeg -y -headers "Referer: https://www.bilibili.com/\r\n" -ss <秒> -i <baseUrl> -frames:v 1 out.png
```

- **实测拿到 852×480**（匿名上限；`accept_quality` 虽列了 1080p，实际 dash 只给 32/16）
- **产出**：`video_frames/bili_hires/`，22 帧
- 🔴 **这一条拿到了本件最有价值的一张图**：**选择肢菜单**（`BV1HW4y1P7KB_hires_t005310.png`）

### 3.4 抽帧产物怎么找"有界面的帧"

按"下半屏逐行横向强梯度密度"打分排序（脚本一次性），再**人工目视接触表复核**。

> ⚠️ **诚实说明**：这个自动打分**并不好用**——2498 帧里最高分那批（runlen=149/162，即整段全高密度）**全是高细节 CG**，不是界面帧。**最终是目视接触表（`contact_sheets/bili_frames_sample.png`、`bili_bangai_sweep.png`、`bili_ns_sweep.png`、`bili_hires_grid.png`）找到的界面帧**。→ **"检测器给高分" ≠ "有界面"，本件不把自动打分当结论。**

## 五 · ④ 魔夜「加密」这条：**不是加密，是误诊**（**做成了**）

### 5.1 🔴 结论

**`.hfa` 归档既没加密、也没压缩，就是一个明文容器。上一版说的"脚本加密（头 `HUNEXGGEFA10`）"是误诊——`HUNEXGGEFA10` 是归档格式的魔数，不是加密。**

**魔数的全称是 `HUNEX Global Game Engine File Archive 1.0`**（[一手出处：B站专栏「关于Steam《魔法使之夜》hfa文件的一些事」](https://www.bilibili.com/read/cv40087818/)）。逐字依据：

| 依据 | 逐字内容 |
|---|---|
| [`LinkOFF7/HunexFileArchiveTool` · `Archive/Header.cs`](https://github.com/LinkOFF7/HunexFileArchiveTool/blob/main/HunexFileArchiveTool/Archive/Header.cs) | `public String Magic = "HUNEXGGEFA10";` / `// HUNEX Global Game Engine File Archive v1.0` / `HEADER_SIZE = 0x10` / `ENTRY_SIZE = 0x80` / `DataStartOffset => FileCount * ENTRY_SIZE + HEADER_SIZE` |
| [`Alyinghood/unpack_hfa.py`（gist，MIT）](https://gist.github.com/Alyinghood/71b6685ab0afa6d9dfb5edc220da0bc8) | `if f.read(12) != b"HUNEXGGEFA10": raise` → 读 `u32` 文件数 → 每条 `96s name + u32 offset + u32 size + 24x` → `f.read(size)` **原样写出** |

🔴 **判据**：解包器对载荷**不做任何解密/解压**，直接把 `size` 字节原样写出。若载荷是加密或压缩的，写出来的就是密文/压缩流——**但容器本身没有加密这一层**。所以"如何解决加密"这个问题**问错了前提**：**没有加密要解**。

### 5.2 引擎也不是 KiriKiri（连带更正）

| 项 | 上一版说法 | 实际 | 依据 |
|---|---|---|---|
| 引擎 | 「KiriKiri 引擎」 | **HuneX**（HUNEX Global Game Engine） | 魔数全称 + [`RikuNoctis/PS-HuneX_Tools`](https://github.com/RikuNoctis/PS-HuneX_Tools)（HuneX 引擎 `.mrg/.nam/.hed` 工具集） |
| 归档 | `.hfa`（KiriKiri） | `.hfa` ＝ **HuneX File Archive** | 同 5.1 |
| 解包器 | 未找到 | **有三个现成的**：C#（HunexFileArchiveTool）、Python（gist）、C# 全套（MahoyoHDRepack） | 见 §四 G6/G7/G8 |
| GARbro 的 KiriKiri 加密算法 | 可能相关 | **不适用** | GARbro 的 `ArcFormats/KiriKiri/` 里没有 HuneX 支持 |

### 5.3 **能不能拿到官方排版参数**（`Config.tjs` 那类）

**理论上能，本次卡在"打不开原始归档"这一步。**

- ✅ **路径清楚**：`.hfa` 是明文容器 → 用 G7/G8 解包 → 拿到脚本与 UI 定义文件
- ✅ **格式文档已有**：[`MahoyoHDRepack/format notes.txt`](https://github.com/nike4613/MahoyoHDRepack/blob/master/format%20notes.txt) 逐字写了
  - `allui <- MRG archive containing UI graphics`（**UI 图形归档**）
  - `allscr.mrg <- MZP archive containing game script`（脚本归档），并列出脚本指令表：`_ZMxxxxx(textspec) displays text`、`_SCH2(?,img,…) displays an images`、`_IF__`、`_JUMP`、`_WKST` 等
  - ⚠️ **但这份说明写的是 Switch 版**（romfs／BNTX／BFSAR），**不是 PC Steam 版**；PC 版对应的是 `.hfa` + `.mzp` + `.mzx`
- 🔴 **本次卡在哪（如实说）**：
  1. **本机没有任何 7z 解压工具**（`7z`/`7za`/`7zz`/`unar` 全无），**`bsdtar` 也读不了**这个 29 GB 的 `WITCH ON THE HOLY NIGHT.7z`（报 `Error opening archive`）；

### 6.8 别人（非魔夜）的中文/网页 VN 界面长什么样（对照用）

来自 §四 G1–G4 的预览图（`contact_sheets/github_ui_grid.png`）：

- **底部一条对话框 + 左上角姓名条 + 右上/底部一排小文字按钮**（`skip/auto/save/load/q.save/q.load/log/config/title/close`）——这是**当代网页 VN 的标准版式**（`webtalekit_demo.png`、`stcinema_demo.jpg`、`tuesdayjs_preview.jpg` 三张都是这个形态）。
- **`llfs_dialogue_adv.jpg`**：底部对话框 + 「角色名字」标签 + 对话框上方浮着**选项条**（圆角胶囊，选中项换色）。
- **`llfs_save_read.jpg`**：存档页是**卡片网格 + 缩略图 + 编号 + 日期 + 分页**。
- **`llfs_overview_board.jpg`**：标题页是**左侧竖排菜单**（开始游戏/读取存档/游戏设置/画面设置/关于游戏/退出游戏）。
- 🔴 **关键差别**：**"底框 + 姓名条"是当代网页 VN 的主流**，而**魔夜是"无框直排"**。**我们该学哪一派，是一个产品决定，不是"哪个更正统"**——魔夜的无框直排更"读物感"、更像小说；底框+姓名条更"界面化"、更适合多人对话区分说话人（我们的教室场景里**说话人区分是真需求**）。
