## 一 · 定性结论（服务到底给了什么 kind）

**一句话**：0.2.1 的 Chat 快照里**根本没有 `tool-result` 节点**；工具结果被折进 **`tool-call` 节点**的
`data.root` 里，那个 `root.kind` 才是 `'tool-result'`。原代码只认**外层** `kind === 'tool-result'`，
所以一次都没进过板书分支。

真机（隔离 profile `classroom-dev` + `/tmp/lane-e-mock` MODE=draw，仓库工作区）在
`readMessages` 的节点循环开头临时打了一行，抓到的是这样（逐字，来自浏览器 console）：

```
NODEKIND turn-process {"nk":["key","kind","id","target","anchorSeq","location","visibility","groupTree","data"],
                       "dk":["turn","controlAnchorSeq","processStartSeq","answerAnchorSeq","answerStep","inlineReasoning","messageCount","toolCallCount","subagentCount"],
                       "rootKind":null,"rootName":null,"rootKeys":[]}
NODEKIND user         {"dk":["kind","seq","time","content","source"],"rootKind":null,"rootName":null}
NODEKIND tool-call    {"dk":["root"],"rootKind":null,"rootName":"classroom_draw",
                       "rootKeys":["phase","callId","name","turn","step","time","subCalls","args"]}      ← 还在跑
NODEKIND tool-call    {"dk":["root"],"rootKind":"tool-result","rootName":"classroom_draw",
                       "rootKeys":["kind","seq","time","callId","name","args","call","callTime","content","isError","meta","subCalls"]}
```

也就是说：

| 观察 | 事实 |
|---|---|
| 节点 kind 的取值集合 | `turn-process` / `user` / `tool-call`（**没有** `tool-result`） |
| 结果对象在哪 | `node.data.root`，`root.kind === 'tool-result'`，`root.name === 'classroom_draw'` |
| `meta` 在不在 | 在，`root.meta.board = {id, lesson, turn, kind}`（引擎的 `presentationMeta` 真生效了） |
| `content` 长什么样 | 数组，`[{type:'text', text:'板书图已落盘：…\n[board] id=… lesson=… turn=… kind=…'}]` |
| 有没有 `isError` | 有（`false`） |

源码侧对得上（`@deepseek-ai/dsh-client-ui-chat/lib/client.js`，从 app.asar 解出来的）：
`rootResult()` 产出上面那个结果对象，`buildViewNode` 把它包成 `{ root }` 挂在一个 **`kind: 'tool-call'`** 的节点上。
所以契约 K2.3 里"`node.kind === 'tool-result'`"这句话，对 0.2.1 的 Chat 快照不成立 ——
**形状描述对的是 `rootResult()` 的返回值，不是外层节点**。这一条建议主代理回头改契约文本（我没有动
`docs/计划与排产/`：那里是别人的计划文档）。

**对应证据 README 表格里的哪一行**：不是三行里的任何一行原样，而是"**有结果、但它不是独立节点**"——
所以改法不是"换数据源"，而是"**换取值路径**"：判据仍然认结果对象，只是要往 `data.root` 里找。

## 二 · 改了什么

### 2.1 `lib/client.js` · `boardEventOf`（判据不变，取值路径补一条 + 带出事件时间）

- 原来：只认外层 `kind === 'tool-result'`。现在先看 `node.data.root`，**外层是 `tool-call` 也命中**；
  独立 `tool-result` 节点的形状（契约文档写的那个）仍然照旧支持 —— 两条形状并存，不靠猜。
- 新增返回字段 `time`（= 结果对象上的 `root.time`，epoch ms）。**给"刷新页面不弹老图"用**，见 2.3。

### 2.2 `lib/client.js` · `readMessages`（板书信号的真实入口挪到 `tool-call` 分支）

- 在 `kind === 'tool-call'` 分支里先判一次 `boardEventOf(node)`：命中就推一条 `role:'board'` 条目
  （纸带仍然只画对话，`role:'board'` 在纸带渲染里照旧被跳过）。
- **顺序**：先推 board，再做 `callId` 去重（`seenToolCall`）。原来若这个 call 已由 `assistant-step`
  画过，`continue` 会把切屏信号一起吞掉 —— 这是本次顺带钉住的一条（有单测）。
- 独立的 `kind === 'tool-result'` 分支**保留**：将来宿主换形状也接得上。

### 2.3 `lib/client.js` · 自动切屏 effect（K2.4 的"刷新不弹"从'意思对'变成'真对'）

原来的写法是「首帧把当前最新一张记进 `seenBoardIdRef`，之后 id 变了才弹」。**这条只在同步数据下成立**：
Chat 快照是异步到达的，首帧往往一条消息都没有，于是刷新页面时历史里的板书"晚一步出现"，
会被当成新图 —— 也就是**每次刷新都弹一次板书屏**。这个 bug 之前是休眠的（因为根本没有 board 条目），
**本次修好判据后它会被激活**，所以一并处理：

- 新增纯函数 `shouldAutoOpenBoard(mountedAt, seenId, board)`：有 id ＋ 不是已处理那张 ＋
  **事件时间不早于挂载时刻**，三条都成立才弹。
- effect 里用 `mountedAtRef = useRef(Date.now())` 播种；`seenBoardIdRef` 从空串开始。
- 时间未知（老事件没带 `time`）时按"新事件"处理：宁可多弹一次，也不静默吞掉课上画的图。

### 2.4 手动「板书」按钮

逻辑没改（`boardScreen → 收起`；`boardReq → openDiagram(boardReq)`；否则 `openBoard('L03')`），
但 `boardReq` 依赖的 `role:'board'` 条目以前**永远是空的**，所以这条分支等于没测过。
本次真机把两条都跑通了（见 §3 E1 / E2）。

### 2.5 判据单测（新增）

- `test/22-read-messages.test.mjs`（`node --test`，15 条）：用例的节点**逐字照抄这次 dump 的键**，
  钉住"外层 `tool-call` ＋ `data.root.kind = tool-result` 也要命中"；另含 `meta` 缺失退化到 `[board]` 行、
  `isError` 不算、跑动中不算、callId 去重不吞信号、`shouldAutoOpenBoard` 的六种情形。
- `test/20-stage-pure.mjs` 补 8 条（真机形状命中 / 事件时间 / 切屏时间判据），跟着 `check.sh` 的
  纯函数区抽取一起跑。
- `check.sh` 新增 `7f` 组跑 22 号文件（这样 `node check.mjs` 也能覆盖到）。

## 四 · 没做到的 / 需要你知道的

1. **契约 K2.3 的正文与 0.2.1 不符**（`node.kind === 'tool-result'`）。我没改那份计划文档（不在我这条车道）。
   代码现在**两种形状都认**，所以契约改不改都不影响功能；但建议把这句话改成
   "结果对象 `root.kind === 'tool-result'`（0.2.1 挂在 `tool-call` 节点的 `data.root` 上）"，
   否则下一个人还会按错的那句去找节点。
2. **"显示中又来一张"只证明了行为，没证明"消息里有两条 board 条目"**：mock 每次都发同一个
   `toolu_1`，Chat 节点按 `callId` 键控，第二张是**原地更新**同一条目（所以 `latestBoardOf` 拿到的是新 id）。
   真模型每次 callId 不同会是两条 —— 这条差异没法用本 mock 复现，我按"id 变了就换图"的判据验的。
3. **渲染失败是注入出来的**（stub `mermaid.render`）：引擎侧落盘前会真解析一遍，坏源码根本进不了
   `runtime/diagrams/`，所以"客户端渲染失败"这条只能在客户端侧逼出来验。**服务端的"坏源码不落盘"
   没有重新验**（属于 W-e，已有单测）。
4. **`enabled=false`（设置里关掉舞台）这条没单独跑**：我用的是「关闭舞台」的 `killed` 路径。
   两条在 effect 里是同一个守卫 `if (!enabled || killed) return`，但 `enabled` 那条没有真机证据。
5. **P 车道（面板的板书历史列表）没碰也没验** —— 不在本车道。
6. 台架的 mock 为了验"同回合第二张"被我临时加了 `MARK=` / `DRAW_PAIR=` 两个开关
   （在 `/tmp/lane-e-mock/server.mjs`，**不在仓库里**，不入库）。验证完 mock 已停、profile 里
   `llm-deepseek.baseURL` / `agent-default-model` 那两段临时配置已删、3099 上的进程已停。
