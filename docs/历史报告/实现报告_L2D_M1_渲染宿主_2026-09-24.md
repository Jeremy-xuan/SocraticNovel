**CORE 的取法与一次踩坑（重要，写下来免得下轮重踩）**：

  ```
  TypeError: Cannot read properties of undefined (reading 'byteLength')
      at Version.csmGetMocVersion (live2dcubismcore.min.js:9:6362)
      at _CubismMoc.create (live2d-host.bundle.mjs:4837)
  ```

  > **2025-10-14** · Added · *Add `csmGetMocVersion(mocBytes: ArrayBuffer)` with simplified arguments from `csmGetMocVersion(moc: Moc, mocBytes: ArrayBuffer)`.*
- **正解**：从官方 SDK 包取 Core —— `https://cubism.live2d.com/sdk-web/bin/CubismSdkForWeb-5-r.5.zip`（20.7 MB，HTTP 200），
  解出 `CubismSdkForWeb-5-r.5/Core/` 里的 `live2dcubismcore.min.js`（228,042 字节）。
  该版本 `csmGetMocVersion` 已兼容两种签名（逐字：`data instanceof Moc ? _csm.getMocVersion(data._ptr, mocBytes.byteLength) : (mocBytes = _csm.mallocMoc(data.byteLength)) ...`）。
- **文件哈希（可校验）**：
  - `vendor/Core/live2dcubismcore.min.js` = `8741f739779b5d5210872bd3d7d99f0f1e56e6c87409e7d26d6bb4b80aa1ef47`

### 1.3 为什么需要一次打包（这一步绕不开）

官方框架 `src/` 内部全部是**无扩展名的相对 import**（例：`import { CubismModel } from '../model/cubismmodel';`），
浏览器原生 ESM **不接受无扩展名路径** → 必须打一次包。
打包时**官方源码一行不改**，只用 `--alias:@framework=<vendor/CubismWebFramework/src>` 把官方示例用的别名指回源码目录。

### 2.1 渲染宿主是「独立模块」的证据

`src/host.js` 的对外接口（**与页面零耦合**）：

```js
import { Live2DHost, renderFirstFrame } from './live2d-host.bundle.mjs';

// 方式一：显式三步
const host = new Live2DHost(canvas, { shaderBaseUrl: './shaders/WebGL/' });
host.initGL();
await host.load('./models/Haru/Haru.model3.json');
await host.waitForShaders();   // 官方 shader 是异步 fetch 的，未就绪前 draw 不画东西
host.runFrames(30);
host.startLoop();

// 方式二：一行拿到第一帧
const host2 = await renderFirstFrame(canvas, './models/Haru/Haru.model3.json');
```

它**只用传入的 canvas**，不查 `document`、不引用任何页面结构、不注册全局监听。
下一步挂进 DSH 客户端插件右侧面板时，把面板里的 `<canvas>` 传进来即可。
（`host.setLipSyncProvider(provider)` 是替换嘴型来源的唯一入口；`host.readParameter(id)` 是取证读取入口。）

### 3.3 「参数真的驱动了嘴」——隔离验证（本轮新增，比第一帧更强的一条证据）

第一帧只能证明"渲染出了东西"，**不能证明参数驱动有效**。为此单独做了一次隔离实验
（`tools/mouth-iso.cjs`，先**冻结动画**（只 `draw` 不 `update`），再只改 LipSync 参数）：

| 量 | 值 |
|---|---|
| 冻结后 `ParamMouthOpenY = 0` vs `= 1` 的逐像素差异 | **changed = 162 像素**（meanAbsDiff=100.14，maxAbsDiff=176） |
| 差异包围盒 | **`x∈[349,368], y∈[121,132]`（20×12）** |
| 可逆性：再改回 0 与最初的 0 | **changed = 0（完全一致）** |

→ **全部差异集中在一小块 20×12 的区域（就是嘴的位置），画面其余部分一个像素都没动。**
→ 加上"改回 0 完全复原"，可以确认：**这条参数就是嘴，且写入是确定性的、无累积漂移。**

放大目视（本轮已做）：
- `evidence/crop_Haru_mouth_closed.png`（裁切 60×51，放大到 360px 宽）→ **闭着的微笑嘴线**
- `evidence/crop_Haru_mouth_open.png`（同框同倍）→ **张开的嘴**

> 📌 一个实现细节（踩过）：只 `setParameterValueById` 后直接 `draw()` **画面不会变** ——
> 必须再跑一次 `model.update()` 把参数写进顶点缓冲。这一点写进 demo 的注释里了。

### 3.5 🔴 一条必须写下来的反例：`Mark` 的 L2 回退是「静默失败」

**事实**：`Mark.model3.json` 的 `Groups` 里 `LipSync` 是**空数组** `[]`；
按三级回退走到 **L2**，在 cdi3 参数全集里命中 `ParamMouthOpenY`（该参数**确实存在**于模型的 21 个参数中）。
但把它的值从 0 写到 1，**画面变化 = 0 像素**。

**另一路佐证**：Mark 的 cdi3 **没有**参数语义分组（`ParameterGroups` 是空数组 `[]`），
所以无法用"哪个参数属于『口』组"来确认 —— 与"这个参数其实不驱动嘴"一致。

**结论（对设计的影响）**：
> 「按命名风格回退 + 验证参数存在」**不足以保证参数真的驱动嘴**。
> 参数**存在** ≠ 参数**接在嘴的变形器上**。
> → **回退命中必须标成"低置信"，并且要有一次"写值看画面"的验证才能升级为可用**；
> 上层（教室侧）应当把 `Mark` 这类模型当作**不支持嘴型**处理，或走 §3.3 的隔离验证逐个确认。
> **这正是"绝不静默"的另一半**：不仅"找不到要报错"，"找到了但可能没用"也要报出来。

### 4.2 关键结论（与 `研究_8` §1.1 逐条对上）

1. **「每张模型的嘴参数名不统一」已被实测确认，且形态是 4 种**：
   `ParamMouthOpenY`（4 个）／`ParamA`（Mao）／`PARAM_MOUTH_OPEN_Y`（Wanko）／**空数组**（Mark、Rice）。
   → **airi 硬编码 `'ParamMouthOpenY'` 在 8 个官方样本里会有 4 个失效**（Mao 名不同、Wanko 名不同、Mark 空、Rice 空）——与研究结论一致。
2. **「`LipSync = []` 与 `LipSync` 字段缺失是两种不同情况，都要回退」**：本轮的 8 个样本**都**带 `Groups` 项，
   其中 2 个是**空数组**形态；实现里把这两种情况**分开报**（detail 文字不同）。
3. **`Rice` 是真的不支持嘴型**：它 96 个参数里**没有任何**嘴参数（既无 `ParamMouthOpenY` 类命名，也无 cdi3「口」组）。
   → **L3 明确报"这张模型不支持"，绝不静默**（实测：写任何值画面变化都是 0 像素）。
4. **新增一层「第四层补充信号」：cdi3 的参数语义分组**（本轮实测发现，`研究_8` 未记）

### 5.2 算法（三档，本轮实现档 1＋档 2）

```
档 1 · 字符节奏（本轮实现）
  收到一个 text-delta chunk：
    ① 若含标点 → value = 0，并进入 punctuationPause 静默窗（默认 180 ms）   ← 档 2
    ② 否则   → target = amplitude × √(可发音字数 / charsPerTick) × jitter(chunk)
              value = max(value, target)        // 冲高取大
              进入 holdMs 保持窗（默认 60 ms）  // 冲高后先保持，再衰减
  每帧：
    value *= exp(-dt / decayTau)                // 指数衰减
    value < zeroEpsilon → 吸附到 0
档 3 · 音素近似（按研究_8 §4.2 裁定）**明确不做**
```

### 5.3 🔴 与研究_8 §4.2 档 1 公式的差异，以及为什么改（**实测驱动的修正**）

研究里的档 1 写的是 `target = min(1, n / CHARS_PER_TICK)`、`CHARS_PER_TICK ≈ 3`、`getParameter() = value * AMPLITUDE`。
**照它实现后实测失败**，原因是它把「幅度」和「速率」混在一个常数里：

| 现象（实测 CSV 可复现） | 原因 |
|---|---|
| 逐字喂时 61 个采样里只有 **16 个非零**，取值只有 **2 种**（0.2 与 0），曲线是方形脉冲 | 1 个字 → `target = 1/3 ≈ 0.33`，再乘 `AMPLITUDE=0.6` 只剩 **0.2**；而 τ=0.1 s 的衰减在 80 ms 后把它打到 0.09 → 被 `zeroEpsilon` 吸附到 0 |
| 完全看不到「起伏」，也看不到「节奏」 | 同上：峰值被压到接近噪声，形状退化成方波 |

**本实现的三处修正**（都写进了代码注释，便于下轮追）：

1. **幅度只用 `amplitude` 乘一次**；`charsPerTick` 重新定义为「**一个 chunk 多少字算打满幅度**」的归一化基准（默认 3），不再兼职"速率"。
2. **归一化用平方根而不是线性**：`norm = min(1, √(字数 / charsPerTick))`。
   理由：一个 chunk 的字数在 1..50 之间跨两个数量级，线性映射会把"1 个字"压到 1/3 → 小 chunk 永远推不动嘴（实测 16/61 非零就是这个后果）。平方根把 1 个字抬到 √(1/3)≈0.58。
3. **加 `holdMs`（默认 60 ms）**：冲高后先保持一小段再开始衰减。
   这样「断续」来自 hold 之后的衰减，而不是靠把峰值压到噪声以下。
4. **加 `jitter`（默认 0.3，确定性哈希）**：同样字数的 chunk 若给完全相同的目标值，曲线会退化成"重复的两三个数"。
   对 chunk 内容做 FNV-1a 哈希映射到 `[1-jitter, 1]` 的系数 —— **既有多样性又完全可复现**。

**修正前后对照（同为"每 1 字 / 间隔 60 ms"）**：

| 指标 | 照研究旧公式 | 本实现 |
|---|---|---|
| 非零采样数（说话期间） | 16 / 43 | **32 / 61** |
| 非零占比 | 0.372 | **0.525** |
| **取值种类数** | **2** | **11** |
| 最大值 | 0.2449 | 0.3442 |

### 5.7 写字通道：接口与语义（供上层驱动调用）

**「说话卡、写字流畅」不是让嘴动得更慢，而是让「嘴」和「手」走两条不同的通道。**

| 维度 | `speak`（说话） | `write`（写字） |
|---|---|---|
| 实现类 | `TextRhythmProvider` | `WriteChannelProvider` |
| **实现的接口** | **`IParameterProvider`**（与官方同一个） | **同一个 `IParameterProvider`** |
| `update(deltaTimeSeconds?)` | 推进衰减/静默窗，返回 `true` | 计数，恒返回 `true` |
| **`getParameter()`** | 返回 `[0, 1]` 的**嘴开合量** | **恒返回 `0`（嘴不动）** |
| 参数名 | 由能力发现给出（`ParamMouthOpenY` / `ParamA` / `PARAM_MOUTH_OPEN_Y` …） | 同左（但恒写 0，等于不驱动） |
| 语义 | 嘴跟着文字动：冲高 + 指数衰减 + 标点闭嘴 | **嘴不动**；"写字流畅"由白板打字机效果承担，**不经 Live2D** |
| 上层切换方式 | `host.setLipSyncProvider(provider)` | 同左 —— **渲染代码一行不改** |

代码位置：`src/text-rhythm-provider.js` 的 `WriteChannelProvider`；
工厂函数 `createProvider('speak' | 'write', config, opts)`。
两个 provider 都**只依赖两个方法**，所以官方 `CubismLipSyncUpdater` 对二者完全无感。

### 5.8 一个刻意的实现决定（写下来免得下轮困惑）

`src/text-rhythm-provider.js` **没有 import 官方模块**，而是内置了一个**零依赖的形状副本** `IParameterProvider`。
理由：
- 官方 `IParameterProvider` 是**零实现的抽象基类**，官方消费者对它**只做鸭子类型调用**（没有 `instanceof` 检查）→ 继承与否在运行时完全等价；
- 本文件被**纯 Node 的取证脚本**直接 import（那里没有 `@framework` 别名），一旦 import 官方模块就会连带整棵框架树 → 脚本直接跑不起来（实测报 `ERR_MODULE_NOT_FOUND: Cannot find package '@framework/live2dcubismframework'`）。
- 形状副本上写了官方原文与文件路径注释，便于对照。

## 附录 A · 本轮修正的三个「官方/研究侧」事实（供后续引用）

1. **Core 必须从 SDK 包取**（§1.1）：`cubismcore` 直链那份是 5.1.0，与 R5 框架不兼容，崩在 `csmGetMocVersion`。
2. **`CubismUserModel` 基类已建好 `_motionManager` 并设了事件回调**（`cubismusermodel.ts` 构造函数逐字）：
   > `this._motionManager.setEventCallback(CubismUserModel.cubismDefaultMotionEventCallback, this);`
   派生类若再 `new CubismMotionManager()` 会**丢掉这个回调**，一旦动作带 UserData 事件（官方样本 `Mark` 的 Idle 就是），
   `cubismmotionqueuemanager.ts` 会直接抛 `this._eventCallBack is not a function`。**本轮踩到并修掉了。**
3. **`setParameterValueById` 之后必须 `model.update()` 才能改变画面**：只写参数 + `draw()` 画面不变（顶点缓冲没重算）。

## 附录 B · 本轮修正的「研究_8」侧一处公式（供后续引用）

`研究_8 §4.2 档 1` 的 `target = min(1, n / CHARS_PER_TICK)`、`CHARS_PER_TICK ≈ 3`、`getParameter() = value * AMPLITUDE`
