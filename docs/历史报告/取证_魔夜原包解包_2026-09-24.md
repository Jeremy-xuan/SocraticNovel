## §2 HFA 归档格式（本轮逐字节实证）

上一路已确证魔数为 `HUNEXGGEFA10`（`HUNEX Global Game Engine File Archive 1.0`）。本轮把**完整布局**定死，并用**全 52 个包的算术自校验**证明无误：

| 字段 | 位置 | 值 |
|---|---|---|
| 魔数 | 0x00 | `HUNEXGGEFA10`（12 B）〔A01〕 |
| 条目数 | 0x0C | u32 LE |
| 条目表 | 0x10 起 | **每条 0x80 B**〔A02〕 |
| ├ 文件名 | +0x00 | 0x60 B，UTF-8，NUL 填充 |
| ├ 偏移 | +0x60 | u32 LE（**相对数据区起点**）〔A04〕 |
| └ 大小 | +0x64 | u32 LE |
| 载荷起点 | `data_start` | **`16 + 0x80 × 条目数`**〔A03〕 |
| 载荷 | `data_start + 偏移` | 长 `大小` 字节，**原样存储**〔A10〕 |

🔴 **自校验判据**（本轮用它证明布局正确，无需信任任何第三方实现）：

> `Σ 所有条目的 size  ==  文件大小 − data_start`

**52 个归档全部满足，无一例外**〔A05〕。这条判据把"偏移是否含表头"这个最容易搞错的点直接钉死了——若偏移是绝对文件偏移，等式不成立。

> 与上一路的差异：上一路引用的 gist 记作"96 B 名字 + u32 偏移 + u32 大小"（步长 0x68）。本轮实测**步长是 0x80**（名字 0x60 ＋ 偏移/大小 8 B ＋ 0x18 B 全零填充）。gist 的 0x60 名字长度是对的，**步长记错了**；用 0x68 会从第二个条目起全部错位。这条已按实测更正。

### 3.1 🔴 `.chs` 是什么 —— 已定案

**问**：上一路说"本机找不到样本、无法复核"。

**答**：样本一直在包里（5 个归档、共 250 个）。逐字结论：

| 项 | 结论 |
|---|---|
| 是归档吗？ | ❌ **不是。** 它没有条目表，不能"列出里面有什么" |
| 是明文脚本吗？ | ❌ **不是。** 解压后是**编译过的字节码** |
| 那是什么？ | ✅ **LenZuCompressor 压缩的 HuneX 编译脚本** |

**外层**：魔数 `LenZuCompressor\0` ＋ `1\0\0\0` ＋ `0\0\0\0…`（共 0x20 B）〔A06〕
**内层**：解压后首 22 字节为 `HunexCompiledScriptVer1.00\0`

**解压结果**：

| 项 | 数 |
|---|---:|
| `.chs` 总数 | **250** |
| 解压成功 | **250** |
| 解压失败 | **0** |
| 解出总字节 | 20,260,387（约 20.3 MB） |
| **内建校验和通过** | **250 / 250** |

**内容性质（逐字观察）**：字节码中内嵌的是**符号名与字面量**，不是可读源码：

- 原始源码路径：`F:\Witch\Script\000_start\test_script.hss` → **源码扩展名是 `.hss`**，脚本按章节目录组织
- 宏／标签名：`SEL_JUMP2`、`SEL_SELECT`、`WIK_TITLEIN`、`scene_jump`、`OPENING`、`5B_4`、`Include\define_macro.h`
- 音效名：`SE01013`、`SE05012A`、`SEETC01`…
- 变量与常量：`G010 = 0`、`BGM 100`、`SE 80`
- 出现最多的 token：`START`（248 次）

🔴 **没有任何"排版类"命令名**（`FONT`／`TEXT_WIN`／`LINE_SPACE`／`MARGIN`／`COLOR` 全零命中）。命令在字节码里是**数值操作码**，字面量是**二进制操作数**——不做反汇编读不出来。

### 3.2 LenZuCompressor 解码器（先例 → 移植 → 校验）

**先例（第一步先读现成实现，未从零推导）**：

| 来源 | 内容 | 位置 |
|---|---|---|
| `nike4613/MahoyoHDRepack` | **就是本作（魔夜 HD）的解包工具**，C# | `src/MahoyoHDRepack/LenZuCompressorFile.cs`（blob `9131caac…`）〔A08〕 |
| 同上 | **完整托管解码实现**（Huffman 表重建 ＋ LZ 回引 ＋ 校验和） | `src/MahoyoHDRepack/LenZuCompressorFile.Managed.cs`（blob `c6841f2a…`） |
| 同上 | 脚本提取／行边界解析（证明文本是"行表 + 行数据"结构） | `Verbs/ExtractScript.cs`、`ScriptText/LineBoundaryParser.cs` |
| nrvnqsr 论坛帖 | 反汇编出处：`lz_decompress` | [Mahoutsukai no Yoru HD PC file format deciphering](https://forums.nrvnqsr.com/showthread.php/6683) |
| gist | 早期社区实现 | [Alyinghood/hunex_decompression.c](https://gist.github.com/Alyinghood/e1052b715426320257d7591613ad740a) |

**移植**：把 `LenZuCompressorFile.Managed.cs` 的三个核心函数逐字移植为**纯标准库 Python**（零依赖）〔A09〕，落在 `moye_raw/lenzu.py`。格式要素：

| 要素 | 值／做法 |
|---|---|
| 头部 | 0x20 B 固定串 |
| 体部头 | 解压长度 u32 ＋ 校验和 u64（hi/lo） ＋ 未用 u32 |
| 压缩器选项 | 6 B：Huffman 位宽／回引低位宽／回引基准距离 |
| 熵编码 | 自底向上重建的 Huffman 树 ＋ 位流 |
| 回引 | `distance = (hi << low) | lo`，再 `+ base` |
| 校验和 | `c = (c + byte) * LUT[i & 3]`，`LUT = {0xE9, 0x115, 0x137, 0x1B1}`，模 2⁶⁴〔A07〕 |

🔴 **本移植的独立证据不是"我读懂了代码"，而是内建校验和**：250 个 `.chs` ＋ 4 个 `.ctd` ＋ 16 个 `.ccit` **全部校验和匹配**（`ck_ok=True`）。校验和是**原文件的**、不是我算的——匹配即证明解压字节与官方原字节逐字节一致。

### 3.3 `.ctd` = 官方对白文本（4 语言）

`data00200.hfa` 内 4 个文件，均为 LenZu 压缩，**全部解压成功、校验和全对**：

| 文件 | 压缩后 | 解压后 | 语言 |
|---|---:|---:|---|
| `script_text_ja.ctd` | 895,880 | 2,017,337 | 日文 |
| `script_text_zc.ctd` | 806,325 | 1,577,956 | 简体中文 |
| `script_text_zt.ctd` | 810,364 | 1,594,635 | 繁体中文 |
| `script_text_en.ctd` | 771,794 | 1,650,534 | 英文 |

**逐字性质**：

- 纯 UTF-8 文本，**行分隔符只有 `\r\n`**（4 份都是 24,134 个 CRLF）——**全文再无任何其他控制字节**（无 0x00–0x1F 其他值、无 0x7F）
- 行首用**全角空格 `　`** 做段首缩进
- 注音（ruby）标记形如 `<触|ふ>`、`<幼馴染|おさななじ>`：**`<汉字|假名>`**；ja 有 2,636 个不同注音对
- 对白用 `「」` 包裹；存在**姓名字段占位**（例：`「　　、キーを回してきてくれるかい？」` 中两个全角空格处即姓名条内容，运行时填入）
- 中英对照：日文第 0 行 `　その子の影になったのは８年前の冬のこと。` ↔ 英文第 0 行 `  It was a winter's day eight years ago...`

🔴 **关键判定：这里没有排版参数。** 全文只有对白文字与注音标记，**没有**字号／行距／边距／颜色／坐标任何一项。

**关于"换行"的重要更正**：`.ctd` 的 `\r\n` **不是显示换行，而是"一条文本条目（一个对话框的量）"的边界**。证据是先例 `LineBoundaryParser`：Switch 版把**边界表**（BE int32 偏移）与**行数据**分成两个文件；PC 版把两者拼成单个 `.ctd` 并用 CRLF 分隔。因此：

- 行长分布**没有硬上限**：日文 p50 = 23、p90 = 45、p99 = 71、max = 152 字；简中 p50 = 19、max = 129；英文 p50 = 60、max = 399
- 分布**平滑无截断**→ 说明引擎**在运行时按窗口宽度自动折行**，换行宽度**不落在数据里**

→ **不能从 `.ctd` 反推官方折行宽度／字号**。（日文 54% 的条目 ≤ 24 字，只是"作者大致按一屏两三行写"，不是硬参数。）

### 3.4 `.ccit` = 字形映射表（字体）

16 个 `Font*.ccit`（`data00100.hfa`），全部 LenZu 压缩，**全部解压成功、校验和全对**。解压后结构：

```
u32 条目数 | u32 = 8 | (u32 字符码, u32 字形索引) × N
```

例（`Font000000.ccit`，解出 2,984 B）：条目数 106，随后是 `(0x20, 0)`、`(0x21, 1)`、`(0x22, 2)`、`(0x23, 3)`… —— 即 **ASCII 码位到字形格号的顺序映射**。

→ 用途：与同目录的 `FONT_{ja,en,zc,zt}_*.mzp` **位图字形表**配套，把字符映射到字形格。**是字体资源，不是排版参数。**

### 5.2 `.chs` 是什么（定案）

> **`.chs` = LenZuCompressor 压缩的 HuneX 编译脚本**（解压后 `HunexCompiledScriptVer1.00`）。
> **不是归档**（不能列条目）、**不是明文**（是编译字节码，含内嵌符号名与字面量）。
> 对应源码扩展名 `.hss`，原路径形如 `F:\Witch\Script\000_start\test_script.hss`。
> 250 个全部解压成功，校验和 250/250 通过。

### 5.3 有没有拿到官方排版参数

> 🔴 **没有。**
> 根因是**结构性的**：52 个归档里只有 7 种扩展名（`.mzp/.hw/.cbg/.chs/.ccit/.mp4/.ctd`），**不存在任何配置文件类型**。
> 唯一的非编译文本（`.ctd` 对白）**逐字检查过**：只有对白文字 ＋ `<汉字|假名>` 注音 ＋ `\r\n` 条目边界，**没有任何排版码**；且其 `\r\n` 是**条目边界而非显示换行**（先例 `LineBoundaryParser` 证明），行长分布平滑无截断 → **引擎运行时自动折行，折行宽度不在数据里**。
> **因此：想拿官方排版参数，只能① 反汇编 `.chs` 字节码找命令操作数，或② 从官方位图量。** 本轮做了 ②（§4.3），① 未做（§7）。
