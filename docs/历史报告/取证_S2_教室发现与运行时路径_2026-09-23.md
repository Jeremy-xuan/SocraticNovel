## (c) 文件系统访问：插件用 `node:fs/promises` 会不会被沙箱拒？

### C1. 沙箱的**执行点是「文件系统服务」与「shell」，不是 node 模块加载**

**文件**：`tmp/dsh-src-0923/packages/fs/fs-sandbox/src/index.ts`

逐字片段（模块头，**关键段落**）：

```ts
/**
 * `SandboxedFileSystem`: the sandbox-enforcing implementation of the
 * `@deepseek-ai/dsh-fs` Service Definition. It extends `LocalFileSystem` so all
 * text-storage mechanics — resolve, stat, read/stream, list, the atomic
 * write and the read-match-write edit critical section — are the local
 * implementation's, verbatim; this package adds only the per-call POLICY fence
 * on the two mutations. Reads pass through untouched: every mode permits
 * reading.
 *
 * The fence is a policy check in TRUSTED code over a MODEL-CONTROLLED path,
 * NOT a kernel boundary — the operations are the seam's own (open, rename),
 * and only the target path is untrusted, so canonicalize-then-contain is the
 * complete answer to this surface. This is containment, not a security
 * boundary; kernel-grade isolation of untrusted CODE stays `ctx.shell`'s job
 * (`@deepseek-ai/dsh-bash-sandbox`). The residual
 * TOCTOU (an ancestor symlink swapped between the containment re-check and the
 * syscall) is narrowed by re-canonicalizing immediately before delegating and
 * is accepted for this threat model.
 *
 * Per-call policy: `read-only` denies every mutation; `workspace-write` allows
 * a mutation only when the target canonicalizes under the policy's workspace
 * root or a platform temp area from the shared `writableRoots` policy;
 * `danger-full-access` delegates unfenced. A denial throws the structured
 * `FS_SANDBOX_DENIED`.
```

**解读**（三条硬结论）：
1. **沙箱的围栏只加在「两个 mutation」上**（`writeText` / `editText`）；**`resolve` / `stat` / `lstat` / `readText` / `streamText` / `listDir` 一律原样透传**——原文 `Reads pass through untouched: every mode permits reading.`
   → **扫描工作区目录不会被沙箱拒**（不论 profile 是 read-only 还是 workspace-write）。
2. 沙箱是**策略检查，不是内核边界**（`NOT a kernel boundary`）；**对不可信代码的内核级隔离是 `ctx.shell` 的职责**。
   → 插件代码跑在宿主进程里，`import 'node:fs/promises'` **不受 `ctx.fs` 策略拦截**（没有任何模块级拦截层）。
3. 越界写入抛结构化 `FS_SANDBOX_DENIED`。

```js
async function resolveLocalTarget(cwd, path) {
	if (path.trim().length === 0) throw new FsError("file_path must be a non-empty string", "FS_NOT_FOUND");
	const displayPath = resolve(cwd, path);
	try {
		return {
			displayPath,
			targetKey: FsTargetKey(await realpath(displayPath))
		};
	} catch (error) {
		/* v8 ignore next -- Windows reports this case as ENOENT and repairs it in the ancestor walk below. */
		if (isENOTDIR(error)) throw new FsError(`cannot resolve "${displayPath}": a parent path segment is not a directory`, "FS_NOT_FOUND");
		/* v8 ignore next -- non-ENOENT realpath failure needs a permission/IO fault; ENOENT falls through to ancestor resolution. */

	}
```

**解读**（discovery 的错误处理依据）：
- **「路径不存在」用 `stat`/`lstat` 返回 `undefined` 表达，不是抛错** → 判「目录里有没有 classroom.yaml」用 `stat() !== undefined`。
- **`listDir` 在不可读/不存在/非目录时抛 `FsError`**（`FS_NOT_FOUND` / `FS_NOT_DIRECTORY` / `FS_IO_ERROR`）→ discovery 必须 **try/catch 包住每一次 `listDir`，记 `skipped` 而不是让整个扫描炸掉**。
- `lstat` **不跟随末段符号链接**，其 `type` 可为 `'symlink'` → **这是宿主提供的、官方认可的「拒绝符号链接」手段**（见 D1 的 docstring）。

```ts

   * symbolic link. This is intentionally path-shaped, not target-shaped:
   * {@link resolve} follows symlinks to produce the stable identity used by
   * normal reads/writes, while `lstat` lets a consumer reject the path itself
```

### C4. `node:fs/promises` 直用是否被拒 —— 取证结论

**未取证**：在 `tmp/dsh-installed/` 中**没有找到任何「拦截 node:fs 模块」的机制**。
已试 grep 词：`node:fs`（在 `packages/sandbox/**` 仅命中 `sandbox/src/diagnostics.ts` 与 `sandbox/src/roots.ts`，两处都是**宿主自己**用 `accessSync`/`statSync`/`realpathSync` 做诊断与根解析，**不是拦截**）；`sandbox_permissions|file access denied|sandbox: file access`（命中 `dsh-fs-sandbox` / `dsh-tool-fs` / `dsh-tool-bash` / `dsh-tool-pwsh` / `dsh-sandbox`，即**服务层与 shell 层**的拒绝，不是模块层）。

**由 C1 的官方原文可推**：沙箱是**服务层策略**（`ctx.fs` 的两个 mutation）＋**shell 层内核隔离**（`ctx.shell`）。
插件代码在宿主进程内 `import 'node:fs/promises'` **不经过这两层**。
🔴 **但本任务仍以 `ctx.fs` 为主通道**，理由：
① 与宿主自身用法一致（A4 的 `ctx.get("fs")` 模式）；
② 远程/沙箱化后端下 `node:fs` 会读错执行世界（fs 服务文档明确区分 `targetKey` 与 host path）；
③ 单测（无宿主）需要无 fs 服务的降级路径 —— 故实现为「fs 服务优先，`node:fs` 兜底」。
