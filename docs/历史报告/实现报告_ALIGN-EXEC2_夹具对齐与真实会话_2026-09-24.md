## 2. ② 频率语义四条：逐条是"文档级结论"还是"要改代码"

> 上一路的判断是：引擎 layer 枚举只有 5 个〔A03〕，六层靠 **(layer × `position.target` × `frequency`)** 组合编码，**不需要改 schema**；要动的是 4 处语义。下面逐条给结论。

### 2.1 第 1 条：`anchor.check` 的 `n_turns`（**教室侧那半归另一路**，我只判引擎侧）

**问**：`on_demand` 是不是合法值？引擎对它的处理对不对？

**答（两条都有证据）**：

- **合法**：`on_demand` 在频率模式枚举里〔A04〕，`parseManifest` 会正常接受它（本教室已有 4 个块在用它：`state.session_log`／`state.archive`／`state.diary`／`state.wechat`）。
- **引擎的处理是"有意的永不自动注入"**：注入计划器对 `on_demand` 直接 `inject = false`〔A06〕，代码注释写明那是"工具/相位触发路径（TODO：M3 工具接入）"。也就是说：**它合法、但当前等于"这个块永远不会被自动注入"**。
- **对错判定**：按新口径（"教学检查＝需要校准时使用"，不设频率配额），"不按频率自动注入"**方向是对的**；但引擎**只有一半实现**（没有工具触发路径）。

🔴 **结论：文档级结论，不改代码**。理由：`on_demand` 是一个**被声明的**语义（"引擎不主动注入"），不是"配了不生效"的静默错误——引擎把声明的那一半做对了，缺的另一半是**尚未实现的工具路径**（已标 TODO）。cs-os 的 `classroom.yaml` 也**已经把这条语义逐字写在注释里**（连"标 on_demand 会让课程表在课上根本不出现"这句都写了）。
**风险转交内容侧**：上一路建议把 `anchor.check` 从 `{ n_turns: 5 }` 改成 `{ every: on_demand }`——**照做的话那个块会永久不注入**（在 M3 工具路径落地之前）。这在教室里已有同型注释，故我不动代码、只在此登记；**是否接受"检查段彻底不注入"，由教室侧/用户拍板**（写进末尾待确认清单）。

### 2.2 第 2 条：启动层"每课一次" vs "每进程一次" —— 🔴 **这条改代码**

**事实**：`position.target: system` 的块**不经过注入计划器**〔A07〕；引擎在装载时把它们一次性注册成 `systemPrompt.section`〔A08〕。注册后常驻 system prompt（每轮都在），**块上写的 `frequency` 一个字都不参与裁决**——而在此之前，引擎对它是**静默忽略**的。

**为什么必须改**：这正是本项目反复踩过并写进代码注释的那条红线——"未实现的键一律报错，不静默忽略（写错的声明若被放过，就成了'配了不生效'）"。而且新提示词把 **① 常驻层**写成"系统段 · **每轮**"：一个照着官方六层写 `frequency: { every: turn }` 的教室作者，会以为自己在声明"每轮重注"，实际拿到的是"装载时注册一次"——**两份文档说同一件事、行为不同**。

**改法（新增两条校验）**〔A01〕〔A02〕：
```diff
   // 🔴 启动层（target: system）的频率：引擎**只在装载时注册一次** `systemPrompt.section`
   //    （index.mjs 第 2 节），注册后常驻 system prompt（每轮都在）→ 块上的 `frequency`
   //    **不参与任何裁决**。故非 `once` 的写法一律报错，**不静默忽略**（与 assertKnownKeys 同一条规矩：
   //    "配了不生效"正是本项目反复踩过的坑）。
+  if (position.target === 'system') {
+    if (frequency.every !== 'once') {
+      throw new ManifestError(
+        `${at}(${id}) target=system 的块只能用 frequency: { every: once }（得到 ${JSON.stringify(frequency)}）——` +
+          `系统段在装载时注册一次并常驻 system prompt，块上的频率不参与裁决；` +
+          `要随讲次/相位变化的内容请改成 target: chat 的块（可用 frequency.anchor: lesson_start 或 phase 门）`,
+      )
+    }
+    if (frequency.anchor === 'lesson_start') {
+      throw new ManifestError(
+        `${at}(${id}) target=system 的块不支持 frequency.anchor: lesson_start（每讲重注）——` +
+          `系统段注册是一次性的（见 index.mjs），写它等于声明了一个不会发生的行为；` +
+          `要每讲重读的内容请改成 target: chat 的块`,
+      )
+    }
+  }
```

**兼容性（先预检、后改、再复检）**：用引擎自己的解析器扫**全 `code/` 树**（含 `classrooms/`、`clients/`、`skills/` 与全部夹具）：

| 时点 | 可解析的 classroom.yaml | system 块 | 非 `once`／`lesson_start` 的 |
|---|---|---|---|
| 改前 | 54 | 217 | **0** |
| 改后 | 54 | 217 | **0** |

→ **零破坏**（55 个文件里那 1 个解析失败的属另一棵树的残缺夹具，原因与本次改动无关，改前改后一致）。真实教室 `cs-os` 装载自检通过：47 块、5 个 system 块全为 `every: once`。

**新增单测 3 条**〔A10〕：非 `once` → 报错；`anchor: lesson_start` → 报错；`every: once`／`anchor: session_start` **仍然合法**（这两个锚点取值就是频率锚点值域的全部〔A05〕；后者等价于"不写 anchor"＝进程一次，锁住"现有教室逐字不变"）。

**没做的事（刻意）**：**没有**去实现"按讲次重注系统段"。理由：① 官方标准下启动层内容不随讲变化（本教室的 `system_core`／`world.*` 都是不变文件），做了等于为假想需求造机制；② 系统段重注册是否被宿主支持**未取证**——没证据的行为变更不进代码。→ 改为**文档声明**（登记给内容侧：启动层＝每进程一次）。

### 2.3 第 3 条：⑤ 知识锚"没有对应 block"

**事实**：`layer` 是**纯标签**——解析期只做值域校验〔A03〕，**全引擎的功能代码一处都不读它**（`planTurnInjections` 只看 `position.target`／`frequency`／`phase`／`lesson`）。所以"把 `anchor` 这个 layer 改名"**对行为零影响**，改的只是可读性。

**结论：文档级结论，不改代码**。理由：
- 六层能被现有字段表达，**不需要新 layer**；
- 新口径下 ⑤ 的语义是"当前问题涉及相应机制时核对（**按需**）"，而引擎里**真正存在的"按需"只有 `phase` 门与讲次门**（`on_demand` 是死的，见 §2.1）——cs-os 的 ③ 情境层已经是用相位门实现的，落点没有缺失；
- "⑤ 挂哪一块"是**内容侧/用户的 A/B/C 取舍**（上一路 §6.3 U5 已列），引擎侧不需要为它动任何东西。

### 2.4 第 4 条：① 常驻层的 `learner_profile.md`

**事实**：本教室把它放在 `state` 层、`chat`／`depth 0`、`n_turns: 5`；官方 ① 常驻层要求"系统段 · 每轮"。引擎**两种写法都支持**（差别只在教室 yaml 的 `position`／`frequency`），`layer` 标签不影响行为〔A03〕。

**结论：文档级结论，不改代码**。这是**教室配置的选择**（理由是"它是观察累积型文件、每轮注入太贵"），登记在教室文档即可；引擎侧没有任何东西需要改。

### 3.2 四问逐条（贴原始记录）

#### 问 1 · "顺势讲因果链"了没有？

**判据（新规原文）**：*"学生说出关键关系后，确认并讲清当前最相关的一段因果链"*；教室第 1 讲那半句更硬：*"学生说出'轮流'后，**同一轮**明说稿子与程序、编辑与核心的对应关系，并开始讲'切走后怎样接着跑'的进程状态与上下文切换。"*

**结果：两次会话都做到了，而且是同轮完成三件事。**

会话 2 第 2 回合（学生说完"轮流"之后的那一轮，逐字摘）：

> "嗯。**轮流——这两个字是对的。**" … "这两份稿子，就是两个程序。我这双手，就是 CPU 交给程序的执行机会。… 轮流改，就是两个程序轮流用这个位置——**这叫时间共享**。"
> "不过你那句'CPU 一次只能执行一条指令'——嗯，这个得改。那是我这个简化模型的说法，不是真实 CPU 的事实。…所以我们只说：在今天的模型里，一颗核心某一刻只有一个执行位置。"
> "然后是第二件事。我改到第七页，红笔停在半句上，然后放下它去改右边那份。等会儿回来要接得上，我就得先留下'改到哪了'。" … "**进程也一样**。它被切走之前，得留下足以接着跑的东西。最要紧的一个叫**程序计数器**…这一整套，是它的**执行状态**。…这个动作，叫**上下文切换**。"
> "有一点别弄混：保存执行状态不是把程序文件重新抄一遍。…执行状态要是丢了，结果只是接不上——不能说它会自己从程序开头重跑。"
> "**但现在还剩一个洞——由谁决定什么时候切？** 如果 A 一直在算，不读文件、不调用任何系统服务、也不主动停下，那操作系统凭什么还能把控制权拿回来？"

会话 1 第 2 回合同型：先确认对应关系（"稿子，对应程序…一双手，对应核心分出去的那一份执行机会；轮流处理，对应时间共享"），再讲"程序文件是静态的 → 跑起来才有'正在进行的执行' → 寄存器/计数器/内存＝进程状态 → 切走前保存、回来恢复 → 上下文切换"，结尾同样**提出一个真正的新问题**（非自愿抢占）。

**判为"做到"的四条证据**：① 学生**不再提问**的那一轮，教师**没有**用问题收尾，而是把机制讲下去；② 因果链是**完整一段**（静态文件 → 运行中的执行 → 状态 → 保存/恢复 → 切换），不是零散事实；③ 讲完指向**新的关口**（谁决定何时切）而不是复述刚讲的；④ 两次会话还各调了一次 `classroom_animate_template`（`prepId: ctx-switch`，命中课前预热）来承载"随时间变化"的那一步，且**先讲后画**（正文先出现"你看这条时间轴。"／"她把这段交替在时间轴上摊开"）。
