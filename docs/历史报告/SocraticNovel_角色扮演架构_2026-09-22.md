## §1 先回答两句话

### 1.1 "角色卡让我们不用重写人格" —— ✅ **对**（本稿初版判错，2026-09-22 已更正）

> 🔴 **更正记录**：初版写"现成的老师人格不存在 → 人格仍要自建 2–4 天"，**这个结论是错的**，错在**没有读进 `characters/*.md` 的内部结构**。用户当场指出：**"不是老师的人格"** —— 人格**不需要是"老师人格"**，因为教学法在另一层。已按仓库实测重写本节。

**仓库实测：人格文件里本来就分好了两层**（`teacher/characters/*.md`，3 个文件，13.1–15.1KB）：

| 段 | 内容 | 属于 |
|---|---|---|
| 基础信息 / 四维度描写（表层身份、内在经历、人格内核、核心矛盾）/ 她说话的样子 / 过往信息碎片 / 暗线种子 | **人格本体** | 🟢 **可以直接用现成的** |
| 🔴 **「教学功能与行为触发」+「教学方式」**（`rin.md` 是「隐喻空间规范」） | **人格 × 教学法的接口** | 🔴 **只有这一节需要我们补** |
| 「对电磁学的看法」等 | 学科观 | 半接口 |

**接口节的实测体量**：`rin` 3,863B ／ `ritsu` 2,779B ／ `saku` 3,639B → **每个角色 ≈2.8–3.9KB**。

🔴 **所以正确结论**：
- **人格本体可以照搬社区卡**（不要求那张卡是"老师卡"——**教学法在 `system_core.md`，不在卡里**）；
- **我们要写的只有"接口"这一节**：这个人**用他/她自己的方式怎么教这门课**（类比库、行为触发、局限、学科观）——**小时级，不是 2–4 天**；
- **初版"必须自建人格"的结论作废**（连带把"角色卡省不了人格"这条也作废）。

### 1.2 "教学规则独立于人格" —— ✅ **对，而且这正是今天切分后的仓库结构**
| 层 | 文件 | 回答的问题 | 换它要动什么 |
|---|---|---|---|
| **人格** | `characters/*.md` | **谁**在教（性格、语言习惯、她的世界） | 只换人格，教学法不动 |
| **教学规则** | `config/system_core.md` | **怎么**教（苏格拉底法／五级梯度／复习／做题／轮值／防漂移） | 只换教法，人格不动 |
| **叙事规则** | `config/narrative_core.md` | **怎么演**（红线、散文标准、三位老师的声音速查） | 与教学规则**互不污染**（今天切分的唯一目的） |
| **世界与故事** | `story.md`、`story_progression/` | 在**什么情境**里教 | 换世界不改教法 |
| **教什么** | `config/curriculum.md`、`config/knowledge_points/` | **教什么**、教到哪 | 换教材不改人格 |
| **状态** | `runtime/*` | 这个学生**现在**在哪 | 每课更新 |

🔴 **这张表就是"混搭"能成立的全部前提**（`D1-②`：**用户的角色 × 别人的教材**）—— 因为**人格与教学规则正交**，所以两者可以自由组合。

## §2 酒馆最值得抄的一件事：**它按"位置 + 频率"组织提示词，而不是按"时间"**

### 2.0 🔴 源码级更正（2026-09-22 主代理自查，**推翻本节的文档读法**）

> **背景**：用户质疑"那个子代理是不是根本没看源码" → **核实成立**：酒馆研究子代理**只读了官方文档 + V2 规范 + 第三方博客，`public/scripts/*.js` 一个都没抓**（它自己在 §7 第 1／2／6 条承认"未核源码"）。→ 主代理**自己去抓了源码**，落在 `开源线/证据/酒馆源码/`（`st_openai.js` 307KB ／ `st_extensions.js` 88KB ／ `st_authors-note.js` 23KB，均附 SHA-256）。

**核到的事实（`public/scripts/openai.js`，release 分支）**：

1. 🔴 **"Post-History Instructions" 在实现里不是一个独立机制** —— 全文 `post_history` **0 命中**。它实际是 **`injection_depth`（注入深度）的一个取值**。
2. **拼装实现** = `populationInjectionPrompts(prompts, messages)`：
   - 遍历 `i` 从 `0` 到 `getExtensionPromptMaxDepth()`；
   - 取 `prompt.injection_depth === i && prompt.content` 的条目；
   - 按 `injection_order`（默认 `100`）分组，**从高到低**排（`(a,b) => +b - +a`）；
   - 同 order 内按 role 顺序 `system → user → assistant`（注释原文：*"Order of priority for roles (most important go lower)"*）；
   - `messages.splice(i + totalInsertedMessages, 0, ...roleMessages)`；
   - 🔴 **紧接着 `messages = messages.reverse();`（第 873 行）** → 说明传进来的数组是**最新在前**，所以 **`injection_depth = 0` 插在最新消息之前 → 反转后落在 prompt 最末尾** ✅ **与文档一致，但现在这是核过实现的，不是"文档说"。**
3. **同一套实现**还服务于：Author's Note、World Info 的 `@D`、向量检索／Data Bank 注入、STscript 注入（都走 `getExtensionPrompt(extension_prompt_types.IN_CHAT, i, ...)`）。

🔴 **对我们架构的意义（本节的结论要改）**：**"贴尾部"与"固定深度"在酒馆里本来就是同一个机制（depth=0）**，不是两件可以分别照搬的事。
→ **我们的 ② 纪律层 = 一个 depth 值**，不需要设计两套东西。§3 的五层因此可以简化：② 与 ⑤ 共用同一实现（不同深度／不同频率）。

### 2.1 文档读法（保留，作为对照）

酒馆的 Prompt Manager 把内容按**在最终 prompt 里的位置**排序，而不是按"什么时候读"【原文】：
> *"Prompts placed closer to the top of the interface are sent earlier. The bottom of the list is the last thing sent to the model (typically, this would be your Post-History Instructions)."*

并且给了两件我们完全没有的东西：

| 机制 | 原文 | 意义 |
|---|---|---|
| **历史之后指令权重更高** | *"system instructions written **after** the conversation history have a much stronger weight on current models' generations than instructions written **before**"*（V2 spec README） | **纪律放尾部 > 放开头** |
| **depth（固定深度注入）** | *"a Depth of 0 will be sent after the last chat message…"*；*"always stays at a static depth in the chat history, **regardless of its progression**"* | **固定位置 = 不被长对话稀释** |
| **影响力原理** | *"The closer the Author's Note is to the bottom of the prompt, the more impact it has on the next AI response."* | 位置本身就是一种权重 |
| **注入频率** | *"Frequency 1 = … inserted with every user input prompt. Frequency 4 = … every 4th"* | 用频率控制注意力成本 |
| **First Message 定风格** | *"The model is more likely to pick up the style and length constraints from the first message than anything else"* | 开场白定调，比写规则更有效 |

🔴 **而这条与长上下文证据独立撞在一起**：那边说"早置 system prompt 的影响会被长对话稀释"（有出处，厂商自己把 compaction 定为 primary strategy）。**两条互不相关的来源指向同一个动作** —— 这不是巧合，是同一个注意力事实的两种表述。

### ⚠️ 我们现在的架构正好踩在最弱的位置上
`AGENTS.md` 目前是**三级加载、按时间组织**（启动第一步 → 课前第二步 → 用到时第三步），而且**把 `system_core` + `narrative_core` 一次性全读进最前面**。
→ 在 1M 长对话里，**最需要被遵守的纪律，被放在了影响力最弱的位置**。

## §3 🔴 新架构：从"按时间三级加载"改成"按位置与频率的五层"

### 3.0 🔴 先说清一个前提：**宿主不把"拼装权"给我们**（2026-09-22 核实）

| | 酒馆 | 我们（DSH 里的一个 skill） |
|---|---|---|
| 谁拼 prompt | **它自己**（前端，有 Prompt Manager） | **宿主**（`dsh-system-prompt` 包；已核实它的 system prompt 本身就是**按命名段落**组织的：`sectionDefinitions`／`sectionByName`） |
| 能不能指定"这块插到 depth 3" | ✅ 能（每块带 role／position／depth／order） | ❌ **不能** —— 拼装权不在我们手上 |
| 我们能控制什么 | —— | 只有两样：**① 写什么内容 ② 什么时候读文件** |

🔴 **结论**：**"拆成板块"我们做得到；"分别注入到指定位置"我们做不到** —— 除了下面这一条真实可行的路径。

**我们实际能用的三种手段**：

| 手段 | 内容落在哪 | 位置可控吗 |
|---|---|---|
| 工作区 `AGENTS.md`（指令） | 系统提示区（**最前**） | ❌ 只能控制"写什么" |
| **用文件工具读文件** | 🔴 **历史之后**（工具结果就在对话流里） | ✅ **位置由"什么时候读"决定** —— 这就是我们的 depth 0 |
| **模型自己在 thinking 里重述** | 🔴 **历史之后** | ✅ 每轮都能做，成本 ≈ 0 |

→ **所以我们的"分别注入"只有一条路：用「读取时机」控制位置**，而不是像酒馆那样有一个拼装层。

### 3.0.1 那我们该抄的是它的**元数据思想**，不是它的机制

既然宿主不替我们拼，**我们就把"拼装规则"写成纪律，让模型自己遵守**：给教室每个板块标注**「该在什么位置、以什么频率出现」**。这份标注就是我们自己的 Prompt Manager 替身：

| 板块 | 位置（声明） | 频率 |
|---|---|---|
| `system_core.md`（教学法） | 启动（系统段） | 一次 |
| `narrative_core.md`（叙事＋声音） | 启动（系统段） | 一次 |
| `characters/*.md`（人格＋教学接口） | 启动 | 一次 |
| **`_anchor.md`（纪律层）** | 🔴 **每轮课前读（= 历史之后）** | **每轮** |
| `runtime/progress.md`（状态） | 课前 | 每课 |
| 教材片段 | 用到时（= 历史之后） | 按需 |

⚠️ **代价要说清**：这条路的可靠性**靠模型遵守**，不是宿主的确定性机制 → **这正是 M4 要测的东西**（有锚定／无锚定的纪律遵守率）。


| 层 | 放什么 | 位置（在最终上下文里） | 频率 | 体量目标 |
|---|---|---|---|---|
| **① 常驻层** | 老师人设核心（**短**）＋学生档案＋课程定位 | **最前**（固定） | 每轮 | ≤2KB |
| **② 纪律层** | 🔴 **教学铁律**（只问不说／不抢命名权／不给结论／最后一英里规则）＋**本课"不许违反项"** | 🔴 **历史之后**（贴本轮对话，≈Depth 0） | 每轮 | ≤1KB |
| **③ 情境层** | 教材片段、当章故事节点、知识点覆盖 | 中部（按注入位置分级） | 按需 | 按需 |
| **④ 状态层** | 学生名／课次／日期／上次卡点 | **模板化，每次加载时渲染**（不写死在静态文件里） | 每轮求值 | ≤0.5KB |
| **⑤ 锚定层** | 角色锚（老师特质）＋**知识锚**（本课核心事实校验） | 固定深度 | **每 N 轮**（不是每轮） | ≤0.5KB |

**对照酒馆**：① = Permanent Tokens ｜② = Post-History Instructions ｜③ = World Info 注入位置分级 ｜④ = 宏模板每次渲染 ｜⑤ = Character's Note（深度注入）+ Insertion Frequency。

### 3.1 怎么在不改 agent loop 的前提下做到 ②（纪律层贴尾部）
两个候选（**都可测，未定案**，已登记为待办 `R14`）：
- **(a) 每轮自我锚定**：在当轮回复的 thinking 区用极短形式重述 3–5 条最硬纪律 —— 那段文字天然落在**历史之后**。成本 ≈ 0。
- **(b) 固定深度回读**：课前读一次 ≤1KB 的 `_anchor.md`；文件读取结果同样落在历史之后（粗粒度版）。

### 3.2 ④ 状态层为什么要"模板化"
【原文】酒馆的宏 *"are dynamic placeholders that get replaced with actual values when text is processed"*；`{{charDepthPrompt}}`、`{{summary}}`、`{{lastMessage}}` 每次构建 prompt 时**重新求值**。
→【推断】我们的教室也应该定义**每次加载时渲染的字段**（学生名／课次／日期／上次卡点），而不是把状态写死在静态文件里。**状态写死 = 每次都要人改文件 = 一定会漂移。**

## §4 明确**不做**的（因 1M 上下文而失效，照搬是浪费）

| # | 不做的机制 | 理由 |
|---|---|---|
| 1 | **关键词触发式世界书注入**（含递归／预算／Min Activations／组互斥） | 整套机制的前提是"上下文放不下全部资料"；1M 下教材全文可常驻 |
| 2 | **摘要压缩对话历史** | 触发点是"消息被挤出 prompt"；1M 下很少发生。**只保留"跨多日课程的进度摘要"** |
| 3 | **向量检索（RAG）** | 教材已在上下文内；且检索**不可预测**（原文：*"it's impossible to predict exactly what entries will be inserted"*）—— **教学以知识正确性为底线，不能接受不可预测注入** |
| 4 | **多模型族 Instruct 模板体系** | 我们模型栈固定。但"按目标模型的指令遵循习惯组织 system 段"仍然适用 |
| 5 | **概率触发／随机事件** | 游戏化机制，教学不需要随机注入 |

## §5 🔴 必须**自研**的（酒馆没做、而教学必须有）

| # | 缺口（酒馆侧原文依据） | 我们的解法 |
|---|---|---|
| **C1** | **教材不会自动进场景**——酒馆靠用户手动绑世界书；`character_book` 字段的诞生正是因为这个痛点（README 原文：*"the extra effort required for users to download and import external worldbooks turns them away"*） | 教材就是工作区文件，由文件工具直接读，**零用户配置**——"自动进场景"是**系统行为**，不是用户行为 |
| **C2** | 🔴 **注入与摘要都会失真**——WI *"does not guarantee its appearance in the generated output messages"*；摘要 *"may lose some important details or contain hallucinations"* | **事实层绝不依赖生成式注入**：知识点原文经文件工具**逐字读取**、答案可回查；摘要**只用于进度，不用于事实** |
| **C3** | **没有进度/课程状态概念**（状态散在变量宏、chat metadata、手动注记里） | **状态笔记本文件**（当前课次／掌握矩阵／待复习），由工具读写，取代宏变量 |
| **C4** | **从不判断回复对不对** | 加"**对答案**"环节：学生作答后由系统调知识文件比对／讲解 |
| **C5** | **官方对漂移无专章对策**（本次检索未找到） | **知识锚**：核心事实常驻 ＋ 每轮末尾短校验（本课要点是否与教材一致） |

**一句话总结**：**搬走它的"分层 + 深度 + 频率 + 模板化"，丢掉它的"检索 + 压缩 + 随机"，自己做它没做的"自动加载 + 事实回查 + 答案评估"。**
