## 0. 一句话结论（先给）

> **1. 模板化确实是最大杠杆，但省的不是"打字"，是"设计"。**
> 同一场景、同一模型、同一教室，唯一变量是"老师走哪条路"（n=2 每组）：
> **从零写脚本 30.8 秒 → 填模板参数 14.8 秒（模型段，2.1×）**；
> **整轮会话墙钟 79.1 秒 → 28.0 秒（2.8×）**；整轮模型生成 **64.2 秒 → 21.4 秒（3.0×）**；
> 模型要吐的东西 **≈4 KB Python → 618–655 字符 JSON**。
> 拆到 step 才看清省在哪：从零写时模型**先花 30.4 秒"想这张图怎么画"**，再花 10.1 秒把 4.9 KB 脚本敲出来；
> 填参数时**第一个 step 9.8 秒就发出工具调用**。→ **省的是那 30 秒的设计时间，不是那 10 秒的打字时间。**
>
> **2. "备课"（课前预热）可行，而且成本低得几乎可以忽略——但有一个硬前提。**
> 预热起 2 段任务**只要 22 毫秒**（spawn detached 渲染器），2 段全部就绪 **15.6 秒**（渲染 4.24 s ＋ 3.76 s，含闸门）；
> **模型调用成本 = 0**（脚本由模板从课程数据里的参数拼出来，不需要任何模型）。
> 课上老师**取用**时入参只有 **24 个字符**（`{"prepId":"fifo-vs-sjf"}`），**盘上一个新任务目录都不加**（命中缓存）。
> 🔴 **硬前提＝"必须先知道下一轮要什么"。** 模型猜不出学生下一句问什么，**只有课程数据能声明**。
>
> **3. 派子代理写这条路人用户猜的方向对了一半：它更慢、也没有更准。**
> 同一场景：子代理 **217 秒 / 48 秒（均值 132.5 s）** vs 老师自己写那一轮 **103.3 / 54.8 s（均值 79.1 s）**——**慢 1.7 倍**，
> 而且子代理**做的活更少**（它不上课、不读教材，只负责把这段动画做出来）；
> 而"一次就过质量闸门"的比例 **1/2 vs 2/2**（子代理第一份片子被闸门判 **BLOCK**：脚本里声明并 play 了箭头，全片一帧都没画出来）。
> 它唯一不可替代的价值是**能在交付前自己修错**（第二份修掉了 2 个真渲染错）。**就"省时间"这个目的而言，这条路不值得。**
> ⚠️ 两处不可比已在 §3.2 写明：① 两组的活不一样；② A′ 有一轮**自己跑去渲染并看帧**（103 s），说明"老师自己写更快"**只在不自己验证时成立**。
>
> **4. 🔴 用户问的"下一轮要用、这一轮先跑"——明确答复：技术可行，但边界在"知识"不在"技术"。**
> · **可预知的**（课程数据里写明的图元）→ **可行且该做**：课前预热，0 模型调用 ＋ 十几秒渲染，课上 0 秒取用。
> · **不可预知的**（学生即兴提问引出的图）→ **不可能**。子代理也不比老师更早知情——它同样要等到"知道要画什么"才能开工，
>   所以"派子代理先跑"在不可预知的情况下**只是把同一段等待换了个进程**。
> · 对不可预知的那一半，只有三条出路：**能画图就画图（秒级）／用模板（10–20 秒）／先讲后画（把等待挪到学生已有内容之后）**。
>
> **5. 全量单测 347 全绿**（基线 321 未被破坏 ＋ 新增 26）。
> **教室不声明 `animation:` 时不挂 `prep` 段、不注册任何新工具、注入逐字不变。**

## 1. ① 量化"模板化"能省多少（**全部实测，没有估算**）

### 1.1 口径（写死，防事后凑）

| 项 | 怎么量的 |
|---|---|
| 被测对象 | 真实教学会话里的模型（`socratic-headless` profile，教室＝**`cs-os` 的 `rsync` 副本**，cwd＝副本目录 → 教室自己的 AGENTS.md 正常注入）。**绝不写真教室** |
| 场景 | 第 3 讲「为什么 FIFO 会让一个很长的任务把后面短的任务全堵住」——**三组逐字同一句开场** |
| 唯一变量 | 老师走哪条路：自己逐行写 ManimCE 脚本 ／ 调 `classroom_animate_template` 填参数 |
| **模型段** | `turn/start` → 目标工具调用落盘的墙钟。**取自宿主自己落盘的会话事件流**（`session.v3.jsonl` 的 `time` 字段），不是我自述 |
| **端到端** | 模型段 ＋ 渲染 ＋ 质量闸门（A 组现场渲；B 组由引擎后台渲） |
| 成功判定 | 真渲出 mp4 **且** 过质量闸门（`animation-gate` 判 PASS） |
| 组别 | A＝现状（prompt 不给数字，模型自己设计例子）；**A′＝公平对照**（prompt 给与 B **逐字相同**的数字）；B＝模板 |

🔴 **为什么要补 A′ 组**：第一版只跑了 A 与 B，而 B 的 prompt 里**必须**写出具体数字（模板参数就是数字），A 的 prompt 没有——
**A 与 B 的差里混着"少想了一点"**。补 A′ 之后，**A′ vs B 才是纯的"写代码 vs 填参数"**。两组都报，不挑好看的。

🔴 被测路由与本会话同一条（`deepseek-v4.1-flash`）；`manim==0.21.0`；**n=2 每组，方差很大**（见 A′ 的 25.1 vs 36.4），
所以下面只说"这一批实测"与量级，**不当普遍规律**。

### 1.2 三组结果

| 组 | 走哪条路 | **模型段**（要等的那一段） | 整轮模型生成合计 | 整轮会话墙钟 | 端到端到"可播" | 闸门 | 成功率 |
|---|---|---|---|---|---|---|---|
| **A**（现状：自己写；prompt 未给数字） | `classroom_animate` 那条路 | **41.0 / 35.0 s**（均值 **38.0**） | 53.7 / 52.0 s | 58.7 / 73.8 s | 69.0 / 58.3 s | PASS 2/2 | 2/2 |
| **A′**（自己写；prompt 与 B 给同样数字） | 同上 | **25.1 / 36.4 s**（均值 **30.8**） | 80.2 / 48.2 s | 103.3 / 54.8 s ⚠️ | 58.1 / 62.6 s | PASS 2/2 | 2/2 |
| **B**（填模板参数） | `classroom_animate_template` | **10.0 / 19.7 s**（均值 **14.8**） | 17.4 / 25.3 s | **20.0 / 35.9 s** | 37.6 / 74.0 s（含后台渲染，**不占老师时间**） | PASS 2/2 | 2/2 |

**读法**：

- **模型段：A′ 30.8 s → B 14.8 s，快 2.1×**（每轮省约 16 秒）；A（不控信息）38.0 s → 14.8 s，快 2.6×。
- **整轮会话墙钟：A′ 79.1 s → B 28.0 s，快 2.8×**（A 66.2 s → 28.0 s，快 2.4×）。
- **整轮模型生成：A′ 64.2 s → B 21.4 s，快 3.0×。**
- **模型吐出来的东西：A′ 脚本 3.8–4.3 KB Python；B 参数 618–655 字符 JSON（小约 6.5 倍）。**
- **渲染＋闸门那一段与走哪条路无关**（同一台渲染器、同一份闸门）：实测单段渲染 **3.3–18.5 s**（方差来自 CPU 争用）、闸门 **10–25 s**。
  所以"端到端"那一列在 B 组反而可能更大——**因为 B 的渲染在后台跑、与老师继续讲重叠，老师并没有为它等**。
- ⚠️ **A′ run1 的 103.3 s**：那一轮模型**自己**又渲了一遍还看了帧（18 次工具调用里含 6 次 `bash` ＋ 2 次 `read_image`）。
  所以"老师自己写"这条路的耗时**不稳定**：不自己验证 25–36 s，自己验证 103 s。**§3.2 与 §3.3 会再讲这一条。**

### 1.3 🔴 省的是"设计"，不是"打字"（step 级拆解）

逐 step 拆开（`evidence/step-breakdown.json`，A run1 与 B run1）：

| | step 1 | step 2 | step 3 | 之后 |
|---|---|---|---|---|
| **A（从零写）** | 生成 **30.4 s**（模型输出 103 KB 推理）→ 2 个 read | 生成 **10.1 s** → `write`（4.9 KB 脚本） | 生成 2.6 s → bash | 生成 6.3 s（set_phase）＋ 4.3 s |
| **B（填参数）** | 生成 **9.8 s** → **直接调 `classroom_animate_template`** | 生成 3.1 s → 再调一次（见 §1.4） | 生成 4.5 s → 收尾 | — |

→ **A 的第 1 个 step 就花掉 30.4 秒**：它在"设计这张图怎么画"（哪几条泳道、怎么排版、刻度怎么摆）。
B 的第 1 个 step 只有 9.8 秒——**图的形状是模板给的，模型只需要把数字填进去**。

🔴 **这条改变了"该往哪儿优化"的结论**：把模板做得更省 token（少打字）**没用**；
真正省下来的是**让模型不必从零做版面设计**。反过来说，**越是需要"设计"的图，模板的收益越大**；
模型见过很多次的常规图，收益会小一些。

### 1.4 🔴 一条负面发现（不改掉就是白花一轮）：模型真会写 `color: "orange"`

B 组 run1 **调了两次** `classroom_animate_template`——第一次被**拒绝**了，因为模型给第二个任务写了
`"color": "orange"`，而我的白名单里只有 `amber`。**这不是语义错误，只是一个词的拼法**，却白花一轮。

→ 已修（`lib/animtemplates.mjs`）：常见同义词**收敛到规范名**（`orange→amber`、`gray→grey`、`yellow→amber`、`violet→purple`、`cyan/sky→blue`），
规范名进脚本、进缓存键（**同一个视觉只有一份缓存键**）。**边界写死：只收同义，不收近似色**——否则白名单就没意义了。
单测钉住：`别名与规范名算出同一个参数`。

### 1.5 模板本身的可靠性（先证明"能渲出学生看得懂的画面"）

3 个模板用**真实教材场景**（FIFO/SJF 时间轴、进程三态推移、平均周转时间对比）各生成一份脚本并真渲染：

| 模板 | 生成脚本 | 渲染墙钟 | 闸门 |
|---|---|---|---|
| `timeline`（时间轴/甘特） | 72 行 / 3 999 B | 2.68 s | **PASS**（0 阻断，1 条 D2 待人工目视） |
| `state_machine`（状态机推移） | 57 行 / 3 145 B | 2.88 s | **PASS**（0 阻断） |
| `bar_compare`（条形对比） | 48 行 / 2 385 B | 2.06 s | **PASS**（0 阻断） |

目视核对（接触表，`evidence/template_render.json` ＋ 各 `tmp/gate/<case>/contact_sheet.png`）：
时间轴两行泳道＋行标题＋轴刻度＋块内标签（宽块左标签/右完成时刻、窄块居中）无重叠；
状态机三节点环形布局＋四条迁移箭头（成对反向边走弧线）＋推移步骤字幕；条形对比横向条＋左标签＋右数值。
🔴 一处**已被生成器主动规避**的坑：块内文字一律**写在矩形内部**（居中或左右对齐），绝不写到矩形外面——
写到外面就会撞上相邻泳道/刻度，闸门会判 D2 文字重叠直接 blocked。

## 2. ② 课前预热（用户说的"备课"）

### 2.1 数据层：教室怎么声明"本讲要放哪几段动画"

🔴 `code/classrooms/**` **不在可改范围**，所以本批**只设计格式 ＋ 在插件侧实现"读取＋校验"**，
用 fixture（`test/fixtures/prep-classroom/`）测试，**真教室一个字都没改**。

**声明格式**（`classroom.yaml` 顶层新增可选 `prep:` 段）：

```yaml
animation:
  enabled: true            # 已有；声明了 prep 却没启用动画 → 引擎报错（死配置）

prep:
  items:
    - id: fifo-vs-sjf              # 必填，本教室内唯一（老师课上按这个 id 取用）
      lesson: 3                    # 必填，讲次（整数；超 classroom.lessons 报错）
      template: timeline           # 必填，模板 id（timeline / state_machine / bar_compare）
      title: 长任务怎么堵住短任务？  # 必填，写进动画索引
      material: materials/ch03.md  # 必填，**相对教室目录**：缓存键的教材哈希来源
      caption: 针对「FIFO 让长任务把后面全堵住」这一步   # 可选
      required: false              # 可选，默认 true
      params:                      # 必填，模板参数（形状由模板定，校验在模板里）
        note: 周转时间 = 完成时刻 − 到达时刻
        lanes:
          - label: 先到先服务（FIFO）：A → B → C
            segments:
              - { start: 0, end: 100, label: A, color: blue, endLabel: "100" }
              - { start: 100, end: 110, label: B, color: amber, endLabel: "110" }
```

**三条设计口径**（都是被"静默失效"坑出来的，写进 `lib/prep.mjs` 文件头）：

1. `template` 与 `params` **当场校验**，用的是**与课堂上调工具完全同一个校验器**——写错的报错文案逐字相同，
   "课前写声明"与"课上现生成"不会各有一套判据；
2. 声明了 `prep:` 却没有 `animation: {enabled: true}` → **报错**（死配置：预热跑不了、工具也没注册，
   而作者会以为"我备过课了"）；
3. `material` 必须指向教室目录内的真实文件 → **不存在就报错**。
   🔴 它不存在 ⇒ 缓存键永远算不出来 ⇒ **每次上课都重渲一遍，而且不会报错**——这是最难查的一类失败。

### 2.2 缓存键 = 讲次 ＋ 教材内容哈希 ＋ 模板版本 ＋ 参数

```
cacheKey = sha256("v1|lesson=<讲次>|template=<id>@<版本>|material=<教材文件内容 sha256>|params=<规范化 JSON>")
```

| 维度 | 为什么在键里 |
|---|---|
| **讲次** | 同一段动画在不同讲是两次不同的教学事件（索引行、通报、课后回看都按讲次归类） |
| **教材内容哈希** | 教材改了 → 这段动画讲的例子可能已经过时 → **必须重做**。这是"内容变了自动失效"的唯一凭据 |
| **模板版本** | 模板生成逻辑改了 → 旧片子不是新模板的产物 → 必须重做（`TEMPLATES[id].version`，改生成逻辑必须 +1） |
| **参数** | 同模板不同参数当然是两段片子 |

🔴 **两条必须写明的实现细节**：

1. **用内容哈希，不用 mtime**。本项目已有实证：`rsync -a` 保留源 mtime、`git checkout` 也会改 mtime 而不改内容 →
   用 mtime 判"教材变没变"两个方向都会错。单测钉住：`改一个字 → 换键`、`同一份内容 → 同一个键`。
2. **参数必须先规范化再进键**（键排序、数字归一）。否则语义相同的参数写成不同键顺序会算出**两个键** →
   同一段动画渲两遍，而缓存看起来"没命中"。单测钉住：`参数对象键顺序不同 → 同一个键`。

⚠️ **一个已知取舍**（写进「待确认」）：讲次进键 ⇒ 两讲声明了**逐字相同**的一段动画时会各渲一次。
本项目教材按讲分文件（`materials/ch03.md` 与 `ch05.md` 内容不同），哈希本来就不同，所以实践中不产生额外成本。

### 2.3 引擎侧：课前/回合前批量起任务，课上"取用"而非"生成"

| 环节 | 实现 | 触发时机 |
|---|---|---|
| **预热** | `lib/prepstore.mjs` 的 `warmUpPrep`：算键 → 查缓存 → 没命中的按声明顺序起任务（复用 ANIM-ORCH 的 detached 渲染器） | ① **装载后立刻一次**（＝开课/课前就备上）；② **每个回合开头，若讲次变了**（＝上一讲结束时 postclass 把 `current_lesson` 推进，下一回合就把下一讲备上） |
| **清单送达老师** | 引擎在回合开头注入一条 `prep-list` 块（**一讲一次**）：列出本讲备好的段、`prepId`、模板、状态（已就绪/正在预热/别等它） | 同上 |
| **课上取用** | 新工具 `classroom_animate_template`：传 `prepId` → **先查缓存，命中立刻 ready（0 秒、不重渲）**；未命中则用声明里的参数现场套模板起任务 | 老师讲到那一步时 |
| **就绪通报** | 预热的任务到终态时，沿用 ANIM-ORCH 的跨回合通报，**文案改过**：预热的说"课前按课程数据预热的教学动画有结果了…**直接放这段**（不必再自己写脚本）"，与"你上一轮起的"区分开 | 终态后的下一个回合开头 |

🔴 **为什么预热的触发点放在 `pre-step` 而不是 `turn-stopping`**：`turn-stopping` 那一处
postclass 与引擎的监听顺序**没有契约**，讲次可能还没被推进 → 会预热到"上一讲"的清单；
`pre-step` 刚重读过 `progress.md`，讲次没有歧义。且只在**讲次真的变了**时做（每回合都做＝每回合读一遍教材文件，没必要）。

🔴 **并发**：预热受**同一个**并发闸约束（`MAX_CONCURRENT_TASKS`，默认 2）。超出的条目**不起**，
留在 `missing`，下一个回合边界再起（不排队到看不见的地方）。这也意味着预热任务与老师现场起的任务**共享**这 2 个槽位——
实测预热 2 段 15.6 秒就完了，正常不会与课上冲突。

### 2.4 🔴 成本模型（一节课预生成 N 段）

**实测输入**（都是本批真跑出来的数）：

| 量 | 实测值 | 来源 |
|---|---|---|
| 起 1 段任务（spawn detached 渲染器，不含渲染） | **约 11 ms**（2 段共 22 ms） | `evidence/prep-session.json` |

**模型**（用上面的实测值外推，明说是外推）：

```

              ＋ N × 11 ms           （起进程，可忽略）

一节课课上取用成本 ≈ N × 0 s（全部命中缓存）
```

| N（一节课几段） | 预热墙钟（外推，上界口径） | 模型调用 |
|---|---|---|
| 1 | ≈ 25 s | 0 |

**命中率**：

- 预热成功之后，**课上取用 100% 命中**——实测 **2/2** 次会话命中（含**跨会话**：另起一个新进程、复用同一份教室，老师照样传 `prepId`，
  **盘上新增任务目录 0**）。缓存键落在盘上（`task.json.cacheKey`），不靠内存。
- 未命中只有两种情形：① 预热还没跑完（老师讲得比渲染快）→ 退化成"现场套模板"（模型段 10–20 s）；② 教材改了（键变了）→ 重新预热。

**失败怎么退**（写死，不许静默）：

| 情形 | 引擎做什么 | 老师该说什么 |
|---|---|---|
| 渲染失败（`failed`）／闸门判不通过（`blocked`） | **不自动无限重试**：同一个键最多自动起 **2** 次（`MAX_PREP_ATTEMPTS`）；第 2 次还不行 → 状态落 `give-up`，注入里明说"**这段别等了**，改用 `classroom_draw`" | 讲到那一步改用板书图讲完；确实需要动画再现场调 `classroom_animate` |

## 3. ③ 老师自己写 vs 派子代理写（**含"子代理值不值得"**）

### 3.1 口径

- **老师自己写**（A′ 组，§1）：教学会话里的同一个模型逐行写脚本。它**看不到渲染结果**
  （`classroom_animate` 只落盘＋后台渲染，失败要等下一个回合的通报）。
- **派子代理写**（C 组）：一个**带执行权限**的 DSH 子代理，能自己跑 `manim`、读报错、改、再跑，
  **交付前自己确认渲出来了**（任务书逐字留档：`code/tools/anim-prep/子代理任务书_实验③.md`）。

### 3.2 对照表（n=2 每组）

🔴 **先声明两处不可比，不声明就是误导**：
1. **两组做的活不一样**。A′ 那一轮还包含**上课本身**（读教材、画板书图、宣布相位、给学生讲），
   子代理那一轮**只做"把这段动画做出来"**（不读教材、不上课）。所以"整轮墙钟"这一行对 A′ 是**偏重**的。
2. **A′ 有一轮自己跑去验证了**。A′ run1 的 18 次工具调用里含 **6 次 `bash` ＋ 2 次 `read_image`**——
   它自己渲了、还自己看了帧，**行为上已经接近子代理**。所以"老师自己写就快"这个结论**只在"老师不自己验证"的前提下成立**。

| | **老师自己写**（A′） | **派子代理写**（C） |
|---|---|---|
| **模型段**（turn 开始 → 动画请求落地） | **25.1 / 36.4 s**（均值 **30.8 s**） | 不适用（子代理那一轮没有"上课"这回事） |
| **整轮会话墙钟** | **103.3 / 54.8 s**（均值 **79.1 s**） | **217 / 48 s**（均值 **132.5 s**）——**慢 1.7×** |
| 尝试次数（渲了几次） | 各 1 次写成；run1 自己额外渲了 1 次核对 | **2 次 / 3 次** |
| **一次过质量闸门** | **2/2** | 🔴 **1/2** |
| 产物规模 | 脚本 3.8–4.3 KB / 111–130 行 | 脚本 6.8 KB / 199 行、5.8 KB / 124 行 |
| 自验证修好了什么 | run1 自己渲了一遍核对（**主动的**，不是被要求的） | run2：**修掉 2 个真渲染错**（`FadeIn(mob, shift=[...])` 传 list 而非向量；空 `Text("")` 取 `.width` 越界） |
| 自验证**没**修好什么 | — | 🔴 run1：子代理自己目视"末帧无重叠"判通过，**闸门判 BLOCK**——`D3 block`：脚本里声明并 `play` 了箭头/连线，**全片抽样帧里该色系墨迹 ≈ 0（连框线都没有）→ 箭头确实没画出来**；run2：交付文案里一个数字算错（"平均等待时间 70 → 10"，正确是 6.7），**它自己发现了但没改** |

### 3.3 结论（**如实说**）

> **1. 就"省时间"这个目的而言，派子代理写这条路不值得。**
> 整轮墙钟 **132.5 s vs 79.1 s（慢 1.7×）**；而且它做的活**更少**（不上课、不读教材）却更慢。
> 更要紧的是**一次过闸门还更差**：**1/2 vs 2/2**——子代理 run1 渲染成功、自己目视也判通过，**闸门判它阻断**。
> 原因：它多出来的"自己跑一遍"**只保证渲得出，不保证画面对**；而且它每修一次就要重渲一次（run2 渲了 3 次）。
>
> **2. 但它有一个不可替代的价值，要单独写清楚**：它是本批**唯一"在被要求之后稳定地、在交付前"发现并修掉渲染错误**的路径
> （run2 的两个错都是它自己读报错修掉的）。老师自己写那条路拿到 `failed` 通报时，**学生已经听完那一步了**。
> → 正确的用法不是"拿它替代老师写"，而是：**把它用在"可预知且模板表达不了"的那几段上、并且只在课前用**——
> 那时它慢一点没关系，学生不在场。
>
> **3. 一条附带发现，值得单独记住**：A′ run1 **自己**渲了一遍还看了帧（没人要求它这么做）。
> 说明"老师自己写"这条路的耗时**不稳定**：不自己验证时 25–36 s，自己验证时 103 s（与子代理同量级）。
> **"老师写更快"这句话，成立的前提是"老师不验证"；一旦它选择验证，两条件就并到一条路上去了。**

## 4. ④ 🔴 "下一轮要用、这一轮先跑"到底可不可能（**本任务的明确答复**）

**技术层面：可行，而且已经跑通了。** 非阻塞任务机制（工具占用 8 ms）、跨回合就绪通报、跨进程/跨会话磁盘缓存，
本批都实测过；预热起 2 段只用 22 ms，全部就绪 15.6 秒。

**但"先跑"必须先知道"跑什么"——边界在这里，不在技术上。**

| 情形 | 能不能预热 | 为什么 |
|---|---|---|
| **可预知**：课程数据里写明的图元（"第 3 讲要放 FIFO/SJF 时间轴对比"） | ✅ **能，而且该做** | 声明写在 `classroom.yaml` 的 `prep:` 里 → 引擎课前就能把参数变成脚本、把脚本渲成片子。**0 次模型调用** |
| **不可预知**：学生即兴提问引出的图（"那如果换成最短作业优先会怎样？"——下一句问什么只有学生知道） | ❌ **不可能** | 模型猜不出下一句；**课程数据也猜不出**。没有"要画什么"就没有参数，没有参数就没有脚本，没有脚本就没有片子 |

🔴 **三条必须一起说的边界**：

1. **"派子代理先跑"不能绕开这条边界。** 子代理不比老师更早知情——它同样要等到"知道要画什么"才能开工。
   在**可预知**的情形下，用子代理预热是可行的（代价：一次模型调用 ＋ 子代理墙钟）；
   在**不可预知**的情形下，它只是**把同一段等待换了个进程**，学生该等多久还是多久。
   → 所以：**预热的正确形态是"课程数据驱动"，不是"模型猜"**。
2. **预热也不该用模型。** 模板路径把"参数 → 脚本"这一步做成了**确定性变换**，于是预热**零模型调用**——
   这是它比"派子代理写"强的根本原因。只有"模板表达不了的过程动画"才需要回到模型（那时才有模型成本）。
3. **不可预知的那一半，出路是"换渠道"，不是"抢时间"**：能画图就画图（秒级）→ 用模板（10–20 秒）→ 先讲后画。
   其中"先讲后画"是 ANIM-ORCH 已经落地的那一条，**它不减少总时间，但它把等待挪到学生已经有内容可读之后**。

## 5. ⑤ 建议的默认路径（一条决策规则）

```
要讲某一步时，按这个顺序选渠道，不要跳级：

① 能画成一张静止的板书图  → classroom_draw

                          → classroom_animate_template + template/params
   （模型段实测 **10–20 秒**；对照：从零写脚本 25–41 秒）

④ 只有模板表达不了的过程动画 → classroom_animate 自己写脚本
   （模型段实测 **25–41 秒**，是最慢的一条）
   🔴 并且：如果这一段能被课程数据预知，**优先把它写进 prep: 让引擎课前渲好**，

· **先讲后画**：先在同一回合的正文里把这一步讲给学生，再调工具；工具调用不许当开场白。

  不许对学生说"动画正在生成"然后不放。
```

| 1 | **真教室没有 `prep:` 声明，也没有提模板工具的渠道纪律** | `code/classrooms/**` 不在可改范围。→ **生产启用需要教室内容侧两处改动**：① `classroom.yaml` 加 `prep:` 段（形状见 §2.1）；② 内容侧补一条渠道纪律（"先取备好的 → 再套模板 → 才自己写"）。**没有这两处，模型不会自己用新工具**（ANIM-ORCH 已实证"引擎挂上工具 ≠ 老师会用"） |
| 2 | **"教室内容不提模板工具时，模型会不会自己用"没测** | B 组的 prompt **明说了**工具名；prep-session 的副本里补了渠道纪律。**"不提就不用了"这条没有被本批证伪或证实**，只能照 ANIM-ORCH 的 B 组证据推断为风险 |
| 3 | **客户端那半没做** | 播放仍在 `code/clients/**`（本轮不许碰）。`prep-list` 的机器可读字段已给出（`source.form='prep-list'`, `lesson`），播片的契约与 ANIM-ORCH 的 `animation-notice` 一致 |

### 8.3 本批踩到并已修的坑（写下来防重犯）

| # | 坑 | 修法 |
|---|---|---|
| 1 | `CurvedArrow` 不接受 `buff` 参数（`TypeError: Mobject.__init__() got an unexpected keyword argument 'buff'`） | 端点自己算（落在圆周外留缝），`Arrow` 与 `CurvedArrow` 共用同一套端点算法 |
| 2 | manim 的产物目录是**脚本文件名**（`scene.py` → `videos/scene/480p15/`），不是 `-o` 给的名字 | `findMp4()` 扫 `videos/*/*/*.mp4`；并加了 `regrade.mjs`（**判据写错不必重跑会话**） |
| 3 | 事件流里工具入参字段是 **`data.arguments`（JSON 字符串）**，不是 `args`/`input` | 三处统一改；否则 `argChars` 全 null（数看起来"没量到"） |
| 4 | 预热计时数的是"有 `status.json` 就算一个"，而渲染器一开工就写 `rendering` → 循环立刻返回，量到 0.3 秒 | 只数**终态**（ready/blocked/failed） |
| 5 | `status.json` 里**没有** `gate.gateMs` 这个字段（只有 `ran`/`verdict`/`blockingCount`）→ 端到端少算十几秒 | 改用 `status.finishedAt − task.createdAt`（含渲染＋闸门＋进程启动） |
| 6 | 分支条件写死 `MODE === 'scratch'`，加 A′ 组后**静默失效**（两轮全记成 `ms_model=n/a`） | 改成按前缀判；并把"从盘上重算"做成 `regrade.mjs` |
| 7 | `checkTemplateArgs` 返回的是**规范化后**的参数（补了自动配色、`tmax` 等派生字段），预热层拿它**再校验一遍**就会报"无法识别的键 tmax" | 拆出 `renderTemplateScript(id, title, normalizedParams)`：声明在装载期校验**一次**，预热只负责拼脚本 |
| 8 | 颜色白名单太窄（模型真会写 `orange`） | 加同义词别名收敛到规范名（见 §1.4） |
