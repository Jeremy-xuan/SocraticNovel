## 一 · ① 演示页渲染循环 rAF 叠加

### 1.1 怎么复现（说清步骤，别人能照做）

被测对象是宿主自己的演示页 `demo/demo.html`（`?nomodel=1` 起，装载由脚本显式点，判据才可归因）。
**新探针** `tools/raf-loop-probe.cjs` 做三件事：

1. **装计数器**：页面里 `await import('./live2d-host.bundle.mjs')` 拿到**同一个模块实例**（同 realm、同 URL → ES 模块注册表里是同一条记录），把 `Live2DHost.prototype.step` 包一层自增计数〔A13〕——**演示页用的就是这个类**，所以页面上每一次 `step()` 都被数到；
2. **按帧分桶**：再起一条**只读**的 rAF 采样器，每帧读一次计数器的增量〔A14〕。演示页的 tick 与采样器在同一帧的 rAF 回调表里各跑一次 → 分桶结果就是"**每帧 step 了几次**"；
3. **装载 N 次**：依次点「装载并渲染」N 次（每次等到日志出现 `[shaders] ready=true` 才算装完），然后开窗口量。

⚠️ **分桶是相位偏移一帧的**：采样器的 rAF 回调注册得比演示页的 tick 早，同一帧里它先跑 → 读到的是**上一帧**的次数，所以**第 1 桶恒为 0**（窗口边界）。
判据因此取「**除第 1 桶外**每桶恒为 1」〔A15〕〔A16〕，并把原始序列（`firstFrames`）一并打出来供核对 —— **不是**把判据放宽。

### 1.3 根因（两处，都在"循环的归属"上）

**根因一（缺陷现场）**：演示页的 `startLoopControlled()` 每次被调用都**新起一条 rAF 链**，而它**不保存、也不取消**上一条：

- 修前的 tick 末尾是裸的 `requestAnimationFrame(tick)`，**没有任何 id 可停**；
- 于是装载 N 次 → N 条链同时在跑 → 同一帧里 `host.step(dt)` 被调 N 次；
- 更细一层：`host` 是模块级变量、在装载开始时就被赋成**新宿主**，所以旧链 tick 的不是"旧模型"，而是**新模型**——效果不是"两个模型各自在动"，而是**新模型每帧被推进 N 步（N 倍速 + N 倍开销）**。

**根因二（同一个洞在宿主 API 上）**：修前 `Live2DHost.startLoop()` 也不幂等——调两次就是两条链，而 `stopLoop()` **只能取消最后一条**，旧的再也停不掉。
（旁证：演示页装载前的 `if (host) host.stopLoop();` 对**演示页自己那条链**完全无效 —— 它调的是宿主的 `stopLoop`，而演示页根本没走宿主的 `startLoop`。）

| # | 位置 | 改动 |
|---|---|---|
| ① | `src/host.js` `startLoop()`〔A01〕 | **起新循环前先 `stopLoop()`**；并把 `_lastTimestamp` 清零〔A02〕（重启后旧时间戳无意义，否则首帧 dt 会被钳到上限） |

## 二 · ② `loadMotion()` 解析失败时的明确报错

### 2.1 修前实测：两条路，两种看不懂

用**故意造坏的动作文件**跑（探针见 §2.4），修前原文（页面侧，逐字）：

```
── 动作文件截成 0 字节 ──
  window.onerror/unhandledrejection: unhandledrejection: Cannot read properties of null (reading 'setEffectIds')
  pageerror: Cannot read properties of null (reading 'setEffectIds')

── 动作文件写成语法坏掉的 JSON ──
  window.onerror/unhandledrejection: unhandledrejection: Expected double-quoted property name in JSON at position 45 (line 1 column 46)
  pageerror: Expected double-quoted property name in JSON at position 45 (line 1 column 46)
```

两条都**没有一个字**提到是哪个文件、哪个动作组 —— 而坏的是 `models/__broken_empty__/motions/haru_g_idle.motion3.json`。

### 2.2 一条重要的更正：**坏 JSON 不是"返回 null"，是"抛异常"**

上一路的待确认清单把这件事写成"`loadMotion()` 返回 null（动作解析失败）时……会在 `setEffectIds` 处抛一句难懂的 TypeError"。实测下来要分两条路说清（两条都读源码核过）：

| 输入 | 官方行为 | 出处 |
|---|---|---|
| **0 字节文件** | `loadMotion()` 开头就 `if (buffer == null \|\| size == 0)` → `CubismLogError('Failed to loadMotion().')` → **返回 null** | 〔A24〕 |
| **坏 JSON** | `CubismJson.parseBytes()` 里 `JSON.parse(decodeBuffer)` **没有 try/catch** → **SyntaxError 直接冒到调用方**（不是返回 null） | 〔A23〕 |

→ 所以修前那句"难懂的 TypeError"只覆盖**空文件**这一路；**坏 JSON 那一路更糟**：它抛的是一个**连"这是 JSON 解析"都看不出来**的 SyntaxError，还带一个没有主语的字节偏移（`position 45`）。
（附带结论：`CubismMotion.parse()` 里那个 `if (!json)` 早退分支在本路径上是**够不到的死代码** —— `CubismMotionJson` 这个包装对象永远是真值，`null` 的是它内部的 `_json`。）

### 2.3 行为判定：**拒绝装载（抛错中止）**，不跳过

**我的判定：抛错，中止整个 `load()`。** 理由三条：

1. **本项目口径是"不许静默"，而"跳过 + 告警"在本宿主里会变成事实上的静默**：宿主自己没有 UI，告警只能落 `console`／调用方的日志；而**画面照样出来、动作少一个**，用户与验收脚本都看不出异常 —— 这正是本项目最恨的那类失败。
2. **跳过会污染"按下标取动作"这条接口**：`startMotion(group, index)` 是按下标取的；跳过之后下标错位或塞 `null`，面板点一下只会拿到 `false`，而演示页对 `false` 的提示是「该模型没有可用的 Idle 动作」〔A29〕—— **一句误导人的话**。
3. **坏动作文件是"打包坏了"，不是"运行时运气不好"**：模型资源是随宿主一起打包的，坏掉说明构建/拷贝环节出了问题。抛错 = 在流水线里**响亮地红**；跳过 = 可能带着"少一个动作"的模型上线。

代价与边界（如实说）：**一个坏动作文件会让整个模型装载失败、面板上什么都不显示**。这是有意的取舍 —— 由**调用方**决定怎么兜（换模型、报错给用户），宿主不替它决定"少点东西也能凑合用"。
（另一条路"跳过该动作但明确记一条可见告警"我没有选；若将来教室面板需要一个"降级但能用"的模式，那是**面板的策略**，不是宿主的默认。）

### 2.4 修法与造坏输入的验收

**修法**（`src/host.js`，三处）：

1. 新增 `motionLoadError()`〔A03〕：把失败包成同一种「**人话 ＋ 文件路径 ＋ 组/下标 ＋ 原始原因**」，并把尾句写死为「装载已中止：宿主不装载「少了一部分动作」的模型 —— 静默跳过会变成「点了动作没反应」」〔A04〕；

## 三 · ③ `mouth-iso` 改成"先 `stopAllMotions()` 再冻结"

### 3.1 为什么读数会波动

修前脚本的"冻结"只有**一步**：勾上「冻结动画」→ 演示页的渲染循环只 `draw()` 不 `update()`。
于是**姿态被冻在"勾选那一刻恰好走到的那一帧"**：

- 冻结发生在装载后第几帧，取决于装载/等待时序（每次都不一样）；
- 而宿主每帧会推进 Idle 动作（`update()` 里起 Idle、`updateMotion()` 写参数）→ 每一帧的姿态都不同；
- 冻哪个姿态，嘴部可见面积就不同 → `changedPixels` 跟着跳。

**修前实测（`Teacher`，同一份代码同一份产物，连跑三次）**：

| 次 | changedPixels | bbox | 改回后 |
|---|---|---|---|
| 1 | **20** | 7×4 @ (362,162) | 0 |
| 2 | **89** | 12×9 @ (366,158) | 0 |
| 3 | **82** | 12×9 @ (365,157) | 0 |

（上一路报的是 24／87／21 —— 同一个现象；数值不同只是因为冻结时刻不同。）

### 3.2 修法：把"冻结"变成两步

| 步 | 做什么 | 为什么 |
|---|---|---|
| ① | 勾「冻结动画」→ 循环只 `draw` 不 `update` | 画面不再被动作推着走 |
| ② | **`stopAllMotions()` 清空动作队列**〔A20〕 ＋ **全部参数复位到 moc 默认值**〔A21〕 ＋ `model.update()` | 把姿态钉成**确定性**状态 |

**为什么只有 ① 不够、只有 `stopAllMotions()` 也不够**（这条是本轮实测踩出来的）：

- `stopAllMotions()` 只清**队列**，不清**参数**：参数留在"最后一帧被写到的那组值"，而"最后一帧"是随机的；
- 也不能靠"再 `loadParameters()` 回到快照"：宿主每帧 `update()` 的**头尾就是** `model.loadParameters()`〔A27〕 / `model.saveParameters()`〔A28〕 —— **每帧都会把快照覆盖成当前动画姿态**，所以快照本身也是随机的；
- 所以必须**显式**把参数写回一个确定性来源：moc 里的**参数默认值**〔A25〕（`getParameterDefaultValue`）。这条与"冻结发生在第几帧"完全无关。

**顺带说明一处依赖**：②里的 `stopAllMotions()` 会 `entry.release()`〔A26〕；**只有在宿主已按官方签名把 `autoDelete` 传 `false` 之后**（上一路 L2D-FIX-IDLE 的修复），它才**不会**把宿主长期缓存的动作对象掏空。也就是说 —— **③这条能做成，前提是上一路那修已经落地**。
