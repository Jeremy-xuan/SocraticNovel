## 2 · 宿主半边：两个只读方法

### 2.1 为什么清单必须并进 `typert.host.js`

`dsh-typert-loader`（0.2.1-rc.2）解析宿主清单的路径是**唯一**的：`package.json` 的
`exports["./typert"]` → 一个文件 → 它的 `TYPERT`（`typertExportOf` 只处理字符串或带 `default` 的对象）。
所以：

- 另加一个 `exports["./typert.narrative"]` **不会被任何人读到**；
- 把 `exports["./typert"]` 改指向叙事那份，白板的 `save/load/index` 会整批从注册表里消失。

因此 `lib/typert.narrative.host.js` 只是**片段的宿主**，由 `lib/typert.host.js` 合并：

```js
invocations: [ …白板三条…, ...NARRATIVE_INVOCATIONS ],
model: { services: [ …白板…, NARRATIVE_SERVICE ], events: [], objects: [] }
```

（实测：合并后 `TYPERT.invocations` 5 条、`services` 2 个，每个 codec 的 `create()` 都是函数。）

### 2.2 两个方法的语义

| 方法 | 入参 | 返回 |
|---|---|---|
| `status` | `scope` | `{ ok:true, status:{ ok, active, lastError, lastSuccess, recent } }` ／ `{ ok:false, reason:'narrative-absent' }` ／ `{ ok:false, reason:'status-failed', message }` |
| `diaries` | `scope`、`limit`（1..50，缺省 20） | `{ ok:true, entries:[{date,lesson,text}], bad }` ／ `{ ok:false, reason:'narrative-absent' }` ／ `{ ok:false, reason:'no-classroom' \| 'read-failed', message }` |

- 🔴 **叙事包缺席时照旧 provide 本服务**，两个方法回 `narrative-absent`。理由：面板需要一个
  "问她有没有"的稳定出口；如果连服务都不 provide，浏览器侧只能看到 `undefined`，每个消费点都要自己判一次。
- 🔴 **失败一律不抛**（`ctx.get` 抛错、叙事服务内部异常、读盘失败都在方法里吃掉并转成 reason）。
  面板那边另有 try/catch 兜底——`SlotErrorBoundary` 会把抛错的槽**永久**锁成崩溃占位。
- **教室目录委托叙事服务自己解析**（`narrative.group.resolveDir(scope)`）：工作区根 → 教室目录的判定
  （根自己就是教室／只有一个 `classrooms/<name>`／多个不许静默选一个）是叙事包的知识，抄一份到面板
  就有两份会漂移。面板只拿 `workspaceFileScope`。
- 面板**不读** `runtime/.narrative/` 的账本与运行日志（NE 报告 §7.4 的边界）。

### 2.3 🔴 类里的私有方法会炸（实测）

第一版把转发逻辑写成 `#narrative()` / `#absent()` / `#classroomDirOf()`。活体一调就回：

```
gateway/internal — Receiver must be an instance of class ClassroomNarrative
```

原因是网关派发 Remote 方法时的接收者不是裸实例（cordis 的 `Service` 会被代理一层），
V8 的 `#` 私有字段访问对接收者做品牌校验。改成**模块级函数**（`narrativeOf(service)` 等，读 `service.ctx`）后正常。
同一隐患在 `lib/whiteboard-host.mjs` 的 `#rootOf` / `#readCurrentRev` 上也存在（见 §9.1）。

## 3 · 🔴 浏览器侧：命名空间必须自己挂（K4.1 没写的一步）

K4.1 写的是"浏览器侧 `ctx.remote.classroomGroup.<method>(sessionId, …)`"。实测**这句话只对了一半**：

- `ctx.remote.<ns>` 的命名空间来自 `dsh-api-remotes` 的**静态装配表**（`lib/types/client/index.js` 只
  `import` 了官方包各自的 `remote` 产物，逐个 `ctx.remote.$mount(...)`）；
- 第三方包（`socratic-narrative`）没有 client 面的 `typert.remote-client` 产物，于是
  `ctx.remote.classroomGroup` 在浏览器里**根本不存在**——而宿主日志一句错都没有；
- 现象就是面板两页都落到"没有服务"，看着像叙事包没装（第一次活体就踩到了）。

修法（本插件内，不碰叙事包）：由消费方自己挂一份手写清单。

```js
ctx.remote.$mount({ package: 'classroom-ui', descriptors: [ …六条… ] })
```

- 清单在 `narrativeRemoteContribution()`，codec 是**手写 strict codec**
  `{ mode:'strict', typeSymbol, create:()=>({parse}) }`——客户端产物不经打包器、`require` 只认 `react`，
  拿不到 zod；`$mount` 的校验只要求 `mode==='strict'` ＋ `create` 是函数。
- 挂载是异步的，`ctx.effect` 里接成"同步返回卸载器 ＋ 完成后再补 dispose"；失败只记一条 `console.warn`
  （最可能的两种：命名空间已被将来的叙事包 client 面挂过、新版拒收清单形状），面板照旧显示"缺席"。

### 3.1 🔴 读命名空间为什么不能直接 `ctx.remote.x`

`remote.<ns>` 是 cordis 的**服务键**（`remoteServiceKey` → `remote.<namespace>`），读它要求在 `inject` 里声明；
而这两个命名空间正是本插件在 `apply` 里挂的——声明进 `inject` 就是死锁（服务没挂 → 插件不激活 → 永远挂不上）。
实测报错：`cannot get property "remote.classroomNarrative" without inject`。

所以走 `ctx.get('remote.<ns>')`（"读服务但不要求 inject"那条路），失败再退回传入对象上的同名属性
（node 侧测试直接喂假 remote 时走这条）。见 `remoteNamespaceOf()`。

### 3.2 两层返回：外层"通没通"，内层"服务说行不行"

网关 client 面把宿主返回值**包进 `value`**：

```
ctx.remote.<ns>.<m>(…) → { ok:true, value:<宿主返回值> } | { ok:false, error:{ code, message } }
```

而本插件宿主的两个方法**自己也**回 `{ ok:false, reason }`。两层 `ok` 各管一件事，混起来就会把
"网关不通"说成"叙事包没装"。拆包在 `unwrapRemoteResult()`；日记页因此能分开显示
"读日记失败：gateway/internal — …"（故障）与"没有叙事服务"（能力缺席）。

## 5 · 「群聊」tab（N3.1）

### 5.1 版式与行为

版式照 `templates/wechat-chat.html` 的**视觉语言**（别人在左＝浅底气泡＋人名，自己在右＝暖底气泡，
系统提示居中一行小字，状态行在消息区上方），但全部用面板现有的 `H()` + `styles()` 实现——
那个模板的 CSS 与渲染脚本一个字都没搬进来，也没有塞任何原生 HTML。
新增样式键 14 个（`chatThread` / `chatRow` / `chatRowOut` / `chatName` / `chatBubble` / `chatBubbleOut` /
`chatSys` / `chatMetaRow` / `chatTyping` / `chatComposer` / `chatInput` / `chatSend` / `chatSendBusy` / `chatBadge`），
全部走既有 token（`ink` 四档 / `t.*` 排版角色 / `line.hair|box|gold` / `radius` / `space` / `fill.plate|canvas`），
**没有一处 `fontWeight`**（测试 7.7 的判据照旧）。

- 消息分流：`role==='system'` → 居中一行；`student` → 右（`data-cui-group-own="true"`）；
  其它 → 左，带人名（没名字写"对方"）。
- **「对方正在输入」＝ `poll().typing === true`**。只在真的在输入时才渲染那一行——
  空行会留下 `chatTyping` 的 2px 金褐竖线，在消息区顶端画出一小截"点"（第一版截图里就看到了）。
- **未读**＝`history/poll` 的 `unread`：打开这一页、或轮询收到新消息，就把已读游标推到**已见到的最后一条 seq**；
  推不动（服务端 markRead 失败）时**如实保留**未读数（不假装已读）。
- **发送失败**：把服务端 `error.code`（`EMPTY`／`TOO_LONG`／`RATE_LIMITED`／`AGENT_FAILED`／`STORE_CORRUPT`）
  原样显示出来（文案里也有），并给「重试发送」。重试**复用同一个 `clientId`**（K4.2 的幂等键），
  所以重试不会在真源里写下第二行。
- 客户端先挡一层空串（`text.trim()===''` 直接不发）；`TOO_LONG` 之类仍由服务端判、错误照显。
- 叙事包没装：`classroomGroup` 命名空间仍被挂上、但宿主没有对应服务 → 每次调用 404。第一版因此显示
  "读群聊失败：gateway/internal … HTTP 404"，与"中性说明"的要求不符。修法：**调用失败之后**先问一句
  `classroomNarrative.status()`（它总是被 provide，缺席时自己回 `narrative-absent`），缺席就转成 `absent`；
  probe 自己失败（`unknown`）仍按故障处理——不许把"问不出来"冒充"没装"。成功路径不多付一次往返。

### 5.2 🔴 轮询游标：`nextSeq` 不是游标（活体踩到的真 bug）

K4.3 的 `nextSeq` 是**下一个要分配的序号**（服务端 `maxSeq + 1`）。第一版把它直接当 `afterSeq`：

- 历史里有 seq 1–3 → `nextSeq` 4 → `poll(4)`；
- 她的回复恰好拿到 seq 4 → 服务端 `seq > afterSeq` 过滤掉 → **回复永远不进面板**；
- 而 `typing` 与未读数都正常 → 肉眼看起来像"她一直在输入、就是不回话"。

修法：游标＝**已见到的最大 seq**（`lastSeqOf(messages)`）——历史、发送成功、每次轮询后都按它推进；
`markRead` 也推到最后一条（服务端本来就会 `min(readSeq, maxSeq)` 收敛）。
回归测试 12.8 里的假 `poll` **真的按 `afterSeq` 过滤**（原来的假 poll 忽略 afterSeq，两种写法都能过，
这正是它漏掉的原因）。

复现与修后证据：修前活体 45s 后仍"共 2 条"（她那条没进面板），修后同一脚本"共 3 条"（§6 的表）。

## 9 · 给别人发现的问题（本车道不改）

### 9.1 🔴 `whiteboard-host.mjs` 有同款"私有方法 + Remote 接收者"隐患

`clients/classroom-ui/lib/whiteboard-host.mjs` 的 `WhiteboardStore` 用了 `#rootOf` / `#readCurrentRev`（私有方法）。
按 §2.3 实测到的机制，网关派发 `save` / `load` / `index` 时接收者不是裸实例 → 一调就会抛
`Receiver must be an instance of class WhiteboardStore`。

**没被发现的理由**：面板里 `grep whiteboard` = 0 处，这三个方法至今**没有浏览器侧调用方**，
所以这条路径从来没有被真实走过（`test/whiteboard.test.mjs` 只测纯逻辑，不经过 Remote 派发）。
建议 S3 车道把 `#rootOf` / `#readCurrentRev` 改成模块级函数，并补一条"经网关调一次"的活体断言。

### 9.2 契约 K4.1 缺"客户端挂载"这一步

原文只写"浏览器侧 `ctx.remote.classroomGroup.<method>(sessionId, …)`"，没有写命名空间从哪来。
按实测（§3），第三方包**必须**由消费方 `ctx.remote.$mount(...)` 挂一份清单，否则命名空间不存在。
建议在 K4.1 补一句：*谁提供 client 清单、谁负责 `$mount`*（要么叙事包自带 `exports["./remote"]`，要么明写由 P 车道挂）。
另外 `inject` 与"自己挂"的死锁（§3.1）也值得写进去——第一个踩的人会卡很久。

### 9.3 叙事包 `readRecentDiaries` 把末尾「参考口吻」算进最后一条

NE 报告 §9.1 已记录，本次活体截图再次看到（`docs/证据图/面板_P2_日记tab_2026-10-21.png`）。
面板如实显示、`plugins/**` 不在本车道文件清单内，未改。

### 9.4 `wechat_group.rules.md` 的失败会以 `role:'system'` 消息出现——面板已覆盖，但值得写进面板验收

`INVALID_OUTPUT` 之类失败会在流里留一条 `role:'system'` 的说明（本车道实测到了这条路径：
mock 一开始回纯文本 → `AGENT_FAILED`/系统说明）。面板把它画成居中灰行，读起来是"系统提示"而不是报错，
这是有意的（K4 允许 `system` 作为"无法回复的说明"）。
