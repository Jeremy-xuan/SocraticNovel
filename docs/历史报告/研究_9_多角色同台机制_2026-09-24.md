### 1.1 总览：SillyTavern 把群聊拆成「前台调度」＋「单角色生成」两层

🔴 **最关键的一个事实（先说，因为它决定了我们要不要抄它）**：

SillyTavern 的群聊**不是**"一个模型同时演多个角色"。它是**客户端循环**：**逐个**把角色设为"当前角色"，然后**为每个角色单独调一次 `Generate()`**。

**源码（逐字）** — `public/scripts/group-chats.js:945–1096`：

**解读（逐点）**：
1. **`activationStrategy` 先算出一个「本轮该发言的角色 id 列表」**（`activatedMembers`，是**数组**，可含多人）；
2. 然后 `for (const chId of activatedMembers)` **串行**循环；
3. 每次循环做三件事：`setCharacterId(chId)` → `setCharacterName(...)` → `await Generate(...)`；

**对我们的直接含义**：
- ✅ **"多个角色同台"不需要模型同时演多人**——这一点 SillyTavern 用最朴素的工程手段解决了（一次一个）。**这直接降低了我们 §5 的通道难度**：我们不需要"一次请求出两条消息"，只需要"一次请求里让引擎知道**现在是同学在说话**"。
- 🔴 **但也暴露了它的代价**：N 个角色 = N 次 LLM 调用 = N 倍延迟与成本。这与我们约束 ⑥（多角色稀释教学密度）**同源**——SillyTavern 用 `talkativeness` 把 N 压小，见 §1.2。

#### ① `LIST`（列表顺序）— 最确定，纯轮转

**解读**：**全部成员按列表顺序、全部激活** → 一回合内每人说一次，顺序固定。
🔴 **这就是"剧本"**——确定性 100%，但**没有现场感**，也不会因为学生卡住而多说话。**我们不借**（违反用户"冻结事实不冻结教学行为"）。

#### ② `POOLED`（池化）— **"轮着来，没说过话的优先"**

`public/scripts/group-chats.js:1197–1232`：

**解读（三条规则，逐条）**：
1. **从对话尾部往回扫**，收集"自上次用户发言以来已经说过话的人"（`spokenSinceUser`），**扫到用户消息就停**（`if (message.is_user || isUserInput) break;`）；
2. **优先从未发言者中随机抽一个**（`haveNotSpoken`）；
3. 若人人都说过了 → **随机抽，但排除最后发言者**（`members.filter(x => x !== lastMessage.original_avatar)`）→ **防止同一人连说两次**。

🔴 **这一条是我们最该借的 prior art**：它把"**轮转**"与"**公平性**"用一个**从对话历史推导的确定性规则**实现了——**不需要模型自己判断"该谁了"**。
- **对我们的映射**：把 `spokenSinceUser` 换成「**本讲已出场过的 cue**」→ "每讲 3–5 次"这个额度**可以直接用同一个模式计数**（§9.2）。
- **不借的部分**：它是**纯随机**选人（`Math.floor(Math.random() * haveNotSpoken.length)`）。我们的约束 ⑤ 明确**不建议纯随机**——教学关系要连续性 → 我们要在"没说过话的"里面**按认知风格与当前错法匹配**选，而不是随机抽（§9.4）。

#### ③ `NATURAL`（自然）— **默认策略，按 `talkativeness` 概率 + 点名触发**

`public/scripts/group-chats.js:1242–1320`（**这是默认值**：`:1002` `const activationStrategy = Number(group.activation_strategy ?? group_activation_strategy.NATURAL);`）：

```js
function activateNaturalOrder(members, input, lastMessage, allowSelfResponses, isUserInput) {
    let activatedMembers = [];

    // prevents the same character from speaking twice
    let bannedUser = !isUserInput && lastMessage && !lastMessage.is_user && lastMessage.name;

    // ...unless allowed to do so
    if (allowSelfResponses) {
        bannedUser = undefined;
    }

    // find mentions (excluding self)
    if (input && input.length) {
        for (let inputWord of extractAllWords(input)) {
            for (let member of members) {
                const character = characters.find(x => x.avatar === member);

                if (!character || character.name === bannedUser) {
                    continue;
                }

                if (extractAllWords(character.name).includes(inputWord)) {
                    activatedMembers.push(member);
                    break;
                }
            }
        }
    }

    const chattyMembers = [];
    // activation by talkativeness (in shuffled order, except banned)
    const shuffledMembers = shuffle([...members]);
    for (let member of shuffledMembers) {
        const character = characters.find((x) => x.avatar === member);

        if (!character || character.name === bannedUser) {
            continue;
        }

        const rollValue = Math.random();
        const talkativeness = isNaN(character.talkativeness)
            ? talkativeness_default
            : Number(character.talkativeness);
        if (talkativeness >= rollValue) {
            activatedMembers.push(member);
        }
        if (talkativeness > 0) {
            chattyMembers.push(member);
        }
    }

    // pick 1 at random if no one was activated
    let retries = 0;
    // try to limit the selected random character to those with talkativeness > 0
    const randomPool = chattyMembers.length > 0 ? chattyMembers : members;
    while (activatedMembers.length === 0 && ++retries <= randomPool.length) {
        const randomIndex = Math.floor(Math.random() * randomPool.length);
        const character = characters.find(x => x.avatar === randomPool[randomIndex]);

        if (!character) {
            continue;
        }

        activatedMembers.push(randomPool[randomIndex]);
    }

    // de-duplicate array of character avatars
    activatedMembers = activatedMembers.filter(onlyUnique);
...
}
```

**解读（三条规则）**：
1. 🔴 **点名优先**：把用户输入（或上一条消息）**逐词**与每个角色**名字**比对，命中就激活（`extractAllWords(character.name).includes(inputWord)`）。→ **"提到谁，谁答"**。
2. 🔴 **概率门**：其余成员**打乱顺序**后逐个 `Math.random()` 掷骰，`talkativeness >= rollValue` 就激活 → **`talkativeness` 就是"该角色发言的期望概率"**（0.5 → 约 50% 概率插话）。
3. **保底**：若一个人都没激活 → 从 `talkativeness > 0` 的人里随机抽 1 个（避免"没人说话"）。
4. `bannedUser` 机制：**默认禁止上一条的发言者连说两次**（除非 `allowSelfResponses`）。

**`talkativeness` 的取值与语义（逐字）**：
- 默认值：`public/script.js:549` → `export const talkativeness_default = 0.5;`
- UI 滑块：`public/index.html:6642` → `<input id="talkativeness_slider" name="talkativeness" type="range" min="0" max="1" step="0.05" value="0.5" form="form_create">`，滑轨标签 `Shy / Normal / Chatty`（`public/index.html:6645–6647`）
- 语义说明（UI 原文）：`How often the character speaks in group chats!`（`public/index.html:6639`）

🔴 **这是本节对我们最有价值的一条**：**"发言频率"被建模为一个 0–1 的每角色标量，默认 0.5，按概率门生效。**
→ **映射到我们的 `cast`**：`cast[].cue_rate` 就是这个字段的等价物。**但我们的取值要低得多**——用户要求"每讲 3–5 次"，一讲约 20–30 回合 → 单角色 `cue_rate` 应在 **0.05–0.15 量级**，**不是 0.5**（0.5 会变成每两回合插一次嘴 = 违反约束 ⑥）。**这是"借机制、改参数"的典型**。

```js
            console.debug(`Skipping disabled group member: ${member}`);
            continue;
        }

        const depthPromptText = baseChatReplace(character.data?.extensions?.depth_prompt?.prompt?.trim(), null, character.name) || '';
        const depthPromptDepth = character.data?.extensions?.depth_prompt?.depth ?? depth_prompt_depth_default;
        const depthPromptRole = character.data?.extensions?.depth_prompt?.role ?? depth_prompt_role_default;

        if (depthPromptText) {
            depthPrompts.push({ text: depthPromptText, depth: depthPromptDepth, role: depthPromptRole });
        }
    }

    return depthPrompts;
}
```

**解读（这是本节对我们第二条关键发现）**：
- `SWAP` ＝ **只装当前说话角色的卡**，其他人的卡完全不进上下文（`return []`）；
- `APPEND` ＝ **把其他成员的 depth prompt 也追加进来**（让模型"知道在场还有谁"）；
- 🔴 **注意 `characterId` 参数**：`if (group.disabled_members.includes(member) && characterId !== index)` —— **当前说话者即使被 disabled 也照样注入自己的卡**。

**对我们的映射**：
- 我们的场景**必然需要 APPEND 语义**——用户明确说"同学常驻"、"作为 NPC 一样插入其中"→ **同学必须在场（模型知道他们在）**，但**不发言**。
- 🔴 **但 SillyTavern 的 APPEND 只追加 `depth_prompt`（一小段）**，不是整张角色卡。**这正好是我们该抄的分寸**：
  - **当课老师（komari）**＝ 完整 persona 卡（走 `persona.komari` 块，已在 `classroom.yaml` 常驻）；
  - **同学**＝ **只有一段 `depth_prompt` 级别的在场声明**（"他在场、他上次错在哪、他此刻不发言"），**不是完整人格卡**。
  → 这直接服务于约束 ④（常驻 ≠ 常发言）与约束 ⑥（稀释教学密度）：**常驻的代价是一小段文本，不是一整张卡**。

### 2.2 调度循环：**先选人，再让被选中的人发布**

**源码（逐字）** — `_base_group_chat_manager.py:172–193`：


**解读（三条）**：
1. 🔴 **`select_speaker(thread)` 是一个纯函数式的裁决**：入参是**消息线程**，出参是**说话人名字（或名字列表）**。**它不生成台词。**

- ✅ **"选谁说话"与"说什么"彻底分离**：我们应当把 `cue` 裁决做成**纯函数**（输入＝课堂状态，输出＝角色 id ＋ 绑定的知识点/错法 id），**台词由被选中的角色单独生成**。这正是约束 ①（角色只贡献声音，问题本体绑知识点）在架构上的正确落点。
- ✅ **名字必须在册，否则硬报错**（`RuntimeError`）：我们应照抄这个**fail-loud**——`cue` 裁决出一个不在 `cast` 里的角色 id 时**报错**，不静默忽略（教室既有设计里已有这条风格，见 `classroom.yaml` 关于相位值域「不在本列表内 → 引擎**报错**（不静默不注入）」的注释）。

```python
            roles=roles, participants=str(participants), history=model_context_history

...

            assert isinstance(response.content, str)
            select_speaker_messages.append(AssistantMessage(content=response.content, source="selector"))
            # NOTE: we use all participant names to check for mentions, even if the previous speaker is not allowed.
            # This is because the model may still select the previous speaker, and we want to catch that.
            mentions = self._mentioned_agents(response.content, self._participant_names)
            if len(mentions) == 0:

                feedback = f"No valid name was mentioned. Please select from: {str(participants)}."
                select_speaker_messages.append(UserMessage(content=feedback, source="user"))
            elif len(mentions) > 1:
                trace_logger.debug(f"Model selected multiple names: {str(mentions)} (attempt {num_attempts})")
                feedback = (
                    f"Expected exactly one name to be mentioned. Please select only one from: {str(participants)}."
                )
                select_speaker_messages.append(UserMessage(content=feedback, source="user"))

                if (
                    not self._allow_repeated_speaker
                    and self._previous_speaker is not None
                    and agent_name == self._previous_speaker
                ):
                    trace_logger.debug(f"Model selected the previous speaker: {agent_name} (attempt {num_attempts})")
                    feedback = (
                        f"Repeated speaker is not allowed, please select a different name from: {str(participants)}."
                    )
                    select_speaker_messages.append(UserMessage(content=feedback, source="user"))
                else:
                    # Valid selection
                    trace_logger.debug(f"Model selected a valid name: {agent_name} (attempt {num_attempts})")
                    return agent_name

        if self._previous_speaker is not None:
            trace_logger.warning(f"Model failed to select a speaker after {max_attempts}, using the previous speaker.")
            return self._previous_speaker
        trace_logger.warning(
            f"Model failed to select a speaker after {max_attempts} and there was no previous speaker, using the first participant."
        )
        return participants[0]
```

**解读（🔴 这是本节对我们第二重要的一条）**：
1. **`max_selector_attempts = 3`**（`:616` 默认值）；
2. **三类失败各有专门的纠正反馈**：
   - 没提到任何人 → `"No valid name was mentioned. Please select from: [...]"`
   - 提到多个 → `"Expected exactly one name to be mentioned. Please select only one from: [...]"`
   - 重复了上一个发言人 → `"Repeated speaker is not allowed, please select a different name from: [...]"`
3. 🔴 **三次都失败后的兜底：`return self._previous_speaker`**（沿用上一个说话人）；若连上一个都没有 → `return participants[0]`。

**对我们的直接含义（一条重要的设计约束）**：
- 🔴 **"模型自选说话人"这条路上，必须有确定性的兜底**。否则一次解析失败 = 课堂上没人说话 = 比僵局更糟。
- ✅ **借这个三段式**：**校验 → 带反馈重试（≤3 次）→ 确定性兜底**。
- 🔴 **但兜底策略要改**：AutoGen 兜底到"上一个说话人"，**对我们不合适**——我们的"上一个说话人"通常就是老师，兜回老师 = **等于没插话**（学生还是那个僵局）。→ **我们的兜底应该是"不出场"**（回到单角色教学），**而不是"老师再说一次"**。这是一个**明确的偏离**，理由见 §6.2。

### 2.6 `SwarmGroupChat`：**模型用"交接消息"自己决定下一个人**（handoff）

**源码（逐字）** — `_swarm_group_chat.py:15–16`、`:82–98`：

```python
class SwarmGroupChatManager(BaseGroupChatManager):
    """A group chat manager that selects the next speaker based on handoff message only."""
...
    async def select_speaker(self, thread: Sequence[BaseAgentEvent | BaseChatMessage]) -> List[str] | str:
        """Select a speaker from the participants based on handoff message.
        Looks for the last handoff message in the thread to determine the next speaker.

        .. note::

            This method always returns a single speaker.
        """
        if len(thread) == 0:
            return [self._current_speaker]
        for message in reversed(thread):
            if isinstance(message, HandoffMessage):
                self._current_speaker = message.target
                # The latest handoff message should always target a valid participant.
                assert self._current_speaker in self._participant_names
                return [self._current_speaker]
        return self._current_speaker
```

**解读**：
- **不调模型做裁决**——直接**倒着扫消息线程，找最后一条 `HandoffMessage`，它的 `target` 就是下一个说话人**；
- **没有交接消息 → 保持当前说话人**（`return self._current_speaker`）。

🔴 **这是第三种"谁下一个说话"的形态：不是引擎裁决，也不是模型从名单里挑，而是"上一个说话人主动点名下一个"。**
→ **对我们的映射（值得认真考虑）**：
  - **老师讲完一句后，可以主动"点名"某位同学**——比如 komari 说「这道题……我上次看他（指向同学 A）在这里翻过车」。
  - 🔴 **优点**：**交接意图来自教学现场，天然贴合"不冻结教学行为"**；且实现极简（就是一个消息类型 ＋ 一个倒扫）。
  - 🔴 **缺点**：**依赖模型主动产出 `HandoffMessage`**——模型不产出就没有交接。且**这与约束 ①（角色不许自由生成问题）有张力**：模型一旦能"点名下一个说话人"，它就能间接编排课堂。
  - **结论**：**不借**为默认机制，但**记在案**作为 §6.2 的候选之一（作为"老师主动邀请同学"这条特定 cue 的实现方式，见 §10.3 路 C）。

```python
    utt, end = generate_one_utterance(maze, target_persona, init_persona, retrieved, curr_chat)

    curr_chat += [[target_persona.scratch.name, utt]]
    if end:
      break
...
  return curr_chat
```

**解读（四条）**：
1. 🔴 **循环上限 `range(8)`**——**硬上限，防止无限对话**（与 AutoGen 的 `max_turns` 同类）；
2. **A 说一句 → 检查 `end` → B 说一句 → 检查 `end`** ——**严格的二人交替**；
3. 🔴 **`curr_chat[-4:]`：只把最近 4 句喂回检索** → **滑动窗口**，避免上下文无限增长；
4. 🔴 **每条消息在数据层就是 `[speaker_name, utterance]` 二元组**（`curr_chat += [[init_persona.scratch.name, utt]]`），最后拼成 `f"{speaker}: {utt}\n"`（`plan.py:285–288`）。

**对照 §1 与 §2 的收敛结论**：
| 项目 | 发言人归属的做法 | 位置 |
|---|---|---|
| SillyTavern | `content = \`${chat[j].name}: ${content}\`` | `openai.js:594–611` |
| AutoGen | `message = f"{msg.source}: {msg.content}"` | `_selector_group_chat.py:216–228` |
| generative_agents | `curr_chat += [[name, utt]]` → `f"{speaker}: {utt}\n"` | `converse.py:148`、`plan.py:288` |

🔴 **三个互相独立、语言与架构都不同的项目，都收敛到同一个答案：把发言人名字写进文本，格式是 `名字: 台词`。**
→ **这是本节最硬的证据**：我们的通道设计里，"同学发言怎么进对话"**必须**带 `名字: ` 前缀。这不是我们的发明，是**三个独立先例的共同做法**。

### 4.1 Ren'Py：名牌与配色是**角色定义时声明的字段**，不是运行时算的

#### 🔴 `who_color` —— **每个角色自带一个名字颜色**

**源码（逐字）** — `renpy/character.py:1880–1894`（类文档，`Character` 的 kwargs 说明）：

**源码（逐字）** — `src/actions/Dialog.ts:416–424`（**给当前说话者加上 focus，并给名字上色**）：

- **Monogatari 提供的是"高亮钩子"，不是"变暗效果"** —— `focus` class 加上去了，但**仓库不自带把它画出来的 CSS**（留给主题/使用者）。

- ✅ **可借的正是这一层**：**"当前说话者 = 一个可由 CSS 命名的状态"，引擎只负责切换状态**。这对我们（自有前端 + 自有样式）是**最合适的形状**：引擎切 class/属性，样式我们完全掌控。

### 4.3 🔴 两人以上的立绘：**"谁在说话"必须是显式状态，不能靠位置推断**

**汇总三条源码事实**：

| 机制 | 源码 | 性质 |
|---|---|---|
| `who` 与 `what` 分离 | Ren'Py `character.py:1542–1569` | **数据层分离**（谁说的 vs 说了什么） |
| 角色自带名字颜色 | Ren'Py `character.py:1886–1894`；Monogatari `Dialog.ts:420–424`、`dialog-log/index.ts:71–74` | **声明式配色**（不是运行时算） |
| 当前说话者 = 一个可切换的状态 | Monogatari `Dialog.ts:215`、`:418`（`focus` class 增删） | **状态钩子**（效果由 CSS 定） |
| 换人事件显式标记 | Monogatari `Dialog.ts:319`、`:326`（`nvl-dialog-footer`） | **边界标记** |
| 具名 vs 无名分叉 | Monogatari `Dialog.ts:320`、`:328`（`named`/`unnamed`） | **类型分叉** |

🔴 **对我们 UI 侧（§11）的直接结论**：
1. **名牌 + 配色是"角色声明的一部分"** → 写进 `cast`，不运行时算；
2. **"当前说话者"是一个显式状态字段** → 由引擎裁决结果驱动，不由"谁最后一条消息"推断；
3. **说话者高亮 = 状态切换（class 增删）**，视觉由我们自己的 CSS 决定；
4. **"换人了"要能在 DOM 上被标记**（Monogatari 的 `nvl-dialog-footer` 先例）；
5. **旁白/注入行与角色台词必须 DOM 可分**（`named`/`unnamed` 先例）。

#### 5.1.4 🔴 **本节新增取证：`source.kind` 的 schema 是「开放」的**

**这条 P3 与 S3 都没覆盖**——它是"我们能不能给角色发言一个自有 kind"这个问题的**决定性证据**。

**源码（逐字）** — `tmp/dsh-installed/dsh-session-format-v0-to-v1/lib/index.js:760–921`（`messageSourceValue` 函数）：

```js
function messageSourceValue(value, label, version, expected) {
	const source = releasedV0Record(value, label);
	if (expected === "assistant" && source["kind"] !== "model") throw new SessionFormatError(`${label} must be model source`);
	if (expected === "tool" && source["kind"] !== "tool") throw new SessionFormatError(`${label} must be tool source`);
	switch (source["kind"]) {
		case "user":
			assertReleasedV0Keys(source, ["kind"], ["rpcId", "clientTimeZone"], label);
...
		case "plugin":
			pluginSourceValue(source, label);
			return;
...
		case "webhook":
			assertReleasedV0Keys(source, [
				"kind",
				"provider",
				"source",
				"deliveryId",
				"ruleId",
				"form",
				"summary"
			], [], label);
...
			return;
		default:
			nonEmptyString(source["kind"], `${label} kind`);
			return;
	}
}
```

🔴 **`default` 分支逐字只有一句**：`nonEmptyString(source["kind"], ...)` —— **任何非空字符串都放行**。

**完整已枚举的 kind 清单（逐字，`dsh-session-format-v0-to-v1/lib/index.js` 的 case 标签）**：
```
user | plugin | model | tool | agent-instructions | session-reference | team-message
| goal | skill-invocation | skill-catalog | coordinator | subagent-report
| subagent-settled | webhook        ← 共 14 个被显式校验的 kind
+ default: 任何非空字符串
```

🔴 **两层含义，必须分清**：
1. **对已知 kind，schema 是"严格"的**（如 `plugin` 必须带 `plugin` 字段，`form` 只能取 `instructions|catalog|snapshot|notice|relay|recall` 之一——`pluginSourceValue` 逐字）；
2. **对未知 kind，schema 是"开放"的**（只要求非空字符串）。
→ **`socratic-engine` 正是走了第 2 条**（S3 实测已落盘、已通过校验，见 §5.1.2）。

🔴 **另一条重要旁证（`pluginSourceValue` 的 `form` 值域，逐字）** — 同文件 `:917–940`：
```js
	const form = source["form"];
	if (form === void 0) return;
	literalValue(form, [
		"instructions",
		"catalog",
		"snapshot",
		"notice",
		"relay",
		"recall"
	], `${label} form`);
```
**解读**：**如果我们把角色发言挂在 `kind: 'plugin'` 下，`form` 只能取这 6 个值之一** —— 语义都不对（没有一个表示"某个角色在说话"）。
→ 🔴 **结论：角色发言应当用自有的 `source.kind`（例如 `classroom-role`），不要蹭 `plugin`。** 这是**schema 层面的直接依据**，不是偏好。

#### 5.1.5 【必答 1】的最终结论

| 层 | 结论 | 依据 |
|---|---|---|
| **服务端事件流** | 一个 turn 内可以有多条 `user/message`（不同 `source.kind`），**且可以给任意非空 kind** | S3 §1.7 ＋ 本节 §5.1.4 |
| **客户端呈现** | `assistant/message` → 无名的"助手"气泡（**官方无身份字段**）；`user/message` 且 `kind !== 'user'` → **带 `label = <kind>` 的注入行** | P3 §2.5 证据 C/D |
| 🔴 **"一个回合两个角色说话"的可行解** | **第一人走 `assistant`（气泡），第二人走 `user/message` ＋ 自有 `source.kind`（注入行）** | P3 §2.5「路 A」 |
| ⚠️ **代价（必须认账）** | **第二个说话人在视觉上是"上下文注入"，比 `assistant` 气泡弱**。**这是官方能力的边界，不是我们实现得不好。** | P3 §2.5「路 A 代价」 |

### 5.2 【必答 2】角色发言能不能做成「换一个 source kind 的注入」？

**结论：✅ 能，而且这是目前唯一零改宿主、零改客户端的通道。** 依据见 §5.1.4（schema 开放）＋ §5.1.3（客户端 `default` 分支自动按 kind 出标签）。

**但要认清这条通道的三个边界（逐条带依据）**：

#### 边界 A · 注入是 `user/message`，会**进模型上下文**

`createUserMessage` 的用法（逐字）— `开源线/DSH定制/code/plugins/socratic-engine/index.mjs:267–274`：

```js
      createUserMessage({
        ...
        source: { kind: 'socratic-engine', form: 'classroom-block', block: d.id },
        ...
      })
    return { kind: 'enter', messages: [...decision.messages, ...injected] }
```

🔴 **含义**：注入的消息**既是"给学生看的呈现"，也是"给模型看的上下文"**——两者是同一份东西，**不能只做其中一个**。
→ **对我们的直接影响**：同学说的那句台词，**一旦注入，就永久留在模型的上下文里**（和老师看到的一样）。**这正是我们要的**（"同学也要继承上下文"），但**也意味着"同学台词会持续占用上下文预算"**——与约束 ⑥（稀释教学密度）是同一枚硬币的两面。

#### 边界 B · 注入时机受 `agent/pre-step` 限制

S3 §2.1 已证：`agent/pre-step` payload 含 `{ agent, messages, turn, step, signal }`，且**每个 step 调一次**。
→ **同学发言只能在"回合开始前"注入，不能在"老师说到一半"时插进去。**
🔴 **这是一个真实的能力边界**：**"同学在老师追问到第三句时插话"这个体验，在当前宿主下做不到**——同学只能在**下一个回合的开头**出现。
**这条要写进 §13 的风险清单**（用户原话"作为 NPC 一样插入其中"的"插入"，在时间粒度上是**回合级**，不是**句级**）。

#### 边界 C · `source.kind` 会**永久落盘**（不可改）

`source.kind` 是写入 `session.v3.jsonl` 的持久字段（S3 §1.7 的落盘真相）。
→ **一旦某个 kind 名定了（如 `classroom-role`），改名的代价是"旧会话读不回来"**（P3 §2.3 提到 `replaceRisk` 与 `keyDomain` 的同类风险）。
🔴 **设计含义**：**kind 命名要一次定对，且要能容纳"未来很多角色"**。
→ 建议形态：**一个 kind ＋ 在附加字段里区分角色**（如 `{ kind: 'classroom-role', role: 'peer', castId: 'peer-02', ... }`），**而不是每个角色一个 kind**（否则每加一个同学就要新增一种 kind，且旧会话的 kind 集合会膨胀）。

### 5.4 【必答 4】`ctx.subagents` 与 `dsh-tool-subagent`：后台子代理当"供给端"可行吗？延迟多少？

> **实际包名**：安装版里是 **`dsh-subagent`**（服务）＋ **`dsh-tool-subagent`**（工具）＋ 三个 driver：
> `dsh-subagent-fork-in-process`、`dsh-subagent-in-process-driver`、`dsh-subagent-spawn-in-process`。

#### 5.4.1 🔴 关键发现：**子代理可以有自己的 persona**（且是"影子"式覆盖）

**源码（逐字）** — `tmp/dsh-installed/dsh-subagent/lib/index.js:521–553`（`applyChildComposition`）：

```js
/**
* Compose one child inside its creation window: join its parent's preset,
* register the fixed delegation-scope statement, then apply the child's own
* shadowing persona section and tool restriction, all owned by the child's
* scope and therefore invisible to its parent and siblings. Creation and cold
* resume both pass through here.
*
* The join comes first and the child's own registrations second, which is the
* order the layering already implies — the nearest scope wins a name, and a
* per-child restriction intersects with everything its chain admits — but
* stating it here keeps the two steps from being read as independent.
*
* The join and the per-child registrations live in ONE call because a child
* composed without the join is exactly the defect this function exists to
* prevent: with every model-facing row on the agent plane, a child that joins
* no preset sees an empty tool registry and none of its parent's prompt
* sections. Taking the parent as a parameter is what makes that omission
* unrepresentable at the call sites.
* @param childCtx - the child agent's scoped creation context.
* @param parent - the delegating parent whose composition the child joins.
* @param composition - the per-child persona and tool filter to install.
*/
function applyChildComposition(childCtx, parent, composition) {
	childCtx.get("agentPresets")?.composeFrom(childCtx, parent.ctx);
	childCtx.systemPrompt.context({
		name: "subagent:delegation",
		order: childCtx.systemPrompt.getContextOrder("SUBAGENT_DELEGATION"),
		text: SUBAGENT_DELEGATION_CONTEXT
	});
	if (composition.persona !== void 0) childCtx.systemPrompt.section({
		name: "deployment:persona-prefix",
		order: childCtx.systemPrompt.getSectionOrder("DEPLOYMENT_PERSONA_PREFIX"),
		text: composition.persona
	});
	if (composition.toolFilter !== void 0) childCtx.tools.restrict(composition.toolFilter);
}
```

🔴 **`composition.persona` 是可传的**（`startContinuable` 里 `...request.persona !== void 0 ? { persona: request.persona } : {}`，`:1671`）。

#### 🔴 但是：**子代理会**继承**父的教室 system 段 —— 这是本条通道的致命伤**

**为什么**：`applyChildComposition` 装的 persona **用的是一个固定 section 名** `"deployment:persona-prefix"`，其 order 是 `DEPLOYMENT_PERSONA_PREFIX = 0`（`dsh-system-prompt/lib/index.js:12`）。

**而教室老师的 persona 装在** —— `code/plugins/socratic-engine/index.mjs:211–222`（逐字）：
```js
  // ---- 2) 系统段注册（一次性） ----
  let registered = 0
  for (const block of current.manifest.blocks) {
    if (block.position.target !== 'system') continue
    ctx.systemPrompt.section({
      name: `socratic-engine:${block.id}`,
      order: block.position.order,
      text: block.text,
      interpolate: false, // 骨架：系统段不做 {{var}} 插值；状态渲染走 chat 注入
    })
    registered += 1
  }
```
且 `classroom.yaml` 里 `persona.komari` 的 order 是 **`10200`**（`classroom.yaml` 逐字：`position: { target: system, order: 10200 }`）。

🔴 **两件事叠起来的后果**：
1. 子代理的 persona 装到 **order 0**（`deployment:persona-prefix`）；
2. 教室老师的 persona 装在 **order 10200**（`socratic-engine:persona.komari`）——**section 名不同**；
3. **`systemPrompt.section()` 的文档逐字（`dsh-system-prompt/lib/index.js:233–236`）**：
   ```
   * Register an ordered prompt section in the calling context's scope. A scoped
   * section shadows a global section with the same name; duplicates within one
   * layer and non-finite orders throw.
   ```
   → **只有"同名"才 shadow**。**`socratic-engine:persona.komari` 与 `deployment:persona-prefix` 不同名 → 两条都在。**
4. 🔴 **而且子代理是"join 父的 preset"**（`childCtx.get("agentPresets")?.composeFrom(childCtx, parent.ctx)`）→ **教室插件行也被继承** → **`socratic-engine` 的所有 system 段（含 komari 人格、`system_core.md` 教学法、`world/*`）都会出现在子代理的 prompt 里**。

**结论（🔴 这是本节最重要的负面结论）**：
> **用 `ctx.subagents` 当"同学供给端"，会让"同学"读到一个"既是你自己、又是老师"的 prompt。**
> **它无法只带走"学生人格"而不带走"教师人格与教学法"。**
> **→ 这条通道在当前教室架构下（教师人格走 `target: system` 常驻段）不成立。**

**如果一定要走这条路，唯一的修补方向**（列出但不推荐，因为改动面大）：
- 让教室的教师人格**不注册为全局 system 段**，而**只在父 agent 的 scope 里注册**（`systemPrompt.section()` 是 `layers.effect(this.ctx, ...)`，**scope 决定可见性**）；
- ⚠️ **但这需要改动 `socratic-engine` 的系统段注册策略**（从"插件 apply 时注册"改为"父 agent 专属注册"），**且 `apply()` 的 `ctx` 是不是父 agent 的 scope，本轮未取证**。
- 🔴 **标【推断／待确认】**，且**本轮不建议做**。

#### 5.4.2 延迟：**能给出的结论是"多一整轮 agent 循环"，不是具体秒数**

**源码依据**：
- `startContinuable`（`dsh-subagent/lib/index.js:1643–1734`）逐字文档：`* Start one continuable background child and resolve at initial inbox acceptance.`
- 子代理是一个**完整的 agent**（有自己的 session、自己的 turn/step、自己的 LLM 调用链）：`const activation = await this.activations.materialize({ childId, provider: spec.provider, parent, create: { seed, meta: ..., ... }, ... })`

🔴 **可给的结论（不编数字）**：
- 子代理**不是一个"函数调用"**，是一个**独立的 agent turn** → 延迟 = **至少一次完整的 LLM 往返 ＋ 子代理自己的 tool 循环**；

## §6 【必答 1】谁决定下一个发言：推荐 ＋ 依据

### 6.1 三种形态的对照（prior art 摆在一起）

| 形态 | 谁决定 | prior art | 源码依据 | 特点 |
|---|---|---|---|---|
| **A · 引擎规则裁决** | 引擎（确定性规则） | SillyTavern `POOLED` / `NATURAL`；AutoGen `RoundRobinGroupChat` | `group-chats.js:1197–1232`、`:1242–1320`；`_round_robin_group_chat.py:72–82` | **零 LLM 成本**；可解释、可断言；但"看不懂语义" |
| **B · 模型自选** | 一次额外的 LLM 调用 | AutoGen `SelectorGroupChat` | `_selector_group_chat.py:232–302` | **懂语义**；但**每回合多一次调用**（成本翻倍），且要处理"选不出来"（`max_selector_attempts=3` ＋ 兜底） |
| **C · 上一个说话人点名** | 上一位发言者产出 handoff | AutoGen `SwarmGroupChat` | `_swarm_group_chat.py:82–98` | **最贴现场**；但**依赖模型主动产出**，且与约束 ①（角色不许自由生成问题）有张力 |

**三方共同的一条（🔴 决定性）**：**三家的"谁下一个说话"全都是「选人 → 再由被选中者生成」两步分离的**（SillyTavern `setCharacterId`→`Generate`；AutoGen `select_speaker`→`GroupChatRequestPublish`；generative_agents 上层决定 `init/target_persona`→`generate_one_utterance`）。**没有一家是"模型自己决定要不要说话"的。**

### 6.2 🔴 推荐：**A 为默认 ＋ B 作可选 ＋ C 只用于"老师主动邀请"这一条 cue**

**具体形态**：

```
每回合开头（agent/pre-step，step===1）：
  ① 引擎读课堂状态（纯本地，零 LLM）：
     - 本讲进度（progress.md 的 current_lesson）
     - 当前相位（progress.md 的 current_phase）
     - 本讲已出场次数（引擎内存态，见 §9.2）
     - 最近 N 条消息（用于僵局判据，见 §8）
     - 错题本里本讲相关的行（§7）
  ② 跑 cue 裁决（纯函数，见 §6.3）：
     - 若无 cue 命中 → 不注入任何东西（正常上课）
     - 若命中 → 产出 { castId, kpId, wrongStepId, style }
  ③ 若命中 → 生成同学台词并注入（§7.3 的确定性模板 ＋ 一次 LLM 润色，见 §7.4）
```

**为什么 A 为默认（三条依据，逐条对 prior art）**：
1. **成本**：B 每回合多一次 LLM 调用（AutoGen `_select_speaker` 是完整的一次 `model_client.create`）——**而我们的场景是"每讲 3–5 次出场"，用一次额外的 LLM 调用去决定"要不要出场"，成本收益比极差**。
2. **可断言**：约束 ② 要求"僵局要**可确定性检测**"——**如果连"该不该出场"都是模型说的，那僵局检测就不可断言了**。A 让 §8 的判据成为可写单测的纯函数（AutoGen 的 `FunctionalTermination` 就是这个形状，`conditions/_terminations.py:158–166`）。
3. **确定性兜底**：B 的失败路径（`max_selector_attempts` 用尽）需要兜底，而 AutoGen 的兜底是"沿用上一个说话人"（`_selector_group_chat.py:295–296`）——🔴 **对我们等于"老师再说一次"，等于没插话**（§2.7 已列此偏离）。**A 天然没有这个问题**：规则不命中就是不出场。

**为什么保留 B（可选）**：
- 存在一类 cue 是**规则写不出来**的：**"学生说了一个语义上很接近但方向偏了的想法，这时候该不该让某位同学接话"** —— 这需要语义判断。
- ✅ **落地方式**：把 B 做成 `cast[].cue_judge: 'rule' | 'model'` 的**每角色开关**，**默认 `rule`**；`model` 模式下**只在 A 的粗筛命中后**才调用（**两级过滤，不是每回合都调**）。
- 🔴 **这条是我们的自研部分，标「这一步没有先例」**：SillyTavern 与 AutoGen **都是"二选一"的策略**（`activation_strategy` 或 `selector_func`），**没有"规则粗筛 ＋ 模型细判"的两级结构**。⚠️ **理由（为什么值得自研）**：我们的场景有**硬成本约束（每讲 3–5 次）**，纯 B 太贵、纯 A 太钝，两级是唯一能同时满足"稀疏"与"语义敏感"的形态。

**为什么 C 只用于一条 cue**：
- C（handoff）**恰好适合"老师主动邀请同学"这一条**：komari 说「这道题……我上次看他在这里翻过车」→ 自然交接。
- ✅ **落地方式**：**不让模型自由产出 handoff**，而是**引擎提供一个工具**（如 `classroom_invite_peer`），**老师显式调用时才交接**。→ **这样"交接"是模型的一次工具调用（可审计、可计数），而不是自由文本里的一句话**。
- 🔴 **这条也是自研**：AutoGen 的 `SwarmGroupChat` 是**自由 handoff**（扫消息找 `HandoffMessage`），**没有"用工具调用约束交接"的形态**。**标「这一步没有先例」。**

### 6.3 `cue` 裁决函数的签名（**照着它就能写代码**）

```js
/**
 * 纯函数：给定课堂状态，决定本回合是否要同学出场、谁出场、说什么。
 * 零副作用、零 LLM。所有输入都是本地可读的。
 *
 * @param {object} state
 * @param {number} state.turn               // 本回合号（agent/pre-step payload.turn）
 * @param {string} state.phase              // 当前相位 id（phasestore 内存态，镜像到 progress.md）
 * @param {number} state.lesson             // 本讲编号（progress.md 的 current_lesson）
 * @param {string} state.studentText        // 本回合学生消息的纯文本（无则空串）
 * @param {number} state.roundsSinceProgress// 连续无新知识点回合数（引擎内存态，§8.2）
 * @param {number} state.spokeThisLesson    // 本讲已出场次数
 * @param {object} state.cast               // 教室配置的角色表（§10）
 * @param {number[]} state.spokenCastIds    // 本讲已出场过的角色 id
 * @param {string} state.lastSpeakerCastId  // 上一次出场的角色 id（防连说两次）
 * @param {Array<{kpId:string, wrongStep:string}>} state.mistakeRows  // 错题本里本讲的行
 * @param {string[]} state.openKpIds        // knowledge_points.md 里本讲状态为 [ ] 或 [~] 的条目 id
 *
 * @returns {null | {castId:string, kpId:string, wrongStepId:string|null, style:string, reason:string}}
 *   返回 null = 本回合不出场（正常上课）。
 *   reason 是给人看的诊断串（写进会话事件，便于课后复盘）。
 */
```

🔴 **返回 `null` 是默认且最常见的结果**——这是"稀疏"在代码上的体现（约束 ④⑥）。

### 6.4 裁决流程（伪代码，**照抄即可实现**）

```
function decideCue(state) {
  // ── 门 1：额度门（约束 ④⑥；依据 SillyTavern POOLED 的"没说过话的优先"）
  if (state.spokeThisLesson >= state.cast.policy.lessonQuota) return null   // 本讲额度用完
  if (state.turn < state.cast.policy.minTurnGap) return null                // 开场不插话（见 §9.3）

  // ── 门 2：相位门（依据 classroom.yaml 的 phases 声明）
  //    同学只在 probe / check / review 三个相位可以出场；
  //    open（开场）与 close（收尾）不出场 —— 开场是老师建场景，收尾是老师收束。
  if (!state.cast.policy.allowedPhases.includes(state.phase)) return null

  // ── 门 3：候选角色（依据 SillyTavern activatePooledOrder 的 haveNotSpoken 思路）
  const candidates = state.cast.roles
    .filter(r => r.enabled)
    .filter(r => r.id !== state.lastSpeakerCastId)      // 防连说两次（SillyTavern bannedUser）
  if (candidates.length === 0) return null

  // ── 门 4：触发条件（三条路，命中任一即出场）
  //    路 A · 僵局（§8）—— 最高优先
  //    路 B · 错法命中（§7）—— 学生踩到了错题本里的某一步
  //    路 C · 老师邀请（工具调用，§6.2 C 形态）
  const trigger = matchTrigger(state, candidates)     // 见 §8.3 / §7.2
  if (trigger === null) return null

  // ── 门 5：选人（约束 ⑤：不随机；按"认知风格 × 当前错法"匹配）
  const chosen = pickRole(candidates, trigger, state)  // 见 §9.4
  if (chosen === null) return null

  return {
    castId: chosen.id,
    kpId: trigger.kpId,               // 🔴 约束 ①：问题的本体绑知识点
    wrongStepId: trigger.wrongStepId, // 🔴 约束 ③：错法来自错题本
    style: chosen.style,
    reason: trigger.reason,
  }
}
```

### 6.5 🔴 一条硬性纪律（从 prior art 直接推出）

**裁决出的 `castId` 必须在 `cast` 名册里，否则报错（不静默）**。
**依据（逐字）** — AutoGen `_base_group_chat_manager.py:184–185`：
```python
        for speaker_name in speaker_names:
            if speaker_name not in self._participant_name_to_topic_type:
                raise RuntimeError(f"Speaker {speaker_name} not found in participant names.")
```
**同理**：`kpId` 必须在 `knowledge_points.md` 里存在，`wrongStepId` 必须在错题本／错法库里存在——**否则报错**。
**理由**：这与教室既有风格一致（`classroom.yaml` 关于相位值域：*"块里出现的相位 id 不在本列表内 → 引擎**报错**（不静默不注入）"*）。

## §7 【必答 3】怎么保证「错法来自真实数据」

> **约束 ③（逐字）**：🔴 **错法库＝数据**：同学演示的错法必须来自「学生自己踩过的错（错题本）」或「知识点判据的反面」，**不能是模型即兴编的稻草人**（否则学生觉得"这同学是傻子"，效果反转）。

### 7.1 两个数据源（都是教室已有的文件，**不需要新建**）

#### 源 A · `runtime/mistake_log.md`（**学生自己踩过的错**）

**文件逐字（全文）** — `code/classrooms/cs-os/runtime/mistake_log.md`：
```markdown
# 错题本

> **字段固定**：日期 / 讲次 / 题目 / 他的答案 / 正确答案 / **他错在哪一步**。
> 🔴 **最后一项最重要**：不写"错了"，要写**哪一步**开始偏的。这一步才是复习的靶子。

| 日期 | 讲次 | 题目 | 他的答案 | 正确答案 | **错在哪一步** |
|---|---|---|---|---|---|
| （待第 1 讲后填写） | | | | | |
```

🔴 **这就是约束 ③ 的第一条数据源，且它已经设计好了**：**「错在哪一步」是独立字段**——**"哪一步"就是可确定性引用的错法 id**。
⚠️ **一个待确认点**：当前表**没有"步骤编号"列**，`错在哪一步`是自由文本。→ **若要确定性绑定，建议给它一个稳定键**（见 §7.2 的 `wrongStepId` 方案）。

#### 源 B · `knowledge_points.md` 的「判据」＝**知识点判据的反面**

**文件逐字（节选）** — `code/classrooms/cs-os/knowledge_points.md`：
```markdown
> **用法**：课后由 AI 更新状态。三档：`[ ]` 尚无理解证据 ｜ `[~]` 能复述但尚不能解释或应用 ｜ `[x]` 能解释关键机制或在新情境正确应用。
> **判据写法**：写学生能怎样解释或运用知识，不要求说出指定句子；教师讲解过不妨碍学生随后展示理解。
> 🔴 **不许只因为"老师讲过了"就打 `[x]`**；需要学生在对话或练习中实际展示理解，也不必每个细节都单独设问。
...
## 第 3 讲 · 调度：谁来决定下一个跑谁
- [ ] **KP-3.1 调度指标** —— 判据：学生能区分**周转时间**与**响应时间**，并说出它们为什么互相冲突。
- [ ] **KP-3.2 FIFO 的问题** —— 判据：学生能举出"长任务堵住短任务"的具体例子。
- [ ] **KP-3.3 SJF / STCF** —— 判据：学生能说出它们最优，但**前提是知道未来**。
```

🔴 **"判据的反面"是可机械推导的**：每条判据都是**一个"学生能做到 X"的陈述** → **反面 = "学生做不到 X"的具体形态**。
**例（🔴 逐条可推导，不是编的）**：

| 知识点 | 判据（原文逐字） | 判据的反面（＝错法，可推导） |
|---|---|---|
| KP-3.1 | 学生能区分**周转时间**与**响应时间**，并说出它们为什么互相冲突 | 把周转时间与响应时间当成同一个东西／说"它们不冲突" |
| KP-3.2 | 学生能举出"长任务堵住短任务"的具体例子 | 举不出例子／举的例子其实是短任务堵长任务 |
| KP-3.3 | 学生能说出它们最优，但**前提是知道未来** | 说"SJF 现实中就是最优的"（漏掉"前提是知道未来"） |
| KP-3.5 | 学生能说出"**不是猜未来，是用过去的行为推断**" | 说"MLFQ 是在预测下一个任务要多久" |
| KP-9.2 | 学生能说出"`counter++` 是**多条指令**，中间可以被插队" | 说"`counter++` 是一条指令，不会被打断" |
| KP-11.2 | 学生能说出"**醒来时条件可能已经又变了**" | 说"条件变量醒来就一定满足条件了" |

🔴 **关键：上表右列全部由左列机械推导得出**——**判据写的是"能做什么"，反面就是"做不到／做反了"**。**不需要模型即兴创作。**
⚠️ **诚实边界**：**"判据的反面"到"一句自然的同学台词"之间，仍需要一次语言化**（§7.4）。**这一步是模型做的**——但**它做的是"把给定的错法说成人话"，不是"想出一个错法"**。**这个区分就是约束 ③ 的全部要点。**

### 7.2 🔴 确定性绑定：`(kpId, wrongStepId)` 是**引用**，不是文本

**核心设计**：裁决产出的 `wrongStepId` **必须是一个可定位的键**，指向：
- **错题本的一行**（`mistake_log.md` 的表格行，建议加稳定列 `id`，如 `M-2026-09-25-01`）；
- **或知识点判据反面的一条**（建议在 `knowledge_points.md` 之外单列一份 `runtime/wrong_step_library.md`，每条一个 id，如 `W-KP-3.3-01`）。

🔴 **为什么必须是引用而不是文本**：
1. **可审计**：课后能核对"这次同学说的错法，是哪条记录"（**这是约束 ③ 的可验证形式**）；
2. **可去重**：同一错法不会被反复演示（**§9.2 的额度计数按 id 去重**）；
3. **可失效**：学生**改对了**之后，那条错法应当**从可用池里移除**（错题本状态变化 → 池子变化，**确定性联动**）。

**判据写法（建议加进 `mistake_log.md` 的表头说明，不改表结构）**：
```markdown
> 🔴 **「错在哪一步」必须能被引用**：写成一句可定位的话，并在同讲的知识点清单里能找到对应条目。
>   引擎把它当作 `wrongStepId` 的文本，**同一句话出现两次＝同一条错法**（去重按文本完全匹配）。
>   ⚠️ 待确认：是否加一列稳定 id（见 §14 待确认清单）。
```

### 7.3 同学台词的**确定性骨架**（🔴 这是"照写代码"的部分）

**同学台词 = 骨架（引擎填）＋ 语言化（模型润色）**

**骨架（引擎侧，纯字符串模板，零 LLM）**：
```js
function cueSkeleton(cast, cue, kp) {
  return {
    // 🔴 约束 ①：问题的本体必须绑知识点 —— 这句是引擎给的，不是模型想的
    questionCore: kp.question,       // 取自 knowledge_points.md 的判据，或教材里的对应追问
    // 🔴 约束 ③：错法来自真实数据 —— 这句也是引擎给的
    wrongAttempt: cue.wrongStepText, // 错题本「错在哪一步」的原文，或判据反面的原文
    // 角色只贡献这三样（约束 ①）
    voice: cast.voice,               // 语气速查（_anchor.md「角色声音速查」的风格）
    stance: cast.stance,             // 立场（"我也没想通""我觉得不对"）
    style: cast.style,               // 认知风格（直觉型／精确型／爱钻牛角尖／爱举反例）
  }
}
```

**注入模板（引擎侧，确定性拼接）**：
```
[同学出场 · {cast.name}]
{cast.name}（{cast.styleLabel}）：{wrongAttempt}
—— 然后他转向你：「{questionCore}」
```

🔴 **绑定信息（`kpId`／`wrongStepId`）不写进学生可见文本** —— 它应当放在 `source` 的附加字段里（`source: { kind: 'classroom-role', castId, kpId, wrongStepId }`），**由客户端渲染时忽略**。**这条需要 §5.1.4 的 schema 开放特性**（可以带任意附加字段）。
**作用**：**每一条同学台词都可追溯**（课后复盘／调阈值都靠它）。

### 7.4 语言化（模型侧）——**只准改写，不准增删事实**

**这一步是唯一用到 LLM 的地方**，因此必须**约束到最小**：

```
任务：把下面这条"错法"用 {cast.name} 的语气说出来。
🔴 硬约束：
  - 不得改变错法的技术内容（错在哪一步必须一致）；
  - 不得引入新的技术断言；
  - 不得把问题换掉（问题由 questionCore 给定）；
  - 输出长度上限 {N} 字。
输入：
  voice:  {cast.voice}
  stance: {cast.stance}
  wrongAttempt: {wrongAttempt}
  questionCore: {questionCore}
```

🔴 **依据（prior art 的反面）**：**三家 prior art 全都没有"约束到最小"的这一步**——SillyTavern 直接让角色自由生成（`Generate()`），AutoGen 直接让被选中的 agent 跑（`ChatAgentContainer.handle_request`），generative_agents 让 persona 自由发言。
→ **"错法必须来自数据、只准语言化"是我们的自研约束，标「这一步没有先例」**。⚠️ **理由**：**课堂场景对"事实准确性"的要求远高于角色扮演**——**一个编造的错法会让学生学到错的东西**（这是 roleplay 场景不存在的失败模式）。

### 7.5 一个必须写下来的反证（**约束 ③ 的边界**）

🔴 **"错法来自数据"不能保证"错法看起来自然"**：
- 如果错题本里那条错法**是很久以前的**，而学生**现在已经不这么错了**，那同学演示这个错法会显得**莫名其妙**（"我早就不这么想了"）。
- **依据**：`learner_profile.md` 的「卡点模式（累积，不删）」逐字：*"这里记录**他反复卡住的类型**，不是具体题目"* → **它已经区分了"具体题目"与"反复卡住的类型"**。
- ✅ **修补方向（本轮建议）**：**优先用「卡点模式」里记的"类型"，其次用「错题本」里的具体行**；且**错题本的行在被学生改对后应标记失效**（§7.2 第 3 条）。
- ⚠️ **标【待确认】**（见 §14）。

## §8 【必答 4】僵局检测的可实现判据

> **约束 ②（逐字）**：🔴 **僵局检测**：苏格拉底式教学最大失败模式＝「老师问→学生不会→再问→学生更慌」；同学插话是第三条路（把"你不会"变成"我们俩都不会，一起想"）。**僵局要可确定性检测**（连续 N 回合无实质进展／学生消息变短／"不知道"类表述）。
> **用户原话（2026-09-23）**：同学常驻更好——「**同学是解场的好办法**」。

### 8.1 prior art：僵局检测在别人那里叫什么、怎么做的

🔴 **诚实结论：三家 prior art 都没有"僵局检测"这个概念**——因为**它们都不是教学场景**。
**能借的是"判据的形状"，不是"判据的内容"**：

| 借什么 | 出处 | 为什么形状可借 |
|---|---|---|
| **`(messages) -> bool` 的纯谓词** | AutoGen `FunctionalTermination`（`conditions/_terminations.py:158–166`） | **僵局检测器的签名**；纯函数 = 可写单测 = 可断言 |
| **计数器型判据** | AutoGen `MaxMessageTermination`（`:62–104`） | "连续 N 回合"的骨架 |
| **`sources` 过滤（只在特定来源的消息里匹配）** | AutoGen `TextMentionTermination`（`:111–156`） | 🔴 **"不知道"词表只能扫学生消息**，不能扫老师/同学台词 |
| **"结束了吗"由发言者一并给出** | generative_agents `iterative_convo_v1.txt` Output 段；`run_gpt_prompt.py:2863–2875` | **僵局信号可以由老师在自己那一轮顺带给出**（**双通道**，§8.4） |
| **硬上限** | generative_agents `converse.py:130`（`for i in range(8)`）；AutoGen `max_turns` | **保险丝**：判据失灵时仍有上限 |
| 🔴 **具体的僵局判据本身** | —— | **没有先例。标「这一步没有先例」。** |

### 8.2 三条可写规则（**每条都给出阈值与定阈值的依据**）

#### 规则 1 · 连续 N 回合无新知识点

**定义"新知识点"（可机械判定）**：本回合内，`knowledge_points.md` 里**本讲**的条目中，**有任何一条的状态发生了 `[ ]`／`[~]` → 更高级**的变化。
🔴 **这需要一次状态比对**：引擎在回合开始前记一份本讲 KP 状态快照，回合结束后（`agent/turn-stopping`，S3 已证每 turn 恰好一次）再读一次，比对差异。

**阈值：`N = 3`**

**定阈值的依据（逐条，不用"大概"）**：
1. 🔴 **不能取 1 或 2**：`_anchor.md`「教学取向」逐字：*"**提问不是每轮义务**……到新的关口或混淆点再问，不拿刚讲过的事实考他，也不一次讲完整课"* → **连续 2 个回合无新知识点是"正常讲解"**（讲解片段本身不产生新知识点）。**若 N=2，正常讲课会被误判为僵局。**
2. 🔴 **不能取 ≥5**：`classroom.yaml` 里已有 **`frequency: { every: n_turns, n: 5 }`** 的两块——`anchor.check`（教学检查）与 `state.learner`（学习者档案）。**它们是"自我校准"的节奏**。**僵局检测必须在"校准节奏"之前触发**——否则等于等自我校准来救场，而校准本身不改教学动作。→ **N 必须 < 5。**
3. **取 3 的理由**：`_anchor.md`「教学取向」还写了 *"**讲解后可以自然停顿**；不为保持问答节奏而追加问题"* → **一个"讲解片段 + 一次追问 + 一次学生回应"恰好是 3 个回合**。**3 个回合走完还没动，说明这一轮的讲法对学生无效。**
4. 🔴 **`N = 3` 是初值，必须可调**：写进 `classroom.yaml` 的 `cue.stall.nTurns`，**默认 3**。**调整依据＝真实会话里的误判率**（§8.5 给了记录方式）。

#### 规则 2 · 学生消息变短

**🔴 关键设计决定：用「相对长度」而不是「绝对字数」。**

**为什么不能用绝对字数**（三条理由，逐条）：
1. **中文里"不知道"只有 3 个字，"我觉得应该是这样……"有十几个字**——**绝对阈值会把"不知道"和"简短的正确回答"混在一起**；
2. **不同知识点的回答长度天然不同**（"能举出例子吗"的答案必然比"是不是"长）；
3. **绝对阈值不可迁移**——换个学生、换个语言就失效。

**判据（可写代码）**：
```
设 L = 学生最近 K 条消息的字符长度（去掉首尾空白），K = 5
设 median = L 的中位数
若 本回合学生消息长度 < median * 0.4  且  median >= 8
则 计一次"变短"信号
```
- **`K = 5` 的依据**：与 §8.2 规则 1 的 `N = 3` 同量级，且**足够容纳"老师讲解那一段"的长消息污染**；同时 `classroom.yaml` 的 `anchor.check` 也是 5 回合节奏（同频便于对齐）。
- **`median * 0.4` 的依据**：**40% 是"腰斩再腰斩"量级**——它不会被"稍微短一点"触发（正常波动），但**"从两句话缩到一个词"必然触发**。
- **`median >= 8` 的保护**：**若学生本来就在用短句（median 只有 5 个字），任何消息都会触发"变短"** → **加这个下限防止对"习惯短答的学生"误判**。
- 🔴 **`0.4` 与 `8` 都是初值**，写进 `classroom.yaml` 的 `cue.stall.shortRatio` / `shortFloor`。

#### 规则 3 · "不知道"类表述词表

**词表（中文，初始版；每条都是"学生明示自己不会"的形态）**：
```yaml
stall:
  dontKnowPatterns:
    high:                # ── 直接表述（高置信）
      - "不知道"
      - "不会"
      - "不懂"
      - "想不出来"
      - "想不出"
      - "没思路"
      - "猜不出来"
      - "答不上来"
      - "说不出来"
      - "你直接说吧"      # ── 求助/放弃（高置信）
      - "直接告诉我"
      - "给个提示"
      - "提示一下"
      - "跳过"
      - "跳过吧"
      - "下一题"
      - "换一个"
    mid:                 # ── 不确定（中置信，需配规则 1/2 之一才计）
      - "大概"
      - "可能是"
      - "我不确定"
      - "不太确定"
      - "也许"
```

**🔴 三条使用纪律（缺一不可）**：

**① 只在学生消息里匹配（`sources` 过滤）**
**依据**：AutoGen `TextMentionTermination` 的 `sources` 参数（`conditions/_terminations.py:139–142` 逐字）：
```python
        for message in messages:
            if self._sources is not None and message.source not in self._sources:
                continue
```
**对我们的落地**：**只在 `source.kind === 'user'` 的消息里扫**——**否则同学自己说一句"我也不知道"就把僵局判据触发了**（§2.4 已列此风险）。

**② 高置信 vs 中置信要分开计**
- **高置信词命中 1 次 = 计 1 次僵局信号**（学生明说不会）；
- **中置信词（"大概""可能"）不单独计数**，**必须与规则 1 或规则 2 同时成立才计入**。
- **依据**：`_anchor.md`「教学取向」逐字：*"学生提出想法时，回应对错之处及理由"* → **"大概""可能"是学生在猜，不是不会**——**若把猜测当僵局，同学就会在学生正在思考时插话**（**这是最坏的教学事故**）。

**③ 词表必须可扩充，且要防误伤**
- ⚠️ **已知误伤**：`"不会"` 会命中 **"不会影响"**、**"不会导致"**、**"这样不会出问题"**（这些是**正确的技术表述**！）。
- 🔴 **必须加否定/技术上下文的白名单**（初始版）：
  ```yaml
  dontKnowExempt:
    - "不会影响"
    - "不会导致"
    - "不会出"
    - "不会发生"
    - "不会出现"
  ```
- ⚠️ **这条是本轮识别的真实风险，标【待确认】并建议在真实会话里统计误报**（§8.5）。

### 8.3 僵局判据的合成规则（**照抄即可实现**）

```
function isStalled(state) {
  // 输入：state = { roundsSinceProgress, studentText, recentStudentLens, cast }
  const S = state.cast.cue.stall

  // ── 规则 1：连续 N 回合无新知识点
  const r1 = state.roundsSinceProgress >= S.nTurns          // 默认 3

  // ── 规则 2：消息变短（相对）
  const median = medianOf(state.recentStudentLens.slice(-S.shortWindow))   // S.shortWindow 默认 5
  const len = state.studentText.trim().length
  const r2 = median >= S.shortFloor && len < median * S.shortRatio          // 默认 8 / 0.4

  // ── 规则 3：词表（分置信度）
  const hi = S.dontKnowPatterns.high.some(p => contains(state.studentText, p) && !isExempt(state.studentText, S.dontKnowExempt))
  const mid = S.dontKnowPatterns.mid.some(p => contains(state.studentText, p))

  // ── 合成：高置信词单独成立；中置信词需与 r1/r2 之一共现
  if (hi) return { stalled: true, reason: 'explicit-dont-know' }
  if (mid && (r1 || r2)) return { stalled: true, reason: 'hedged-plus-' + (r1 ? 'no-progress' : 'shortening') }
  if (r1 && r2) return { stalled: true, reason: 'no-progress-plus-shortening' }
  if (r1) return { stalled: true, reason: 'no-progress' }
  if (r2) return { stalled: true, reason: 'shortening' }

  return { stalled: false }
}
```

🔴 **合成规则的设计理由**：
- **单条规则就够触发（r1 或 r2 任一）** —— 因为**僵局的代价高于误判的代价**：多插一次话，最多是"同学说了句多余的话"；**漏掉一次僵局，是学生卡死然后放弃**。
- **中置信词必须共现** —— 因为**猜测不等于不会**（见 §8.2 规则 3 ②）。
- **`reason` 必须落盘** —— 课后能统计"哪一种判据最常触发"（**这是调阈值的唯一依据**，§8.5）。

### 8.4 🔴 双通道：规则判据 ＋ 老师的自陈信号

**依据（prior art）** — generative_agents 的提示词让模型**在同一句里同时给出"说什么"和"说完没说完"**（`iterative_convo_v1.txt` Output 段逐字）：
```
Output format: Output a json of the following format: 
{
"!<INPUT 11>!": "<!<INPUT 12>!'s utterance>",
"Did the conversation end with !<INPUT 13>!'s utterance?": "<json Boolean>"
}
```
🔴 **注意：那个实现里"结束了吗"是模型的输出**（且解析用了脆弱的子串判据，见 §3.3，**我们明确不借那个解析**）。

**我们的形态（建议）**：
- **规则判据（§8.2）是主通道**——零成本、可断言；
- **老师可以用一个工具**（如 `classroom_flag_stuck`）**声明"我这一轮感觉问不动了"** —— **这是第二通道，且是显式工具调用（可审计、可计数）**，**不是解析模型的自由文本**。
- 🔴 **两条通道取或（OR）**：任一成立即视为僵局。**理由同 §8.3**：漏判的代价高于误判。

### 8.5 🔴 阈值怎么定：**给方法，不给拍脑袋的数字**

**这是本节最重要的部分**——用户明确要求"**写清楚阈值怎么定**"。

**当前所有阈值都是初值**（`nTurns=3`／`shortRatio=0.4`／`shortFloor=8`／`shortWindow=5`）。**它们必须由真实会话数据校准**。校准方法（**照做即可**）：

**第一步 · 记录（引擎侧，零成本）**
每回合把以下结构追加到 `runtime/cue_log.md`（**新文件，引擎写；不进模型上下文**）：
```markdown
| 回合 | 相位 | r1 | r2 | 词表命中 | 合成结果 | 是否真的卡住（课后人工标） |
|---|---|---|---|---|---|---|
| 7 | probe | 0 | 1 | — | stalled:shortening | ? |
```

**第二步 · 标注（课后，人工，一次几分钟）**
🔴 **"是否真的卡住"这一列只能人工标** —— 依据：**没有任何自动指标能替代"这次学生是不是真的不会"**。
**标注口径**（写死，避免标不准）：**"下一个回合里，学生是否给出了任何推进教学的新信息？"** 有 = 没卡；没有 = 卡了。

**第三步 · 算两个率，调一个阈值**
- **漏报率** = 真卡住但判据说没卡 / 所有真卡住 → **漏报率高 → 放宽判据**（降 `nTurns`、升 `shortRatio`）；
- **误报率** = 判据说卡了但其实没卡 / 所有判据说卡的 → **误报率高 → 收紧判据**（升 `nTurns`、降 `shortRatio`）。

🔴 **调整方向写死（避免反复横跳）**：
> **优先压漏报率，把误报率当成次要指标** —— 依据：**多插一次话的代价 ≪ 学生卡死的代价**（§8.3 的设计理由）。
> **具体操作**：`nTurns` 每次只调 ±1，`shortRatio` 每次只调 ±0.1，**一次只动一个参数**，**至少跑完一讲（30–45 分钟）再评估**。

**第四步 · 上限（保险丝）**
**无论阈值怎么调，`spokeThisLesson` 的额度门（§9.2）始终生效** —— **它保证"判据再敏感也不会刷屏"**。
**依据**：AutoGen 的 `max_turns` 与 generative_agents 的 `range(8)` 都是同一形状的硬上限（`conditions/_terminations.py:80`、`converse.py:130`）。

### 8.6 诚实边界

- ⚠️ **三条规则与全部阈值都是初值，未经真实会话校准**。**本节给的是"校准方法"，不是"调好的参数"。**
- ⚠️ **`roundsSinceProgress` 的实现依赖"KP 状态快照比对"**，而**引擎目前没有读 `knowledge_points.md` 状态的功能**（`classroom.yaml` 的 `kp.current` 只是**注入**，`frequency: { every: phase }` ＋ `phase: { phases: [check, close] }`）。**这是新增功能，见 §12 工期。**
- ⚠️ **词表的中文覆盖度未验证**；**"不会影响"这类误伤是本轮识别的、未解决的**。
- ❌ **没有跑过任何真实会话**（红线禁止）。**所有判据都只经过"读起来对"，没有经过"跑起来对"。**

## §9 【必答 5】稀疏出场怎么落地

> **约束 ④（逐字）**：🔴 **常驻 ≠ 常发言**：常驻的是舞台上的存在感（确定性反应，零模型成本），发言是**稀疏事件**（每讲 3–5 次）。
> **约束 ⑤（逐字）**：**不建议纯随机轮换**（主代理判断待裁）：教学关系需要连续性 → **固定搭子 1 位（记得你上次错在哪）＋ 每讲客串 1 位**；"玩法多样"的来源应是**认知风格差异（直觉型／精确型／爱钻牛角尖／爱举反例）× 知识点错法**。

### 9.1 「常驻」在工程上是什么：**三个层次，成本完全不同**

🔴 **必须先把"常驻"拆成三件事，否则会做出成本失控的方案**：

| 层次 | 是什么 | 成本 | 依据 |
|---|---|---|---|
| **L1 · 模型知道他在场** | 一段**在场声明**进 system prompt 或 chat 注入 | **一次性文本成本**（几百字节） | SillyTavern 的 `generation_mode: APPEND` 只追加 `depth_prompt`，**不是整张角色卡**（`group-chats.js:129–133`、`:427–475`）；AutoGen 的 `ChatAgentContainer` 让所有参与者都收消息进 buffer（`_chat_agent_container.py:56–67`） |
| **L2 · 学生在界面上看见他** | 右侧面板的**立绘／名牌** | **零模型成本**（纯前端） | P3 §7b：`sidebar.right.pane.tab`（`replaceRisk = "none"`） |
| **L3 · 确定性反应（无台词）** | 立绘的一个动作／表情／名牌的一个状态变化 | **零模型成本** | Monogatari 的 `focus` class 增删（`Dialog.ts:215`、`:418`）——**引擎只切状态，不生成文本** |

🔴 **关键结论：`L1` 是唯一有文本成本的，且它只该写一次。**
**L1 的文本形态（建议，写进教室的一个块）**：
```markdown
## 在场的同学（他们不发言，但你看得见他们）

- **程霁（校样组，固定搭子）**：坐在你左手边。他记得你上次在第 3 讲把周转时间当成了响应时间。
  他现在不说话。
- **阿澈（新人记者，本讲客串）**：今天第一次来编辑部。他没看过你的稿子。
```
🔴 **这段文本的作用是"让模型知道他们存在"，不是"让他们说话"** —— 所以它**必须显式写"他现在不说话"**（否则模型会替他们发言）。

### 9.2 额度门：**每讲 3–5 次**怎么落到代码

**先解决"一讲有多少回合"这个前提**（**否则"3–5 次"没法转成频率**）：
- `curriculum.md` 逐字：*"**每讲 30–45 分钟**"*；
- **本项目的会话实测**（S3 §3.1）：2 turn 的短会话；**没有"一讲多少 turn"的实测数据**。
- 🔴 **故取一个可调的估算**：**一讲 ≈ 20–30 个回合**（依据：30–45 分钟、含讲解与停顿、每回合 = 一次学生输入）。
- ⚠️ **标【推断／待确认】**——**但下面的设计对这个数不敏感**（因为额度是"绝对次数"，不是"频率"）。

**额度门（照抄即可实现）**：
```
// 引擎内存态，每讲重置（讲次变化时清零；讲次来源 = progress.md 的 current_lesson）
state.spokeThisLesson = 0
state.spokenCastIds  = []        // 本讲已出场过的角色
state.lastSpeakerCastId = null

// 裁决门 1（§6.4）
if (state.spokeThisLesson >= cast.policy.lessonQuota) return null   // cast.policy.lessonQuota 默认 4
```

🔴 **`lessonQuota` 默认取 4 的依据**：用户给的是**区间 3–5**。**取中间值 4**，并把区间两端写进配置注释（**这样调整有据可依，不是拍脑袋**）：
```yaml
lessonQuota: 4      # 用户口径 3–5 次/讲；取中值。调高→更热闹但更稀释；调低→更稀疏
```

**额度的复位时机（🔴 必须写死，否则会跨讲累积）**：
- **讲次变化时清零**——判据：`progress.md` 的 `current_lesson` 与引擎上次读到的值不同；
- **依据**：`classroom.yaml` 的 `runtime_store.lesson_key: current_lesson`，且**引擎已实现"每回合开始前再读一次"**（`index.mjs` 逐字注释：*"装载时读一次（早失败），每个回合开始前再读一次（课后更新改了讲次就立刻跟上）"*）。

### 9.3 开场保护：**前 N 回合不出场**

**阈值：`minTurnGap = 5`**
**依据（逐字）** — `world/setting.md`「五、过渡与余韵」：
> **过渡场景**（每讲开头 200–500 字）：从编辑部的具体细节切入（抽屉卡住、便签被压在最下面、装订机停了），落到本节课要解决的那次事故。

→ **开场是老师建场景的时段**（200–500 字的过渡 ＋ 落到事故）。**同学此时插话会破坏场景建立**。
**`5` 的依据**：200–500 字的过渡场景 + 第一个关口提问 + 学生第一次回应，**大约 3–5 个回合**。取上界 5（**宁可晚一点**）。
⚠️ **标【推断／待确认】**（无实测回合数）。

### 9.4 🔴 选人：**不随机**（约束 ⑤ 的落地）

**prior art 的对照**：
- SillyTavern `POOLED`：**纯随机**（`members[Math.floor(Math.random() * haveNotSpoken.length)]`，`group-chats.js:1214`）；
- SillyTavern `NATURAL`：**掷骰**（`talkativeness >= rollValue`，`:1285`）；
- AutoGen `SelectorGroupChat`：**模型选**（`_selector_group_chat.py:232–302`）。
- 🔴 **三家都不是我们要的**（约束 ⑤ 明确"不建议纯随机"）。

**我们的选人规则（照抄即可实现）**：
```
function pickRole(candidates, trigger, state) {
  // ① 固定搭子优先（约束 ⑤：教学关系需要连续性）
  const buddy = candidates.find(r => r.role === 'buddy')
  //    搭子的定义：本讲固定那一位，且他记得学生的卡点
  //    命中条件：他还没出场过
  if (buddy && !state.spokenCastIds.includes(buddy.id)) return buddy

  // ② 否则按"认知风格 × 当前错法"匹配（约束 ⑤ 的核心）
  //    匹配表写在 cast 里（§10.2），是显式数据，不是算分
  const byStyle = candidates.filter(r => r.styles.includes(trigger.style))
  if (byStyle.length > 0) return byStyle[0]      // 列表顺序 = 优先级（在 cast 里显式排）

  // ③ 兜底：客串位（每讲 1 位）
  const guest = candidates.find(r => r.role === 'guest')
  return guest ?? null
}
```

🔴 **`trigger.style` 从哪来**：**不是模型判的，是错法自己带的**。见 §10.3 的 `wrongStepLibrary`——**每条错法在配置里就标好了它对应哪种认知风格**（"漏掉前提" → 精确型该说；"举不出例子" → 爱举反例的该说）。
**依据**：**约束 ⑤ 逐字**：*"'玩法多样'的来源应是**认知风格差异（直觉型／精确型／爱钻牛角尖／爱举反例）× 知识点错法**"*。

### 9.5 密集模式（可选项，约束 ⑥ 的落地）

**约束 ⑥（逐字）**：🔴 **风险：多角色稀释教学密度** → **默认稀疏，把"密集模式"做成可选项**。

**落地方式**：一个开关 ＋ 三个参数
```yaml
policy:
  density: sparse        # sparse（默认）| dense
  lessonQuota: 4         # sparse 下生效
  denseQuota: 12         # dense 下生效（约每 2 回合一次）
  denseMaxPerTurn: 1     # 🔴 即使 dense，每回合也至多 1 个同学发言（依据：约束 ⑥）
```
🔴 **`denseMaxPerTurn: 1` 是硬约束，不可调** —— **依据（prior art 的产品级证据）**：Character.AI 用户的头号抱怨就是"角色互相盖过对方、把用户晾在一边"（§4.4，第三方实测归纳逐字：`Characters talk over each other and ignore you — Auto-reply is on`）。
→ **产品级教训：多角色同台的失败模式不是"话太少"，是"话太多"。**

**逃生舱（用户手点）**：**借 SillyTavern 的 `MANUAL` ＋ `force_chid`**（`group-chats.js:1004`、`:1029–1031`）——**学生／用户可随时点某位同学发言**，**不受额度门限制**（但计入额度，防滥用）。
**落地**：一个引擎工具（如 `classroom_call_peer`），参数是 `castId`。

### 9.6 「确定性反应」零成本清单（约束 ④ 的"舞台存在感"）

**这些全部零模型成本，由引擎／前端确定性触发**：

| 反应 | 触发条件（确定性） | 成本 |
|---|---|---|
| 同学立绘**变亮**（进入"在场"） | 讲次变化（`current_lesson` 变） | 0 |
| 同学立绘**变暗**（退到后景） | 本回合无该同学发言 | 0 |
| **当前说话者高亮**（其余变暗） | 本回合裁决出 `castId` | 0 |
| 名牌**闪一下** | 该同学被裁决命中（**生成台词之前**） | 0 |
| 同学**换姿势**（"他在翻自己那份校样"） | 错法命中的知识点变化 | 0 |
| 名牌上**一个小标记**（"他上次在这里错过"） | 该同学的错法关联 KP = 当前 KP | 0 |
| **发言队列预告**（"阿澈要说话了"） | 裁决命中后、生成之前 | 0 |

🔴 **最后一条的依据（prior art）**：SillyTavern 的 `show_group_chat_queue` 维护一个 `Map<avatar, 队列号>`，**在生成之前就知道"接下来谁要说"**（`group-chats.js:1034–1040`）。→ **我们可以在台词生成之前就在 UI 上预告**，**显著降低"突然冒出第三个声音"的突兀感**。

### 9.7 诚实边界

- ⚠️ **"一讲 ≈ 20–30 回合"是推断，无实测**（§9.2）。
- ⚠️ **`minTurnGap = 5` 是推断**（§9.3）。
- ⚠️ **`lessonQuota = 4` 是区间中值，不是实测最优**（§9.2）。
- ❌ **未做任何成本实测**（§13.4 会给成本估算的**方法**，不是数字）。

## §10 【必答 6】`cast` / `cue` 在教室配置文件里长什么样

### 10.3 `cue` 段（出场条件，**另立字段**）

```yaml
# ══════════════════════════════════════════════════════════════════════════════
# cue · 出场提示（剧场术语）
# 🔴 纪律（约束 ⑦）：出场条件**另立字段**，不复用 phase.advance_on
#    （phase.advance_on 已裁定不做；相位推进由模型调 classroom_set_phase 宣布）
# 🔴 纪律（用户 2026-09-24 口径）：这里写的是**备料单**（哪些知识点／哪些错法／
#    哪些角色**可以**出场），**不是脚本**；"何时出场、谁出场、说什么、怎么接"
#    由现场状态决定 → 所以本段**只声明"可用素材与条件"，不写"第几回合谁说什么"**
# ══════════════════════════════════════════════════════════════════════════════

cue:

  # ── 僵局判据（§8；全部是初值，须用 §8.5 的方法校准）────────────────────────
  stall:
    nTurns: 3              # 连续 N 回合无新知识点；依据：_anchor.md「提问不是每轮义务」
                           #   → N 不能取 1/2（会误判正常讲解）；<5（须早于 n_turns:5 的自检节奏）
    shortWindow: 5         # 取最近 5 条学生消息算长度中位数（与 anchor.check 的 5 回合同频）
    shortRatio: 0.4        # 本回合长度 < 中位数 × 0.4 → 计"变短"
    shortFloor: 8          # 中位数 < 8 字时不判"变短"（防对习惯短答的学生误判）
    dontKnowPatterns:
      high:                # 高置信：命中 1 次即计僵局
        - "不知道"
        - "不会"
        - "不懂"
        - "想不出来"
        - "没思路"
        - "答不上来"
        - "你直接说吧"
        - "直接告诉我"
        - "给个提示"
        - "跳过"
        - "下一题"
      mid:                 # 中置信：必须与 nTurns 或 shortRatio 之一共现才计
        - "大概"
        - "可能是"
        - "我不确定"
        - "也许"
    dontKnowExempt:        # 🔴 误伤白名单（"不会影响"是正确技术表述，不是"不会"）
      - "不会影响"
      - "不会导致"
      - "不会出"
      - "不会发生"
      - "不会出现"
    # 🔴 只扫学生消息（source.kind === 'user'）
    #    依据：AutoGen TextMentionTermination 的 sources 过滤（_terminations.py:139-142）
    #    —— 否则同学自己说一句"我也不知道"就把僵局触发了
    sources: [user]

  # ── 触发条件（三条路，命中任一即出场；§6.4 门 4）────────────────────────────
  triggers:

    # 路 A · 僵局（最高优先）
    - id: on-stall
      when: stall                 # 引用上面 stall 段的判据
      priority: 1

    # 路 B · 错法命中（🔴 约束 ③：错法必须来自真实数据）
    - id: on-wrong-step
      when: student-hit-known-wrong-step
      # 判据：本回合学生消息命中了错法库里某条的"触发形态"
      # 错法来源（二选一，都是教室已有文件）：
      sources:
        - runtime/mistake_log.md          # 学生自己踩过的错（"错在哪一步"字段）
        - runtime/wrong_step_library.md   # 知识点判据的反面（🔴 新文件，见 §7.2）
      priority: 2

    # 路 C · 老师邀请（工具调用，不是自由文本）
    - id: on-teacher-invite
      when: tool-call:classroom_invite_peer
      priority: 3

  # ── 错法库的绑定（🔴 约束 ①③ 的核心：确定性绑定，不许模型即兴）──────────────
  wrongStepLibrary:
    file: runtime/wrong_step_library.md
    # 🔴 每条错法 = 一个 id ＋ 它绑的知识点 ＋ 它对应的认知风格
    #    风格字段的作用：让 §9.4 的"认知风格 × 错法"匹配是**查表**，不是算分
    format: |
      | id | kpId | 错法（判据的反面） | style | 状态 |
      |---|---|---|---|---|
      | W-KP-3.1-01 | KP-3.1 | 把周转时间与响应时间当成同一个东西 | precise | active |
      | W-KP-3.2-01 | KP-3.2 | 举不出"长任务堵住短任务"的例子 | counterexample | active |
      | W-KP-3.3-01 | KP-3.3 | 说"SJF 现实中就是最优的"（漏掉"前提是知道未来"） | precise | active |
    statusValues: [active, retired]   # 🔴 retired = 学生已改对，不再演示（§7.2 第 3 条）
```

🔴 **`cue` 段的三条设计纪律（逐条对应约束）**：

| 纪律 | 依据 |
|---|---|
| 🔴 **`triggers` 只声明"可用条件"，不写"第几回合谁说什么"** | **用户 2026-09-24 原话**：*"出场编排不能直接套用，需要有定制化方面的考量"*；踩坑原文：*"把所有东西给定死，然后角色扮演和苏格拉底式教学法就都成了一种形式和摆设"* |

## §11 【必答 7】UI 侧：谁在说话怎么让用户一眼看出

> **任务书要求**：名牌／配色／立绘高亮；与"学生答题时老师立绘退到后景"这条已定设计怎么配合。
> 🔴 **与 `研究_8_Live2D驱动与集成_2026-09-24.md` 的分工（避免重复劳动）**：
> - **研究 8 已定**：立绘**不放进消息节点，放右栏 tab**（§2.3 逐字：*"立绘是「常驻的、跨消息持续的状态」，不是「消息内的一次性内容」"*）；**相位→立绘映射表**（§5.1）；**`answer` 相位立绘要「退让」**（§5.1 逐字：*"`answer` 相位把所有状态预设的 intensity 乘 0.3，并禁用事件层动作"*）。
> - **本节只做研究 8 没覆盖的**：**"多个角色同台"时，右栏怎么摆、名牌怎么给、说话者怎么高亮、与"退让"怎么叠**。

### 11.1 🔴 先定一条不可回避的约束（来自 P3，不是我们的选择）

**P3 逐字结论**（`取证_P3_客户端槽位与派发语义_2026-09-24.md` §2.5）：
> **客户端把一条消息显示成"另一个人说的"，靠的是 `kind`（节点类型）+ `source`（来源），而不是任何"说话人身份字段"。**

**且 `AssistantNodeView` 不渲染任何说话人标识**（P3 证据 B）。

🔴 **由此推出的三条硬事实**：

| 事实 | 后果 |
|---|---|
| **老师的台词走 `assistant`** | **官方渲染成"无名的助手气泡"**——**不显示"小鞠知花"这个名字** |
| **同学的台词走 `user/message` ＋ 自有 `source.kind`** | 客户端渲染成 **`kind: "context"`** 的注入行，**带 `label = <kind>`**（P3 证据 D 的 `default` 分支逐字：`role: "inject", label: kind`） |
| 🔴 **两者形态不对称** | **老师是气泡、同学是注入行** —— **视觉权重天然不同** |

→ 🔴 **结论：在"零改客户端"的前提下，"谁在说话"只能靠两条线索表达**：
1. **消息流里的 `label`**（同学那条会带一个标签；老师那条没有名字）；
2. **右栏面板的立绘状态**（谁在场、谁在说话、谁退到后景）。

**⚠️ 这两条都不足以做到"一眼看出"** → **"名牌"这件事在当前约束下有一个真实缺口**，见 §11.5。

### 11.2 右栏的形态：**一个 tab 体，里面横向排三个位置**

**扩展点依据（P3 §7b 逐字）**：
```

kind: "keyed",
...
replaceRisk = "none"（纯增，不覆盖任何官方件）
```

**布局（照抄即可实现）**：
```
┌──────────────────────────────────┐
│  教室 · 操作系统      第 3 讲     │  ← tab 标题（会话级）
├──────────────────────────────────┤

│    [程霁]      [小鞠]      [阿澈] │  ← 三个"位置"（stage slots）
│     dim         FOCUS       dim   │     FOCUS = 当前说话者
│     0.45        1.0         0.45  │     dim  = 在场但不说话
```

|---|---|
| **横排三个位置，不是堆叠** | 立绘是"在场"的表达（约束 ④ 的舞台存在感）；横排 = 学生一眼看到"今天有谁在" |
| **说话者 `FOCUS`／其余 `dim`** | Monogatari `Dialog.ts:215`、`:418`：**先全清 `focus`，再给当前说话者加** —— 引擎只切状态，样式归我们（研究 §4.2） |

| **"他上次在这里漏掉了一步"这行** | 零成本（§9.6）：**由"该同学的错法关联 KP = 当前 KP"确定性触发** |
| **"本讲出场：2 / 4"可视** | **把约束 ④⑥ 变成学生可见的信息** → 学生知道"同学不会刷屏"，**降低对插话的抵触** |
| **tab 标题带讲次** | 讲次是 `progress.md` 的 `current_lesson`（机器可读行，引擎已读） |

### 11.3 🔴 「退让」与「多角色」怎么叠：**两级强度，不是一级**

**研究 8 已定的"退让"是单角色形态**（`answer` 相位所有预设 intensity × 0.3）。
**多角色下要加一层**——**"谁在说话"本身就是一个强度维度**：

```
最终 intensity = 相位基线（研究 8 §5.1 的表）
               × 说话者系数（FOCUS = 1.0 / dim = 0.45 / absent = 0）
               × 相位退让系数（answer = 0.3，其余 = 1.0）
```

**逐格验算（举三个例子，确认叠法不会出问题）**：

| 场景 | 相位基线 | 说话者系数 | 退让系数 | 最终 | 读起来对不对 |
|---|---|---|---|---|---|
| 老师提问，程霁在场不说话 | `probe` = 0.5–0.8 | 0.45 | 1.0 | **0.22–0.36** | ✅ 对：老师在问，程霁在场但安静 |
| **老师提问，程霁正在说话** | `probe` = 0.5–0.8 | 1.0 | 1.0 | **0.5–0.8** | ✅ 对：说话的人最显眼 |
| **学生作答（`answer`），老师在场** | `answer` = `listening` | 0.45 | 0.3 | **0.135 × 基线** | ✅ 对：**学生答题时所有人都退到很后** |

🔴 **最后一行是关键**：**"学生答题时老师退到后景"这条已定设计，在多角色下自然扩展为"所有人都退到后景"** —— **不需要新规则，只需要把说话者系数乘进去**。
**依据**：研究 8 §5.1 逐字：*"教学场景的成功标准是「学生学会了」→ 学生思考/作答时，立绘抢注意力是负面效果"* —— **这个理由对同学同样成立**。

### 11.4 「当前说话者」这个状态由谁给（🔴 引擎侧的唯一新增输出）

**P3 已证：客户端没有说话人身份字段** → **"谁在说话"必须由引擎显式产出**。

**落点**：一个**会话级投影／状态**，由引擎在裁决命中时写入、在回合结束时清空。
**为什么用"投影"而不是"消息字段"**：**"谁在说话"是瞬时状态，不是消息属性**（研究 8 §2.3 逐字：*"立绘是「常驻的、跨消息持续的状态」"*——同理，"当前说话者"也是状态而非消息）。

⚠️ **诚实边界**：**具体用哪个投影键、`sessionProjections.register` 的签名，本轮未取证**（S3 §1.5 已证 `ctx.get('sessionProjections')` 可用，但**未读其 register 签名**）。**标【待确认】**。
**已试检索词**：`grep -rn "sessionProjections.register" tmp/dsh-installed/*/lib/*.js`（S3 已给 `dsh-agent-loop/lib/index.js:1300` 的 `turnBoundaryProjectionDefinition` 作为**形状参考**：`{ key, stateVersion, stateSchema, init, apply, viewSchema }`）。

### 11.5 🔴 诚实缺口：**"名牌"这件事在当前约束下有真实缺口**

**把三条事实摆在一起**：

| # | 事实 | 出处 |
|---|---|---|
| 1 | `AssistantNodeView` **不渲染任何说话人标识**（老师的气泡没有名字） | P3 证据 B（`client.js:3053` 起） |
| 2 | 同学的台词渲染成 `context` 注入行，**`label = <kind>`**（能显示 kind 名，**但 kind 名不是角色名**） | P3 证据 D |
| 3 | `conversation.chat.node` 能自画名牌，**但 `replaceRisk = "shadows-shipped-ui"`（会盖掉官方工具卡片）** | P3 §2.4／§2.3 |

🔴 **结论：在"零改客户端 ＋ 不用 chat.node"的前提下，"消息流里的角色名牌"做不到。**

**三条出路（**列选项，不给结论**——这是设计判断，标【待确认】**）：

| 出路 | 做法 | 代价 | 依据 |
|---|---|---|---|
| **A · 接受缺口** | 名牌**只在右栏面板里**；消息流里靠 `label`（kind 名）＋ 立绘状态判断 | 学生要"看右栏"才知道谁在说；消息流本身不自解释 | P3「路 A」 |
| **B · 把角色名写进台词文本** | 同学的台词**以 `程霁：` 开头**（就是 prior art 的 `名字: 台词`） | ✅ **零改动**、✅ **与三个 prior art 一致**、✅ **模型也分得清**（这才是 prior art 做这件事的真正原因） | SillyTavern `openai.js:594–611`；AutoGen `_selector_group_chat.py:216–228`；generative_agents `converse.py:148` |
| **C · 用 `chat.node` 自画** | 复用某个 kind 自画带名牌的气泡 | 🔴 **会盖掉官方工具调用卡片**（项目已裁定第一版不用） | P3 §2.4；AGENTS.md 工具链条目 |

🔴 **本轮的倾向（写下来供裁定，不是定论）**：**A ＋ B 同时做**。
**理由**：**B 是三个独立 prior art 的共同做法**（§3.1 的收敛表），**成本为零，且它解决的不只是 UI 问题——它同时解决"模型分得清谁在说"这个更根本的问题**（§5.1 已证官方没有说话人字段）。
⚠️ **但 B 有一个副作用必须写下来**：**角色名进了台词文本，就等于进了模型的上下文**（§5.2 边界 A：注入的消息既是呈现也是上下文）→ **同学名字会持续占上下文**。**这是 B 的代价，需要算进 §13.4 的成本。**

### 11.6 与"学生答题时老师退到后景"的配合（**汇总**）

**已定设计（研究 8 §5.1 逐字）**：
> **`answer` 相位立绘要「退让」**——学生作答时，立绘的动作应该**减弱**而不是增强。
> **实现**：`answer` 相位把所有状态预设的 intensity 乘 0.3，并禁用事件层动作。

**多角色下的完整规则（照抄即可实现）**：
```
进入 answer 相位（引擎收到 classroom_set_phase('answer')）：
  ① 所有角色的 intensity ×= 0.3（研究 8 的既有规则，不变）
  ② 禁用事件层动作（同上，不变）
  ③ 🔴 新增：清除"当前说话者"状态 → 所有人回到 dim（不是 FOCUS）
     —— 依据：学生作答时"没人正在说话"，此时不该有谁被高亮
  ④ 🔴 新增：右栏名牌区显示"（学生在作答）"而不是任何角色名

离开 answer 相位：
  ① intensity 恢复正常
  ② 恢复正常事件层
  ③ "当前说话者"状态由下一次裁决重新给出
```

🔴 **第 ③ 条是多角色新增的唯一规则**，**依据**：**"当前说话者"是引擎产出的显式状态（§11.4）**，**而 `answer` 相位下没有任何角色在说话** → **状态应为空**。
**若不做这一条会怎样**：学生会看到"我在答题，但程霁的立绘还是亮的"——**与"退让"的设计意图直接冲突**。

## §13 【必答 9】反证与风险

> **本节纪律**：🔴 **最硬的两条排在最前**（主代理收尾简报要求 ⑥）。**每条给依据，不给安慰。**

### 13.1 🔴 最硬的一条：**「作为 NPC 一样插入其中」在当前宿主下只能做到「回合级」，做不到「句级」**

**用户原话（2026-09-23 第 ① 条）**：
> 「不太像是子代理或者直接给主 AI 注入，而是**继承了主代理的上下文**，但是合适的时候要**作为 NPC 一样插入其中**」

**反证（源码级）**：
- **注入点只有 `agent/pre-step`**（S3 §2.1 已证：payload `{ agent, messages, turn, step, signal }`，**每个 step 调一次**）；
- 而 `pre-step` 是**回合开始前**的钩子（S3 §2.2：`turn/start` → `step/start` → … → `step/end` → `turn/end`）；
- 🔴 **`step` 只在"一个 turn 内 LLM 多次往返（工具调用）"时增加，不是"老师说到第几句"**（S3 §3.2 实测：纯对话 prompt 下 **每 turn 只有 1 个 step**）。

**结论**：
> **同学只能在"下一个回合的开头"出现，不能在"老师这一句说完之后"出现。**
> 用户想象中的"插入"（在老师话说到一半时插一句）**在当前宿主下做不到**——**除非改宿主或走 `chat.node` 自画（项目已裁定不用）**。

**影响评估**：
- ⚠️ **教学上仍然可用**：学生说完 → 下一个回合同学接话，**这已经能把"你不会"变成"我们俩都不会"**（约束 ② 的目标）；
- ⚠️ **但"同学在老师追问到第三句时插话"这个体验做不到**——**这是本节必须让用户知道的第一条硬限制**。

### 13.2 🔴 第二硬的一条：**错法绑定的数据源现在几乎是空的，机制会"跑起来但没内容"**

**反证（教室文件的现状，逐字）**：

| 数据源 | 现状 | 出处 |
|---|---|---|
| `runtime/mistake_log.md` | **表体只有一行占位**：`\| （待第 1 讲后填写） \| \| \| \| \| \|` | 文件逐字 |
| `runtime/learner_profile.md` 的「卡点模式」 | **只有一行占位**：`- （待观察）` | 文件逐字 |
| `runtime/wrong_step_library.md` | 🔴 **文件不存在** | `ls runtime/` 实测（8 个文件，无此文件） |
| `knowledge_points.md` 的状态 | **全部是 `[ ]`**（第 1 讲至第 12 讲，无一例外） | 文件逐字（`:16` 起） |

🔴 **含义**：
- **约束 ③（错法来自真实数据）在"第 1 讲之前"是无数据可用的** → **同学第一次出场时，`wrongStepId` 只能是"判据的反面"（推导值），不是"学生踩过的错"（实测值）**；
- ⚠️ **这是一个"机制先于内容"的必然阶段**，**不是设计缺陷**；**但必须写下来，否则会被误认为"机制做好了就有效果"**。

**修补顺序（建议，写进 §12 的工期）**：
1. **先跑一讲没有同学的真实课堂**（用现有 P1 骨架），**让错题本与卡点模式有真实数据**；
2. **再开同学**——**第一讲的同学只用"判据的反面"（推导值）**，从第二讲起才可能用"学生踩过的错"。

### 13.3 串味（同一模型演多个角色的必然风险）

**这是本节第三硬的一条**，且**有独立的产品级佐证**：

**证据（逐字）** — Character.AI 第三方实测（§4.4）：
> `Characters blend into one voice — Too many characters, or definitions that are too similar`
> `Keep the cast small. The more characters, the less each one gets to say, and the more the model has to keep apart.`

**机制层面的原因（🔴 必须说清，因为它是结构性的，不是调参能解决的）**：
- 我们的形态是**同一个模型、同一个会话上下文**在演老师与同学（§5.2 边界 A：注入的消息**既是呈现也是上下文**）；
- 而 **prior art 里"多角色不串"的方案，全靠"每个角色一次独立生成"**（SillyTavern `setCharacterId`→`Generate`，§1.1；AutoGen `GroupChatRequestPublish`，§2.2）；
- 🔴 **我们做不到这一点**：注入通道**没有"换角色再生成"这一步**——同学台词由**引擎模板 ＋ 一次语言化调用**产出（§7.4），而**老师台词仍由主 agent 生成**。
→ **两者共用同一份上下文，串味的风险天然高于 prior art。**

**缓解措施（三条，逐条给依据）**：
| 措施 | 依据 |
|---|---|
| **同学台词短**（上限 120 字） | 约束 ⑥；Character.AI 产品教训 |
| **角色少**（MVP 只 1 位搭子） | Character.AI 逐字：*"Two or three characters with you usually make a better scene than eight"* |
| **语言化用独立的调用，不共用主 agent 的生成** | §7.4 的"只准改写不准增删"约束需要一个**独立、短、约束强**的调用 |

⚠️ **诚实声明**：**串味是否真的发生、程度如何，本轮未实测**（红线禁止起会话）。**标【未实测】。**

### 13.4 成本与延迟（**给方法，不编数字**）

**延迟的三个来源（逐条给依据）**：

| 来源 | 量级 | 依据 |
|---|---|---|
| **同学台词的语言化调用** | **+1 次 LLM 往返**（仅在场次：每讲 3–5 次） | §7.4 的独立调用 |
| **注入本身** | **0**（引擎本地拼接） | §5.4.2：对比子代理方案的"每句多一次完整 agent 往返" |
| **立绘渲染** | **0 模型成本**（纯前端） | §9.1 的 L2／L3 |

🔴 **可给的结论（不编数字）**：
> **同学出场的额外成本 = 每讲 3–5 次 LLM 往返**（不是每回合）。
> **依据**：额度门（§9.2）是**绝对次数**，不是频率 → **成本与"一讲多少回合"无关，与"出场几次"线性相关**。
> **对比**：若用 `judge: model`（§6.2 形态 B）**每回合**都调一次裁决，**成本是每回合 +1**——**这就是 §6.2 选 A 为默认的核心经济理由。**

**上下文成本（🔴 容易被忽略的一项）**：
- **同学台词一旦注入就永久占上下文**（§5.2 边界 A）；
- **且角色名进了台词文本**（§11.5 出路 B 的代价）；
- → **每讲 3–5 条、每条 ≤120 字 ≈ 每讲 400–600 字** → **量级可接受**，但**它是"永久增长"的**（不会随回合被挤掉，除非 compaction 介入）。

⚠️ **未实测项**：**语言化调用的实际 token 消耗与延迟**（需起真实会话）。**标【未实测】。**

### 13.5 复杂度风险（**工程层面的三条**）

| 风险 | 具体是什么 | 依据 |
|---|---|---|
| 🔴 **新增"读 KP 状态"的能力** | `roundsSinceProgress`（§8.2 规则 1）需要**解析 `knowledge_points.md` 的三档状态并做快照比对**——**引擎目前完全没有这个能力**（`kp.current` 只是注入，不是解析） | `classroom.yaml` 的 `kp.current` 块定义 |
| 🔴 **`cast`/`cue` 不进现有校验器** | 顶层是白名单取值（§10.1）→ **写错了不报错，静默失效** —— 与项目既有风格（"不静默"）冲突 | `manifest.mjs:586` 逐字 |
| 🔴 **"当前说话者"需要一个新的投影键** | §11.4 的落点**未取证**（`sessionProjections.register` 签名未读） | 已试检索词见 §11.7 |

### 13.6 一条"设计层面"的反证：**用户第 ④ 条与教室既有设计有重叠**

**§0.4 已识别**：`komari.md` 逐字已有"她会**先自己写一遍错的**，然后问'我这里哪一步不对？'"
→ **用户第 ④ 条（先让 AI 同学展示错误方法）在机制上是"归属迁移"**。

🔴 **由此产生的一条真实风险**：
> **如果老师与同学都能展示错法，学生可能分不清"现在是谁在写错的"。**
> **依据**：`_anchor.md`「教学取向」逐字：*"每个问题要有明确对象和判断目标"* —— **"谁在展示错法"就是"问题的对象"**。

**缓解措施（建议，写进 `cue` 的纪律）**：
- **同一回合内，只有一个人展示错法**；
- **且同一条错法（同一个 `wrongStepId`）不在同一讲里被演示两次**（§7.2 第 2 条的可去重性正好支持这一点）。
