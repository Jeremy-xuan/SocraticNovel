## 〇 · 一句话结论

**舞台的可读性不是短板，信息结构才是。** 程序化实测：12 张原型截图**没有一行白字压亮背景**
（文字处局部背景对比度 p50 全在 **9.6–18.3:1**，最低 2.0 的个别像素来自描边本身）；
真正会让它被打回的是五件**结构性**的事：**① 板书位与正文带互斥；② 选择肢根本没写；③ 元信息缩到 10.8px；
④ 「谁在说」在插件里没有落成界面元素；⑤ 正文带只放得下约 100 个中文字**。这五条都不是美术问题，是**裁定与工程量**问题——
所以先出样稿对齐，比继续往里堆代码便宜。

## 一 · 审核怎么做（可复算）

三个程序化通道，全部落在 `code/tools/`：

| 通道 | 脚本 | 答什么问题 |
|---|---|---|
| 对比度分布 | `audit_stage_contrast.py` | 白字压在什么背景上？每一行的对比度是多少？ |
| 几何交叠 | `audit_stage_geometry.py` | 立绘/板位与正文带在**同一块地方**吗？ |
| 令牌比值 | 见 §三（一次性算式） | 令牌之间的相对亮度差，在屏上还分得出来吗？ |

复算命令（工作目录 = `开源线/DSH定制/code/tools`）：

```bash
python3 audit_stage_contrast.py "../prototypes/stage3/shots" --json /tmp/stage_contrast.json
python3 audit_stage_geometry.py "../prototypes/stage3"
```

### 1.0 借了 `huashu-design` 技能的哪几条

按技能口径，**用户已有明确设计参考**（STAGE-3 的 B 骨架 ＋ C 材质 ＋ 一整张从真实截图量出来的令牌表）
→ 走「核心哲学 #1 从 existing context 出发」主干，**不进「设计方向顾问 Fallback」**（那三套逻辑是给
「没有参考、要打破惯性」的场景用的）。本次实际借用的：

1. **事实验证先于假设**（技能核心原则 #0）——本项目对应动作是**先读真实素材与既有令牌**，
   任何数值不靠记忆、不靠推测。本审核的所有数字都从**原型截图**量出来，不从代码注释抄。
2. **诚实 placeholder 好过拙劣的真实尝试**——样稿里的立绘与场景是打样占位，**画面内已标注**；
   板书位的材质、木框／书脊这类正式资产**不假装已经做完**。
3. **「一个细节做到 120%，其他做到 80%」**——样稿把 120% 投在**文字**上（描边、旧行压暗、行距），
   因为真实界面里文字是唯一的主角。
4. **反 AI slop 清单**——样稿主动规避：紫色渐变、emoji 当图标、圆角卡片＋左彩色 border accent、
   装饰性投影、Inter／系统字当 display。**层级只靠 字号 · 字距 · 字色阶梯 · 字面，全画布 `font-weight:400`**
   （已用断言机核，见 §六）。
5. **固定尺寸内容自己实现缩放**——1920×1080 画布由 JS 整体 `scale` 并 letterbox；**画布内纵向尺寸一律 px**。
6. **交付前自己跑一遍真实点击**——样稿的四组断言里 D 组就是真实点击（点在场者／点选择肢／输入送出）。

**明确不借的**：技能那套「三套逻辑并行出 3 版真实视觉」——**本次一版就够**，
因为三个方向上一轮（STAGE-3）已经摆过、用户也已裁决走「B 讲台 ＋ C 材質」；
再来三版等于把已定的事重做一遍。

### 1.1 两次踩坑（写在这里，防下一个会话重犯）

1. **第一版把「整行非白像素的中位亮度」当背景** —— 白字周围那一圈**深色描边**也是非白像素、且紧贴字形，
   于是系统性把背景压暗，**12 张图全被算成 9~18:1，一张目视几乎读不出的白字压奶白纸也判成 10.6**。
   → 症状是「**全绿**」，比报红更危险。（这也是这个项目 AGENTS.md 里那条「验收不得关掉被测样式」的同族错误。）
2. **第二版改成「邻域最亮值」** —— 邻域里取到的正是白字自己，对比度恒等于 `1.00`，**12 张图全判 fail**。
   → 症状是「**全红**」。两次都源于同一个错误：**没有把字形自己（含描边、含邻域）排除干净**。

定稿做法：先把**文字像素 ＋ 6px halo** 从图里挖掉 → 按 32px 分块取剩余像素的 **25 分位**亮度 →
每块再从周围 5×5 块取有效块中位数 → 放回原尺寸。**用分位数而不是最大值**，避免偶发高光把整块判成亮背景。

## 三 · 令牌之间的落差（真正的问题在这里）

用 WCAG 相对亮度算一遍令牌之间的关系（`contrast = (Lhi+0.05)/(Llo+0.05)`）：

| 关系 | 比值 | 意味着 |
|---|---|---|
| 当前行 `#ffffff` vs 旧行 `#cccccc` | **1.61** | 🔴 **相邻两行几乎分不出谁新谁旧** |
| 当前行 vs 旁白 `#d8d8d8` | **1.43** | 旁白与台词的差别更小 |
| 旧行 `#cccccc` vs 画布底 `#05070a` | 12.56 | 单看旧行本身完全够读 |
| 墨 `#1b1b1b` vs 奶白纸 `#F2EADA` | 14.40 | 短册/板书头条这条材质对比成立 |
| 板身字 `#eaeaea` vs 板底 ≈`#0a1a22` | 14.75 | 板位可读性没有问题 |
| 发丝线 `#3F787B` vs 底 | 4.02 | 未选中条的分隔线看得见 |
| 青 `#37DBF7` vs 压暗层 | 11.58 | 指示器/选中边看得见 |

🔴 **这是本次审核最值得看的一个数**：真实界面那条「**字号完全相同、只差亮度**」的规则，
落到 `#ffffff`/`#cccccc` 这对色上只有 **1.61:1**。色差本身**不足以承担**「谁是当前行」，
实际起作用的是**末行末尾那枚青色梯形指示器**（33×30px）。
→ **行动**：指示器是**主信号**不是装饰，不许省、不许挪到固定角落、不许缩小；
其余四行的「旧行色」只是氛围层。
→ **不建议动这两个色值**：它们是量出来的（依据图 U1），要改得先有新素材。我的建议是**把这条落差写进设计说明**，
免得下一轮有人「顺手把旧行调暗一点让它更明显」——那会偏离真实界面。

## 四 · 四条会让人打回的问题（按严重度）

### 🔴 P0-1 · 板书位与正文带**互斥**，而且插件里根本没有板书位

- **事实**：`LAYOUT` 给了「立绘列 340×520px，落在右侧 19.8% 留白」，**没有给板书位**；
  `lib/client.js` 里 `grep` 不到任何板书/投影组件——README §1 逐字写着
  *「不引 mermaid（板书图本轮不做，那由 classroom-ui 负责）」*。
- **后果**：教室最重要的动作之一（**板书/投影**）在舞台上**无处安放**；
  且右侧那条 19.8% 的留白同时被立绘列占着。
- **建议**：板书位**与立绘列互斥、随屏切换**（板书屏藏立绘、正文带收窄到 `60%`、板子成为焦点；
  其余屏藏板子、恢复 80.2%）。样稿按这个做。

### 🔴 P0-2 · 选择肢**完全没实现**

- **事实**：README §10 待确认表第 5 条逐字：「选择肢（六条固定项）本轮未做 … 只记录事实
  （`inputActions` 有 `setDraft`/`insertText`），**不实现 UI**」，理由是逐字文案要从 STAGE-3 §5.2 取，
  *「编一份等于造内容」*。
- **这不是设计问题，是缺件**：而现在**连设计都没有**——原型里那六条是静态排布，
  没有 hover/focus/keyboard/选中/回退任何一条状态。
- **建议**：样稿给出六条的**完整状态机**（未选中/hover/当前/选定后回到对话），
  文案**逐字取 STAGE-3 原型里那六条**（那是已落盘的既有内容，不是我编的）。

### 🔴 P0-3 · 元信息条缩到 **10.8px**

- **事实**：`CANVAS_TYPE.meta = 24`（画布 px）；舞台画布会被整体缩到 **0.4–0.5 倍**（README §10 第 4 条自述），
  → 屏上 **≈ 10.8px**。人在 **1 米**距离看 10.8px 字 ≈ **0.2° 视角**（舒适阈 0.3–0.4°）。
- **用户已经在 09-28 提出过这一条**（进度汇报「已知问题」第 3 条），**目前未改**。
- **建议**：元信息字号**跟随实际 scale 补偿**（scale < 0.6 时把画布内字号提到 32px ⇒ 屏上 ≈14px）。
  样稿按这个做，并把补偿规则写在画面上。

### 🔴 P0-4 · 「谁在说」在**插件**里没有落成界面元素

- **事实**：`nameTagPlan(present)` 存在，但 `present` **恒为空**（README §5：多角色同台未实现，
  教室目前只有 1 张角色卡）→ 实际渲染成**没有姓名短册**；`LAYOUT` 里也没有在场者栏。
- **后果**：一个回合里多个人说话时，读者只能靠**正文里的「某某：」**自己认人。
  原型里 B 版做的「姓名牌＋在场者栏＋立绘亮度三处冗余」**没有进插件**。
- **建议**：把「在场者栏 ＋ 姓名短册」做进舞台（哪怕 `present` 只有 1 人时也能显示当前说话者）；
  它同时是**多角色同台的骨架**，不做它，「同台」永远只能停在原型。

### 🔴 P0-5 · 正文带**只放得下约 100 个中文字**，而模型的讲课消息通常几百字

- **实测**（样稿程序化验收里量出来的）：单行 `81.8px` ＋ 段距 `82px` ⇒ `bandMaxHeightPx = 700`
  **只放得下 4 条**，每行约 **25 个中文字** ⇒ **一屏总量 ≈ 100 字**。
- **后果**：README §3.3 那套「`flex-end` ＋ `overflow:hidden`，被裁的是顶部旧文」的设法规避不了——
  **真实消息必然超**。而裁切线**落在字形中间**（不是行边界），实测截图里表现为**半行残字**，
  加上顶部渐隐，读起来像渲染 bug。
- **另有一处实现坑**：那个「顶部渐隐」遮罩如果**常显**，会变成一块**清晰可见的暗矩形压在首行上**
  （本次样稿第一版就踩了；详见 §六）。修复＝**只在真的溢出时才出现**。
- **建议（两条，我倾向第二条）**：
  - **(a) 把裁切线对齐到整行边界**：`band` 的高度取「行高的整数倍」而不是 700 这个自由值，裁切就不再切字。
  - **(b) 一屏正文做成「分页推进」**——真实界面本来就是「一屏几行、按键往下推」，
    **不是把一条消息一次铺满**。这条同时修掉「100 字上限」和「半行残字」两个问题，
    而且**更贴真实界面**。代价是要引入「推进」这个交互与状态（目前完全没有）。

## 五 · 明确**不要动**的三件（防下一轮返工）

1. **文字带的几何与字号**：左 17.2%／右 80.2%／顶 14.9%／47px／行距 1.74／8 向 2px 描边。
   实测对比度全绿，且这些数是**从真实截图量出来的**。
2. **「对话框不存在」这条骨架**：不写框、不写底、不写压暗层。
3. **层级只靠 字号·字距·字色阶梯·字面**：全原型 `font-weight:400`，**不许靠加粗**。

**允许动的**：**板位、选择肢、元信息补偿、姓名短册/在场者栏**——这四件都是**新增**，不是改已有的数。

### 6.1 样稿自己的两个坑（写下来防重犯）

1. **顶部渐隐遮罩常显 ＝ 一块可见暗矩形压在首行上**。它是为「正文溢出、从顶部裁旧文」准备的软边，
   不是装饰层 → 必须**只在真的溢出时出现**。
   ⚠️ **判据不能用 `band.scrollHeight > band.clientHeight`**：`justify-content:flex-end` 下溢出的部分
   跑到**上边界之外**，`scrollHeight` 不计入它（实测 `scrollHeight == clientHeight == 700`，恒判「不溢出」）。
   正确判据＝**内层实际高度 vs 带子可见高度**。
2. **正文带容量这件事必须实测，不能估**：把「一条消息几行」按字符数估会在换行点上系统性出错；
   样稿里改成**量 DOM**（单行高 81.8px、段距 82px、带子可见宽 1210px）。

### 6.2 样稿实测读数

| 项 | 实测 |
|---|---|
| 正文带容量 | `700px` ÷ （单行 `81.8px` ＋ 段距 `82px`）⇒ **只放 4 条**，每行约 **25 个中文字**（见 P0-5） |
| 元信息补偿 | 视口 1920×1080（scale 1.00）→ `--meta-fs: 24px`；视口 900×560（scale 0.47）→ **`32px`** |
| 姓名短册字号 | 26px ＜ 正文字号 47px（不抢戏） |
| 板书屏正文带 | 收窄到 **330–1152px**（宽 822px ≈ 每行 17 个中文字）；板位 1180–1834px |
| 对比度（`audit_stage_contrast.py` 复算样稿 5 张） | p50 全部 **9.39–16.16:1**，FAIL 行 **0**（含三立绘压字的同台屏：p50 **14.55**） |

> 📌 **同台屏的对比度反而更高**（14.55 vs 开场屏 9.80）——因为立绘本身是暗色，等于给文字又衬了一层底。
