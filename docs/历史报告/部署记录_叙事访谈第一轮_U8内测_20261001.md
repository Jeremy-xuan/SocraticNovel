## 二、服务器上让这道门能跑，一共踩了四个坑

| # | 坑 | 症状 | 解法 |
|---|---|---|---|
| 1 | **服务器上没有 jev-gate，也没有 TypeSafe key** | 门卫本体找不到 | 把 jev-gate 整份 **vendored** 进预设（它零依赖，只用 Node 内置模块）；key 单独装进 u008 家目录 |
| 2 | **`node` 不在实例的 PATH 里**（在 `/opt/node/bin/node`） | `exec: node: not found`（exit 127） | `check-turn.sh` 里按顺序找 node：PATH → `/opt/node/bin` → `/usr/local/bin` → `/usr/bin` |
| 3 | 🔴 **服务器国内直连不到 `api.typesafe.ai`** | `TypeError: fetch failed` | 走本机 mihomo 代理 `http://127.0.0.1:7890`（服务器上有，curl 实测通） |
| 4 | 🔴 **Node 22 的 fetch 加不了代理** | —— | `undici` **既不能 require 也不能 import**（两处都 `MODULE_NOT_FOUND`），内部路径 `node:internal/deps/undici/undici` 也不存在 → **带代理时改用 `curl` 当传输层**（curl 原生支持 CONNECT 代理，两台机器上都有，零依赖） |

**key 为什么不能放 `/root` 或 `/etc`**：实例的 systemd unit 有 `ProtectHome=true` ＋ `ProtectSystem=strict`，它读不到 `/root` 和别人的家目录。放 u008 自己家目录（0600）既能读、又不泄漏给其它实例用户。

## 三、🔴 部署时我把 u008 弄挂过一次（已修，留作教训）

**现象**：重启 u008 后实例进入崩溃循环，端口 3088 不监听。

**根因**：我在 `cordis.patch.yml` 旁边建了备份 `cordis.patch.yml.bak-...`，但那是 **`root:root` 0600** —— 实例用户读不了，**文件监视器（chokidar）在启动时扫到这个文件 → `EACCES: permission denied, watch` → 进程退出**。

**处置**：
1. 备份移到 `/root/`（移出监视野）；
2. 顺带删掉 9/17 遗留的一个同类隐患（`cordis.patch.yml.bak-imgmodality-...`，同样是 root 0600）；
3. 重启 → `active`、3088 监听恢复、`http=401`（要 token，正常）。

**教训（写死）**：**不许在实例的 `DSH_HOME` 里留属主不是该实例用户、或模式过严的备份文件。** 要备份就放到 `/root` 或 `/tmp`，别放在被监视的目录里。

## 四、又踩的一个坑：门往只读目录写账本

共享根 `/opt/dsh-presets` 是 root 所有、实例只读。门卫默认把会话账本写到 `queue/`（在预设目录里）→ 每个实例**每次都刷两条 EACCES 到 stderr**。

**为什么必须修**：`stderr` 正是**回给模型的打回理由通道**，噪音会把真理由冲掉。

**修法**：`check-turn.sh` 里把账本指到可写位置——`JEV_GATE_QUEUE=${TMPDIR:-/tmp}/jev-gate-check-$(id -u)`。
这个账本只服务于「豁免券／申诉」那套**问句门卫**，动作自查不需要它，每次重建无所谓。

> 📌 想留全班审计记录的话，改成带 uid 的持久目录即可（如 `/var/log/jev-gate/<uid>`），但那要额外建目录与权限。
