### 1.1 官方 `model3.json` 的真实结构（一手，8 个官方样本全量）

**样本**：`OFF-SA` 的 `Samples/Resources/*/*.model3.json`（脚本 `json.load` 直读输出，非概括）

```

Hiyori.model3.json           motions=['Idle', 'TapBody'] exprs=0
Mao.model3.json              motions=['Idle', 'TapBody'] exprs=8
Mark.model3.json             motions=['Idle']             exprs=0
Natori.model3.json           motions=['Idle', 'TapBody'] exprs=11
```

**`Motions` 的结构**（逐字，`Hiyori.model3.json`）：

```json

    { "File": "motions/Hiyori_m01.motion3.json", "FadeInTime": 1.0, "FadeOutTime": 1.0 },
    ... 共 9 条
  ],
  "TapBody": [
    { "File": "motions/Hiyori_m04.motion3.json", "FadeInTime": 1.0, "FadeOutTime": 1.0 }
```

**🔴 字段可靠性（实测差异）**：

| 模型 | motion 条目实际含的键 |

| Haru `Idle` | `File` / `FadeInTime` / `FadeOutTime` |
| Haru `TapBody` | `File` / `FadeInTime` / `FadeOutTime` / **`Sound`** |
| **Rice `Idle`** | **只有 `File`** |

→ **概括**：`File` 是**唯一必然存在**的字段；`FadeInTime` / `FadeOutTime` / `Sound` 都可缺。
**这一条 airi 也独立确认了**（`OFF` 无关，airi 自己的解析器 `packages/stage-ui-live2d/src/utils/live2d-validator.ts:159–178` 逐字只取 `definition.File`）：

**`Groups` 段**（逐字，`Hiyori.model3.json`，脚本输出）：

```json
{
  "Groups": [
    { "Target": "Parameter", "Name": "LipSync",  "Ids": ["ParamMouthOpenY"] },
    { "Target": "Parameter", "Name": "EyeBlink", "Ids": ["ParamEyeLOpen", "ParamEyeROpen"] }
  ],
  "HitAreas": [
    { "Id": "HitArea", "Name": "Body" }
  ]

```

> **🔴 结论 1（本报告最重要的能力发现结论）**：
> **官方样本的动作组名并集只有 `Idle` / `TapBody` —— 没有任何以情绪命名的动作组。**
> 而 airi 的情绪映射表要求模型提供 `Happy`/`Sad`/`Angry`/`Awkward`/`Think`/`Surprise`/`Question`/`Idle`/`Curious`
> （`packages/stage-ui-live2d/src/constants/emotions.ts:15–23` 逐字）。
> → **拿 airi 的默认表去驱动任何官方样本，9 个情绪里 8 个落空。**
> → **「情绪 → 动作」不能靠约定动作组名。** 这是设计上的硬约束，不是实现细节。

> **🔴 结论 2**：`Groups` 段是**官方提供的参数语义绑定**（`LipSync` 的 ID 是哪个、`EyeBlink` 的 ID 是哪两个）。
> **应当读它，而不是硬编码参数名。**（airi 没读，见 §1.4；OLV 读了，见 §1.3。）

#### 🔴🔴 结论 2 的决定性证据：官方样本里 `LipSync` 参数名**根本不统一**

**方法**：对 8 个官方样本，脚本提取 `Groups[]` 里 `Name == "LipSync"` / `"EyeBlink"` 的 `Ids`。**输出原文**：

```

Hiyori.model3.json         LipSync=['ParamMouthOpenY']  EyeBlink=['ParamEyeLOpen', 'ParamEyeROpen']
Mao.model3.json            LipSync=['ParamA']           EyeBlink=['ParamEyeLOpen', 'ParamEyeROpen']

Rice.model3.json           LipSync=[]                   EyeBlink=['ParamEyeLOpen', 'ParamEyeROpen']
```

**四种互不相同的形态**：

| 形态 | 模型 | `LipSync` 的 `Ids` |
|---|---|---|
| 标准名 | Haru / Hiyori / Natori / Ren | `['ParamMouthOpenY']` |
| 🔴 **完全不同的名字** | **Mao** | **`['ParamA']`** |

**交叉验证（排除「声明了但模型里没有」）**——这两个非标准名**真实存在于模型的动画数据里**：

> ### 🔴🔴 对本项目选型的决定性意义
> **airi 硬编码 `'ParamMouthOpenY'` 的做法，在 8 个官方样本里有 4 个会失效**
> （Mao、Wanko 参数名不对；Mark、Rice 是空数组）。
> **「换模型就坏」在官方样本上是常态，不是边缘情况。**
> → **「读 `Groups` + 三级回退」不是可选优化，是必需项。**
> → **同时**：`LipSync = []`（空数组）与「`LipSync` 字段缺失」是**两种不同情况**，都要回退。
> OLV 的判据（`getSize() === 0`）**恰好同时覆盖两者** —— 这是照抄它的另一个理由（§1.4）。

### 1.2 三种「能力发现」做法的对照（含取舍）

| 做法 | 代表 | 机制 | 优点 | 缺点 |
|---|---|---|---|---|
| **① 全静态写死** | airi 的情绪表 | 代码里写 9 个情绪 + 9 个动作名 | 零解析成本；prompt 稳定 | **换模型即失效**；LLM 被告知有、实际没有（§1.4） |
| **② 外置配置 + 动态注入** | Open-LLM-VTuber | `model_dict.json` 的 `emotionMap` → 渲染进 prompt | 换模型只换配置；**LLM 只知道存在的关键词** | 每个模型要**人肉写一次** `emotionMap` |
| **③ 运行时解析 + 动态注入**（**我们要做的**） | 无现成实现（见下） | 读 `model3.json` → 生成枚举 → 注入 prompt | 换模型**零配置** | 解析器要自己写；`motion3.json` 曲线解读成本高 |

#### 🔴 为什么 ③ 没有现成实现（诚实标注）

- **OLV 走了 ②**：它的 `emotionMap` 是**人写的**，不是从 `model3.json` 推出来的。
  （依据：`model_dict.json` 里 `emotionMap` 的键是 `neutral/anger/disgust/fear/joy/smirk/sadness/surprise` —— 这些**不是**任何 `model3.json` 里出现的字符串；而值是 `0/1/2/3` 这种**expression 数组下标**。见 `研究_8_证据/A4_Open-LLM-VTuber.md` §1 步骤①）
- **airi 走了 ①**：`availableMotions` **确实**从已加载模型动态提取（`Model.vue:364–377` 逐字，见 §1.4），**但提取结果只喂给设置界面，从不喂给 LLM**。
- → **「运行时解析 model3.json 并把结果反向注入 prompt」这一步，两个大仓库都没做。**
  **这是我们的自研点，且必须标明：没有先例，需要我们自己承担解析器的正确性风险。**

> **但「自研」只限于「解析 → 注入」这一步的拼装**：
> - **「注入」有先例**：OLV 的 `<insert_emomap_keys>` 替换（`service_context.py:457–460`）+ DSH 的 `system-prompt/assemble` waterfall（§2.2）。
> - **「从 model3.json 读结构」有先例**：airi 的 `live2d-validator.ts`（§1.4）+ 官方框架 API（§1.5）。
> → **我们只是把两件已存在的事接起来，不是发明新机制。**

```ts
      if (this._lipSyncIds.getSize() === 0) {

        if (idManager) {
          const fallbackId: CubismIdHandle = idManager.getId(CubismDefaultParameterId.ParamMouthOpenY);

          // Check if the model actually has this parameter before adding it
          if (this._model && fallbackId && this._model.getParameterIndex(fallbackId) !== -1) {
            this._lipSyncIds.pushBack(fallbackId);
            console.log('[Fallback] Successfully added "ParamMouthOpenY" as LipSync ID.');

            console.warn('[Fallback] Fallback ID "ParamMouthOpenY" not found in the current model or model not loaded.');
```

### 1.6 能力发现层的设计（可直接实现）

#### 输入
模型的 `model3.json`（**在服务端读，不需要加载渲染器**）。

#### 输出（一个 JSON 对象，就是「能力清单」）

```jsonc
{
  "modelId": "<hash 或路径>",
  "motionGroups": [                      // 来自 FileReferences.Motions 的 key
    { "name": "Idle",    "count": 9 },
    { "name": "TapBody", "count": 1 }
  ],
  "expressions": [                       // 来自 FileReferences.Expressions[]
    { "name": "Angry",  "index": 0 },
    { "name": "Smile",  "index": 4 }
  ],
  "parameterGroups": {                   // 来自顶层 Groups[]
    "LipSync":  ["ParamMouthOpenY"],
    "EyeBlink": ["ParamEyeLOpen", "ParamEyeROpen"]
  },
  "hitAreas": ["Body"]                   // 来自顶层 HitAreas[]
}
```

#### 解析规则（每条都有 §1.1 的一手依据）

| 字段 | 规则 | 依据 |
|---|---|---|
| `motionGroups[].name` | `Object.keys(FileReferences.Motions)` | 官方框架 `getKeys()`；airi `Object.entries(motionManager.definitions)` |
| `motionGroups[].count` | 该组数组长度 | 官方 sample 实测 |
| 单个 motion 的 `File` | **必须读**，是唯一必然存在的字段 | §1.1 字段可靠性表 |
| `FadeInTime`/`FadeOutTime`/`Sound` | **可选**，缺省不报错 | §1.1 字段可靠性表 |

### 2.3 🔴 架构裁定：立绘**不要**放进消息节点，放进右栏 tab

任务书列了两个挂点：`ui-sidebar-right` tab（常驻立绘）与 `conversation.chat.node` keyed node（消息内联动）。

**裁定：第一版只用右栏 tab，`conversation.chat.node` 先不做。** 理由（三条，均为工程性，非偏好）：

1. **`conversation.chat.node` 的 `tool-call` key 是 `shadows-shipped-ui`**（P3 `:584`）→ 一旦注册，**官方 ToolCallTree 被盖掉**，我们要自己承担该 kind 的全部呈现（所有工具的显示都归我们管）。**成本远大于收益。**
2. **立绘是「常驻的、跨消息持续的状态」，不是「消息内的一次性内容」。** 放在消息流里会导致：每条消息一个 canvas 实例、滚动时反复挂载卸载、状态难以跨消息保持。
3. **不需要它**：右栏 tab 里的组件**同样能拿到 `useChat` / `useSession` / `useProjection`**（P3 `:616`）→ **它自己就能订阅流式文本与相位事件**，从而做出「消息内联动」的效果。**功能不减，成本骤降。**

> **⚠️ 待确认（列入 §8）**：右栏 tab 是否也在标准 props 覆盖范围内（P3 的标准 props 是**针对 `conversation.chat.node`** 记的，右栏 tab 的 props 面**本次未取证**）。
> **若不覆盖**：退路是客户端插件内部的**模块级单例 + 订阅**（两个槽位共享同一模块实例），或走 `BroadcastChannel`（airi 就是这么跨 store 同步的，`model-parameters.ts:41` 逐字：`useBroadcastChannel<...>({ name: 'airi-stores-stage-ui-live2d' })`）。

### 2.4 与教学状态的接法：**不新增 LLM 成本**

**核心设计**：立绘驱动**搭在已有的 `classroom_set_phase` 工具上**，不新增调用。

两条路，二选一（**倾向 B**）：

- **路 A（零新增工具）**：`classroom_set_phase` 的**返回值**里带上 `pose` 建议，客户端从工具结果里读。
  - 优点：零新增工具；相位与姿态天然绑定。
  - 缺点：**返回值是给模型看的**，拿来当客户端信号是「借用」，语义不干净。
- **路 B（新增一个并列工具）**：新增 `classroom_set_pose`，参数 `{ emotion?, intensity?, motion?, channel? }`，**与 `classroom_set_phase` 完全同形**（同一个 `defineTool` 形状，`index.mjs:308` 已是现成模板）。
  - 优点：语义干净；schema 校验直接生效；工具描述里可以写「换相位时同时宣布姿态」。
  - 缺点：多一个工具（**但不多一次 LLM 调用**——模型可以在同一轮里调两个工具）。

> **🔴 明确结论**：**这条通道的 LLM 成本 = 0**（模型本来就要宣布相位；多带几个参数不产生额外调用）。
> **且这条通道有先例**：airi 的 `CALL` manifest（`研究_8_证据/A1` §2.4）与 OLV 的 `Actions`（`A4` §1 步骤④）都是「结构化意图随消息一起下发」。

| 项 | 由谁做 | 依据 |

> airi **主动关掉了官方呼吸**（`motion-manager.ts:67–69` 逐字：`export function disableLive2DSdkBreath(internalModel: { breath?: unknown }) { delete internalModel.breath }`），改用自己写的呼吸曲线。

> **代价**：官方行为不可控（例如眨眼节奏固定），若要精细控制再接管——**这是可推迟的决定**。

#### 状态层（**持续状态，后写覆盖先写**）

挂在 **Expression（order 300）** 这一层。写成**参数预设**，不是 expression 文件。

```jsonc
// 状态预设（教室侧数据，每个模型可覆盖）

  "id": "thinking",
  "channel": "write",          // 教学语义，见 §5.3

    "ParamEyeROpen": 0.75,
    "ParamBrowLY": -0.3,       // 眉毛（若模型有）

    "ParamAngleZ": 2.0         // 头微侧
```

**强度（intensity）怎么落地 —— 这是 airi 和 OLV 都没解决的**：

- **airi**：`intensity` 归一化了（`payloads.ts:62–75` 逐字 `Math.max(0, Math.min(1, numeric))`），**但在 Live2D 路径上被丢弃**（`研究_8_证据/A2` §3.4：触发点只设 `currentMotion` 的 group 名）。
- **OLV**：**根本没有 intensity 概念**（`emotionMap` 的值是 expression 下标，`A4` §1 步骤⑤）。
- **我们的做法**：**intensity 作为「参数预设」与「中立值」之间的插值权重**。

```
finalParam = lerp(neutralValue, presetValue, intensity)
```

依据：`intensity ∈ [0,1]` 已由 airi 的归一化语义确立（`payloads.ts:74`），**lerp 是唯一自然的映射**（0 = 不动，1 = 满值）。
**这一步是自研点**（无先例），但它只是把「已有的 0–1 标量」映射到「已有的参数值域」，**风险低**。

#### 事件层（**一次性动作，抢占**）

**用 airi 的 `handled` 抢占语义**（官方没有）：

```js
// 伪代码，形状照抄 airi 的 markHandled
const ctx = { handled: false, markHandled() { this.handled = true } }
for (const plugin of eventPlugins) {       // 按优先级
  if (ctx.handled) break
  plugin(ctx)
}
```

**事件层注册在 order 900**（官方最大命名值是 800 Pose）→ **事件动作永远最后写，能压过状态层**。
**事件跑完自动注销**（一次性）→ 下一帧回到状态层的值。

**信号源**：`classroom_set_pose` 工具调用（§2.4）。

#### 各层的信号源与优先级汇总表

| 层 | 官方序位 | 信号源 | 写参数的方式 | 生命周期 |
|---|---|---|---|---|
| 基础 | 200 / 400 / 500 / 600 | 官方自带（无外部信号） | updater 内部 | 常驻 |
| 状态 | **300** | `classroom_set_phase` / `classroom_set_pose` 的 `emotion`+`intensity`+`channel` | `setParameterValueById`（**覆盖**） | 持续到下次变更 |
| 基础（嘴型） | **700** | **`TextRhythmProvider`**（§4.2） | `addParameterValueById`（**加性**，官方 `CubismLipSyncUpdater` 行为，`cubismlipsyncupdater.ts:73` 逐字 `model.addParameterValueById(this._lipSyncIds[i], lipSyncValue);`） | 说话时有效 |
| 事件 | **900（自定）** | 工具调用 / 相位切换 | `setParameterValueById` | 一次性，跑完注销 |

> 🔴 **一个必须注意的机制冲突**：官方 LipSync 用 **`addParameterValueById`（加性）**，状态层用 **`setParameterValueById`（覆盖）**。
> 因为 LipSync（700）**在** Expression（300）**之后**跑，**加性写入会叠在状态层的值上** → 嘴部值可能超界。
> **处理**：① 依赖官方参数 clamp（Cubism 参数有 min/max，越界会被截）；② 或在状态层不写 `ParamMouthOpenY`（让嘴型只归 LipSync 层管）。
> **🔴 倾向 ②**，理由：嘴型有专门的一层，状态层不该碰它。**但这是推断，需实测确认 clamp 行为**（列入 §8）。

## 4. 嘴型：**无音频**的替代方案（本轮最实用的一条）

### 4.1 🔴 关键发现：官方 R5 的嘴型驱动是**可插拔接口**，不绑音频

**文件**：`OFF-FW` `src/motion/iparameterprovider.ts:12–33`（逐字）

```ts
/**
 * Interface class for providing parameter values.<br>
 * Defines the base interface for classes that supply parameter values to the model.
 */
export abstract class IParameterProvider {
  /**
   * Constructor
   */
  constructor() {}

  /**
   * Update process.
   *
   * @param deltaTimeSeconds Delta time in seconds (optional).
   *
   * @return true if the update is successful.
```

> ### 🔴 结论（本轮最重要的可实现结论）
> **`LAppWavFileHandler` 只是 `IParameterProvider` 的「一个实现」。**
> 它的接口只有 **两个方法**：`update(dt) → boolean` 与 `getParameter() → number`。
> → **我们写一个 `TextRhythmProvider`，实现同样两个方法，产出口型值，就能直接塞进官方的 `CubismLipSyncUpdater`，一行官方代码都不用改。**
> **这就是「无音频嘴型」的落地方式，且有官方接口作为依据 —— 不是我们的发明。**
> **✅ 先例归属**：**接口是官方的**（`IParameterProvider`）；**「用文本节奏而非音频喂它」这个实现没有先例**（airi 与 OLV 都只做音频）→ **标为自研点**。

### 4.2 `TextRhythmProvider` 的设计（我们的自研点）

#### 输入（都是我们已有的东西）
- **流式文本增量**：DSH 的 `text-delta` chunk（`assistant-stream.js:44` 逐字）。
- **`channel` 语义**：`speak` / `write`（§5.3）。

#### 输出
`getParameter() → number`，值域 `[0, 1]`（对应 `ParamMouthOpenY`）。

#### 算法（三档，从简到繁）

**档 1 · 字符节奏（最简单，第一版用这个）**

```
每来一个 text-delta chunk：
  记下 chunk 的到达时间 t 与字符数 n
  瞬时目标值 target = min(1, n / CHARS_PER_TICK)      // CHARS_PER_TICK ≈ 3
  进入衰减：value 以 τ ≈ 80–120 ms 的时间常数向 0 衰减
每帧：
  value = decay(value, dt)                            // 指数衰减
  getParameter() = value * AMPLITUDE                  // AMPLITUDE ≈ 0.6
```

- **依据**：airi 的嘴型插件本来就有「release 衰减 + smoothstep 混合」的现成形状可参考
  （`motion-manager.ts:751–800` 逐字：`RELEASE_DURATION_MS = 200`、`HANDOFF_HOLD_MS = 500`、`const smoothstep = (t: number) => t * t * (3 - 2 * t)`）。
- **为什么合理**：流式输出本身有节奏（token 到达不均匀），**字符到达密度天然近似「说话速度」**。
- **风险**：**token 到达 ≠ 发声**。模型可能一次吐 50 个字符 → 嘴会大张一下。→ 用**上限 + 衰减**压平（档 1 的 `min(1, ...)` 与 `τ` 就是干这个的）。

**档 2 · 句读节奏（第二版）**
在标点（`。！？，；`）处插入一次「闭嘴」，让嘴型随句子分段。依据：OLV 的 prompt 明确要求模型用标点（`live2d_expression_prompt.txt` 示例逐字 `"Hi! [expression1] Nice to meet you!"`），**说明模型输出天然有标点**。

**档 3 · 音素近似（远期，**不建议**）**
把文本按拼音/音素转成开口度。**成本高、收益低**（无音频时用户听不到声音，嘴型的精细度无人校验）。**明确不做。**

#### `channel = write` 时的行为（**这是我们的教学语义，见 §5.3**）

**`getParameter()` 恒返回 0** → 嘴不动。
**取而代之**：白板上的文字用打字机效果推进（**由白板组件做，不走 Live2D**）。

> **🔴 这就是「说话卡、写字流畅」的工程实现**：
> **不是让嘴动得更慢，而是让「嘴」和「手」走两条不同的通道。**
> - `speak` → 嘴型动（且有衰减、有上限 → 视觉上就是「卡、断续」）
> - `write` → 嘴不动，白板逐字出现（视觉上就是「流畅」）
> **两条通道的视觉对比本身就是人物辨识特征。**

## 5. 与教学状态接法

### 5.1 相位 → 立绘（映射表）

**相位枚举**（一手，`开源线/DSH定制/code/classrooms/cs-os/classroom.yaml:73–79` 逐字）：

```yaml
phases:
  - { id: open,   name: 开场 }
  - { id: probe,  name: 追问 }
  - { id: answer, name: 学生作答 }
  - { id: check,  name: 对答案 }
  - { id: review, name: 复习 }
  - { id: close,  name: 收尾 }
```

**相位推进机制**（同文件 `:65–72` 逐字注释）：

```
# ✅ M3-STATE 已修（2026-09-24）：**相位推进已落地，但不由引擎按规则推进**——
#    教师（模型）在课堂上判断"该进哪个相位了"，调 `classroom_set_phase` 工具宣布；
#    引擎只做两件事：① 记录（取值必须落在本列表内，否则报错并列出合法 id）；
#    ② 按新相位重新裁决所有带相位门的块（**下一回合**生效）。
```

**建议映射（教学语义驱动，非装饰）**：

| 相位 | 状态预设 | 视觉理由（教学） |
|---|---|---|
| `open` | `idle`（默认呼吸+眨眼） | 开场，不需要额外姿态 |
| `probe` | **`curious`**，intensity 0.5–0.8 | **提问时前倾/睁眼**——把「老师在等你想」视觉化 |
| `answer` | `listening`（**轻微点头 + 视线聚焦**） | **学生在说话**——立绘应表现出「在听」而不是继续演 |
| `check` | `focused`，channel 切 `write` | 对答案要写字——**通道切换的天然时机** |
| `review` | `recall`（视线略偏，像在回忆） | 复习是检索，不是新输入 |
| `close` | `relaxed` | 收尾 |

> **🔴 关键教学差异（与 airi 的分野，见 §6）**：
> **`answer` 相位立绘要「退让」**——学生作答时，立绘的动作应该**减弱**而不是增强。
> 陪伴场景（airi）的成功标准是「不出戏、有魅力」→ 立绘越活跃越好；
> **教学场景的成功标准是「学生学会了」→ 学生思考/作答时，立绘抢注意力是负面效果。**
> **实现**：`answer` 相位把所有状态预设的 intensity 乘 0.3，并禁用事件层动作。

### 5.2 讲次变化 → ？

**讲次门**（一手，`classroom.yaml:60` 逐字）：

```yaml
  lesson_key: current_lesson
```

**建议**：
- **讲次变化 = 一次「场景重设」事件**，不是持续状态。
- **具体动作**：切讲时**重置**所有状态预设到 `idle`，并（可选）播一次「翻页/换姿势」的一次性动作。
- **不要**为每讲写一个专属姿态（**维护成本爆炸**：14 讲 × N 个模型）。
- **讲次级差异应该体现在「台词与白板」**（已有机制），**不是立绘**。

### 5.3 🔴 我们独有的教学语义：「表达通道切换」

**设定原文**（一手，`开源线/DSH定制/code/classrooms/cs-os/_anchor.md:25–26` 逐字）：

```
- **小鞠知花**：开口时声音小、会停顿或结巴；写白板时更快、更有条理。**她可以说得慢，但每道题、每次反馈都必须说完整**；卡住就写完整句，不把半句话留给学生猜。讨论到在意的结构时语速和自信明显提高。有轻微毒舌，但攻击性弱；被夸会慌。
- 🔴 **她的"说话"主要发生在看得见的地方**：白板、屏幕、手机。**要台词时先想"她是写出来还是说出来"** —— 这是她最重要的辨识特征。
```

**同文件 `:20` 逐字**（另一条相关约束）：

```
- 面向学生的正文始终留在场景里。动作和心情用自然叙述，不用括号旁白、`<sub>`、章节状态标签或"你可以怎么回答"的界面说明。
```

#### 能否落到参数/动作层？**能，而且这正是 §4.2 的设计动机**

| 语义 | 落到哪一层 | 具体做法 |
|---|---|---|
| **「说出来」** | **LipSync 层（order 700）** | `TextRhythmProvider` 输出非零 → 嘴动；**因为文本节奏是断续的 + 衰减，视觉上就是「卡」** |
| **「写出来」** | **LipSync 层返回 0 + 白板组件** | 嘴不动；白板用打字机效果逐字出现 → 视觉上「流畅」 |
| **「说话主要发生在看得见的地方」** | **channel 的默认值** | 教学场景里 `channel` 默认 `write`（因为她主要靠写）；`speak` 是要被**显式选择**的 |
| **「被夸会慌」** | 状态层 | 一个 `flustered` 预设（低头 + 视线偏移） |
| **「轻微毒舌」** | 事件层 | 一次性动作 + 特定表情预设 |

> ### 🔴 这一步 airi 没有（明确标注为我们的独有设计）
> airi 驱动的是**情绪**（happy/sad/angry/…，`研究_8_证据/A1` §2.3 白名单逐字）。
> **我们驱动的是「表达通道」**（说出来 vs 写出来）——**这是一个正交于情绪的维度**。
> - **无先例的部分**：**「通道」这个概念在 airi 与 OLV 里都不存在**（两边都只有 emotion）。
> - **有先例的部分**：**用 `IParameterProvider` 控制嘴型是官方的**（§4.1）；**「嘴型不跟音频」没有先例**。
> → **自研点定位**：**「channel 作为一等驱动维度」是自研；其实现手段全部借用既有接口。**

#### 为什么这条语义值得单独驱动（而不是靠台词写出来）

1. **它是 `_anchor.md` 里被标 🔴 的两条之一**（另一条是「必须说完整」）→ 作者认定的最高优先级特征。
2. **它无法只靠文字表达**：如果模型写「（她小声说）」→ **违反 `:20` 的「不用括号旁白」**。
   → **立绘是唯一合规的表达载体。** ← **这是「必须做立绘」的硬理由。**
3. **它有教学功能**：`speak` 卡顿 → 学生知道「这句要重点听」；`write` 流畅 → 学生知道「这是要记下来的」。

## 6. 教学场景 ≠ 陪伴场景：借什么、不借什么（逐条）

**判据**：airi 的成功标准是「不出戏、有魅力」（陪伴）；我们是「学生学会了」（教学）。

| airi/OLV 的做法 | 借 / 不借 | 理由（教学侧） |
|---|---|---|
| **`IParameterProvider` 抽象**（官方） | ✅ **借** | 官方接口，让我们能把嘴型换成非音频源 |
| **`Groups` 读参数 ID + 三级回退**（OLV） | ✅ **借** | 换模型不失效；有日志 |
| **能力清单动态注入 prompt**（OLV） | ✅ **借** | LLM 只知道真存在的动作 → 减少无效调用 |
| **工具调用承载结构化意图**（DSH 原生） | ✅ **借** | schema 校验，非法值入口即拒 |
| **`CubismUpdateOrder` 官方序位** | ✅ **借** | 官方规范，稳定 |
| **`handled` 抢占语义**（airi） | ✅ **借** | 一次性事件动作需要压过循环动作 |
| **intensity 落到参数（lerp）** | ✅ **借（并补全）** | airi 归一化了却丢弃；我们落地 |
| **Beat Sync（音频节拍 → `angleX/Y/Z`）** | ❌ **不借** | **无音频**。且教学场景里随节拍摇头是纯干扰 |
| **LipSync 走音频（`wlipsync` / RMS）** | ❌ **不借** | **无 TTS**。改用 `TextRhythmProvider`（§4.2） |
| **`<|ACT|>` / `[joy]` 文本标签** | ❌ **不借** | DSH 无此机制（§2.1）；且有更可靠的工具调用通道 |
| **多情绪叠加 / 高频换表情** | ❌ **不借** | 陪伴要「有魅力」→ 表情多变；教学要「不抢注意力」→ 表情应**少而稳** |
| **MediaPipe 面部追踪（把用户表情反馈进 LLM）** | ❌ **不借** | ① 隐私与成本；② **教学场景里「学生表情」不是可靠的教学信号**（走神与思考的表情难以区分）→ 误判风险高 |
| **`answer` 相位保持活跃动作** | ❌ **不借（反着做）** | 学生作答时立绘应**退让**（§5.1） |
| **屏幕环境光滤镜 / 阴影滤镜**（airi 有） | ❌ **不借（第一版）** | 纯氛围，零教学价值，纯成本 |
| **模型的「自我感动」型闲聊姿态** | ❌ **不借** | 教学场景里立绘是**状态指示器**，不是**表演者** |

> **🔴 一句话总结这份表**：
> **我们借「机制」，不借「审美」与「表演强度」。**
> airi 的机制层（插件分层、能力发现、参数抽象）做得很好，**直接可用**；
> airi 的**表演层**（表情频率、节拍摇动、氛围滤镜、面部追踪）**在教学场景是负资产**。

### 7.2 🔴 裁定：**用官方 `CubismWebFramework` R5，不用 `pixi-live2d-display`**

**理由（全部基于 §7.1 的一手数据）**：

1. **`IParameterProvider` 只存在于官方 R5 框架里**（`OFF-FW` `src/motion/iparameterprovider.ts`）。
   → **我们的核心机制（无音频嘴型，§4.2）依赖它。** 用 pixi 封装层就拿不到这个接口。
2. **`CubismUpdateScheduler` + `CubismUpdateOrder` 也只存在于 R5**（`OFF-FW` `src/motion/`）。
   → **驱动分层的骨架依赖它。**
3. **`pixi-live2d-display` 停更 2 年**（`pushed_at: 2024-08-20`，最近提交 2023-12-15），**latest 稳定版 `0.4.0` 是 2022 年的**。
4. **维护中的 fork 只有 24 stars** → 长期被弃风险高，且它**同样不暴露 `IParameterProvider`**（它是 Pixi 插件，抽象层在 Pixi 之上）。
5. **官方 R5 的 updater 架构正是为「插一层自定义驱动」设计的**（`setExecutionOrder()` 可运行时改序，`icubismupdater.ts:79–84`）。

**代价（必须承认）**：
- 我们要**自己写渲染宿主**（WebGL canvas、纹理加载、视图矩阵）——官方 sample 的 `LAppModel`/`LAppSubdelegate` 提供了**可参考的完整实现**（`OFF-SA` `Samples/TypeScript/Demo/src/`），但那是 sample 代码，不是稳定 API。
- 没有 Pixi 的便利（场景图、滤镜、`ticker`）。
- **工作量显著高于「装个 pixi 插件」。**

> **⚠️ 这是本报告最大的一个「成本换能力」的取舍，必须由用户确认**（列入 §8）。
> **若用户选择「先跑起来优先」**：可用 `pixi-live2d-display-advanced`（Pixi v7、维护中）做**第一版**，代价是**放弃 `IParameterProvider` 路径**（嘴型要自己在 Pixi 层猴补丁，像 airi 那样），**并且后续换回官方框架等于重写渲染层**。

## 8. 最小可用形态（MVP）

### 8.1 MVP 定义（**为了第一版能跑起来，最少要做哪几件事**）

**目标**：右栏常驻一个立绘，能眨眼/呼吸（白送）、能在换相位时换表情、能在文字流出时嘴动。

| # | 任务 | 依赖 | 是否可白送 |
|---|---|---|---|
| **M1** | **渲染宿主**：WebGL canvas + 加载 `model3.json`/`.moc3`/纹理 + 每帧 tick | 官方 framework | ❌ 要写（可参考官方 sample） |
| **M2** | **能力发现解析器**（§1.6）：服务端读 `model3.json` → 清单 JSON | 无 | ❌ 要写（~200 行） |

## 9. 风险与反证

### 9.1 性能

| 风险 | 依据 | 缓解 |
|---|---|---|
| 立绘常驻占 CPU/GPU | 官方 sample 的模型校验器明确给了性能阈值：`moc` **> 100 MB 报 error**、**> 30 MB 报 warning**（airi `live2d-validator.ts:437–454` 逐字：`The MOC file is ${sizeMb.toFixed(2)} MB and exceeds the import limit.` / `...can reduce rendering performance.`） | **选模型时先看 `moc3` 体积**；`>30 MB` 的模型在常驻场景慎用 |
| 逐帧 tick 与 DSH 客户端渲染竞争 | 未取证 | 降到 30fps；或仅在窗口可见时 tick |
| **渲染宿主自研带来的性能不确定性** | §7.2 裁定 | 官方 sample 有 `CubismUpdateScheduler`，按其序位跑；不要自己乱序 |

### 9.2 动作与台词不同步（**最可能出问题的一条**）

| 子风险 | 说明 | 缓解 |
|---|---|---|
| **工具调用与文本流不同步** | 模型可能**先**输出一大段文字，**再**调 `classroom_set_pose` → 观众看到「先说完了才变表情」 | ① 工具描述里写「**在说出那句话之前**先调用」；② 或允许在**相位切换时**（下一回合生效）而非文本中间变——**接受这个延迟** |
| **嘴型与文字节奏错位** | token 到达不均匀（一次吐 50 字） | §4.2 档 1 的 `min(1,...)` + 衰减；必要时用档 2（句读） |
| **`channel` 切换滞后** | 模型宣布 `write` 时，前一句还在「说」 | `TextRhythmProvider` 的 `channel` 切换**立即生效**（不排队） |
| **相位门是「下一回合生效」** | 一手：`classroom.yaml:68` 逐字「按新相位重新裁决所有带相位门的块（**下一回合**生效）」 | **立绘不要挂在相位门上**，要挂在**工具调用事件**上（即时） |

### 9.3 模型不配合

| 风险 | 依据 | 缓解 |
|---|---|---|
| **官方样本没有情绪动作组** | §1.1 结论 1（并集只有 `Idle`/`TapBody`） | 走 §1.6 的 P1–P4 降级链；**P4 参数预设是兜底** |
| **5/8 官方样本没有 expressions** | §1.1（`Hiyori`/`Mark`/`Rice`/`Wanko` 全为 0） | 同上；**必须准备参数预设** |
| **`Groups` 缺失或 `LipSync` 为空数组** | 一手实测（§1.1 结论 2 的决定性证据）：`Rice` 与 `Mark` 的 `LipSync` 的 `Ids` 是 **`[]`**（空数组）；`Mao` 是 `['ParamA']`；`Wanko` 是 `['PARAM_MOUTH_OPEN_Y']` | 触发 §1.6 的回退链；**`[]` 与「字段缺失」都要回退**（OLV 的 `getSize()===0` 判据同时覆盖两者） |
| **参数名因模型而异** | `Groups` 存在的意义就是这个 | 读 `Groups`；不硬编码 |
| **模型根本不支持某参数** | 未取证（需实测 `getParameterIndex` 行为） | OLV 的做法：**回退后验证存在**（`lappmodel.ts:391` 逐字 `this._model.getParameterIndex(fallbackId) !== -1`）→ 照抄 |

### 9.4 无障碍（**airi 与 OLV 都没处理，我们必须自己定**）

| 问题 | 说明 | 建议 |
|---|---|---|
| **纯装饰动画对屏幕阅读器是噪音** | 立绘是 `canvas`，无文本语义 | canvas 加 `aria-hidden="true"`；**所有立绘承载的信息必须有文字等价物** |
| 🔴 **「通道切换」承载教学信息 → 无障碍风险** | §5.3 里 `speak`/`write` 是**有意义的信息**（学生据此判断「要重点听」vs「要记下来」） | **不能只靠立绘表达**。→ 正文里要有**文字标记**（如引用块 vs 正文），或白板区域本身就是文字。**立绘是强化，不是唯一载体。** |
| **动效偏好** | 用户可能开了「减少动态效果」 | 读 `prefers-reduced-motion` → 降为静态立绘（或只保留呼吸） |
| **闪烁/频闪** | 高频换表情可能触发不适 | §6 已裁定「表情应少而稳」→ 天然规避 |

### 9.5 升级脆弱

| 风险 | 依据 | 缓解 |
|---|---|---|
| **`conversation.chat.node` 依赖 DSH 内部结构** | P3 `:519` 逐字：`main`/`rightbar`/`root`/`conversation.chat.node` 均为 **`"shadows-shipped-ui"`** | **第一版不用它**（§2.3 已裁定）；只用右栏 tab |

- Live2D 官方许可总览：<https://www.live2d.com/en/sdk/license/>
- Live2D Open Software License（框架源码顶部逐字引用）：<https://www.live2d.com/eula/live2d-open-software-license-agreement_en.html>
- 官方 sample 的许可声明文件（本地已 clone 到 `/tmp/CubismWebSamples/LICENSE.md`，对应仓库：<https://github.com/Live2D/CubismWebSamples>）

**③ 需要用户决定的选择项**：

- (c) 使用**自建模型**（用 Cubism Editor 自绘）—— 无第三方模型授权问题，但有 Editor 授权问题；
- (d) 以上组合，或先按 (a) 做原型、上线前再换。
