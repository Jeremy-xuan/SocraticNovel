## §0 一句话结论，与"我们之前错在哪"

**用户的原话（本次任务的动机）**：

> "我觉得你这个皮肤的设计思路不对啊，**这个插件不应该是改个侧边栏，这不叫深度定制**。**你是不知道 galgame 的界面长什么样吗？**"

**这句话是对的，之前的方向错了。** 错在两点，都要认：

1. **把"信息面板"当成了产品形态。** 之前的做法是"在右栏加一块教室面板，把它打扮漂亮"（课程表 / 进度 / 立绘缩略）。
   那只是**一个工具面板**，不是产品的"脸"。用户要的是**脸**。
2. **设计依据是印象，不是真实界面。** 我们没有查过任何一个真实视觉小说引擎的界面定义就动手了。
   这一轮补上了（见 §2.1，全部带源码路径与官方文档出处）。

**这一轮做出的是**：**整屏场景 ＋ 立绘 ＋ 底部对话框（带说话人姓名条）＋ 点击推进**——
一个能点着走的**原型**，用真实教室内容（`cs-os` 第 1 讲）与真实教师人格（小鞠知花）写的示例台词。
**三种布局变体，15 张截图，57 项程序化断言全绿。**

### 1.1 🔴 取证里最关键的一条：`conversation.chat.node` 与 `conversation.view` 是**竞争关系**

`conversation.chat.node` 的 `declaredBy` 逐字是 **`an entry in 'conversation.view' (client-ui-chat)`**——
**它的生命周期绑在 `chat` 这个 view 上**。你一旦切到自己的 view，`chat` 不渲染，那些节点渲染器**也就不工作**。

→ **"换掉 assistant 的渲染器做成对话框"与"自己开一个整屏舞台 view"，只能选一条当主轴，不能都要。**
这是本报告 §4 接线方案分叉的根源，也是**必须由用户拍板的第一件事**（见 §5）。

## §2 真实 galgame 的构件清单 ＋ 我们的取舍

### 2.1 先做功课：真实引擎的界面构成（**不是凭印象**）

对三套**开源、可核对**的视觉小说引擎取了界面定义源码与官方文档：**Ren'Py 默认 GUI 模板**（`gui/game/screens.rpy`）、
**Monogatari**（`develop@86659ba`）、**Naninovel**（v1.21 文档）。完整取证见 `evidence/_galgame_research_raw.md`。

**共同构件（三引擎都有，共 21 项）** —— 摘要：

| 构件（职能） | Ren'Py 官方术语 | 出处（节选） |
|---|---|---|
| **主文本对话框** | **`say` screen** / `window` | `gui/game/screens.rpy` 的 `screen say(who, what):`；官方文档 `screen_special.html` §Say |
| **说话人姓名条** | **`namebox`** | `screens.rpy` 的 `style namebox`；官方小节名就叫 **"Name and Namebox"** |
| **点击推进** | `dismiss` 键位 | `renpy/common/00keymap.rpy`：`dismiss = ['K_RETURN','K_SPACE','K_KP_ENTER','K_SELECT','mouseup_1']`（**回车/空格/鼠标左键抬起**）；文档 `dialogue.html` 逐字 "until the user **clicks to dismiss** it" |
| **立绘三档位置** | `left` / `center` / `right` | `00compat.rpy`：`Position(xalign=0.0/0.5/1.0)`；Monogatari 文档逐字 "If omitted, defaults to **center**" |
| **选择肢** | **`choice` screen** | `screens.rpy` 的 `screen choice`；`style choice_vbox` 居中、垂直约屏幕 37.5% |
| **快捷按钮条** | **`quick_menu`**（**底部居中**） | `screens.rpy` 的 `screen quick_menu()`；`style quick_menu: xalign 0.5 / yalign 1.0` |
| 背景 / 场景 | `scene` + `master` layer | 文档 `displaying_images.html`：`master` 层 "generally used for **backgrounds and character sprites**" |
| 转场 | `with` + `Transition` | 同上 §With Statement |

**三条对我们特别有用的逐字事实**：

1. **姓名条与对话框是两种不同的东西**：`namebox` 的背景是 **`Frame(...)` 九宫格**（能自适应文字宽度），
   而 `window`（对话框）是**整张位图**。→ **"姓名条是一个贴上去的小标签、对话框是整屏底图"这一形态差异是有源码根据的**，
   不是审美选择。（出处：`screens.rpy` 的 `style namebox` 与 `style window`；官方 `gui.html` 逐字
   "The character's name is placed inside a **frame** that uses gui/namebox.png as its background."）
2. **姓名条位置在"框顶之上"是官方默认**：官方文档逐字说 `gui.name_ypos` 设成负数时
   "causes it to be placed 22 pixels **above the top of the textbox**"——**我们的原型正是这么做的**（姓名条贴在对话框上沿）。
3. **官方默认快捷条是 8 个按钮**（逐字顺序）：`Back` / `History` / `Skip` / `Auto` / `Save` / `Q.Save` / `Q.Load` / `Prefs`；
   而且 **The Question 与 Tutorial 两个独立项目逐字相同** → 这是"Ren'Py 项目默认快捷条"的稳定形态。
   **触摸端变体只留 4 个**（`Back`/`Skip`/`Auto`/`Menu`），官方注释逐字解释是为了"fewer and bigger buttons"。

**"不是共同构件"的（只有部分引擎有）**：skip 指示器、角落 toast、**CG 画廊**（Ren'Py 默认 GUI 里**没有** gallery screen）、
对话气泡、聊天软件式窗口、粒子层、帮助/键位说明屏。

### 2.2 我们的取舍（要 / 不要 / 以后再说）

| 构件 | 判定 | 理由 |
|---|---|---|
| **底部对话框 + 说话人姓名条** | ✅ **现在就要** | galgame 的"脸"就是这两件；三引擎都有，且形态差异有源码根据（§2.1 事实 1） |
| **立绘（位置/大小/表情切换/进出场）** | ✅ **现在就要** | 没有立绘就不是 galgame。位置用官方的左/中/右三档语义；表情切换＝换帧；进出场＝淡入 + 位移 |
| **逐字显示（打字机）＋ 点击/空格推进** | ✅ **现在就要** | `dismiss` 键位是官方默认（回车/空格/鼠标左键）。**"文字还在逐字时点一下＝立刻显示完，再点＝下一句"是必须的**，否则长段落会被逼着等 |
| **回想** | ✅ **现在就要** | 它是**教学刚需**（学生回看老师上一条说了什么），不只是 galgame 惯例。官方 `history` 座默认滚到最底（最新一条） |
| **自动播放 / 快进** | ✅ **现在就要（实现成本极低）** | 两个都是几行定时器。**快进在教学里有个特殊用途**：学生想快速重看已懂的部分 |
| **存档 / 读档** | 🟡 **要，但落点必须改** | 原型里用 localStorage 是**临时**的。正式实现应落**教室 `runtime/`**（我们的状态真源在那里），不要留在浏览器里 —— 否则换设备/清缓存就丢，而且与教室的 `progress.md` 会形成**两个写者** |
| **设置** | 🟡 **只做"正文字号 + 文字速度"** | 三引擎的最小公共设置集是"文本速度 + 自动播放间隔 + 分源音量"。**音量现在没意义**（还没语音）；**字号在中文长文里比速度更重要** |
| **标题画面 / 主菜单** | ❌ **不做** | 教室不是一个"游戏"，没有"开始新游戏"这个动作；入口就是 DSH 会话本身 |
| **CG 画廊** | ❌ **不做（Ren'Py 默认 GUI 里也没有）** | 而且它和"回想"重叠 |
| **确认对话框** | ⚪ **以后再说** | 现在没有破坏性动作需要确认（存档已存在教室 runtime，覆盖由教室自己管） |
| **隐藏 UI 看立绘/背景** | ⚪ **以后再说** | 三引擎都有（Ren'Py 默认给键位 `hide_windows`，但**默认快捷条里没有这个按钮**）。对上课没用，除非要做截图分享 |
| **回退（rollback）** | ❌ **不做** | galgame 的 rollback 是"回到上一句并撤销状态"；**课堂上撤销状态是错的**（学生的回答不能因为老师回退就消失）。要"回看"用回想，不要回退 |

### 2.3 🔴 分支选项 vs 自由输入 —— 这是产品的关键差异点，判如下

**判断：内容问题一律自由输入；选择肢只用在"元层面"。**

理由：

1. **苏格拉底式教学的全部机制就是"按学生当下理解选择下一个教学动作"**（教室 `system_core.md` 的取向、
   `materials/ch01.md` 的"教学地图"逐字写着"根据学生的回答选用提问、解释、演示或拓展"）。
   **给出选项＝提前把学生的答案空间框住**，学生会在你给的三个选项里挑，而不是暴露他自己的理解。
   **那正好废掉这个教室唯一有价值的东西。**
2. **但我们也不能只有自由输入**：galgame 的选择肢之所以有用，是因为它给了玩家一个**零成本的表达动作**。
   在课堂上，学生有时**不想打字**，只想说"继续"/"换个讲法"。**这个需求是真的。**
3. → **所以把选择肢降一层，用来表达"学生状态"，而不是"知识答案"**：
   原型里演示的三个选项就是 **`继续说` / `画给我看` / `让我自己写第一步`** ——
   它们全是**元层面**的（我要老师做什么），**不含任何知识内容**，因此不会污染答案空间。
4. **对照教室的真实节点**：`characters/komari.md` 写着她对"学生敷衍（'大概懂了'）"的反应是
   **"把白板递过去：那你写一下第一步"** —— 这正是 `让我自己写第一步` 这个选项的来源。
   **选项是从人格里长出来的，不是从 galgame 惯例里搬的。**

**落地约束（写给实现者）**：
- 知识问题（"如果只有一个核心，它怎么让两个程序都有机会执行？"）→ **永远走自由输入**，不给选项；
- 选项只在**三种时刻**出现：① 学生卡住且不想打字；② 老师要给"下一步怎么走"的选择；③ 收尾（继续 / 今天到这）；
- **选项的文案里不许出现任何技术答案**。

### 2.4 我们特有的东西放哪（**不破坏沉浸感**）

| 我们的东西 | 放哪 | 理由 |
|---|---|---|
| **老师画的图（`classroom_draw`）** | **"投影区"** —— 对话框**上方**的一块浅色纸面，从下方滑入；**出现时立绘自动让位** | 真 galgame 放 CG 时立绘会退到一侧；投影区是"白板/投影幕"的自然隐喻，且**不覆盖对话框**（学生还在读老师上一句话） |
| **白板文字** | 同上（投影区的另一种内容：纯文字行） | 与"她先写不说"的人格一致——`story/ch01.md` 明确"她第一件事是**写**，不是**说**" |
| **动画（`classroom_animate`）** | **投影区**（和画图同一块地方） | 动画与图是同一类"老师在展示的东西"，分两个地方会让学生不知道看哪 |
| **工具调用记录** | **幕后抽屉**（默认收起，一个按钮打开） | galgame 里没有这个东西，**它属于"引擎"不属于"舞台"**。变体 ②/③ 的侧栏里列的是**真实工具名**（`classroom_set_phase` / `classroom_draw`） |
| **课程表 / 知识点 / 进度 / 相位** | **侧栏**（变体 ②）或**抽屉**（变体 ③） | 它是"教室的状态面板"，是**工具**，不是舞台的一部分。**这一条直接回应了用户的批评**：工具面板可以留，但**不能当产品形态** |
| **学生的输入** | **对话框内**（自由输入就长在框里） | 不跳到别的地方，因为它是"回合的一部分" |

### 2.5 舞台背景从哪来（编辑部世界观）

**问题**：我们的世界观是**《月刊·连载中》编辑部**（长桌 + 整面墙的公告板 + 档案柜 + 修改记录本 + 台灯），
**但我们没有任何一张编辑部的图**。原型里用的 `back_class_normal.png` 是官方样本包的**教室**，**必须当占位看**。

**建议（三步，从零资产到真资产）**：

1. **第一步（现在就能做，零美术资产）：把场景做成"极简舞台"而不是"写实背景"。**
   用纯 CSS 拼出**光景**：一盏台灯的光锥（径向渐变）＋ 公告板的一块纸色（矩形）＋ 长桌的一条水平线（细线）＋ 暗角。
   **这与教室自己的氛围基线完全一致**——`world/setting.md` 逐字写着"**安静**，但安静里全是'正在进行的动作'"、
   "白天靠窗；傍晚之后是台灯。**深夜的编辑部只有一盏灯亮着**"。
   → **不需要美术，而且不会出现"占位图被当成成品"的问题。**
2. **第二步：立绘优先于背景。** galgame 的"脸"是**立绘 + 对话框**，背景可以极简（大量视觉小说就是这么做的）。
   资源应该先投到立绘上。
3. **第三步：真要写实背景时，按"每讲一个场景"的节奏做，不要一次做全 14 讲。**
   教室的 `world/setting.md` 已经给了场景基线与过渡场景的做法，可以直接当美术需求书。

### 2.6 🔴 立绘从哪来（**这一节要用户拍板，见 §5**）

**现状**：小鞠知花（148cm / 红棕蘑菇头 / 长刘海遮住一只眼 / 侧单马尾 / 金瞳）**没有立绘**。
原型用**仓库里现成的 Live2D 官方样本 Hiyori 的真实渲出帧**占位，并在原型页面显著位置标明"不是小鞠知花"。

**四条可选路（不替用户判断，只列选项与代价）**：

| 路 | 做法 | 代价 | 备注 |
|---|---|---|---|
| A | **先占位**（现在这样） | 零成本，但**不能交付** | 只能用于"看形态"，不能给外人看 |
| B | **委托/自绘立绘** | 成本最高，**但这是唯一正解** | 需要：1 张基准立绘 + N 个表情差分（差分可以从基准裁/改） |
| C | **只做"半身/侧身/背影"** | **美术成本显著下降** | 🔴 **而且更贴人格**：`characters/komari.md` 写她"不敢看学生的眼睛"、"紧张时会停顿、借白板把话说清"、"她的手机才是她真正的嘴"。**一个不正面看你的立绘，比一个正脸立绘更对。** 这条**不需要新美术也能先用现有静帧裁切试** |
| D | 用 Live2D 官方样本改造 | — | 涉及素材来源与授权，按项目纪律**不在本报告展开**（属于"法律/许可"范畴，须用户自行研究） |

**另有一条与 Live2D 的衔接**：仓库里已有 `code/clients/live2d-host/`（真实渲染链路已跑通，含表情/嘴型能力）。
**本原型用的是静帧**；要动起来，接入点是现成的，但**那是下一步**（见 §6 实施顺序）。

## §4 接线方案（**只写方案，不改代码**）

**前置判断（用户要先拍板，见 §5）**：舞台的**主轴**选哪条？两条路互斥（§1.1）。

### 4.1 方案 A（推荐）：**`conversation.view` 整屏视图 + 自带 tab**

| 要做的事 | 落到哪 | 备注 |
|---|---|---|
| 注册舞台视图 | **`conversation.view`**（`list`/`session`，`replaceRisk:"none"`），新 `id`（如 `stage`）+ `label:"舞台"` | 会话头会自动多一个 tab（安装版已有 `chat`/`trajectory` 两个，所以 tab 条本来就在） |
| 舞台组件本体 | 我们客户端插件包里新写一个组件（`React.createElement`，**不用 JSX/CSS 模块**） | 产物是手写的 `lib/client.js`（`window.__ModuleLoader__.load({id, factory})`），宿主不转译 |
| 舞台要的数据 | 用该座的 `standardProps`：`useChat` / `useConversation` / `useProjection` / `useTrajectory` / `useInput` / `inputActions` / `sessionId` | 这些**在 `conversation.view` 里是齐的**（这是它比 `main` 好的根本原因） |
| 立绘 / 场景 / 投影区 | 组件内部 DOM + CSS | 场景建议先做 §2.5 的"极简光景层"（零美术资产） |
| **点击推进层** | **`conversation.composer`**（`chain`/`session`，`replaceRisk:"none"`），`select` 只在**课堂会话**返回真值 | 这是"整块替换输入区"的官方通道；非课堂会话完全不受影响（`scope: session`） |
| 自由输入 | 同上（你接管了输入区，就由你画输入框并调 `inputActions`） | 学生的话要**同时**进回想与真实会话 |
| 系统功能条 | 舞台组件内部（右上角） | 不必用座 |
| **回想 / 幕后** | 舞台组件内部的面板；**数据源用真实会话数据**（`useChat`/`useProjection`） | 原型里的"幕后工具名"是演示数据，正式实现要读真实工具调用 |
| **课程表 / 知识点 / 进度 / 相位** | **`sidebar.right.pane.tab`**（`keyed`/`session`，`replaceRisk:"none"`，P3 已定案） | 这就是**现有教室面板该待的地方**——它不撤，只是不再是产品形态 |
| 立绘层（若要浮在全屏之上） | **`shell.overlay`**（`list`/`root`，`replaceRisk:"none"`）🔴 **默认 click-through，必须自己开 pointer events** | 只在需要"立绘跨列"时才用；否则立绘就画在 view 内部 |

**成本**：中。**风险**：低（全部 `replaceRisk:"none"`）。**代价**：用户要**点一下 tab** 进舞台。

### 4.2 方案 B：**影子换掉消息流渲染器**

| 要做的事 | 落到哪 | 备注 |
|---|---|---|
| assistant 那条画成对话框 | **`conversation.chat.node`**，`key:"assistant-step"`，**更低 priority** | `replaceRisk:"shadows-shipped-ui"`，**官方 `AssistantNodeView` 的呈现（含它挂的子座）由你接手** |
| 学生那条画成另一套气泡 | 同座，`key:"user"` | 同上 |
| 工具调用画成"投影区" | 同座，`key:"tool-call"`（**会盖掉官方 ToolCallTree**） | P3 已取证过这条路 |
| 输入区改造 | 同方案 A（`conversation.composer`） | — |
| 场景 / 立绘 | **`shell.overlay`**（因为消息流本身没法放"整屏场景"） | 于是变成"舞台浮在聊天记录上" |

**成本**：**高**（要自己实现官方那 17 个 kind 里你碰到的每一个的呈现）。**风险**：**高**（影子覆盖）。
**代价**：**官方对话形态被永久改变**——所有会话都变，不只是课堂（`scope` 是 `session`，但 kind 是全局的）。

### 4.3 方案 C（最小可用）：**先只加一个 `shell.overlay` 舞台浮层**

只做"立绘 + 底部对话框 + 点击推进"浮层，**不动消息流、不动输入区**；点击推进用浮层自己的按钮。
**成本**：最低。**风险**：无。**代价**：学生打字还得用下面那个官方输入框 —— **沉浸感是断的**。
→ 只适合当**第 0 步的形态演示**，不适合当终态。

### 4.4 三方案对照

| | 方案 A（view + tab） | 方案 B（影子渲染器） | 方案 C（浮层） |
|---|---|---|---|
| 会话主区被占满 | ✅（点 tab） | ✅（默认就在那） | ❌（叠在上面） |
| 官方对话是否被改 | ❌ 一个字不动 | 🔴 **被永久改变** | ❌ 不动 |
| `replaceRisk` | **全部 `none`** | **`shadows-shipped-ui`** | 全部 `none` |
| 能不能拿到会话数据 | ✅（`standardProps` 齐） | ✅ | ❌（root 级座，只有 root 那几个钩子） |
| 点击推进层 | ✅ `conversation.composer` | ✅ 同上 | 🟡 只能浮层自己按钮 |
| 实现成本 | 中 | **高** | 低 |
| 沉浸感 | 高（点进去就是舞台） | **最高**（进来就是舞台） | 低（上下两层） |

## §5 🔴 要用户拍板的点（**五条**）

| # | 要拍的事 | 选项 | 我的倾向与理由 |
|---|---|---|---|
| **1** | **舞台怎么"进"** —— 是**自己开一个 view（要用户点一下 tab）**，还是**直接换掉消息流的渲染**（进来就是舞台，但官方对话形态被永久改变）？ | A：`conversation.view` + tab（`replaceRisk:"none"`）／B：影子换 `assistant-step` 渲染器（`shadows-shipped-ui`） | **倾向 A。** 理由：① B 会让**所有会话**的对话形态改变，不只是课堂；② B 要自己接手官方那 17 个 kind 的呈现，**维护成本长期压在定制线上**；③ A 的 tab 只多一次点击，而"教室"本来就是用户主动进入的场景。**但 B 的沉浸感确实更高——这是真正的取舍，我不替用户决定。** |
| **2** | **工具调用与老师画的图怎么显示** | ① 全部进"投影区"（我的原型做法）／② 图进投影区、工具调用进幕后抽屉／③ 图进投影区、工具调用干脆不显示 | **倾向 ②。** 理由：图是**教学内容**（学生要看），工具调用是**引擎事实**（学生不看），两者混在一起会让投影区变成日志。原型里已经是 ② 的形态（投影区放图 + 侧栏"幕后"列工具名） |
| **3** | **侧栏那块教室面板还留不留** | ① 留，但移到右栏 tab（`sidebar.right.pane.tab`，现成入口）／② 缩进"幕后"抽屉／③ 撤掉，课程表/进度只在需要时弹出 | **倾向 ①。** 理由：它是**真的有用**（课程表、知识点状态、进度），只是**不该当产品形态**。移到右栏 tab 之后，它和舞台是"两个并列的东西"，正好回应了用户那句"这不叫深度定制" |
| **4** | **分支选项 vs 自由输入** | ① 内容问题一律自由输入 + 元层面选项（我的做法）／② 知识问题也给选项（更像 galgame）／③ 完全不要选项 | **倾向 ①，且这一条我认为不该让步**。理由见 §2.3：给知识选项＝**把苏格拉底式教学唯一有价值的东西废掉**。但**元层面选项是真需求**（学生有时不想打字），所以不是"要不要选项"而是"选项放在哪一层" |
| **5** | **立绘怎么办** | A 先占位（现在这样）／B 委托/自绘（唯一正解，最贵）／C **只做半身/侧身/背影**（美术成本大降，且更贴人格）／D 用官方样本改造（涉及素材来源，**不在本报告展开**） | **倾向 C 起步。** 理由：`characters/komari.md` 里她"不敢看学生的眼睛"、"靠白板把话说清"、"手机才是她真正的嘴"——**一个不正面对你的立绘比正脸立绘更对**，而且**不需要新美术也能先用现有静帧裁切验证形态**。同时**并行启动 B**（真立绘迟早要有） |

**另有两条不是"拍板"但需要用户知道的**：
- **存档落点**：原型用 localStorage 是临时的；**正式实现应落教室 `runtime/`**，否则与 `progress.md` 会形成两个写者（这是本项目已经踩过的坑）。
- **窄屏版没有"存档/读档"按钮**（设计如此：窄屏只留 5 个胶囊）。如果要，就放进设置面板里。

## §6 实施顺序建议（哪一步最省事、哪一步最贵）

| 顺序 | 步骤 | 成本 | 为什么排在这 |
|---|---|---|---|
| **0** | **用户拍 §5 的五条** | 零 | **不定主轴就没法开工**（方案 A 与 B 的代码结构完全不同） |
