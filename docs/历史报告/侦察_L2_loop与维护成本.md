## 1. loop 相位结构

### 1.1 一轮（turn）的步骤分解

**源码**：`packages/core/agent-loop/src/agent.ts`（647 行，核心类 `ReactLoopAgent`，`implements Agent`）

驱动骨架（`agent.ts:251` `kick()`）：

```ts
private async kick(): Promise<void> {
  try {
    while (await this.turn()) {}      // 一轮结束若 inbox 仍有 pending，就再开一轮
  } catch (_error) { /* 错误与取消在驱动边界被吞掉 */ }
  finally { /* 回到 idle 相位 */ }
}
```

`turn()`（`agent.ts:295`）的真实顺序（逐行核对，非概括）：

| 序 | 动作 | 源码位置 | 落盘事件 |
|---|---|---|---|
| 1 | `session.append('turn/start', { turn })` | `agent.ts:305` | `turn/start` |
| 2 | `preStep(target, {turn, step})` → 从 inbox **claim** 消息（`next-turn` 或 `next-step` 两个队列） | `agent.ts:266-286` | —（claim 由 inbox 侧发 `agent/inbox/claimed`） |
| 3 | `systemPrompt.assemble(...)` 组装系统提示 + 工具 schema | `agent.ts:270` | — |
| 4 | `runtimeContext.project(...)` 投影运行上下文 | `agent.ts:273` | — |
| 5 | **waterfall `agent/pre-step`** → 得到 `PreStepDecision`（`enter` / `reject`，可**改写进入本步的消息数组**） | `agent.ts:275-282` | — |
| 6 | `session.append('step/start', {turn, step})` | `agent.ts:328` | `step/start` |
| 7 | `step(decision)`：模型请求 → 流式 → 工具调用 → 结果 | `agent.ts:380` | `request/header`、`system/message`、`assistant/message`、`tool/call`、`tool/result` 等 |
| 8 | `finally { session.append('step/end', {turn, step}) }` | `agent.ts:333` | `step/end` |
| 9 | 若本步判定「该收尾」且 next-step 队列空 → **serial `agent/turn-stopping`** | `agent.ts:342` | — |
| 10 | `finally { session.append('turn/end', {turn, reason}) }` | `agent.ts:366` | `turn/end` |

**关键结论**：一轮 = `turn/start` → 循环（`step/start` → 模型请求 → 工具调用 → `step/end`）→ `turn/end`。**多步（step）在一轮内循环**：工具调用后若 `inbox.nextStep` 还有活，就再进一个 step（`agent.ts:346` `target = 'next-step'`），而不是新开 turn。

### 1.3 turn 边界与钩子位（🔴 本节是「教学状态机」的直接依据）

**权威声明**：`packages/core/agent/src/runtime-types.ts:305` 起的注释块标为
`// ---- the machine's extension points ----`，即**官方自认的机器扩展点**。完整清单：

| 钩子 | 模式 | 位置 | 能做什么 |
|---|---|---|---|
| `agent/pre-step` | **waterfall** | `runtime-types.ts:320`，调用点 `agent-loop/src/agent.ts:275` | **每步开始前**：可 `reject` 该步，或**替换/追加进入该步的消息数组**（`messages`）→ **这就是「每轮开始前注入」的官方位** |
| `agent/request` | waterfall | `runtime-types.ts:347`，调用点 `agent.ts:prepareRequest` | 替换**冻结的调用配置**（模型/供应商/参数）。注释明写：**该 waterfall 不能改消息**（"cannot mutate messages"） |
| `agent/request-error` | waterfall | `runtime-types.ts:364` | 请求失败重试策略接管 |
| `agent/assistant-stream` | emit | `runtime-types.ts:381`，调用点 `agent.ts:414` | 流式帧（start/chunk/end）的进程内发布 |
| `agent/turn-stopping` | **serial** | `runtime-types.ts:400`，调用点 `agent.ts:342` | **轮结束前的最后一个钩子**：注释明写"listener that objects steers (`agent.steer(...)`) and the machine re-reads its inbox: fresh steering runs another step" → **可以否决收尾、强制再跑一个 step** |
| `agent/created` / `agent/disposed` / `agent/status` / `agent/inbox/inserted` / `agent/inbox/claimed` / `agent/inbox/discarded` / `agent/error` | emit | `runtime-types.ts:250-430` | 生命周期与通知（只读观察） |

**对问题 2 的直接含义**：存在**正式的、被文档化的**「每步开始前」与「轮结束前」两个钩子位，且都是插件可注册的（`Scoped<Agent>` 作用域过滤，agent 级监听只收本 agent）。**改教学相位不必然要改 loop 源码。**

> ⚠️ 一个必须注意的约束（原文）：`agent/pre-step` 的替换消息**必须是已注册的 logged channel**；`agent/request` 注释明写"Model-visible content must use logged channels; this waterfall cannot mutate messages."→ **注入的内容要走可落盘的通道**，不能凭空塞非事件消息。具体「哪些消息类型算 logged channel」见 §2.3。

## 2. 教学状态机插入点

### 2.1 结论（先给判断）

**「每步开始注入当前相位 + 相位纪律」有一个官方、已文档化、且被本仓库 3 个内置插件实际使用的落点：`agent/pre-step` waterfall。**
→ **不需要改 loop 源码**。相位本身可以由插件自己持有（配置/文件驱动），通过该 waterfall 把「当前相位」作为一条消息注入。

**「每轮结束前做收尾动作（更新状态文件）」对应 `agent/turn-stopping` serial 钩子**，它在一轮收尾前被 await，且可以否决收尾（`agent.steer(...)`）。

### 2.2 仓库内三个「同类先例」（这是最有说服力的证据）

| 先例 | 路径 | 做法 |
|---|---|---|
| **模型切换通知** | `packages/core/agent/src/model-selection.ts:110-121` | 注册 `agent/pre-step` → `await next()` → `{ ...decision, messages: [...decision.messages, modelSwitchNotice(previous, selected)] }`；并带 `{ prepend: true }` 选项 |
| **时间上下文注入** | `packages/context/time-context/src/index.ts:188` | 注册 `agent/pre-step` → `await next()` → 用 `createUserMessage(...)` 造消息、按 `refreshIntervalMs` 节流后追加进 `decision.messages` |
| **项目指令（AGENTS.md）注入** | `packages/context/agent-instructions/src/index.ts:315` | 注册 `agent/pre-step` → `await next()` → `decision.messages.toSpliced(lastClaimedIndex + 1, 0, desired)` **精确控制插入位置**（在 claim 批次之后、驱动追加的 runtime context 之前） |

→ **「教学相位」本质上是「时间上下文 / 项目指令」的同类问题**（每步动态变化的上下文注入），本仓库已有**两套可照抄的成品实现**。

### 2.3 注入消息的合法形态（🔴 硬约束，容易踩坑）

**不能凭空塞一条非事件消息。** 注入的消息必须是已注册的 message source（"logged channel"）：

- 权威定义：`packages/llm/llm/src/message.ts:110-115` 的 `MessageSourceMap`，内置 4 类：`user` / `model` / `tool` / `system-prompt`。
- **外部插件新增 source 的方式是 TypeScript 模块增强（declaration merging）**，本仓库有大量实例：
  - `packages/core/agent-loop/src/runtime-context.ts:12-15`：`declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap { 'runtime-context': { kind: 'runtime-context' } & ContextFormed } }`
  - 同样模式见 `packages/context/time-context/src/index.ts:15`、`packages/context/tmux-context/src/index.ts:30`、`packages/context/agent-instructions/src/state.ts:49`、`packages/schedule/schedule/src/runtime.ts:11`、`packages/experimental/agent-team/src/types.ts:124`、`packages/webhook/webhook/src/types.ts:72`
- **role → 持久化事件类型的映射是封闭的**：`packages/core/session/src/index.ts:325-331`
  ```ts
  const MESSAGE_ROLE_BY_TYPE = { 'system/message':'system', 'developer/message':'developer',
    'user/message':'user', 'assistant/message':'assistant', 'tool/result':'tool' }
  ```
  注释明写：`This map is closed because every model-visible role must have a durable Session event and an adapter projection.`
  → **新 source 只扩展「source kind」，不能扩展「role」**。相位消息只能落在现有 5 个 role 里（实践中用 `user` role + 自定义 source kind，与 time-context / model-selection 完全一致）。

### 2.4 相位由「外部（配置/文件）驱动」的可行路径

三条都已存在于本仓库，按侵入度递增：

1. **纯插件 + 每步读文件**（零改 loop）：`agent/pre-step` 里读教室 runtime 状态文件 → 组装相位纪律 → 注入。风险：每步同步 IO；需要自己做缓存/失效（`agent-instructions` 用 `stepTouches` + `session/event('step/end')` 做了这件事，`agent-instructions/src/index.ts:307-314` 是现成范式）。
2. **插件 + session projection**（零改 loop，推荐）：本仓库有 `SessionProjectionDefinition` 机制（`agent-loop/src/index.ts:70-105` 的 `turnBoundaryProjectionDefinition` 就是范例：`key/stateVersion/stateSchema/init/apply`），把相位作为**从事件日志折叠出的状态**——相位变更本身变成事件，可回放、可持久化、崩溃可恢复。
3. **改 loop 源码**：只有当你需要「相位影响的是 loop 自身的控制流」（例如相位强制改变 step 上限、强制拒绝工具调用）时才必要。**目前的 5 个相位（讲新课/提问/作答/对答案/收尾）看起来都可以用 1 或 2 表达。**

### 2.5 `agent/turn-stopping` 的真实语义（决定"课后自动更新状态"该怎么写）

原文（`packages/core/agent/src/runtime-types.ts:363-381`）要点：
- 触发时机：**"The turn is about to close: the model owes no response (no live tool calls, no fresh steering)."**
- 被 await 后才提交边界 → **在这里写盘是安全的（有 await 保证）**
- 若监听器反对：`agent.steer(...)`，机器重读 inbox → **会再跑一个 step**（可用来做"收尾必须确认状态已更新"的闭环）
- 收尾"由数据决定"：注释明写 "Data decides, so listener order cannot change the outcome."

### 2.6 教学状态机的另一个天然落点：工具 `concludesTurn`

原文（同上）："a tool result carrying `concludesTurn` ends the turn at its step." → **「对答案完成」这类确定性收尾，可以由工具返回值直接宣告轮结束**，不需要 hook 判定。待确认：`concludesTurn` 的具体类型与生产位置（见 §7 待确认清单）。

### 3.4 模型/供应商路由在哪一层（🔴 换模型要不要动 loop）

**三层，都不在 loop 里：**

| 层 | 包/文件 | 职责 |
|---|---|---|
| **适配器注册层** | `packages/llm/llm/src/`（`call-config.ts`、`types.ts`）+ 具体适配器 `llm-deepseek`、`llm-pi-ai` | provider 的注册与 `prepareCall()` 解析；`LlmCallConfig` 类型定义在 `call-config.ts` |
| **per-session 选择层** | `packages/core/agent/src/model-selection.ts`（132 行） | 通过 `agent/request` waterfall **替换 provider/model**，并用 `agent/pre-step` 追加一条"模型已切换"通知消息 |
| **默认选择层** | `packages/core/agent-default-model/` | 新 agent 的缺省 route |

**loop 自身怎么用这些**：`agent-loop/src/agent.ts:529` `prepareRequest()`：
```ts
const proposedConfig = await this.dispatch.waterfall('agent/request', { turn, step, signal },
  () => Promise.resolve(seedConfig))
...
preparedCall = await this.loopCtx.llm.prepareCall(proposedConfig, signal)
```
→ **loop 只做「提出 seedConfig → 过 waterfall → 交给 llm 服务」**；provider/model 的解析全在 `llm` 服务与适配器里。

**结论（直接回答"换模型要不要动 loop"）**：**不要。**
- 静态换默认：改 `agent-default-model` 的 config（profile patch / 设置页），或换 `AgentOptions.provider/model`。
- 按条件动态换（如"教学相位=讲新课 用 A 模型，对答案 用 B 模型"）：注册一个 `agent/request` waterfall 监听器即可，**本仓库已有成品**（`core/agent/src/model-selection.ts:95-110`）。
- 若换供应商（如新增一个 API gateway / 中转）：新增一个 `llm` 适配器包（照 `llm-deepseek` / `llm-pi-ai` 的结构），**仍是插件，不碰 loop**。

**（2）「重度 fork 后跟上游」的真实成本结构**

- **不是「一次 merge 有多痛」，而是「merge 永远排不上队」**：上游 194–250 提交/天，且**每 1.6 天打一个 tag**。你的 fork 只要落后一周，`agent-loop` 就有 26 个文件被上游动过——**而 `agent-loop/src/agent.ts` 一共才 647 行**（§1.1）。**一周的漂移 ≈ 大半个核心文件的量。**

**（4）给判断的结论**

> **"功能这么多，fork 比插件组简单"——在本仓库的数据下不成立，至少在 loop/UI/子代理三块上不成立。**
> - **改 loop**：不需要 fork。`agent/pre-step` + `agent/turn-stopping` + `agent/request` 是官方标注的扩展点，且**仓库里有 3 个成品先例**（§2.2）。一个插件包 + 若干行注册代码即可。

> - **批改作业子代理**：`ctx.subagents` 服务 + `outputSchema` 结构化返回（§4.3），**本来就是插件 API**。

```ts
  if (!target) { warn('patch: entry %C not found', id); continue }

  if (name && name !== target.name) {           // ← name 只是「匹配校验」
    warn('patch: name mismatch for %C (expected %C, got %C), skipping', id, target.name, name)
    continue
  }

  for (const [key, value] of Object.entries(overrides)) {
    if (key === 'id') continue                  // ← 唯一被排除的可覆写键
    target[key] = value
  }
}
```

**读法**：
- `name` 被 `...overrides` **解构剔除**，随后只做「与目标不一致就跳过」的校验 → **patch 无法改写 `name`**。
- `id` 在覆写循环里被显式 `continue` 跳过 → **patch 也无法改写 `id`**。
- 能被覆写的只有**其余键**（最常用的是 `config`、`disabled`；用户本机 `profiles/web/cordis.patch.yml` 里 113 行全是这两类）。

→ **结论：不能通过 profile patch 把内置 `@deepseek-ai/dsh-agent-loop` 换成你自己的包。** patch 只能「改配置 / 关掉 / 往 group 里 insert 新行」。
（`insert` 无 `id` 时可往 entry 列表尾部**追加全新条目**，`name` 任意 → **新增插件包完全支持**；这是 §2/§10 的插件路线。）

### 11.3 对「插件组 vs fork」的最终修正

| 方案 | 机制支持 | 维护面 |
|---|---|---|
| **A. 纯插件组**（推荐） | ✅ 官方支持：profile patch 的 `insert`（§11.1）+ `agent/pre-step`/`agent/turn-stopping` 等扩展点（§2/§10） | 只跟**钩子签名 + `MessageSourceMap` source kind**；上游漂移绝大多数不触及 |
| **B. 只 fork `agent-loop` 单包** | ⚠️ **不能靠 patch**（§11.1）；但**可尝试 symlink 替换**（§11.2，未实测） | 跟 `agent-loop` 一个包（785 提交历史、核心文件 647 行）——**比全仓小 3 个数量级** |
| **C. fork 整个 monorepo** | ✅ 当然可行 | **一周漂移 `agent-loop` 26 文件、`client` 1474 文件**（§5.5d）；全仓 30 天 `+1616537/-243508` → **跟不动** |

→ **推荐顺序 A > B > C。** 只有当需求是「相位要改变 loop 的控制流」（§10.2 那张官方表里**找不到对应行**）时，才降到 B；**C 在任何情况下都不划算**。
