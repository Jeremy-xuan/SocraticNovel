## 二、这条会改动什么（四条）

1. ✅ **对 F5／F1 是利好**：教室目录里的 `AGENTS.md` 由宿主**原生、按需、带作用域**地注入 → 「skill 模式」（不装插件也能用）在 DSH 里本来就成立，**我们不用写任何东西**；而且它正好消费草案 §5.1 的设计（`classroom.yaml` 是唯一真源、`AGENTS.md` 是它的投影视图）——**投影有原生消费者**。
2. 🔴 **对 P1 是新的「重复注入」风险**：代理在教室目录下工作时，教室 `AGENTS.md` 会被宿主拼进来；若 P1 同时按 manifest 注入同源内容 → **同一份内容从两条通道到达**。
   → **集成实测必须数一遍注入次数**，口径：事件流里 `Additional instructions from: <教室路径>` 的条数 ＋ 我们 `source.kind='socratic-engine'` 的条数，两者相加不应覆盖同一段内容。
3. 🔴 **「manifest 不声明 AGENTS.md」这条口径的理由要更正（不是推翻，是补全）**：
   - 旧理由（实测①）：宿主**每回合**注入**根** `AGENTS.md`（user role ＋ source kind `agent-instructions`）。
   - 🆕 **完整理由是两条**：① 根 `AGENTS.md` 每回合注入；② **任何子目录的 `AGENTS.md`／`CLAUDE.md` 会被按需拼接并声明作用域**（本件）。
   - S4 据此判「教室的 `CLAUDE.md` 同样不声明为 manifest 块」→ **结论成立，且证据现在是对的**（它的另一条依据也成立：该文件 419 B，正文只是指向 `AGENTS.md` 的别名指针）。
4. ⚠️ **两种模式的触发条件不一致（需要想清楚，尚未定案）**：教室 `AGENTS.md` 只在「代理**碰到教室目录下的文件**」时才被拼接（事实 4）；而真实上课若靠插件注入内容、代理并不 touch 教室文件 → **`AGENTS.md` 根本不会进来**。
   → 即 **skill 模式的生效条件是"文件被碰到"，插件模式的生效条件是"引擎按 manifest 注入"**，两者不等价。这会影响草案 §5.3 那两处「skill 模式的真实降级」的表述，**下次改草案时要一并修**。

## 三、🔴 主代理的一处误判（留痕，教训比结论值钱）

我最初**怀疑 S4 编造了这条观察**，理由是：**工作区根没有 `CLAUDE.md`**（并已核：`/Users/wujunjie/Documents/ChatGPT`、`/Users/wujunjie/Documents`、`/Users/wujunjie` 三级父目录也都没有）。

**查它自己的会话日志后证明我错了**：被注入的是**教室子目录**里的那两份（`…/cs-os/AGENTS.md`、`…/cs-os/CLAUDE.md`），不是根目录的；触发原因是 S4 读了教室目录下的文件，触发了子树拼接（事实 4）。

→ **教训（建议进 AGENTS.md 的工具链节）**：
