## 〇 · 怎么用这份文档

1. 先读 §一（现状快照）和 §二（并行开发约定），再开工。
2. 工作分三波：**第 1 波（地基，串行）→ 第 2 波（并行）→ 第 3 波（叙事层，依赖第 2 波的 A）**。时间不够时，从第 3 波尾部往前砍。
3. 每一项按同一结构写：**目标 / 需求（FR）/ 验收（AC）/ 边界情况（EC）/ 入口与已知坑**。
   - **AC 全部满足才算完成**。做到一半就写「🟡 部分完成」，并写明缺哪条 AC；不要写「基本完成」。
   - EC 是必须处理的输入或状态。实现时逐条对照，每条 EC 至少要有一个测试或一条实测记录。
4. **全局完成定义**（每一项都适用，下文不再重复）：
   - `node check.mjs` 在仓库根退出码为 0；新增代码有对应的单测；
   - 第 1 波完成后，所有功能都要在 **0.2.1 的 stage 实例**上用真实浏览器验证，并留截图或日志证据；
   - 改了教室文件（`classrooms/cs-os/`），要按既有流程同步技能包镜像（`skills/socratic-classroom/sync-classroom.sh`）；
   - 每完成一项，在 `docs/历史报告/` 写一份简短的实现报告：做了什么、证据、没做到的。

## 二 · 并行开发约定（效率的关键）

### 2.1 为什么按「车道」而不是按「功能」并行

功能是横跨的（白板同时动引擎、舞台、面板），但三个**热点文件**都是单文件大件：

| 热点文件 | 行数 |
|---|---|
| `clients/classroom-ui/lib/client.js` | 4159 |
| `clients/classroom-stage-warm/lib/client.js` | 1581 |
| `plugins/socratic-engine/index.mjs` | 1451 |

两个子代理同时改其中任何一个，都必然冲突。所以**按文件所有权分车道**，一个车道同一时间只有一个子代理：

| 车道 | 独占的文件 | 负责的条目（顺序即车道内顺序） |
|---|---|---|
| **E 引擎** | `plugins/socratic-engine/index.mjs` 及其 `lib/`、`test/`；教室提示词文件 `classrooms/cs-os/{system_core.md,_anchor.md,AGENTS.md,classroom.yaml}` | A → W-e → C-e → N0 → N-e（第 3 波的引擎侧接线）→ J |
| **S 舞台** | `clients/classroom-stage-warm/**` | S → W-s → C-s |
| **P 面板** | `clients/classroom-ui/**` | D → W-p → N-p（日记／群聊 tab） |
| **X 独立模块** | 只建**新文件**，不碰上面任何文件 | C-x（表情驱动模块）、N-x（独立 agent 运行器、群聊存储与调度） |

- **X 车道是并行度的来源**：重逻辑尽量写成新文件里的独立模块（带自己的单测），热点文件里只留几十行接线。
- 舞台的 `client.js` 是浏览器端单文件，但舞台已有**按清单从 `/stage-static/…` 加载静态 JS** 的机制（Live2D 库就是这样加载的）。新的浏览器端模块可以作为 `assets/` 下的独立 JS，走同一套加载器，不必塞进 `client.js`。

### 2.2 工作方式

- 每个车道一个 git worktree、一个分支（如 `feat/lane-e`），都从同一条集成分支切出。
- **主代理是集成者**：按「先 E、再 S、再 P」的固定顺序合并，每合一次跑一次 `node check.mjs`，绿了再合下一个。
- 车道内按上表顺序做，做完一项提交一次。别的车道需要你车道里的东西时，**看契约（§2.3），不要等对方的代码**。
- 需要改别的车道独占的文件时：在自己的实现报告里写清「需要 X 车道在某处加某行」，交给主代理转达，不要自己动手。

### 2.3 第 0 步：先把跨车道契约写死（主代理，开工前 30 分钟内）

在 `docs/计划与排产/契约_功能开发_2026-10-20.md` 里写定下面四份契约，各车道照契约同时开工。**契约要改，只能由主代理改，并通知所有车道。**

| 契约 | 生产方 → 消费方 | 至少要定的内容 |
|---|---|---|
| **K1 情绪标记** | E（教老师怎么写）→ S/X（解析与剥离） | 语法、情绪标签集、强度范围、出现位置（句首/句尾）、非法标记怎么处理 |
| **K2 板书事件** | E（`classroom_draw` 结果）→ S（板书屏）／P（板书历史） | 舞台如何得知「刚画了一张」（从会话事件流里识别 `classroom_draw` 的工具结果）、图的 id、宿主读图路由的路径与返回格式 |
| **K3 课堂记录** | E（`classroom_note` 落盘）→ N（群聊/日记 agent 读取） | 记录的存储格式与字段（见 A 的 FR） |
| **K4 群聊 API** | X（存储与调度）→ P（群聊 tab） | 读消息、发消息、「正在输入」状态、未读数；会话认证方式 |

## 四 · 第 2 波：主体功能（各车道并行）

### A · 课后写回补全（车道 E）

**目标**：让「第一节课的卡点，第二节课被引用」真正发生。这是长线陪伴的地基，第 3 波也复用它的机制。

**用户已定的设计**：判断在课上做，落盘是确定性的。
- 新增课上工具 **`classroom_note`**：老师在课上发现卡点、误解或掌握证据时**当场**调用。
- 引擎只做确定性落盘；`review_queue` 和 `progress` 由记录**机械推导**。
- **不加**课后另调一次 LLM 做总结（引擎红线：不许用 LLM 生成式改写教学事实）。

**FR**
- A1. `classroom_note` 参数：
  - `type`：至少包含「卡点 / 误解 / 掌握证据 / 群里提的问题」；
  - `kp`：知识点编号，格式 `KP-<讲>.<序>`，取自 `knowledge_points.md`；
  - `quote`：学生原话引文，必填；
  - `note`：老师一句话说明，可选；
  - 引擎自动补上讲次、回合、时间、会话 id。
- A2. 落盘：卡点和误解写入 `mistake_log.md`；掌握证据推导 `knowledge_points.md` 里对应条目的三档状态（`[ ]` / `[~]` / `[x]`）。推导规则由你设计，但必须**确定性、可单测**，并写进文档。
- A3. `review_queue.md` 由卡点/误解记录机械生成（间隔规则由你定，写明）；`progress.md` 维护当前讲次与每讲状态，保留引擎依赖的机器可读行 `<lesson_key>: <int>`（`index.mjs` 约 173 行在读它）。
- A4. 下一节课开头，引擎把「未解决的卡点 + 到期复习项」注入给老师，注入规则写进 manifest 的块定义，和现有注入走同一套去重。
- A5. 在 `system_core.md` / `_anchor.md` 里教老师**什么时候**调用 `classroom_note`，不要每轮都调。原则：有学生原话作证据时才记。
- A6. 记录的存储格式即契约 K3，第 3 波的 agent 要读。

**AC**
- 单测覆盖：每种 type 的落盘、推导结果、幂等（同一回合重复结束不重复追加，沿用 `postclass.mjs` 的标记机制）、并发写（原子写 + 文件锁）。
- stage 上实测：第一节课里出现一次误解并被记下 → 新会话开第二节 → 注入内容里有这条卡点，老师能自然提起。保留会话原文作证据。

**EC**
- `kp` 不存在、`quote` 为空：工具返回明确错误，不静默落盘。
- 同一知识点先「误解」后「掌握证据」：状态按时间推导，`mistake_log` 里那条标记为已解决，不删除。
- 学生从中间讲次进入（见 J）时，跳过的讲次不能被推导成「掌握」。
- 老师只是「讲过」、学生没有展示理解：**不得**推导出 `[x]`（`knowledge_points.md` 文件头的红线）。
- 记录里的学生原话可能带情绪标记或 markdown：落盘前按 K1 剥掉标记。
- 运行时文件现有权限是 0600，新建文件保持一致。

**入口**：`plugins/socratic-engine/lib/postclass.mjs`（`updaters` 接口、`turnMarker`、原子写）；`classrooms/cs-os/knowledge_points.md`；验收流水线的 A4 断言（`acceptance/README.md`），解析的是旧标记格式，不要破坏它。

### C · Live2D 实时情绪驱动（车道 X → S，E 负责提示词）

**目标**：老师的表情跟着**她此刻说话的语气和心情**实时变化，而不是按课堂状态在 5 个预设表情间切换。

**用户已定的设计**
- **信号**：老师在回复里**逐句带一个隐藏情绪标记**（K1），舞台解析后剥掉不显示，交给表情引擎；没带标记的句子，用本地规则分类器按文字兜底。
- **引擎**：引入 **[Soullink Emotion SDK](https://github.com/nanlingyin/soullink-emotion-sdk)**（Apache-2.0，用户已同意新增此依赖），**只用纯 engine**（`@soullink-emotion/engine`：连续情绪三轴 VAD、FACS 表情合成、待机/反应/说话分层混合、模型 Profile 适配），不用它的 Planner、TTS、Embedding。
- **废弃**：`classroom_express` 工具、`expression-table.json` 这套预设切换，以及舞台 `client.js` 里「状态 → 预设表情」的那段代码。
- **口型**：本阶段口型由**纸带文字逐字显现的节奏**驱动。口型驱动要抽象成一个可替换的「口型源」接口，将来接入音频时只换源，不动混合层。

**FR**
- C1（X）先做**限时验证（2 小时）**：用 Soullink 的 profile-generator 扫描 `assets/models/` 下的 DeepSeek 模型（26 个参数，含眉、眼球、眨眼、嘴形），生成 profile，在本机浏览器里驱动出「开心 / 困惑 / 害羞 / 兴奋 / 平静」五种可辨认的状态。
  - **验证失败**（适配不了，或浏览器构建体积、兼容性不可接受）：退回用同样的分层思路手写参数混合，并在实现报告里写明原因。
- C2（X）把 engine 的浏览器构建 vendor 进舞台的 `assets/l2d/`，按现有方式**分阶段加载**。再写一个独立的「表情驱动」模块（新文件），负责：接收情绪事件 → 喂给 engine → 每帧把参数写进模型；接收口型源 → 写嘴部参数。
- C3（E）在教室提示词里教老师写 K1 标记：每句至多一个，表达的是她此刻的语气，不是对课堂阶段的描述。
- C4（S）舞台的接线：流式正文里实时解析 K1 → 剥离 → 发情绪事件；纸带逐字显示时驱动口型源。动作层保留现有逻辑（正在生成 → thinking，说话 → speak），**表情层**改由表情驱动模块接管。
- C5 待机层：呼吸、眨眼、视线微动持续进行，情绪会自然回落到平静。

**AC**
- stage 上录一段 3 轮以上的真实对话（屏幕录像或连续截帧）：表情随句子语气变化，过渡平滑，没有「跳脸」；说话时嘴在动，一句显示完嘴闭上。
- 纸带、DSH 原生聊天界面（舞台关闭时）、`session_log.md`、`classroom_note` 记录里**都看不到** K1 标记的原文。
- 关掉 Soullink 模块（模拟加载失败）时：舞台回落到静态待机，不白屏、不报未捕获异常。

**EC**
- 标记在流式输出里被截成两半（`〔emo:sh` + `y 0.6〕` 这种）：要能跨 chunk 拼接，在标记不完整时不能把半截显示出来。
- 非法标签、强度越界：按 K1 处理（建议当作无标记，走兜底），不报错打断对话。
- 一句话里有多个标记：取第一个，或按 K1 的规定。
- 学生连发、老师长回复：情绪事件队列不能无限堆积。
- DSH 原生界面的 markdown 渲染可能不会隐藏某些标记写法：**K1 的语法要先在 0.2.1 的原生界面里实测确实不可见**，再定稿。
- 舞台关掉再打开（`props.killed` 依赖，10-19 修过的坑）：表情驱动要跟着 PIXI 应用一起重建和销毁，不能泄漏 ticker。
- 模型资产的许可在 `dsh-live2d` 仓库里没有说明（`换角_DeepSeek娘_改造清单` §1.3）；vendor 时 Soullink 的 LICENSE 和 NOTICE 要一起带上。

## 五 · 第 3 波：叙事层（依赖 A；E/X/P 三车道配合）

> 第 3 波的总体思路：日记、群聊、世界观由**独立上下文的 AI** 运营，和课堂上下文分开。**这是叙事内容，不是教学记录**：除了下面写明的几条，不要给它们加事实性约束。

### N0 · 换角残留清理（车道 E，第 3 波的前置）

把 `world/metaphor.md`、`world/setting.md` 里的「小鞠／编辑部」，以及 `runtime/wechat_group.md` 文件头里的「编辑部同事」改成当前的世界设定（鲸、潮汐观测站）。
**AC**：`grep -rn "小鞠\|编辑部" classrooms/cs-os --include="*.md"` 只剩 `characters/komari.md`（保留的备用角色卡）和有意保留的历史说明。

### N1 · 独立上下文 agent 运行器（车道 X）

**目标**：一个可复用的「在后台用独立上下文跑一次模型任务」的能力，日记、群聊、世界观审阅、定时消息都用它。

**FR**
- N1.1 每次运行都是**全新上下文**：输入 = 本次需要的文件内容 + 任务说明；输出 = 结构化结果（要写哪些文件、写什么）。记忆靠文件，不靠长会话。
- N1.2 使用实例已配置的模型通道，可以在 `classroom.yaml` 里为每类任务单独指定模型；**不在代码里放任何密钥**。
- N1.3 异步运行，不阻塞课堂回合；**不出现在学生的会话列表里**。
- N1.4 失败要大声：写日志，并在面板上有可见的错误状态，不吞错（验收流水线 A6 的「静默失败」红线）。
- N1.5 在 0.2.1 上用什么机制实现，由你调研决定：可选的方向有宿主的 subagent / agent-team 能力、隐藏会话、宿主的 provider 层直接调用。调研限时 2 小时，结论写进实现报告。

**AC**：单测（模型调用用替身）覆盖成功、模型报错、超时、输出格式不合法四种情况；stage 上真实跑通一次「读文件 → 调模型 → 写文件」。

### N2 · 日记（E 接线 + X 逻辑 + P 展示）

**FR**
- N2.1 **触发**：课堂进入收课相位（`classroom_set_phase` 切到 close）后，异步运行一次。兜底规则：学生至少有 5 个回合发言、且会话闲置超过 2 小时，也视为一节课结束。每节课只写一条（按会话 + 讲次幂等）。
- N2.2 输入：本节课的记录（`session_log`、`classroom_note`）、她最近 3 条日记、角色卡、`_anchor.md` 的角色声音段、世界设定、最近的群聊。
- N2.3 写法遵守 `runtime/diary.md` 文件头的规则：第一人称、短、只写她注意到的具体细节、不超过 120 字、可以写与课无关的事。
- N2.4 下一节课，老师能读到自己的日记（注入最近一条），用于连续性。
- N2.5（P）面板里新增「日记」tab，按时间倒序展示日记。

> 🔒 **开发者须知（只给你看，不得进入任何模型可见的文本）**：日记**会**在面板上展示给学生。但给日记 agent 的提示词、工具描述、`diary.md` 文件头里，**一律不得提及**「会被学生看到」「有读者」之类的意思。它必须以为这是只写给自己看的私人日记，因为知道有读者的日记会变成写给别人看的表演。现有 `diary.md` 文件头里的「这是她自己的日记，不是课堂记录」保持原意。

**AC**：stage 上上完一节课并收课 → 2 分钟内出现一条新日记 → 面板「日记」tab 能看到 → 下一节课的注入里有这条日记。

### N3 · 群聊（可互动）（X 存储与 agent + P 界面 + E 互通）

**用户已定的设计**：**应用内的仿微信群**（不接真微信），学生可以在里面发言，由独立上下文的群聊 agent 回应。

**FR**
- N3.1（P）面板新增「群聊」tab，使用 `templates/wechat-chat.html` 的版式，可以输入、发送，有「对方正在输入」提示和未读数（契约 K4）。
- N3.2（X）群聊存储：只能有**一个真源**。可以把 `runtime/wechat_group.md` 改成结构化存储（比如 JSONL）再生成可读的 md，也可以保留 md 作为真源，由你判断，写明理由。
- N3.3 **群里说话的人**：只有 `characters/` 和 `world/` 里已经定义过的人物，全部由同一个群聊 agent 扮演。可以出现一次性路人。新增会反复出场的角色要走 N5 的提议流程，不能直接写进群聊。
- N3.4 **回复节奏**：学生发言后显示「正在输入」，10–30 秒内（随机）回复；学生连发多条时合并成一次回复。**课堂会话进行中她不回群**，下课后补回。「进行中」的判定：相位不是 close，且最近一次回合活动在 30 分钟以内。
- N3.5 **双向互通**：
  - 课堂开始时，引擎把最近若干条群聊注入给老师；
  - 群聊 agent 读最近的课堂记录；
  - 学生在群里问知识题时，她遵守「群聊不承载知识点」（`wechat_group.md` 文件头的规则），简短回应、约到课上讲，并以 `type=群里提的问题` 写一条 `classroom_note`，下节课自然接上。
- N3.6 文件头里原有的写死规则继续有效：她在群里比当面话多但仍然短、每条不超过 2 行、不使用 emoji。
- N3.7 **首次开场**：`wechat_group.md` 为空时视为首次启动，按现有规则先发开场消息。

**AC**
- stage 实测：学生在群里发一句闲聊 → 显示「正在输入」→ 30 秒内收到她的回复。
- 课堂进行中发一句 → 不回 → 收课后补回。
- 在群里问一个知识题 → 她约到课上讲 → 下一节课开头老师主动提起这个问题。

**EC**：学生在她回复前连发 5 条；群聊 agent 调用失败（面板显示发送失败，可以重试）；学生在两个浏览器标签里同时发言（存储写入不能丢消息）；学生发空消息或超长消息。

### N4 · 定时主动发消息（车道 X）

**FR**
- N4.1 她每天主动在群里发 **1–3 次**，时间随机分布在**北京时间 8:00–23:00**。
- N4.2 **预生成**：每天 8:00（或当天第一次触发时），由群聊 agent 一次性生成当天的消息和发送时间，存进持久队列。
- N4.3 **到点发送前的确定性检查**：从生成到现在，只要发生过学生发言、上课、或者新的群聊消息，这条就作废，用最新的上下文重新生成一条再发；什么都没发生就直接发预生成的那条。
- N4.4 **退避**：自学生最后一次发言以来，已经连续发了 2 条主动消息都没人回，就停止主动发，直到学生再次发言。这条规则是确定性代码，不交给模型判断。
- N4.5 页面没开时照样发送；学生下次打开时看到未读。

**AC**：用可注入的假时钟写单测，覆盖：正常发送、作废重生成、退避、跨天、实例重启后队列恢复。stage 上真实观察一天（或用缩短的时间窗口演示一次完整周期）。

**EC**
- 服务器时区不能当真：北京时间要用 UTC+8 显式计算（A 机出现过系统时钟快 8 小时的事故，服务器日志 8.63 节）。
- 实例重启时恰好跨过发送时间：补发还是作废，由你定，写明。
- 队列文件损坏：重建当天队列，不崩溃。

### N5 · 世界观提议（车道 X + E）

**FR**
- N5.1 群聊 agent、日记 agent、课堂老师都可以往 `world/proposals.md` 追加提议：内容、理由、触发它的对话片段。

**AC**：stage 上演示一次完整流转：群聊里出现一个灵感 → 写入提议 → 课后被审阅 → 新角色卡出现 → changelog 有记录 → 下一次群聊里这个角色能出场。

**EC**

- 审阅时提议之间互相冲突：按时间顺序处理，后来的看到先前的结果。
